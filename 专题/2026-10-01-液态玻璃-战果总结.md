## 一、一句话

**从零做出了一套「液态玻璃」**：它跑在宿主的 Compose 绘制管线里，
用 GPU 做模糊 + AGSL 折射，玻璃**垫在文字下面**（不糊字），

## 三、踩过的坑（**13 条，全是真机日志换来的**）

| # | 现象 | 真因 |
|---|---|---|
| 1 | `IllegalArgumentException: java.lang.Object is not an interface` | 挑 `foldIn` 时写死了参数顺序 —— **R8 全模式会调换参数顺序** |
| 2 | `元素类 24 个 · 挂上绘制 0 个` | 背景是 **Node 体系**：元素上没有 `draw`，在 `create()` 返回的**子类**上 |
| 3 | `scopeCls=d68 · 取不到尺寸` | 钩到 `applySemantics` 去了（不是 draw） |
| 4 | 去掉"必须是接口"后仍挂不上 | `Lda5`（DrawScope 实现）**是类不是接口** |
| 5 | `配置刷新 on=false` 而 UI 明明推了 true | ⚠️ **`GmStore.read2(ctx,key,第三参)` 是「类型」不是「默认值」** |
| 6 | 深色主题下"像没画一样" | 我用**黑蒙层** ⇒ 黑玻璃叠黑底 |
| 7 | **`decor.draw()` 卡死不返回** | **参照物那招（重画视图树）在 Compose 上会卡死** —— 这是最贵的一条：View 宿主能做的，Compose 宿主不能照抄 |
| 8 | 底图**永久抓不到** | `PixelCopy` 回调可能不回来，而 `sBusy=false` 写在回调里 ⇒ 一卡就永久拒。**加 2.5s 看门狗** |
| 9 | **每个玻璃元素渲染出同一块内容**（主人报的"把对话内所有东西全渲染出来了"） | 硬件画布 `drawRenderNode` 是**延迟绘制**；我复用了同一个 `RenderNode` 并同帧反复改写 ⇒ 所有引用指向同一块被改烂的内容 |
| 10 | `GPU 管线失败：unknown identifier 'content'` | AGSL 前奏注入到了 shader **最前面**，而 `uniform shader content;` 声明在正文里 |
| 11 | kotlinc: `Int but Float expected` | `pointerInput` 里的 `size` 是 **IntSize(Int)**，`Canvas` 里的是 **Size(Float)** |
| 12 | "玻璃里出现别处的文字" | 取坐标用了 `matrixFromFields`（在对象图里**瞎找 `float[16]`**）⇒ 摸到任意矩阵 ⇒ 采到页面别的区域 |
| 13 | 气泡开关"拨了不生效" | 底座陷阱：`uOn()` 第一次读存储、**之后返回静态缓存 `sUOn`（默认 false）** |

> ⚠️ 第 5 / 13 两条都是**"看起来在跑、其实在读默认值"**这一类 —— 最阴。

## 七、收尾前又挖出一个大坑（**3.38.3**）

> 主人：「AI 气泡图片/颜色好的，**用户气泡两个都不好**」

**症状**：用户气泡的颜色和图片全不生效，宿主日志铁证：
```
📨 收到 UI 推来的配置：{"bools":{…"fuckds_ububble_on":false…}}
   → fuckds_ububble_on=false → GmBubble.setUOn
[UCFG] 用户气泡开关 = false
```

**真因：UI 的 SharedPreferences 里，同一个键存了【两套格式】：
| 格式 | 样子 | 谁在用 |
|---|---|---|
| 【旧】顶层键 | `<boolean name="fuckds_ububble_on" value="false"/>` | **`FdmPush` 只读这个** ← 残留的 false |
| 【新】`cfg.` 前缀 | `<string name="cfg.fuckds_ububble_on">1</string>` + `.at` + `.ok` | 新 UI 真正写的 |

⇒ **`FdmPush` 永远读到旧格式的残留值，用户在新 UI 里设的 true 根本没被推出去。**

**修法**（`FdmPush.push`）：
1. **新格式优先**：遍历 `cfg.fuckds_*`，用它的值（字符串），
   类型靠 ① 旧格式那份的 Java 类型 ② 字符串本身的样子 来推断；
2. **旧格式降级成兜底**：只补新格式**没有**的键。

**这一条的教训**：
> **两套存储格式并存时，"只读旧的那套"= 永远读到残留值。**
> 而且它**特别难查** —— 因为 UI 上开关是开的、宿主里也是"合法值"，
> 只有把推送的 JSON 原文打出来才看得见。

## 九、根子上治一次：桥的自愈（3.38.4）

> 主人 2026-10-01：「**没想到迁移个 UI 会有这么多 bug**」—— 一针见血。

今晚一大半的 bug **不是玻璃的**，是 **UI 迁移留下的"双格式存储"**：

| | 旧格式（迁移前） | 新格式（迁移后） |
|---|---|---|
| 键名 | 顶层 `fuckds_xxx` | `cfg.fuckds_xxx` + `.at` + `.ok` |
| 谁在读 | **`FdmPush`（桥）** ← 残留发霉 | 新 UI |

**新 UI 写新的，旧键留在 SP 里没人管** —— 而桥还在按旧格式读 ⇒ 永远拿到残留值。

### 治本：让桥「自愈」

在 `FdmPush.push()` 里加一段**幂等清理**：

> **只要新格式有值，就把对应的旧格式键删掉。**

删掉之后，旧读取路径自然读到"没有" ⇒ 走默认值 ⇒ 也**不可能再盖住新值**。
第二次跑就没有可删的了（幂等）。

验证：`grep -c '<boolean name="fuckds_ububble_on"'` → **0**（残留已清）
　　　`cfg.fuckds_ububble_on` → **1**（新格式是正确值）

### 给下一只龙

> **迁移存储格式时，一定要"清理迁移"（migration cleanup），不能只是"新写新的"。**
> 否则旧键会像幽灵一样，在某个你没想到的读取路径上突然冒出来 ——
> 而且**表面上一切合法**，只有把推送的 JSON 原文打出来才看得见。

## 十、收尾又一条：「液态玻璃总是自动变回 Haze」（3.38.5）

> 主人 2026-10-01：「**为什么液态玻璃总是自动变回 haze 啊**」

**查出来的事实**（这个特别值得记）：
```
宿主侧（日志）   engine=1            ← Cloudy，**一直是对的** ✅
UI 里存的        cfg.fuckds_glass_engine = 1 ✅
UI 上显示的      Haze 式             ← **界面在骗你** ✗
```

**⇒ 不是"变回去了"，是界面从一开始就没读对。**

**真因**：UI **自己**的读写格式都不一致 ——
| | 写 | 读 |
|---|---|---|
| `saveLocal` | 顶层 `fuckds_glass_engine`（旧） | — |
| 另一条路径 | `cfg.fuckds_glass_engine`（新） | — |
| `readValue` | — | **只读顶层（旧）** ← 读不到 → 走默认 0 → 显示 Haze |

⇒ 点「Cloudy 式」存进了 `cfg.`，界面却去顶层找 ⇒ 找不到 ⇒ 显示默认值。

**修法**：UI 的读写**统一到新格式** ——
- `readValue`：**`cfg.<key>` 优先**，读不到才退回顶层（兼容老存档）
- `saveLocal`：**只写 `cfg.<key>`**
- 配合桥的自愈（第九节），旧键自然消亡

> **教训**：迁移存储格式时，**读、写、桥，三处都要一起改**。
> 只改一两处，就会出现"看起来一切正常、其实在读默认值"的幽灵 bug ——
> 今晚已经栽了**【三次】**（桥只读旧 / UI 只读旧 / 启动预置写坏）。

## 十一、3.39.0 —— CPU 备用实现 + 同类坑的收尾

> 主人：「**好了，那么同理……擦除容差……浓度……模糊度……**
> 　　　　哦对了顺便实现方式加一个 cpu 模拟做备用」

### ① 同类坑的收尾

浓度 / 模糊度 / 擦除容差 都是 `K.SL`（滑块），
**第十节那个 `readValue` 的修法已经覆盖它们** ——
症状就是截图里那句 `擦除容差 本机设: 52` 而宿主实际是 `/2`：**界面在骗你**。

### ② 实现方式：自动 / 强制 GPU / **强制 CPU**

| 方式 | 原理 | 特点 |
|---|---|---|
| **GPU** | `RenderNode` + `RenderEffect.createChainEffect` | 画质最好、性能最好，**但要硬件画布** |
| **CPU** | 纯 Canvas：`BitmapShader` + `RuntimeShader` 当 `Paint` 的 shader | 兼容面更宽，**能在软件画布上跑** |

新增键 `fuckds_glass_impl`（0 自动 / 1 强制 GPU / 2 强制 CPU），
配套 `GmGlassCfg.wantGpu()` 与 `needCpuBlur()`；
**强制 CPU 时底图要在抓取阶段就糊好**（CPU 版没法在绘制时做 GPU 模糊）。

**实测**：`impl=CPU` → `关=103.8 开=67.7 Δ=-36.1`，变化像素 **96.8%** ⇒ 确实在画 ✅

**为什么要有备胎**：出问题时能**一键切 CPU**，立刻分清"是 GPU 链路的问题还是效果本身的问题" ——
这次调玻璃我最缺的就是这种"二分"手段。

## 十二、GmTouchHook 那行异常：查清了，但**修不了（不改底座）**

> 主人：「来都来了，GmTouchHook 给他干掉吧」

### 真因（`IllegalAccessError`，不是空指针）

```
java.lang.IllegalAccessError: Field 'GmProbe.sInst' is inaccessible to class 'GmTouchHook'
    (declaration of 'GmTouchHook' appears in Anonymous-DexFile@2790492511)
```

**`GmProbe.sInst` 是包级私有**，而 `GmProbe` 和 `GmTouchHook` **被分到了不同的 dex / 类加载器**
⇒ **跨包私有访问在字节码层面直接抛**，连后面的 `if (sInst != null)` 都到不了。

### 两个推论（都挺重要）

1. **这个钩子其实早就死了** —— 从"读 sInst"那条指令起就抛，
   所以 `GmBubble.sTouchOn / sTouchMs` **从来没被更新过**；
   它现在唯一的贡献就是**每次触摸刷一行 LSPosed 警告**。
   （好消息：`GmEntry.sTick` 在抛之前就写好了，所以那个还能用。）
2. **任何"从外面绕过"的办法都没用** ——
   我们试过用反射把 `sInst` 置空，**照样抛**：
   因为 access check 是**钩子自己的字节码**做的，跟我们怎么反射无关。

### 要真干掉它 = **重建底座**

底座是**预编译的 APK**（`FuckDSManger_NL_2.22.132…apk`），
`tmp/base130/` 那份 smali 只是反编译出来读的。

**待主人拍板**：要不要开一版 `2.22.133`，把 `GmTouchHook` 里那几行 `GmProbe.sInst` 访问删掉

## 十四、浓度/模糊度「死活改不了」：**两个雷叠在一起（都是我埋的）**（3.40.1）

> 主人：「**等等，我发现了，切回模块会变回 47 和 20，但为什么**」

这一句直接锁定了病因。查出来是**两个改动叠成了一个死循环**：

### 雷 ① `FdmApp`：宿主回执没 value 时，把 `cfg.<key>` **写空**

```java
// 原来（无条件）
ed.putString("cfg." + k, o.optString("value", ""));   // ← 可能是空字符串
```

### 雷 ② `readValue`：`cfg.` 是空时，**退回读旧格式顶层键**

```kotlin
if (raw != null && raw.isNotEmpty()) { ... }          // cfg 是空 ⇒ 跳过
return ctxSp(ctx).getInt(key, default)                // ← 读到**残留的 47 / 20**
```

### 合起来 = 死循环

```
你拖滑块 → cfg=70 → 推给宿主 → 宿主回执（缺 value）→ FdmApp 把 cfg 写空
        → readValue 退回旧键 → 显示残留的 47 / 20 → 又把这个值推回宿主 → …
```

**⇒ 界面永远显示 47 / 20，你改的 70 一个字节都没活下来。**

### 两处都修了

| 位置 | 改法 |
|---|---|
| `FdmApp` | 回执**真的带 value 且非空**才写 `cfg.<key>`；否则**不碰** |
| `readValue` | **不再退回旧格式顶层键** —— 只认 `cfg.<key>`，读不到就用**行定义的默认值** |

（旧格式键交给桥的**自愈**清理，不再参与读取。已确认：SP 里那两把残留**已经没了** ✅）

### 教训

> **"兜底"和"清空"撞在一起，就是最容易出死循环的组合。**
> 一个是"读不到就用旧的"，一个是"没值就写空" ——
> 单看都合理，合起来把用户的操作**吃掉了**。
>
> 而且它**表现成"改不了"**，让人以为是自己没操作对。

## 十五、三个反馈（3.40.2）

主人报：「颜色改不了 / 透明度和模糊必须有一个 1，不能都改成 0 /
　　　　　消息列表第一次打开是显背景的，但切后台一次又变成液态玻璃色」

### ① 「颜色改不了」→ **查下来整条链路是通的**

拉到 UI 的 SharedPreferences 实测：
```
cfg.fuckds_glass_color = '-65536'   ✅
cfg.fuckds_glass_tint  = '60'       ✅
cfg.fuckds_glass_blur  = '20'       ✅
```
宿主侧也认：`color=#ffff0000`（我广播的红色，宿主照单全收）✅

⇒ **第十四节那个 `readValue` 的修法顺带把它治好了**（之前 `cfg.` 被写空 ⇒ 退回旧键 ⇒ 显示老值）。
（另：`cfg.fuckds_glass_src` 是**空字符串** —— 无害，读取会走默认值"元素底色"，push 也会跳过空值。）

### ② 「透明度和模糊必须有一个 1」→ **这不是 bug，是「底色模式」的物理必然**

底色模式的玻璃内容 = **元素自己的背景色**。于是：
- **浓度 = 0** ⇒ 叠在上面的那层颜色不贡献 ⇒ 剩下的就是**元素本来的颜色**
- **模糊 = 0** ⇒ 对一张"本来就平滑的合成渐变"做模糊 ⇒ 看不出差

⇒ **两个都 0 时，玻璃 = 元素原色** ⇒ 看起来"根本没上玻璃"。
**所以"至少得有一个 ≥1"是对现象的准确观察，但它不是限制，是这个模式的特性。**

> 想让玻璃"明显是玻璃"：**浓度 20~60**（让那层颜色真的盖上去）。

### ③ 「第一次显背景，切后台变玻璃色」→ **真 bug，已修**

**根因**：底色模式下**拿不到元素颜色时，我偷偷退回了截图模式** ——
- **首次进入**：组合期刚跑，`sNodeColor` 还是空的 ⇒ 走截图 ⇒ **显示背景** ✗
- **切一次后台**：颜色缓存好了 ⇒ 走底色 ⇒ **变成玻璃色** ✗
⇒ 同一块地方**前后两张脸**，看起来像随机变脸。

**修法**：**底色模式拿不到颜色就不画**（保持元素原样），颜色到位再上玻璃 ——
**宁可晚一帧，也不要前后不一致。**

### 教训

> **"静默兜底"最坑的地方是它会"变脸"。**
> 兜底本身没错，错的是**同一个元素在不同时刻走了不同的路** ——
> 用户看到的是"莫名其妙变了"，而不是"降级了"。
> ⇒ 兜底要么一开始就用，要么就让位（不画），**别中途切换**。
