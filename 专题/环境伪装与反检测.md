## 二、侦察结论（本轮全部逆向实证）

### 2.1 那句提示的出处：服务端返回的风险码

资源 id 定位：

| 资源 id | 名称 | 中文 |
|---|---|---|
| `0x7f0f00be` | `create_pass_code_risk_device_toast` | 当前设备运行环境异常，请尝试更换环境 |
| `0x7f0f00db` | `exection_environment_execption_toast` | 同上 |

`0x7f0f00be` 的唯一引用点：

```
Loh2;->b(ILdo8;)V        # CreateSmsVerificationCodeErrorCode 的错误码 → toast 映射
    value == 0  → 直接 return
    value == 1  → 0x7f0f004c
    value == 2  → 0x7f0f00be   ←【风险设备】就是这一支
    value == 3  → 0x7f0f00bd
    value == 99 → 0x7f0f00ba（短信服务异常）
    value == 5  → 0x7f0f025f
    value == 4  → 0x7f0f0216
```

**结论：错误码由服务端下发，客户端只负责显示。**
⇒ 单纯 hook 这个 toast 没用（短信根本发不出去），必须让**上报的设备指纹变干净**。

### 2.2 检测方：数美反欺诈 SDK（com.ishumei.smantifraud）

APK 里同时存在这些风控/采集 SDK：

| SDK | 位置 | 备注 |
|---|---|---|
| **数美** | `com.ishumei.smantifraud.*` + `lib/arm64-v8a/libsmsdk.so`（842KB） | **本次主攻目标** |
| 字节 APM(insight) | `Lsr9;` + `libapminsighta/b.so` | 有个 `is_root` 字段 |
| 火山日志 | `libvolc_log.so` | 无关 |
| 瑞数 crypto | `librscrypto.so`（Rust） | 无关 |

`Lj4;->A(Ljava/lang/Object;)Ljava/lang/Object;`（协程壳）里直接 `SmAntiFraud.getDeviceId()`，
数美上报的 JSON 形如 `{"organization":..., "smid":..., ...}`（见 `l1l1l111Il;->l1111l111111Il`）。

### 2.3 ⭐ 关键发现：数美自己有一张「系统 API 监控清单」

类 `l1111l111111Il` 里挂了一个 base64 + zlib 常量，解压后是一段 **9.8KB 的 JSON**：

```json
[{"key":"element","clazz":"dalvik/system/DexPathList$Element","method":"toString","type":1},
 {"key":"insPkg","clazz":"android/app/ApplicationPackageManager","method":"getInstalledPackages","type":1},
 {"key":"spget1","clazz":"android/os/SystemProperties","method":"get","type":2},
 {"key":"native","clazz":"java/lang/reflect/Modifier","method":"isNative","type":2},
 {"key":"exec","clazz":"java/lang/Runtime","method":"exec","type":1},
 {"key":"file1","clazz":"java/io/File","method":"<init>","sig":"(Ljava/lang/String;)V","type":3},
 {"key":"probuild1","clazz":"java/lang/ProcessBuilder","method":"<init>","type":3},
 ...]
```

含义（`type`：1=调用取值 / 2=读取 / 3=构造监控）——**这张表就是「防 cloaking 模块」的探测清单**：
`Modifier.isNative` 那条是经典的 Xposed 钩子探测（LSPosed 会把被 hook 的方法标成 native）。
**我们如果乱 hook 这些 API，反而会被它标记成风险。**
⇒ 所以本轮的第一优先级是**把这张表在源头掐掉**（见 `l111l11111lIl()`），再谈伪装。

### 2.4 数美 Java 层全部环境探测点（类 `com.ishumei.smantifraud.l1111l111111Il`）

| 方法 | 返回 | 干什么 |
|---|---|---|
| `l111l11111I1l()` | Z | 查类加载器里有没有 `XposedBridge.jar` |
| `l111l11111Il()` | Map | 查 `XposedBridge.hookedMethodCallbacks` 等字段 |
| `l111l1111l1Il()` | Set | 查 `XposedHelpers` 的 `fieldCache/methodCache/constructorCache` |
| `l111l1111llIl()` | List | **读 `/proc/self/maps` 找 `/data/app/` + `xposedmodule`（模块探测）** |
| `l111l1111lI1l()` | String | ServiceManager 里 location/phone 的 hook 痕迹（`locateServiceName:`） |
| `l111l11IlIlIl()` | String | `XposedInit.loadedPackagesInProcess` |
| `l11l1111I11l()` | Z | `de.robv.android.xposed.XposedHelpers` / `de.robvf...`（故意带错拼写） |
| `l11l1111Ill()` | List | `Runtime.exec("sh -c set")` 类探测 |
| `l11l1111lIIl()` | List | 栈帧里有没有 `at com.ishumei` / `at android.view.View` |
| `l11l111l11Il()` | String | riru：`com.elderdrivers.riru.edxp.config.EdXpConfigGlobal` |
| `l11l111l1lll()` | String | `XposedInit.loadedModules` |
| `l111l11111lIl()` | Map | **2.3 那张 API 监控清单** |
| `l11l11IlIIll()` | I | filesDir 下 `exp_base.apk` 相关计数 |

调用链（`l1111l111111Il;->l111l11111lIl/llIl/11Il` 的唯一消费者）：

```
com.ishumei.smantifraud.l111l1111llIl;->l1111l111111Il(Ll11l11IIII1l;Ljava/util/Set;Ll11l1111lIIl;Ll11l11IIII1l;Ll11l111l11Il;ILl11l11IIII1l;)V
        ↓ 收集
com.ishumei.smantifraud.l111l1111llIl;->l1111l111111Il(IZ)Ljava/lang/String;   （950 条指令的总采集）
        ↓
com.ishumei.smantifraud.dfp.SMSDK;->v1(...)Ljava/lang/String;                 （Java 传入 Set/List）
        ↓
com.ishumei.smantifraud.dfp.SMSDK;->w1(...)Ljava/lang/String;                 （native，出加密指纹）
```
**好消息**：Xposed / 模块 / maps 这三类信号全是 **Java 侧采集**，而且明确作为 `Set`/`List` 参数传进 native
⇒ 在 Java 侧掐掉 = 干净数据进 native。

### 2.5 字节 APM 的 root 标记（顺带）

`Lsr9;->w()Z`：查 `/sbin/su`、`/su/bin/su`、`/data/local/su`、`/data/local/bin/su`、`/data/local/xbin/su` …
结果写进上报实体的 `is_root` 字段（`Lsr9;->n(Lyda;)V`）。

## 三、实现（2.9.5）

### 3.1 新增 9 个类

| 类 | 职责 |
|---|---|
| `GmEnv` | 总控：状态（开关/缓存）、掩体表、hook 安装、吐司、属性伪装表 |
| `GmEnvHook` | 通用「改返回值」钩子，`m` 字段选模式：0=false / 1=空 Map / 2=空 Set / 3=空 List / 4="" / 5=0 |
| `GmEnvFileHook` | `File.exists()`：命中黑名单路径就改判 false（**只覆盖 true→false**） |
| `GmEnvPmHook` | `ApplicationPackageManager`：`getPackageInfo`/`getApplicationInfo` 对黑名单包名抛 `NameNotFoundException`；`getInstalledPackages`/`getInstalledApplications` 过滤列表 |
| `GmEnvExecHook` | `Runtime.exec` / `ProcessBuilder.start()`：命中 su/magisk 类命令就抛 `IOException("not found")` |
| `GmEnvPropHook` | `SystemProperties.get`：`ro.build.tags`→release-keys、`ro.debuggable`→0、`ro.secure`→1、`ro.boot.verifiedbootstate`→green … 共 12 条 |
| `GmEnvSwitch` | 两个开关的 `OnCheckedChangeListener`（m=0 总开关 / m=1 系统 API） |
| `GmEnvClick` | 打开/关闭「环境伪装」页（m=0 open / m=1 close） |
| `GmEnvDialog` | 独立设置页（沿用 `GmBeautyDialog` 的 UI 范式） |

### 3.2 改动 3 个类 + 清单

| 位置 | 改动 |
|---|---|
| `DisableFlagSecure.handleLoadPackage` | `:cond_24` 取到 classLoader 后**第一件事**就 `GmEnv->install(cl)`（必须早于数美 SDK 初始化） |
| `GmMenuDialog.open()` | 在「服务端灰度下发查看」前插入一行 **「环境伪装 ›」**（副标题：隐藏 root / 模块痕迹，绕过风控环境检测） |
| `GmResumeHook.afterHookedMethod` | `GmEntry->setAct` 之后追加 `GmEnv->onResume(activity)`（刷新开关状态 + 首帧吐司） |
| `AndroidManifest.xml` | `versionCode 91→92`、`versionName 2.9.4→2.9.5` |

### 3.3 开关（两个，都默认开）

| MMKV 键 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `key_env_bypass` | b | **开** | 总开关：数美 Java 探测 + APM root 标记 |
| `key_env_api` | b | **开** | 系统 API 伪装（File/包名/Runtime/SystemProperties/Build.TAGS）—— 更激进 |

- 判定：`GmStore.read2()` 返回空串 = 没设过 = **默认开**；只有显式写入 `"false"` 才关。
- `sOn` / `sApi` 是静态缓存，hook 安装**无条件执行**（在 `handleLoadPackage` 最早期），
  每次调用时读缓存 ⇒ **改开关即时生效，不用重启 App**。
- 吐司：`GmEnv-Install` 时若已能拿到 Application 就弹；拿不到则等 `MainActivity.onResume` 补弹（`sToast` 只弹一次）。
  文案：`环境伪装已开启：root / 模块痕迹已隐藏`。

### 3.4 默认开启的实现要点（防坑）

`handleLoadPackage` 阶段还没有 Context，读不了 MMKV ⇒
`sOn`/`sApi` 在 `<clinit>` 里**先置 true**，能拿到 Context 时（install 末尾 / onResume）再 `refresh()` 校正。
这样既满足「默认开」，又不会因为「读不到设置」而误判成关。

## 四、怎么验证生效

1. 装 `FuckDSManger_2.9.5_for_ds2.5.1.apk`，LSPosed 勾选 DeepSeek，重启 App
2. 进设置页 → FuckDSManger → 应看到新行「**环境伪装**」，两个开关默认都是开
3. 注入后应弹一次吐司「环境伪装已开启：root / 模块痕迹已隐藏」
4. **关键**：去登录页点「获取验证码」，看是否还弹「当前设备运行环境异常」
5. 用 LSPosed 日志过滤 `FuckDSManger`，应能看到：
   - `GmEnv installed`
   - `env hook com.ishumei.smantifraud.l1111l111111Il#l111l1111llIl=1` 之类（`=N` 是命中的重载数）
   - 失败的会打印 `env hook FAIL`（说明该方法名在 2.5.1 里对不上，需重新逆）

排查用：
- 若还拦：先把「系统 API 伪装」关掉只留总开关，排除「hook 系统 API 反而被 `Modifier.isNative` 抓到」的可能
- 若日志里 `env hook ... = 0`：说明类/方法名漂了，回到 2.5.1 重新 outline `l1111l111111Il`

### 5.1 native 侧没动

`libsmsdk.so` 的字符串是加密的（例：`/Kmfqf(kfi`(Tsuni`<`），
它自己的指纹采集/校验逻辑**无法用 Xposed 在 Java 层改**（native 直接走 syscall / 自读 maps）。
本轮把所有 **Java 侧**信号清干净了，native 那部分只能靠：
- LSPosed **隐藏/DenyList（+ Shamiko/Zygisk 隐藏）** 把 DeepSeek 的模块可见性关掉
- 或后续考虑 patch 宿主 so / 走 native inline hook（工程量另算）

### 5.2 服务端是裁判

错误码 2 是服务端判的。如果服务端**已经给这台设备的 SMID 打上了标记**，
只清信号可能仍拦 —— 这种情况的处理顺序建议：
1. 保持 2.9.5 开着，清 DeepSeek 的 `shared_prefs`/MMKV 里的 SMID（换新指纹）
2. 再观察是否放行

### 5.3 副作用

| 项 | 影响 |
|---|---|
| `File.exists` 快路径 | 每次调用都会 lowercase + 41 条 contains；已做「非 true 直接 return」优化，实测调用量下可接受 |

## 六、方法论存档（这轮最有价值的东西）

1. **APK 里 base64 长常量 = 先怀疑「压缩配置」**。
   数美那段 `eJy1...` 就是 zlib。环境里没有 python/zlib，我给 QuickJS 手写了一个
   inflate（fixed + dynamic Huffman）现场解出来 —— 9.8KB 的 JSON 直接暴露了它的探测清单。
   *脚本没留，下次要的话照 writeup 里的思路重写即可（约 150 行 JS）。*
2. **`hookAllMethods(类, 方法名, hook)` 比 `findAndHookMethod` 香**：一个方法名覆盖所有重载，
   命中数还能当「钩子是否生效」的可视化指标（本项目既有套路）。
3. **`if-eqz` = 等于 0 跳，`if-nez` = 不等于 0 跳** —— 本轮自己写的新代码里**又翻车 7 处**，
   全靠写完立刻回读抓回来。**新写的每个条件跳转都要回读确认方向。**
4. **共用 return 标签是 VerifyError 温床**：不同分支里同一个寄存器类型不一致 → 校验器拒绝。
   本轮统一改成「每个提前返回都给独立标签，且标签放在主流程 `return-void` 之后」
   ⇒ 天然没有类型合流问题。
5. **`edit_check(runBuildChecks=true)` 仍然不做字节码校验**（2.9.2 的老教训）—— 通过 ≠ 不崩。

## 一、「插件失效」的头号嫌疑（我自己的锅）

`GmEnv.install()` 被插在 `DisableFlagSecure.handleLoadPackage` 的**最开头**：

```
:cond_24
iget-object v0, ...->classLoader
invoke-static {v0}, GmEnv;->install(Ljava/lang/ClassLoader;)V   ← 这里
const-string v1, "kf5"        ← 后面一大串模块核心 hook 注册
...
```

LSPosed 对 `handleLoadPackage` 的调用是**整体 try/catch**：
只要 `install()` 中途抛出，异常被框架吃掉，但**同一次调用里后面的代码全部不执行**
⇒ 偷换入口（`GmResTextHook`/`GmClickHook`）、`GmTouchHook`、`GmPainterHook`、`GmVectorHook`、
`GmResumeHook`、防撤回、头像…**全部不注册** → 表现就是「插件整个失效」。

### 可能在 install() 里抛的位置（按嫌疑排序）

| # | 位置 | 说明 |
|---|---|---|
| 1 | `hookShumei()` / `hookRoot()` 里的 `new-instance GmEnvHook(...)` | `h()` 里**new 实例在 try/catch 之外**；若该类 VerifyError / NoClassDefFound，异常直接窜出 |
| 2 | `toastOnce()` → `GmUtil->toast` | `Toast.makeText(...).show()` **没有 try/catch**，早期无 Looper / Context 异常会窜出 |
| 3 | `GmDiag.log(...)` | 待确认是否有文件 IO 依赖 |
| 4 | `AndroidAppHelper.currentApplication()` + `refresh()` | refresh 内部有 try/catch，嫌疑低 |

## 二、反检测无效的原因（已可判定）

- 服务端判风险，且数美 **native 侧（libsmsdk.so，字符串加密）**采集的 root 信号
  在 Java 层改不了 → 清 Java 侧信号不够
- 本轮 Java 侧清单（Xposed 探测 / `/proc/self/maps` 模块扫描 / API 监控表）**是打掉了的**，
  但那只覆盖了「模块检测」，「root」那部分大概率在 native

## 三、2.9.6 要做的修改

1. **`GmEnv.install` 整体包 try/catch**（`sInit` 标记之后全部内容），
   保证**无论任何异常都不影响 `handleLoadPackage` 后续 hook 注册**
2. `h()` 改法：`new GmEnvHook(mode)` 放进 try/catch；失败只记日志
3. `toastOnce()` / `refresh()` 各自再包一层 try/catch（双保险）
4. `GmEnv.bad()` 去掉 **`"/su"`** 这个误伤极大的子串（它会把 `/xxx/subject`、`/xxx/support` 之类
   的**正常路径**判成 root，`File.exists` 会返回 false）→ 只保留精确 su 路径 + 明确的关键字
5. 稳妥起见：`key_env_api`（系统 API 伪装）**默认改关**，总开关保持开
   —— 先确认「Java 层伪装」到底有没有用，避免它带来的副作用干扰判断
6. 新增：把 `install()` 的每一步结果写进 `GmDiag`，真机上能一眼看出卡在哪
