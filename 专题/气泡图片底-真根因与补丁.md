# ⚠️ 真·根因：`if-eqz` 方向打反（把「解码成功」判成「失败」）

> 发现者：另一条线（`deepseek-flash`）· 记录：尼得亚伯 · 状态：**已定位，补丁待应用**（记录时 MT MCP `127.0.0.1:8787` 掉线，无法出包）

## 一、根因（一句话）

`saveImage` 的四路读图链与 `imgBrush` 里，**判断「拿到图了没」的分支方向全部打反**：

```smali
    invoke-static {v1}, BitmapFactory;->decodeStream(...)Bitmap
    move-result-object v3
    if-eqz v3, :dec_ok          ← ❌ v3==null（失败）才跳「成功块」；成功反而继续走 fallback
```

⇒ **解码成功被当成失败丢弃**（一路 fallback、最后 `return false`）；
⇒ 而**真失败时**反而跳进 `:dec_ok` ⇒ `compress(null, …)` ⇒ **NPE**。

`imgBrush` 同一个错法 ⇒ **图片底永远建不出来**。

## 二、因此被推翻的（全是误判 / red herring）

| 曾经的"结论" | 真相 |
|---|---|
| 「四种读法全灭」 | **假象**：第一次其实就成功了；日志里那四行本是"上一步失败"才该打的 |
| 「picker URI / 授权 / `CATEGORY_OPENABLE` / Activity 来源不对」 | **全部与现象无关**（换 URI 换读法当然都没用） |
| 「文件存在但非空、却解码失败」（2.22.9） | `imgBrush` 的反法所致 |
| 「选了图没反应 / 重启还是颜色底」 | `saveImage` 返回 false + `imgBrush` 反法 |
| 「同图同设备、背景能用气泡不能」 | 背景那条路的判断方向是对的，所以能用 |

## 三、精准补丁（**5 处**）

```smali
# ① GmBubble;->saveImage  —— 4 处（四路读图链），建议 replace_all
    if-eqz v3, :dec_ok      →      if-nez v3, :dec_ok

# ② GmBubble;->imgBrush   —— 1 处
    if-eqz v0, :decoded     →      if-nez v0, :decoded
```

### ✅ 不要动这些（方向本来就是对的）
| 位置 | 写法 | 语义 |
|---|---|---|
| `imgBrush` | `if-eqz v2, :fb_no_file` | `exists()==0` ⇒ 文件不存在 ✓ |
| `imgBrush` | `if-eqz v0, :fb_empty` | `length()==0` ⇒ 空文件 ✓ |
| `saveImage` | `if-eqz v1, :open_fail` | 流为 null ⇒ 打开失败 ✓ |
| `wrapImg` | `if-eqz v1/v2/v3, :ret` | 开关关 / 无 shape / 无 brush ⇒ 返回 null ✓ |
| `wrap` | `if-nez v0, :no_shape`、`if-eqz v0, :fallback_color` | shape 非空去建 / 图片结果空则退纯色 ✓ |

## 五、教训（补记）

| # | 要点 |
|---|---|
| **743** | ⭐⭐⭐ **`if-eqz` / `if-nez` 是手写 smali 的头号坑，且症状是"成功被丢掉"** —— 它不会报错，只会让功能像"读不到"，从而把人引向完全错误的领域（我为此在 URI/授权/格式上撞了十几版）。**规范：每个 `if-*z` 写完后，用一句话注释"跳到 X 的条件是什么"再往下写。** |
| **744** | ⭐⭐⭐ **"诊断日志本身也可能在说谎"** —— 我那四条"失败"日志其实是"上一步失败"才该打的；**当一组日志互相矛盾（如"成功"与"全灭"同时出现）时，先怀疑打点的条件，而不是被观测的系统**。 |
