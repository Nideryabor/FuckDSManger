# 气泡背景 · 静态分析（宿主 2.7.2 真实结构）

> 2026-10-31 · 尼得亚伯 🐲
> **这份文档纠正了同一天早先的错误结论。** 早先我把 `l23.a`(AppSurface) 当成气泡载体，是错的。

---

## 一、宿主 2.7.2 里的真实组件（从 `const-string` 的组件名校验串里挖出来的）

R8 把 UI 组件全塞进少数几个大类（`l23`、`v5a`、`zi9`、`cfb`…），所以**必须按字符串常量定位**，不能按类名猜。

### 用户气泡（`UserChatMessageBubble.kt`）

| 组件 | kt 行 | 2.7.2 里的位置 |
|---|---|---|
| `UserChatMessageBubble` | 214 | `l23.t(Ljava/lang/String;×3, Lyj7, Lfy4, Ljava/lang/String;, Lvy4, F, Lfy4, Lhy4, Z, Lfy4, Z, Lr15, I, I, I)V` |
| `MessageBubbleLayout` | 385 | `l23.n(Lr33; Lyj7; Lyj7; Lvy4; Lvy4; Lr15; I)V` |
| `MessageBubbleContentLayer` | 422 | `l23.m(Lr33; Lyj7; Lvy4; Lr15; I)V` |
| `MessageOverflowButton` | 502 | 同类 |
| `rememberBubbleState` | 99 | 同类 |

**调用链**：
```
l23.t (UserChatMessageBubble)
  └─ l23.n (MessageBubbleLayout)      ← ★ 两个 Modifier 参数 p1 / p2
        ├─ zi9.S(composer, p1)
        └─ l23.m(content, p2, ...)     ← ★ p2 传进内容层
              └─ zi9.S(composer, p1)
```

### 助手消息（`AssistantChatMessage*.kt`）

**没有 Bubble 组件**。全是：
`AssistantChatMessageCell` / `AssistantChatMessageCellScaffold` / `AssistantChatMessageContent` / `AssistantChatMessageFooterV2` …

⇒ **助手消息天生没有气泡边框**（是一块内容区）。
⇒ 这就是为什么当年只能拿 `wrap`（挂 `cfb.g` 整行）给它染色 —— 也是"按钮/代码块一起被染"的**设计源头**，不是调参能解决的。

## 二、三个被我判错的锚点（重要纠错）

| 早先的结论 | 实际情况 | 证据 |
|---|---|---|
| `l23.a`(AppSurface) = 气泡载体 | ❌ **通用表面容器**（卡片/面板都用） | `l23.a` 只被 3 处调用：`de.G:1839`、`de.I:7539`、`hy.q:580`；组件名校验串 = `AppSurface (AppSurface.kt:25)` |
| `v5a.m` = 气泡 | ❌ `HeaderBackground (AssistantContentScaffold.kt:285)` | v5a 类里的组件串 |
| `x98.t` / `x98.s` 可做挂点 | ❌ 通用 background 原语，**70+ 调用点** | `grep Lx98;->t(` 全宿主 70+ 文件 |

### `l23.a` 内部结构（曾被我当成气泡底色的来源）

```smali
.method public static final a(Lyj7;Lsy9;JJLr33;Lr15;I)V
    move-wide/from16 v3, p2                       # v3 = args[2] 底色
    :cond_a0
    invoke-static {p0,p1}, Lvcc;->B(Lyj7;Lsy9;)   # 按 shape 裁剪
    move-result-object v10
    invoke-static {v10,v3,v4,v11}, Lx98;->t()     # 画底色
```
这段**本身是对的**，但它是"通用容器怎么画底色"，**不代表气泡**。

## 三、下次该怎么做（结论）

### 用户气泡

挂 **`l23.n`（MessageBubbleLayout）**，改 `args[2]`（p2，会传进内容层）：

```
l23.n(Lr33 p0=content, Lyj7 p1, Lyj7 p2, Lvy4 p3, Lvy4 p4, Lr15 p5, I p6)V
                                        ↑ 改这个
```
或挂 **`l23.m`（ContentLayer）** 改 `args[1]`。

**为什么比 `x98.t` 好**：这两个方法**只在用户气泡渲染时**被调用 ⇒ 天然精确，不需要 caller 字符串、不需要计数器。

### 助手消息

需另找：`AssistantChatMessageContent` / `AssistantChatMessageCellScaffold`。
注意**它没有气泡容器**，所以"给助手消息加背景"要么加在外层内容区（会连同代码块一起染），要么接受"只有用户气泡有背景"。

### 绝对不要再用

- ❌ `x98.t` / `x98.s`（通用原语，70+ 调用点）
- ❌ `l23.a` / AppSurface（通用容器）
- ❌ `cfb.g`（消息整行，按钮/代码块全在里面）

## 四、定位方法论（这次是这么挖出来的）

1. 宿主 APK 里搜**组件名校验字符串**：
   ```
   com.deepseek.chat.ui.<路径>.<组件名> (<文件名>.kt:<行号>)
   ```
   这是 Compose 的 recomposition 校验串，**每个 composable 都有**，是定位组件的黄金线索。
2. 用 `grep -rl "组件名 (文件名.kt:行号)"` 找到所在 dex → 反编译
3. 用 `awk 'NR<=命中行 && /^\.method/{m=$0;ln=NR} END{print ln": "m}'` 反查所属方法
4. 别信类名（`l23` 里混着 IO、HashMap 工具方法），**只信字符串和方法签名**

## 五、这次静态分析的教训

| # | 教训 |
|---|---|
| 1 | ⭐⭐⭐ **不能只看片段就下结论**。我看到 `l23.a` 里有 `x98.t` 就认定它是气泡，没验证"谁调用它、它是什么组件" |
| 2 | ⭐⭐⭐ **先查组件名校验串**，能一句话确定身份，比猜调用链快十倍 |
| 3 | ⭐⭐⭐ **R8 混合类不能按类名判断用途**。`l23` 里同时有 AppSurface、UserChatMessageBubble、文件 IO —— 必须按方法定位 |
| 4 | ⭐⭐ **通用原语（x98.t）永远不是挂点**。挂了就得靠 caller 筛，又慢又脆，还会误伤 |
| 5 | ⭐⭐ **"助手消息没有气泡容器"这个前提必须早知道**。否则"AI 气泡背景"这个需求本身就要重新定义 |
