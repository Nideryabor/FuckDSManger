# 开关 → 配置应用入口 映射表

> 为什么需要这张表：**有些开关不是"往存储里写个键"就完事的**。
> 功能自己还带着两样东西，裸写存储会把它们漏掉 —— 症状就是"面板上拨了，宿主没反应"。
>
> 建立于 2026-09-26（一天之内连栽两次之后）· 尼得亚伯 🐲

---

## 一、裸写存储会漏掉什么

| 漏掉的东西 | 症状 | 实例 |
|---|---|---|
| **功能自己的「读过了」缓存** | 拨了不生效，重启宿主才变 | `GmBubble` 的 `sRead` / `sURead` / `sReadCfg` |
| **功能自己的副作用** | 标志变了但宿主那份数据没动，等于没变 | `GmModel.setOn` 还会**改写宿主自己的模型配置 JSON**（`kv_remote_settings_model_configs_v1` 里的 `"switchable"`）再 `hostPut` 写回 |

⇒ **正解：走功能自己的入口（`setOn` / `setUOn` / `apply*`）。** 模块自己的 UI 就是这么干的，
所以那条路一定是"完整"的 —— 写值、维护缓存、附带副作用，它自己全做了。

## 二、已核实的表（都是**对着 smali 验的**，不是猜的）

验证方法：`grep` 出读这个键的类 → 看它的 `setOn/setUOn` 里 `const-string` 写的是不是同一个键。

| 配置键 | 该走的入口 | 入口顺带做的事 | 何时生效 |
|---|---|---|---|
| `fuckds_bubble_on` | `GmBubble.setOn(ctx, v)` | 置 `sOn`、把 `sRead` 标成已读、写存储 | **立即**（下次绘制） |
| `fuckds_ububble_on` | `GmBubble.setUOn(ctx, v)` | 置 `sUOn`、把 `sURead` 标成已读、写存储 | **立即**（下次绘制） |
| `fuckds_model_switch` | `GmModel.setOn(ctx, v)` | **改写宿主模型配置 JSON 并写回宿主** ✅ | ⚠️ **要宿主重新读**（一般=强停宿主再开）。若宿主启动时重新下发，改动会被覆盖 ⇒ 那时要改在**下发点**（`GmDsHook*`） |
| `fuckds_device_on` | `GmDevice.setOn(ctx, v)` | 写存储（+ 它自己的初始化标志） | 建议强停宿主 |
| 其余（`fuckds_bg_*` / `fuckds_suggest_*` / 气泡颜色圆角…） | 暂时**裸写 + 清 `GmBubble` 读取缓存** 兜底 | 还没找到对应入口 | 不确定 |

### 2.1 模型切换的自证结论（2026-09-26 实测）

```
【FdmBridge】fuckds_model_switch=false → GmModel.setOn → true
【FdmBridge】回读宿主配置：len=23430 含switchable:false=true 含switchable:true=false
             片段=[…"enabled":true,"switchable":false,"show_model_na…]
```

⇒ **宿主那份 JSON 确实被改写了**。所以"拨了没反应"**不是桥的问题**，
而是宿主读完/缓存之后不会自己重读 ⇒ 这是**该功能本来的脾气**
（模块原生 UI 里拨它也是同样两件事，同样要重启宿主）。


## 三、还有哪些"应用入口"没接（下次做）

模块里这些类都有 `setOn` / `apply` / `reapply`，但**还不确定对应哪个键**（先留着，别猜着接）：

```
GmBg.setOn            GmEnv.setOn        GmAvatar.setOn     GmDb.setOn
GmHello.apply/reapply GmPrompt.apply(+hostPut)             GmProbe.toggle
GmBubble.applyColor / applyRadius / applyOn / setAlpha …
```

> ⚠️ 注意有两个类（`GmAvatar`、`GmDb`）的 `setOn` 写的是同一个键 `fuckds_gm` ——
> 看起来是"总开关"性质，接之前得先弄清语义，别乱拨。

## 四、给未来的自己：加一个新开关时的检查单

1. 在 smali 里 `grep` 这个键 → 找到读它的类
2. 看这个类有没有 `setOn` / `setUOn` / `apply*`；有 ⇒ **走它**，别裸写
3. 看这个 `setOn` 里有没有 `GmPrompt.hostPut` / `GmStore.write` 之外的调用 ⇒ 那些就是"附带副作用"，走入口才带上
4. `grep "sput-boolean"` 看这个类有没有静态缓存 ⇒ 有缓存又只能裸写时，记得清
5. 把结论补进上面那张表

## 五、桥侧的落地（`FdmBridge.dispatch`）

```
收到配置 → 对每个 bools 键：
   dispatch(ctx, key, v) 有对应入口？ ── 有 ──▶ 调入口（setOn/setUOn），从待写集合里移除
                                    └─ 无 ──▶ 裸写存储（后面统一清一次 GmBubble 缓存兜底）
```

日志会明确打出来：`【FdmBridge】走专用入口的开关：fuckds_bubble_on fuckds_model_switch`
