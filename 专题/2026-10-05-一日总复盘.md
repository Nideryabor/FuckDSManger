## 二、这一天啃穿的东西：**「点一下，AI 就回话」**

### 2.1 目标

> AI 在回复末尾写 `<Suggestion>▸ 再详细讲讲</Suggestion>`
> ⇒ 界面渲染成一个**能点的东西**
> ⇒ 点一下 ⇒ 这句话**当作消息发给 AI**

### 2.2 两半拼图

**① 可点击** —— 抄宿主自己的（不是自己造）：
```
宿主 or6 里 markdown 链接的实现（逐字）：
  new ri6(tag, styles, listener)      # LinkAnnotation.Clickable
  in.h(si6)                           # ★ Builder.pushLink(link)
  in.e(文字) ; in.f()                 # append + pop
⇒ 照抄三行 + 用 Proxy 实现 ti6(LinkInteractionListener) 接口
```
**难点其实是"敢不敢信"**：Compose 里自己塞控件被封死（`AndroidView` 是 `@Composable`），
但**宿主自己的链接本来就可点** ⇒ **搭它的车**。

**② 发送** —— 走了一大圈冤枉路，最后从**底座的旧代码**找到钥匙：
```java
gh2.h0(gh2, 文本, [], [], "", m1a, ns, false, false, false, false)
                                   ↑   ↑
                                m1a  目标会话 —— ★ 就是它
```

### 2.3 ★★★ 两个必须记住的坑

**坑 1 · 别用 `gh2.S(...)`** —— 它**不带会话参数**，走"兜底"逻辑 ⇒ **每发一次开一个新会话**。
（尼尼连开 5 个空会话才醒悟。）

对照 2.5.2 底座 `GmCallDialog.send()` 里的注释，**写得明明白白**：
```
"发送：用有会话的 component（sid 非空）"
"发送：兜底（没有候选带会话 ⇒ 可能新开）"     ← ★ 就是这个
```
**⇒ 老代码的注释是金子。早读它能省一整晚。**

**坑 2 · 必须挑「当前会话」的 `gh2` 实例**
宿主进程里同时活着**多个** `gh2`（每个打开过的会话一个），实测同时 4 个：
```
sid="ff420901-…"  3 条
sid="c64bb7d0-…"  3 条
sid="d9efadb8-…"  76 条   ← 当前会话（消息数最多）
sid=""            1 条    ← 空会话（之前乱发造出来的）
```
**判据 = `W().a` 非空 且 `W().f` 消息表最大。**

## 四、★ 这一天最有价值的三个"手艺"

1. **frida 投递式网关 = 35 秒一个答案**
   改代码-编译-装机-重启 是 10 分钟一轮；frida 是 **35 秒一轮**。
   ⇒ **能用"观测"拿到的，绝不用"推断"代替。**

2. **触摸窗口聚焦**（探针 v2 的关键设计）
   `fz2.p` 那种热路径每帧都过，日志必然淹没。
   ⇒ **只记"用户刚摸过屏幕 1.5 秒内"的命中** ⇒ 主人点一次，日志里就只有那一下。

3. **让脚本自己触发，别等人**
   frida 的 30 秒窗口 vs 人看到消息再操作的几分钟延迟 ⇒ **永远对不上**。
   ⇒ 最后靠"脚本自己调 `gh2.h0`"才闭环。
   （后来还用 adb `input tap` 把**发送按钮的真实坐标**算出来了：1440×3168 的屏，
   截图是 921×2048 ⇒ **缩放 1.56 倍**，一开始坐标全错。）

## 七、教训（927~943）

- **927 ⭐⭐⭐ 「借宿主自己的机制」永远优于「自己造」** —— 链接可点这件事，宿主早就实现了
- **928 ⭐⭐⭐ 「名字被复用」比「名字变了」更危险** —— `ao1` 在 2.6.1 照样存在，只是变成了别的东西
- **929 ⭐⭐⭐ 死代码要分清「源码删了」和「底座删了」** —— 底座里那套 `testSend` 完整活着，注册语句都在
- **930 ⭐⭐ 「静默失败」是老代码常态** —— 两道 `if-eqz return` 守卫 ⇒ 按下去零日志
- **931 ⭐⭐ 接口是"不依赖宿主类"的缝隙** —— 选锚点优先挑接口（`ti6` 是接口 ⇒ 一个 Proxy 就补上）
- **932 ⭐⭐ 尖括号标记有被 markdown 吃掉的风险** —— 备一条 `⟦⟧` 退路成本极低
- **933 ⭐⭐⭐ 老代码的注释是金子** —— `"兜底 ⇒ 可能新开"` 一句话点破当晚最大的坑
- **934 ⭐⭐⭐ 「能调通」≠「是对的」** —— `gh2.S`/`x42.s` 都能调、都不崩，但一个开新会话一个根本不发
- **935 ⭐⭐⭐ 参数语义要从「默认值」反推** —— `m1a` 默认 `randomUUID` ⇒ 它是"本次发送标识"
- **936 ⭐⭐ 同一个类可能有多个实例** —— `Java.choose` 拿第一个不靠谱，要按业务判据挑
- **937 ⭐⭐ frida 投递式和"人的反应时间"天生对不上** —— 能让脚本自己触发的别等人
- **938 ⭐⭐ 试探要控制爆炸半径** —— 每次动手前先想"最坏结果是什么、能不能收拾"
- **939 ⭐⭐⭐ 「前提条件」要写在功能旁边不能只写文档里** —— 依赖没开 ⇒ 十有八九看着像 bug
- **940 ⭐⭐ 幂等判据用内容特征而非定界符**
- **941 ⭐⭐ 「追加 vs 覆盖」必须显式确认** —— 用户手写数据被覆盖一次就再也不敢用了
- **942 ⭐⭐⭐ 「改了不生效」先问「是不是要重启」** —— Xposed 开关分"渲染时现读"和"启动时注册钩子"两类
- **943 ⭐⭐ 把"设计如此"写进 UI，比修一个修不了的 bug 更有价值**
- **944 ⭐⭐⭐ 「样本里成立」不等于「规律」** —— 选会话的旧判据（消息数最多）是"实测出来的"，
  那次恰好当前会话消息最多 ⇒ 被当成通解 ⇒ 换场景就发错会话。
  **只有能解释清楚因果的判据才敢当通解**（"正在显示的会话会被频繁调用"能解释，所以它行）
- **945 ⭐⭐ 高频方法上挂钩子，只要"只赋值"就可以很便宜** ——
  `W()` 每秒几十次，但 `sRecent = x` 的开销可忽略。别因为"这是热路径"就放弃最准的观测点
