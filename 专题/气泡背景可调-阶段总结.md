## 3′. ✅ 结案（2.22.22）：真凶是 **6 处分支极性写反**（`if-eqz` → `if-nez`）

| 位置 | 处数 | 症状 |
|---|---|---|
| `GmBubble.saveImage` 的四路读图链 | **4** | **解码成功被当成失败** ⇒ 一路走兜底并打印「读不出图 ⇒ 改用…」⇒ 四路全成功后 `goto` → **`return false`**（图从不落盘）；**真失败**（任一路 null）才跳 `:cond_8e`，那里 `compress(null)` ⇒ NPE 被 catchall 吞掉 |
| `GmBubble.imgBrush` 的两次解码判空 | **2** | **两张图都解码成功时它 `return null`** ⇒ 图片底永远退回纯色（`wrapImg` 自身极性是对的） |

**破案钥匙 = 日志的自证性**：那串
「openInputStream 读不出图 ⇒ loadThumbnail 也没拿到 ⇒ ImageDecoder 也失败 ⇒ 连 MediaStore 缩略图都拿不到」
**每一条都是「上一步成功」才会打印**的那句 ⇒ **四行全打 = 四路读法全都读到了图**（picker URI 一直可读）。

**为什么「修改背景」一直好使**：`GmBg.saveImage` = **裸流拷贝**（26 指令、**零分支**）；`GmBubble.saveImage` = **解码链**（86 指令、**4 分支全反**）
⇒ 主人「同图同机一好一坏」的对照实验**依然是最强信号**，只是它指向的是「**两个实现的代码差异**」，而 2.22.21 只 diff 了 Intent 与发起 Activity。

**已证伪（别再当线索）**：URI 临时授权归属（2.22.21 那两行结论要打星号）· `CATEGORY_OPENABLE` 重定向 · 编码不可解（HEIC/AVIF）· 发起 Activity 不对。
**修**：6 处 `if-nez`（每处用它后面**各自不同的日志串**定位）；产物 `2.22.22`（vc353 / 117 类 / `e690c2e5…`），已回读产物确认「4+2 处已改、0 处残留」。

## 3. 历史现场：自建选图通道「读不到内容」的取证过程（**结论已被 §3′ 取代**）

### 现场证据（主人做了对照实验：**同一张图、同一台设备**）
```
修改背景 → 可用（fuckds_bg.png 会更新）
选择气泡图 → 失败，日志：
[气泡] 选中 uri = content://media/picker_get_content/0/com.android.providers.media.photopicker/media/1000020917 ｜ type=null
[气泡] openInputStream 读不出图 ⇒ 改用 loadThumbnail（Photo Picker 兜底）
[气泡] loadThumbnail 也没拿到 ⇒ 改用 ImageDecoder（现代解码 API）
[气泡] ImageDecoder 也失败 ⇒ 改用 MediaStore 直读
[气泡] 连 MediaStore 缩略图都拿不到
```

### 已排除（每一条都做过实验）
| 假设 | 结论 |
|---|---|
| Intent 写法不同 | ❌ 与 `GmBgDialog.pickBg()` **逐字一致**（`GET_CONTENT`+`image/*`） |
| `CATEGORY_OPENABLE` 触发重定向 | ❌ 去掉后 URI **仍是** `picker_get_content` |
| 图片格式不可解 | ❌ **同一张图**在背景通道能解 |
| Activity 来源不对 | ❌ 已改 `GmBgDialog.act()` 发起，现象不变 |
| 请求码 | ❌ `0x435a` 与 `0x435b` 表现一致 |
| 读法不对 | ❌ **四种独立读法**（含文档选择器给的普通 `documents` URI）全灭 |

### ~~仍在桌面的假设~~（**2.22.22 已证伪：picker URI 一直可读**）
**系统「照片选择器」的 URI 临时授权，只对"发起 `startActivityForResult` 的那个 Activity 实例/任务"生效**；而我们的读取发生在 `GmPickHook.beforeHookedMethod`（钩在 `Activity.onActivityResult` 上）里，与"发起者"不是同一身份 ⇒ 授权判定不通过 ⇒ 流能开、内容读不到。
（`documents` URI 也失败，说明可能还有第二层：读取发生在**宿主自己的 `onActivityResult` 之前**，而授权/交接在那之后才完成。）

### 两条候选解法（**均已不需要**：2.22.22 已从根因修好）
1. **复用现成通道**：气泡的「选择气泡图」直接调 `GmBgDialog.pickBg()` ⇒ 稳（走已验证路径），**代价**：那张图同时成为 App 背景
2. **借用 + 还原**：走背景通道选图后，立刻把 `fuckds_bg.png` 另存给气泡、再还原原背景 ⇒ 无副作用，步骤多（约 60 行 smali）
3. （可选第三条）**不在读 URI 上做文章**：改为"用户用系统相册把图放到某个约定目录"或"从已渲染的消息图片里提取"，彻底绕开 picker 授权

| 745 | ⭐⭐⭐ **「多路独立读法全灭」有两种相反解释**：① 公共前置坏了 ② **我的判据写反了**。2.22.20/2.22.21 连续选了 ①，并据此写下「编码不可解」「授权归属」两个**结论**，实际是 ② |
| 746 | ⭐⭐ **「他们能用我不能用」要 diff 到函数体**：只 diff Intent + 发起 Activity 不够；本次真差异在函数实现（裸流拷贝 vs 解码链） |
| 747 | ⭐⭐ **「取不到就 null」的函数，要顺手验证「能取到时真的返回了东西」**：`imgBrush` 在返回图片时反而打「不可用」——**日志朝向反了**，观感上就像"永远取不到" |
| 749 | ⭐⭐⭐ **`android.graphics.Shader` 天生「无尺寸感知」**：`BitmapShader` 默认按**单位矩阵 + CLAMP** 画 ⇒ 永远是「1:1 贴节点左上角 + 右/下拉伸边缘」。**要当背景/铺满，必须自己按绘制尺寸算 `localMatrix`**（这正是 Compose `Brush.Bitmap` 存在的理由） |
| 750 | ⭐⭐⭐ **「借宿主现成实现」也有粒度**：`tn0` 只借到「`Shader`→`Brush` 的包装」，没借到「按尺寸缩放」（本宿主 R8 把 `Brush.Bitmap` 剪掉了 ⇒ 全 dex 只有 5 个 `ShaderBrush` 子类，无一包 `ImageBitmap`）⇒ **借之前先确认「要借的那一步」在不在** |
