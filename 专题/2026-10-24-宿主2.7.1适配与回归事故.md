### 2.2 方法会跑到「别的碎片」★ 最阴的一条

> **`qn7` 的 48 个方法里，47 个在 `jr7`，只有 `s`（GotoBottomButton）在 `dz7`。**
> 因为它属于 `ChatFloatingToolViewV2` 这个域，而该域整体划给了 `dz7`。

原来的 `hookM`：

```java
String cls = GmRemap.cls(oldCls);        // "qn7" → "jr7"
String mth = GmRemap.method(oldCls, m);  // "s"   → "o"
findClass(cls); hookAllMethods(cls, mth, hook);   // ← jr7 里没有 o！静默失败
```

**修法**：新增 `clsFor(类, 方法)`，MTH 表加一列 `owner`，按**方法**查它真正所在的类。
`GmEntry.hookM` 里 `cls(p1)` → `clsFor(p1, p2)`（寄存器不变，只是 invoke 参数 1→2 个）。

**真机验证成功**：`hookM dz7.o count=1` ✅

## 四、⚠️ 事故：我引入的回归（3.71.3）

### 4.1 我干了什么

为了让「重启后背景/气泡失效」好起来，我改了 `GmStore.get()`：

```smali
# 我加的"就绪校验"
invoke-interface {v0}, Landroid/content/SharedPreferences;->getAll()Ljava/util/Map;
move-result-object v1
if-nez v1, :cond_ok
invoke-interface {v1}, Ljava/util/Map;->size()I
move-result v2
if-gtz v2, :cond_ok
# 空表 ⇒ 丢缓存重取
```

### 4.2 为什么是错的

**`FdmBridge.java` 的注释里早就写着：**

> ★ 不用 `allKeys()`（MMKV 的 SharedPreferences 包装类上反射不到 ⇒ **实测回读 0 个键**）

`getAll()` 是同源问题（同一个包装类）。所以：

```
每次 getAll() → 空表 → 判空 → 丢缓存重取 → 又空 → ...
⇒ 所有配置读取全乱
⇒ 玻璃失效 + 系统提示词抹除失效
```

### 4.3 现场

主人报：**「不仅玻璃没了，而且系统提示词的抹掉内容也失效了，背景还是一样的」**

### 4.4 违反了哪几条铁律

| 铁律 | 我怎么破的 |
|---|---|
| **升级轮开工第一件事：先翻自家文档** | 注释就写在同一行附近，我没看 |
| **一次只动一处，改完必须验** | 我同时动了全局读取路径的缓存策略 |
| **别拿真机当第一个验证场** | 改完直接出包装机 |
| **「没有效果的新代码」= 纯风险** | 那段校验不仅无效，还有害 |

### 4.5 处置

已回滚。`GmStore.get()` 与备份 diff **只剩注释**：

```smali
.method public static get(Landroid/content/Context;)Landroid/content/SharedPreferences;
    .registers 4
    sget-object v0, sSp
    if-eqz v0, :cond_5
    return-object v0      ← 恢复原样（无条件返回缓存）
    :cond_5
```

## 五、背景/气泡/玻璃 的排查现状


## 七、给下一轮的三句话

1. **依赖「方法」的锚点，类名一律用 `clsFor()`，别用 `cls()`** —— 拆类后它们可能不是同一个类。
2. **`count=1` 之后还要数「调用点」** —— 前者证明挂上了，后者才证明会跑。
3. **动全局路径前，先把同文件上下 200 行的注释读一遍** —— 项目里踩过的坑基本都写在那儿了。
