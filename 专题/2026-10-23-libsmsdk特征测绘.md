## 0. 一句话结论

**这个 so 不是靠「看你的字节码长得像不像」来判定，而是靠 `popen` + `syscall` + `opendir/readdir` 主动扫描宿主进程环境，压缩后上报。**

→ 因此 **r8 混淆 / 改类名 / 改名基本无效**。它看的是「宿主进程里多了什么」，不是「你的代码长什么样」。

## 2. `libflipped.so` 完整解剖（已闭环）

### 2.1 身份

**`com.bytedance.mira.plugin.hook.flipped.compat.FlippedV2Impl`** 的 native 兼容层。
不是加固、不是检测，是框架自带的反射桥（老 Android 上 `getDeclaredMethod` 兼容用）。

### 2.2 编译痕迹

- clang `r522817b`（12.0.x），`+pgo +bolt +lto +mlgo`
- Linker: `LLD 18.0.2`
- **完全没 strip、没混淆、没加固**，AArch64，PIE + NX + stack canary

### 2.3 导出符号（全裸）

| 符号 | 地址 | 大小 |
|---|---|---|
| `JNI_OnLoad` | `0x1080` | 272 |
| `GetDeclaredMethodInternal(void*)` | `0xdb4` | 224 |
| `GetDeclaredMethod(JNIEnv*, jobject, jobject, jstring, jobjectArray)` | `0xf30` | 336 |
| `AttachCurrentThread()` | `0xd0c` | 112 |
| `DetachCurrentThread()` | `0xd7c` | 56 |
| `LOG(char const*, int)` | `0xcd0` | 24 |
| `LOG(char const*, char const*)` | `0xce8` | 24 |
| `LOG(char const*)` | `0xd00` | 12 |

### 2.4 `JNI_OnLoad` 反汇编还原

```c
jint JNI_OnLoad(JavaVM *vm, void *reserved) {
    JNIEnv *env;
    if ((*vm)->GetEnv(vm, &env, 0x10006) != 0)      // [iface+0x30], JNI_VERSION_1_6
        return -1;                                  // LOG("Failed to get env...")
    jclass c = (*env)->FindClass(env, ".../FlippedV2Impl");  // [env+0x30]
    if (!c) { LOG(...); return -1; }
    if ((*env)->RegisterNatives(env, c, &tbl, 1) < 0)        // [env+0x6b8]
        return -1;                                  // LOG("Failed to register Native method...")
    LOG("init succeeded.");
    return 0x10006;
}
```

### 2.5 RegisterNatives 表还原

注册表 `x2` 由 `adr x2, 0x5278` 给出，位于 **`.data.rel.ro` @ `0x5278`**（file offset `0x1278`）。
静态字节全 0（RELATIVE 重定位，加载时填），故从重定位表反查：

| 槽位 | 重定位类型 | numericType | addend | 解析结果 |
|---|---|---|---|---|
| `0x5278` | RELATIVE | 1027 | `0x9F8` | `"getDeclaredMethod"` |
| `0x5280` | RELATIVE | 1027 | `0x8F6` | `"(Ljava/lang/Object;Ljava/lang/String;[Ljava/lang/Class;)Ljava/lang/reflect/Method;"` |
| `0x5288` | JUMP_SLOT | 257 | — | `GetDeclaredMethod` @ `0xf30` |

### 2.6 等价 Java 签名

```java
// com.bytedance.mira.plugin.hook.flipped.compat.FlippedV2Impl
private static native Object getDeclaredMethod(Object obj, String name, Class[] types);
```

### 2.7 依赖（仅 6 个 import）

`__cxa_finalize`、`__cxa_atexit`、`__android_log_print`、`pthread_create`、`pthread_join`、`__stack_chk_fail`

→ **干净得不能再干净**，无任何检测能力。

## 3. `libsmsdk.so` 解剖（重点）

### 3.1 基本信息

| 项 | 值 |
|---|---|
| 大小 | 842,488 字节 |
| 架构 | ELF64 ARM aarch64，PIE + NX + canary |
| entry | `0xa040` |
| needed | `liblog.so` `libz.so` `libm.so` `libdl.so` `libc.so`（**无 libc++_shared**） |
| imports | 83 |
| symbols | 561 |
| `.init_array` | **22 个槽** |
| relocations | 671 |

### 3.2 反分析层特征（它自己的"代码特征"）

| # | 特征 | 证据 | 效果 |
|---|---|---|---|
| 1 | **全段字符串加密** | `.rodata` 零明文；`frida/xposed/magisk/zygisk/lspatch/riru/proc/self/data_adb` 全查无结果 | 静态 `strings` 完全失效 |
| 2 | **22 个 `datadiv_decode*`** | `.dynstr` 内 22 个符号，**数量恰好等于 init_array 22 槽** | 每个构造器负责解密自己那一块数据段 |
| 3 | **自定义码表解码** | `@0x61270`：`ldrb w4,[x0]` → `lsr x4,x4,#2` → `ldrb w4,[x15,x4]` → `strb [x1]`；码表基址 `adrp x15,0xbb000` + `0x36c` = `0xbb36c` | 非 base64，自研查表 + 跨字节位拼接 |
| 4 | **控制流平坦化 (CFF)** | `JNI_OnLoad` 位于 `0xa79c`，**size = 3148 字节**（正常壳只要几十字节，膨胀约 50 倍）；通篇 `mov/movk` 造幻数状态键 + `cmp/b.eq/b` 二分派发 | 逻辑被切碎，反编译得面条 |
| 5 | **符号名抹除** | 561 符号中仅 `JNI_OnLoad` 是真名，其余 `x.285` / `y.307` 之类 | 函数语义不可读 |
| 6 | **混淆幻数示例** | `0xa1e7f008`、`0xbd19169d`、`0x13c9ed4b`、`0x69fa4661`、`0x2dffe261`、`0x52a5b4ae`、`0xcff2ceb7`、`0xc1e33033`、`0xb28d5dd1` … | 状态机键值 |

**字符串加密的判定依据**：
`.dynstr` 里除了 libc 导入名和 `datadiv_decode*` 之外，**一个 ASCII 可打印串都没有**。
一个 842KB 的业务 SDK 不可能真没有字符串——只能是全加密。

### 3.3 能力清单（导入表——符号名藏不了，import 名字也藏不了）

这 83 个导入就是它的能力边界：

| 导入 | 用途 |
|---|---|
| `popen` / `pclose` | **执行 shell 命令**（getprop、读 /proc、ps） |
| `__system_property_get` / `__system_property_read` | 读系统属性：`ro.debuggable` / `ro.secure` / `ro.build.tags` |
| `opendir` / `readdir` / `closedir` | **扫目录**（`/data/local/tmp`、框架路径、`/proc/self`） |
| `stat` / `lstat` / `access` | 探路径存在性 |
| `regcomp` / `regexec` / `regfree` | **正则匹配**（maps 段名、包名、路径特征） |
| `syscall` | ⚠️ **直呼系统调用，绕过 libc 上的 hook** |
| `mprotect` / `mmap` | 代码段改写 / 自解密 |
| `socket` / `bind` | 本地端口探测（frida-server 27042 那一套） |
| `deflate` / `deflateInit2_` / `deflateBound` / `deflateEnd` | **采集结果 zlib 压缩后上报** |
| `rand` / `srand` | ⚠️ **随机化探测顺序**，让抓包难复现 |
| `ioctl` | 反调试 / 网卡/设备信息 |
| `getpid` / `sysconf` / `nanosleep` / `clock_gettime` | 进程/时序探测、sleep 反调试 |
| `open` / `read` / `pread` / `fopen` / `fgets` / `fread` | 任意文件读取（`/proc/*/maps`、`/proc/*/status`） |
| `qsort` / `strtok` / `sscanf` / `sprintf` / `vsprintf` | 字符串解析与拼装 |

**关键判断**：
- `syscall` 直调 + `rand` 乱序 + `mprotect` 自改 → 这是**专门针对 frida/xposed 侵入**设计的
- `deflate*` 说明采集结果要压缩上报（体积大，含环境信息）
- `popen` + `opendir/readdir` + `regexec` 组合 → 典型的**运行时环境扫描器**

## 4. 对上「模块被 DS 标记」这件事

### 4.1 三层特征模型

| 层 | 特征形态 | r8 / 改名管用吗 |
|---|---|---|
| ① 静态产物 | dex 里的类名、包名、字符串、方法体字节码哈希 | ✅ 管用 |
| ② 运行时内存 | 宿主进程里多出不属于宿主的 DexFile、ClassLoader 链多一层、反射出的类名 | ❌ 完全不管 |
| ③ 行为 / 痕迹 | ArtMethod entry 不在 libart 区间、maps 有可疑 so、frida 端口、线程名、hook 后方法头字节 | ❌ 完全不管 |

### 4.2 据本章测绘的结论

`libsmsdk.so` 的导入表全部指向 **②③ 层**：`popen`（跑命令看进程）、`opendir/readdir`（扫框架路径）、
`regexec`（匹配 maps 段名）、`syscall`（绕 hook 探环境）、`socket/bind`（探 frida 端口）、
`deflate`（压缩上报）。

→ **对方说的「代码 A 被标记」，在这个 SDK 里对应的真实机制大概率不是「比对字节码」，而是「在进程环境里发现不应该存在的东西」。**

→ **「走运行时混淆 + r8」只能治①，治不了②③。**

### 4.3 待验证（不要急着改代码）

1. **二分法关功能**：模块功能一块块关，看还封不封
   - 「全关还封」→ ②③ 层，模块存在本身被看见，r8 白干
   - 「关掉某块就不封」→ ① 层，r8 有用
2. **挂 frida 看判定入口**（测试号 + 沙盒机）
3. **ProxyPin 抓上报**：数美封控上报常见 `*sm*.cn` / `fp.ishumei.com`，看载荷里到底带什么字段
   - 对比「干净机 vs 装模块机」两次上报载荷 diff，差出来的就是特征

## 5. 下一步：动态 dump（静态到此为止）

静态已被 CFF + 全串加密封死，继续硬啃成本极高。正解是**加载后取明文**。

### 5.1 原理

22 个 `datadiv_decode` 由 `init_array` 在 `dlopen` 阶段执行完毕，
**执行完之后明文就已经在进程内存的数据段里了**。

所以：不等它自己的函数跑，而是在 **`dlopen` 返回的瞬间** 扫 `libsmsdk.so` 的整个映射区间，
把可读段整块 dump 出来 → 特征串（`/proc/self/maps`、`frida`、`xposed` 等）全部现形。

### 5.2 为什么这样能绕开它的防护

- 它用 `syscall` 直调是为了防 **函数级 hook**（frida 的 `Interceptor.attach`）
- 我们的取点在 **`android_dlopen_ext` 返回 / `JNI_OnLoad` 之后**，做的是 **内存 dump 而非 hook 它的函数**
- 它没加壳内自校验到「数据段被读过就崩」的程度（不然自己也用不了），所以 dump 安全

### 5.3 计划脚本（frida）

```javascript
// 骨架：等 libsmsdk.so 加载完，整段 dump，再离线 strings
const target = "libsmsdk.so";
// 1) hook android_dlopen_ext，拿到 path 含 target 的 dlopen
// 2) onLeave 里 Module.findBaseAddress(target) 拿到基址
// 3) 读 /proc/self/maps 里所有 r--/rw- 段，readByteArray 落盘
// 4) 之后离线跑：strings -el + 自定义码表反解
```

### 5.4 备选路线（若 dump 受阻）

- 直接调它的 `getDeclaredMethod` / JNI 导出做**行为观测**（但只有 `JNI_OnLoad` 一个真名导出）
- GDB/`/proc/pid/mem` 在 `init_array` 断点后 dump（需 root + 关闭 SELinux 限制）
