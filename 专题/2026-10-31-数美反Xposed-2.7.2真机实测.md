## 二、为什么全哑？—— 三条硬原因

### 2.1 LSPosed 的类不在目标的 ClassLoader 链里

```
=== app ClassLoader 链 ===
  [0] dalvik.system.PathClassLoader  -> .../com.deepseek.chat.a-.../base.apk
  [1] java.lang.BootClassLoader
（就这两层，再往上没了）
```

用**三种方式** forName 全部 `ClassNotFoundException`：

```
[XposedInit]
    a) Java.classFactory.use              → FAIL: ClassNotFoundException
    b) Class.forName(n,false,appLoader)   → FAIL: ClassNotFoundException
    c) Class.forName(n)                   → FAIL: ClassNotFoundException
[XposedHelpers]  [XposedBridge]  [IXposedHookZygoteInit]  同上
```

★ **并且用数美自己的 ClassLoader 也失败**：

```
数美类 loader = dalvik.system.PathClassLoader[DexPathList[[zip file ".../com.deepseek.chat.a-.../base.apk"...
★ 用数美 loader forName XposedInit → FAIL: ClassNotFoundException
```

⇒ **数美在它自己的能力范围内，永远看不到 `de.robv.android.xposed.*`。**
LSPosed 把 Xposed API 放在**模块专属**的 ClassLoader 里，不污染目标进程。

### 2.2 那些 Xposed 类实际住在 4 个独立的 Loader 里

```
loader = dalvik.system.InMemoryDexClassLoader[DexPathList[[dex file "InMemoryDexFile[cookie=[0, -5476376632200513184]]"]...]
loader = dalvik.system.PathClassLoader[DexPathList[[directory "."],nativeLibraryDirectories=[/system/lib64, /system_ext/lib64]]]
loader = LspModuleClassLoader[module=/data/app/~~QnPt4gu-.../com.little_femaleboy.cannot_show.the_big_won_whale-.../base.apk, o1[DexPathList[[dex file "InMemoryDexFile[cookie=...]]]]
loader = LspModuleClassLoader[module=/data/app/~~bOpbHlXl20ov22jEqpntVw==/com.flass.layoutinspect-.../base.apk, ...]
```

★ **注意**：`LspModuleClassLoader` 的 `toString()` 里**带着我们 base.apk 的完整路径**！
但那是 **ClassLoader 对象的 toString**，不是内存映射 —— 数美只有 Java 层手段，**拿不到这个对象**。

### 2.3 `/proc/self/maps` 里真的没有我们

```
=== /proc/self/maps 统计 ===
总行数              = 3716
含 /data/app/ 行数   = 62
含 little_femaleboy = 0     ★★ 关键：0
含 xposedmodule     = 0
严格算法不同包数      = 2  -> {"~~iuqUiMgzZzgqL_KspRmFPA==/com.deepseek.chat.a": 32,
                              "~~bOpbHlXl20ov22jEqpntVw==/com.flass.layoutinspect": 30}
```

① **我们的模块 apk 一次都没被 map 过**（`primaryCpuAbi=null`，没有 native lib，LSPosed 用 `InMemoryDexClassLoader`）
② 而且顺着数美的**严格算法**（`indexOf("-", i)`）跑出来的两个"包名"是 `~~hash==/com.deepseek.chat.a` 这种**垃圾串**，
　 拿去 `getApplicationInfo` 必然 `NameNotFoundException` ⇒ **它对自己也报错了**

```
[~~iuqUiMgzZzgqL_KspRmFPA==/com.deepseek.chat.a] getApplicationInfo 失败: NameNotFoundException
[~~bOpbHlXl20ov22jEqpntVw==/com.flass.layoutinspect] getApplicationInfo 失败: NameNotFoundException
[com.deepseek.chat.a] 无 xposedmodule ⇒ 放过
```

⇒ **`xpApp` 这条检测在 Android 15 上是"自伤"的**：路径加了 `~~hash==` 前缀后，
它的 `substring(i+10, j)` 切不到纯包名，**连自己的 apk 都查不到**。

## 三、ApplicationLoaders 这条路也堵死了

数美 `l11l111l11Il()` 想摸 `android.app.ApplicationLoaders.gApplicationLoaders.mLoaders`
（全局 PathClassLoader 表），是 Java 层唯一可能"枚举所有 loader"的路：

```
mLoaders.size() = 1        ← 只有宿主自己那一个
没有 LspModuleClassLoader
```

⇒ **LSPosed 的 `LspModuleClassLoader` 不注册进 `mLoaders`**，这条也瞎。

## 四、还有一个"未调用"证据

挂上 8 个无参检测方法的 hook，观察 **15 秒**：

```
15 秒内调用次数: （一次都没被调用）
```

⇒ 数美那批检测**在这一段时间里根本没被触发**。

⚠️ **但不能过度解读**：数美很可能是在 **App 启动时**跑一次检测。
我们 frida 是 App 已经跑了几分钟后才 attach 的 ⇒ 那次调用已经过去了，**看不到**。
**要验"启动时到底有没有跑"，得重启宿主后立刻 attach** —— 这是下一步待办。

## 五、⚠️ 两个必须记进本子里的技术坑

### 5.1 `timeout` 默认只有 12 秒！

```
run.sh:130  MAX_RUN_CAP=180      # 任务指定 timeout= 时的上限
run.sh:583  timeout=<可选，秒，默认 12，封顶 180>
```

我第一版探针里 `setTimeout(..., 15000)`（等 15 秒）**必然拿不到输出** ——
连续两次投出去都只有 `Unable to save SELinux policy`，`R.join()` 从来没执行到。
**凡是脚本里有 `setTimeout` / 长驻 hook，`timeout=` 必须显式写。**

### 5.2 `Unable to save SELinux policy to the kernel: Out of memory` 是**无害警告**

frida-agent 启动时会往 `/sys/fs/selinux/load` 装载给自己加 `type`/`rule` 的 policy
（证据：二进制里有 `Unable to add SELinux rule: %s` / `Unable to add SELinux type: %s` /
`Unable to save SELinux policy to the kernel: %s` / `agent.vala:411: Oops, SELinux rule probably missing`）。

**首次失败的真凶是设备内存不足**：
```
失败时: Mem 总 11098MB  used 10585MB  free 只剩 512MB   Swap used 5612MB
       ↑ 抖音 com.ss.android.ugc.aweme 一个占 1586MB
清理后: free 1384MB  → 立刻注入成功
```
但即便清完，这句警告**仍然会打印**（`probe_e`~`probe_g` 每次都出现），
**只是 agent 照样起来、Java 桥照样可用** ⇒ **看到这句话不要当成失败**。

### 5.3 frida 17 的 Java wrapper 会把 Java 对象显示成 `[object Object]`

判断"有没有数据"必须 `Java.cast(v, Java.use('java.util.Map')).size()`，
不能看 `String(v)`。

## 六、结论与建议

| 项 | 结论 |
|---|---|
| **`xpApp`（maps 扫 data/app）对我们** | ✅ **无效**（我们 apk 没被 map；且它对 Android 15 路径前缀都切错） |
| **#1/#2 模块列表** | ✅ **无效**（XposedInit 不在目标 loader） |
| **#3 hook 表 / #4 缓存** | ✅ **无效**（空 Map / 空 Set） |
| **#8 XposedHelpers.jar / 错拼名** | ✅ 一直是 `false` |
| **`ApplicationLoaders.mLoaders`** | ✅ **只有 1 条**，不含我们 |
| **要不要再做对抗（A~E 五套方案）** | ❌ **不需要** —— 现在是"环境本身干净"，不是"我们骗过去了"。做了反而可能引入新特征 |

> ★ **唯一还悬着的**：数美可能在**启动时**跑过一次检测（我们没观测到）。
> 下次宿主重启时立刻 attach 就能验。**在那之前，别急着写对抗代码。**
