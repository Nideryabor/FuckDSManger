### 1.2 第二级：为什么空？—— class loader 隔离

```
app ClassLoader 链：
  [0] PathClassLoader -> .../com.deepseek.chat.a/base.apk
  [1] BootClassLoader
（就这两层）

forName("de.robv.android.xposed.XposedInit") 三种方式全 ClassNotFoundException
  ① Java.classFactory.use
  ② Class.forName(n, false, appLoader)
  ③ Class.forName(n)
★ 用数美自己的 ClassLoader 也一样失败
```

那些 Xposed 类实际住在 **4 个独立 loader**：
```
InMemoryDexClassLoader[...]
LspModuleClassLoader[module=/data/app/~~QnPt4gu-.../com.little_femaleboy.../base.apk, ...]   ← 我们
LspModuleClassLoader[module=/data/app/~~bOpbHlXl2.../com.flass.layoutinspect-.../base.apk, ...]
```

`ApplicationLoaders.gApplicationLoaders.mLoaders.size() = 1`（只有宿主自己），
**LSPosed 的 `LspModuleClassLoader` 不注册进去。**

## 二、★ 初始化在哪、为什么没跑

`SmAntiFraud.create(Context, SmOption)` 的**唯一调用点**：

```
t3a.smali:492   invoke-static {p0, p1}, Lcom/ishumei/smantifraud/SmAntiFraud;->create(...)
```

而 `t3a` 的结构：

```
.class public final Lt3a;
.implements Lmc6;            ← Worker 接口
.field a:Lcx2;  .field b:Ln49;
.method <init>(Lcx2;Ln49;Lv5;Lbd3;)V     ← bd3 = WorkerParameters
.method static final a(Lt3a;Ljmb;Lhp8;)V ← 静态 lambda（真初始化就在这里）
.method b(Lzb3;)Ljava/lang/Object;        ← doWork(协程版)
```

> **⇒ 数美初始化是一个 WorkManager Worker 的 `doWork()`。**

`t3a.a()` 里做的事（关键常量都在这）：

```java
SmOption opt = new SmOption();
opt.setOrganization("P9usCUBauxft8eAmUXaZ");
opt.setPublicKey("MIIDLzCCAhegAwIBAgIBMDANBgkqhkiG9w0BAQUFADAy...");
opt.setAppId("default");
opt.setUsingHttps(true);
opt.setNotCollect({"ssid", "sensor", "bssid"});      ← ★ 没有 xpApp！
opt.setUrl(baseUrl + "/deviceprofile/v4");
opt.setConfUrl(baseUrl + "/v3/cloudconf");
// baseUrl 二选一：
//   https://api-device-eur.fengkongcloud.com
//   https://fp-sa-it-acc.fengkongcloud.com
SmAntiFraud.registerServerIdCallback(...);
SmAntiFraud.create(context, opt);
```

★ **注意 `setNotCollect` 只有 `ssid / sensor / bssid` —— `xpApp` 不在排除名单里。**

Worker 由 Koin DI 提供（`z50.smali:1603` `const-class Lt3a;` → `b(Lzb3;)`），
**但它从未被 WorkManager 调度执行** ⇒ `create()` 从未被调用。

> 未验证的猜测（不在本轮范围）：Worker 可能受 `Constraints`（联网/充电/空闲）或
> 远端开关控制，或根本没被 enqueue。

## 四、监控方案（万一哪天它醒了）

### 4.1 最快的判断：logcat 搜 `Smlog`

```sh
adb logcat -s Smlog        # 数美自己的 TAG（SmAntiFraud.String = "Smlog"）
```
**有输出 = 引擎起来了；没输出 = 还在睡。**

### 4.2 静态判据（不用 frida）

```sh
adb shell "grep -c libsmsdk /proc/<pid>/maps"
# 0 = 引擎没起；>0 = 起了（注意需要 root 才能读别的进程 maps）
```

### 4.3 探针（现成的）


## 六、踩坑补记（本轮新增）

| # | 坑 | 解 |
|---|---|---|
| 1 | **`timeout` 默认只有 12 秒** | 凡有 `setTimeout`/长驻 hook，**必须显式写 `timeout=N`**（封顶 180） |
| 2 | `Unable to save SELinux policy ... Out of memory` 是**无害警告** | agent 照样起来；首次真失败是设备内存不足（free 512MB → 清理后 1384MB 就好） |
| 3 | frida 17 Java wrapper 把 Java 对象显示成 `[object Object]` | 判"有没有数据"必须 `Java.cast(v, Java.use('java.util.Map')).size()` |
| 4 | **hook 失败静默 catch 会造成假阴性** | ★ 装完 hook **必须主动调一次自检**，证明真的挂上了 |
| 5 | `uiautomator dump` 看到的是**焦点窗口**，可能不是你以为的 App | 拉前台后要 `dumpsys window \| grep mCurrentFocus` 复核 |
| 6 | 冷启动要抢时间窗 | 设备端一条 shell 串起来：`force-stop; monkey; while ! pidof; do sleep 0.05; done; mv job.pending job` ⇒ 实测 **100ms** 内就位 |

> | **#1 `loadedPackagesInProcess`** | 🔴 **必中** |

> | **#3 hook 表快照** | 🔴 **必中** |

**这四条全错。** 真机实测全部为空。

错因：当时只是**静态读代码**，假设"数美能在宿主进程里 forName 到 Xposed 类" ——
但 LSPosed 的 class loader 隔离让这个前提不成立；而且**引擎根本没 init**。

> 教训：**"它能不能检测到" 和 "它有没有在跑" 是两个独立问题。**
> 只答对前一个，会得出完全错误的结论。
