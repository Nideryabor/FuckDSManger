## 零、一句话结论（先看这个）

**AI 的底被挂在「消息项」上，不是挂在「气泡」上。**
用户气泡挂的是气泡本体（`ls9.f`/`ua0.e`），AI 挂的是整条消息项（`pn9.c`）——
**层不同 ⇒ 基准尺寸不同 ⇒ 用户气泡一直是对的，AI 的一直在错。**

## 一、⭐ 定死两个语义（都是反编译宿主读出来的，不碰手机）

### 1.1 `J` = **真实绘制尺寸**（这个问题本来不用跑五次探针）

宿主 2.6.1（`DeepSeek_2.6.1.apk` / `host_2.6.1.apk`，包名 `com.deepseek.chat.a`）：

```smali
# Loq3;->r(Lmb6;Liq0;JJFFI)V   —— 画矩形的公共路径（drawRect）
iget-object p0, p0, Lxl1;->b:Lst2;      # 取 drawContext
invoke-virtual {p0}, Lst2;->x()J        # ★ 返回 packed Size
move-result-wide v3
invoke-virtual {p1, p7, v3, v4, v0}, Liq0;->a(FJLsf;)V   # brush.applyTo(alpha, size, paint)
...
invoke-interface {p1 .. p6}, Lvl1;->i(JJLsf;)V           # canvas.drawRect(topLeft, size, paint)

# Lxl1;->d(...) 同款：p0->b.x() ⇒ 同一个 J
```

⇒ **两条绘制路径都传 `drawContext.size`**，而不是"某个矩形"。
⇒ 而注入用的是 **`qk7.C` = `Modifier.background(brush, shape, alpha)`**
（旧名 `uia.u(Lc76;Lsn0;Lmd8;I)Lc76;` ↔ 新名 `qk7.C(Lx97;Liq0;Lgn9;I)Lx97;`，4 参、返回同一类型）
—— Compose 里这个 modifier 的 DrawScope **就是节点自己** ⇒ **`J` = 节点尺寸 = 真正被画的矩形**。✅

> ⇒ **fit3~fit6 那五次注入想回答的问题，反编译一遍就出来了。**（教训 372 又中一次）

### 1.2 `Lim9.a` 的缓存：按 size 单条缓存，size 变就重算

```smali
# Lim9;->a(FJLsf;)V
if (a == null || !Size.equals(b, size)) {
    if (Size.isInvalid(size)) { a = null; b = NaN; }
    else { shader = b(size); cache.b = shader; this.b = size; }   # ← b(J) 只有这里被调
}
paint.setShader(cache.b)
```

## 二、⭐ 为什么坏的总是 AI：两条路径挂在**不同的层**

| | 钩在哪 | 注入口 | 套在哪一层 | `[FIT]` 实测 |
|---|---|---|---|---|
| **用户气泡**（**好的**） | `ls9.f` → 2.6.1 `ua0.e` | `GmUBubbleHook` → `GmBubble.ubMod()` | **气泡本体** | `目标=(635,161)` ← 窄，像气泡 ✓ |
| **AI 气泡**（**坏的**） | **`pn9.c`**（消息项 Modifier 构建器） | `GmBubbleCellHook` → `GmBubble.wrap()` → `qk7.C` | **「消息项」** | `目标=(1440,25349)` ← 满宽 + 整页量级 |

**证据**（`mod-src/work/sm_*/.../GmBubbleCellHook.smali:470`，日志文案是它自己写的）：

```
[气泡] 底板已注入
已给**消息项**的 Modifier 套上气泡底（助手/用户各自配色）
```

⇒ 它是在被 hook 方法的参数里找**第一个 `c76`(Modifier) 实例**，然后 `qk7.C(modifier, 我们的brush, shape, 0)` 追加一个 background。

### 2.1 一个机制，解释掉三个老现象

| 老现象（主人原话） | 机制解释 |
|---|---|
| 「AI 图片底**跑到用户气泡下面**」 | 底画在**项/容器级**，天然在用户气泡**底下** ✓ |
| 「AI 图底**被截断** / 糊」 | 基准 = 整项（25349）⇒ `s=sCover=8.0` ⇒ 图放大 8 倍、水平居中各裁掉 5040px ⇒ 看到的是图中间一条放大 8 倍的窄缝 ✓ |
| 「下面**连像素延伸都没有**」 | 那片**根本没被这个 brush 画过** ⇒ 不是 TileMode 能补的（教训 369）✓ |

### 2.2 那 3.42.44「上面镜像了」是怎么来的（顺带结掉）

`min(sCover=8.0, zoom=2.0) = 2.0` ⇒ 图 2880×6336，居中到 25349 的项上 ⇒ 竖直偏移
`-(6336-25349)/2 = +9506` ⇒ **图落在项的中段**、可见区在它上面 ⇒ 配 MIRROR 就是"上面镜像"。
⇒ **根因是"基准尺寸"，不是 TileMode** —— 3.42.44/45 两轮方向偏了。

## 六、⭐ 真机四枪 + 静态：宿主是「一片一片」画的，而且会**抹掉我们的矩阵**

### 6.1 四枪的账（每条都是我的错，一条不藏）

| 枪 | 探针 | 结果 | 我的错 |
|---|---|---|---|
| 1 | `fit7` 钩 `android.graphics.Canvas`（基类） | [C] 对照活 / [B] 12 次返回我们的 shader / [D] 零 | **钩错面**：运行时是 `RecordingCanvas`，**override 了基类方法**，虚分派绕过 |
| 1 | `fit7` 解 `J` | 全是"正方形" | **量具坏**：JS `>>>` 只取 32 位 ⇒ 宽高解成同一个 |
| 2 | `fit8` 钩宿主 `hc.k/g/f` | [D] 零 | **读 shader 用 `paint.getShader()` 抛异常，被我 catch 吞成 `(err)`** ⇒ 静默全跳过，成了假"零命中" |
| 3 | `fit9` | [E] 自诊断抓到上一条；[B] J=(1440,6286)/(1440,1134)/(702,161) | 好：终于知道 `sf` 字段是 `a:Paint b:int c:Shader d:jn0` ⇒ 读字段别调方法 |
| 4 | `fit10` | `FAIL hc: ReferenceError: 'mname' is not defined`；且整轮 `jq0.b`/`sf.i` **一次都没被调** | **代码 bug**（IIFE 的作用域）+ 疑似**滚错了地方**（滚的可能是会话列表，不是带图底的对话） |

> **教训 375**：⭐⭐⭐ **我的探针连错四次，全是"量具"问题，不是"被测对象"问题。**
> 每次都是"零命中"，而零命中的第一嫌疑永远应该是**量具**，不是世界。
> （正对照也是——[C] 只证明"基类那条路有人走"，不证明"我要看的那条路"。）

### 6.2 静态读出来的真机制：`ob7.i` 的"分片 + 抹矩阵"

```java
// ob7.i(Lvl1 canvas, Liq0 brush, F, Lbn9, Ldia, Lnd)
J = pack(float, float);                       // 由片尺寸算出来
Shader sh = brush.b(J);                       // ← 我们的 FitHook 在这里返回 GmBmpShader
Matrix m = new Matrix();
sh.getLocalMatrix(m);                         // 读一下（丢弃）
for (每一个 sz7 片) {
    uf p = piece.a;
    p.g(canvas, new jq0(1, sh), ...);         // 用我们的 shader 画这一片
    canvas.n(x, p.b());                       // canvas 平移
    m.setTranslate(x, -p.b());
    sh.setLocalMatrix(m);                     // ★★★ 整个替换掉 shader 的矩阵
}
canvas.o();
```

**`Matrix.setTranslate` 是"整体替换"，不是叠加** ⇒

> ⭐ **我们在 `b(J)` 里算好的"铺满矩阵"（scale + 居中）根本活不过一次绘制循环** ——
> 宿主先画一片，然后就把 shader 的矩阵**换成纯平移**，下一片、以及复用同一个 shader 的其它地方，
> 拿到的都是"没有缩放的图"。

⇒ 一次性解释：
- 为什么 **FitHook 的缩放"看着没效果"**（矩阵活不下来）；
- 为什么 **图会"跑到别人底下"/出现"半张图"**（同一个 shader 实例被多片/多处复用，矩阵被反复改写）；
- 为什么 **"下半空白"**：**装的图的那一片有图，没装到的片就是空白** —— 问题在"分片"，不在 `TileMode`。

### 6.3 由此得出的修法（按推荐度）

| | 做法 | 代价/风险 |
|---|---|---|
| **B（推荐）** | 我们自己的 `GmBmpShader` **override `setLocalMatrix`**：不照单全收，而是**合成为 `M0 ∘ T`**（保住我们的缩放，同时跟随宿主的逐片平移） | 只改我们自己的类，风险可控；效果要真机看 |
| A | 同上，但**整个忽略**宿主的矩阵（no-op） | 最"铺满"，但多片场景可能"每片同一块图" |
| C | 换基准：不再按 J 铺满，改成**1:1 + 只在片内** | 等于退回主人早期不喜欢的"贴左上角" |

## 七、✅ 结案（2026-10-02 傍晚 · 主人确认"修好了"）

### 7.1 真正的答案（3.42.47 定音）

主人一句话把方向掰正：

> 「是**图片只有开头，后面也一起被截断了**」+（此前）**.44/.45/.46 三版改矩阵算法全"没区别"**

⇒ **`b(J)` 返回的那个 shader 根本不是渲染源。**
真正在采样的是 **3.42.31 那条**：我们造的 `RuntimeShader`，AGSL 直通 `img.eval(p)`，
**输入 BitmapShader 是 1:1 的**（创建时压根没给矩阵）⇒ 图从左上角 1:1 铺、超出即被切。

**3.42.47**：`sInShaderMap`（RuntimeShader → 输入 BitmapShader）+ `fitInput(brush, m)`，
在 FitHook 里把铺满矩阵**贴到输入 shader 上** ⇒ **"上下好了"** ✅（半年里第一次真正动了视觉）

### 7.2 最后一版（3.42.48）——按主人选的 C

- 缩放：`max(W/bw, H/bh)`（cover，放大 2 倍 + 左右裁）⇒ 改成 **`W/bw`（按宽度铺）**
- 竖直：**不居中，图贴顶**；上下不够的部分交给 **CLAMP 边缘色**往下延伸
- 真机结果：**"修好了"** ✅
