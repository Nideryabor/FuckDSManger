## 0. 一句话结论

**`libsmsdk.so` 在 2.6.1 → 2.7.1 完全没变（842,488 字节，逐字节一致）** ——
所以 2.6.1 那轮的 so 层结论**全部继续有效**，本轮新增的是 **Java 侧全貌 + 封控链路**。

| 层 | 组件 | 作用 |

| **人机挑战**（交互） | `com.ishumei.sdk.captcha.*` | 服务端下发挑战 → 弹 WebView 验证码 |

## 4.5 ★ `RegisterNatives` 表已定位（**本轮最大突破**）

### 4.5.1 调用点（`JNI_OnLoad` @ `0xb2c4`）

```asm
b2c0: mov  x0, x26              ; x0 = JNIEnv*
b2c4: ldr  x8, [x8, 0x6b8]      ; ★ RegisterNatives 在 JNIEnv 虚表的 0x6b8 偏移
b2c8: ldur x1, [x29, -0x68]     ; jclass（运行时 FindClass 得到，名字也加密）
b2cc: add  x2, x2, 0xec8        ; ★ methods 数组 = 0xc6000 + 0xec8 = 0xc6ec8
b2d0: blr  x8                   ; 调用
```

**`0xc6ec8` 正是 `.data.rel.ro` 段的起始**（slot vaddr `0xc6ec8` / file offset `0xc2ec8`）。

### 4.5.2 表内容（每项 24 字节 = name / sig / fnPtr）

| # | name 指针 | sig 指针 | **fnPtr** | 备注 |
|---|---|---|---|---|
| 1 | `0xc8084` | `0xc8090` | **`0xa07c`** | CFF 平坦化（幻数 `0x95d7f889`）|
| 2 | `0xc8160` | `0xc8170` | **`0xa2d8`** | |
| 3 | `0xc81ac` | `0xc8170` | **`0xa2cc`** | 与 #2 共用 sig |
| 4 | `0xc81b0` | `0xc81c0` | **`0xa2b4`** | |
| 5 | `0xc8238` | `0xc823c` | **`0xa2e4`** | |
| 6 | `0xc8240` | `0xc8244` | **`0xa448`** | |
| 7 | `0xc8248` | `0xc824c` | **`0xa73c`** | |
| 8 | `0xc8250` | `0xc8260` | **`0xa764`** | **干净真函数**（见下）|
| 9 | `0xc8278` | `0xc8280` | **`0xa5b4`** | |

第 10 项起不再是 `(name,sig,fn)` 三元组（落到 `0xd0258/0xd0230/0xd0230`
—— `.data` 段），说明**数组到第 9 项为止**。

> **9 项 ↔ Java 侧 `dfp.SMSDK` 的 9 个 native 方法完全对应**
> （`d` `ma` `ma2` `native_u2` `u3` `w1` `w3` `x4` `x6`）

### 4.5.3 name/sig 确认是加密的

`0xc8084`（file offset `0xc4084`）处的原始字节：

```
44 03 05 33 | 79 67 79 6E 61 79 62 7F 67 6F 63 65 78 6D 6B 64
63 70 6B 7E 63 65 64 6C 66 6B 6D 0A 87 8B 9E 89 82 EA
```

**不是 ASCII**（`0x79`=y、`0x67`=g 看着像字母，但 `0x7F`/`0x0A`/`0x87` 混在里面）
⇒ 自定义码表解码的结果，**必须在 `datadiv_decode*` 跑完之后才有效**。

### 4.5.4 `fnPtr 0xa764` 反汇编 —— 证明不是跳板，是真函数

```asm
a764: stp  x20, x19, [sp, -0x20]!
a768: stp  x29, x30, [sp, 0x10]
a76c: add  x29, sp, 0x10
a770: mov  x1, x2              ; 参数平移
a774: bl   0xa62b0             ; ① 真实现
a778: mov  x19, x0
a77c: bl   0xb1434             ; ② 真实现
a780: mov  x20, x0
a784: mov  x0, x19
a788: bl   0xa66ac             ; ③ 收尾
a78c: ldp  x29, x30, [sp, 0x10]
a790: mov  x0, x20
a794: ldp  x20, x19, [sp], 0x20
a798: ret
```

⇒ 3 次真实调用 + 返回，**这是 `x6(String,String)String` 之类的一层薄封装**。
（相比之下 `0xa07c` 是 CFF 平坦化的重函数 —— 两类实现风格并存。）

## 6. 宿主侧封控链路（**本轮新增，最有价值**）

### 6.1 服务端下发的挑战模型

| 类 | 字段 | 来源 |
|---|---|---|
| `ChallengeResponse.ShumeiVerification` | `rid`, `region` | 聊天/通用接口返回的 `ChallengeResponse` |
| `auth.model.users.ShumeiVerification` | `rid`, `region` | **登录/注册链路**的验证 |

序列化器：`Laq1;`（通用）/ `Lpy9;`（登录侧）—— 都只有 `rid` / `region` 两个字段。

⇒ **`rid` = 数美请求 id**，服务端判定风险时下发，客户端拿它去过验证码。

### 6.2 为什么 `SmAntiFraud` 在 DeepSeek 侧没有调用点

`dex_xref(SmAntiFraud)` 只有 **4 处，全是自己类内部**（`const-class`）：

```
SmAntiFraud.create            ← const-class
SmAntiFraud.getDeviceId       ← const-class
SmAntiFraud.registerServerIdCallback ← const-class
dfp.SMSDK.<clinit>            ← const-class
```

⇒ DeepSeek **不直接用 `SmAntiFraud`**，走的是数美内部封装（`l111l11I1IIIl` /
`l1l1l11Il` / `l11l1111lI1l` 这些 `l111l…` 风格类）。
`getDeviceId()` 内部就是转发到 `l111l11I1IIIl->l111l1111l1Il / l111l11111Il`。

### 6.3 关键结论：它怎么"标记"你的模块

> **不是看字节码像不像，是「主动扫描宿主进程环境」+「压缩上报」+「服务端打分」。**

| 它扫什么 | 用的能力 | 我们的处境 |
|---|---|---|
| 进程里有哪些 so | `opendir(/proc/self/maps)` + `regexec` | 模块自己的 so / frida-agent 会被看到 |
| 有没有 frida-server | `socket` 探 27042 + 扫 `/data/local/tmp` | 直连 frida 会被抓 |
| 是不是 debuggable / 可调 | `__system_property_get` + `ioctl` | — |
| 类加载器里有什么 | 走 Java 侧反射 | **模块的类名/包名可能被枚举到** |
| 目录里有没有可疑文件 | `opendir` + `stat` | 落地文件要小心 |

⇒ **R8 改名 / 改类名对它基本无效**（它看的是运行时环境，不是你的代码长什么样）。
这也解释了为什么「模块代码被 DS 标记」—— 是 **smid 变了/环境异常** 导致服务端判风险，不是静态特征匹配。

### 6.4 可对抗面（据导入表推导，未实测）

| 面 | 思路 | 风险 |
|---|---|---|
| `syscall` 直调 | 没法只 hook libc；得 hook `svc` 指令或内核态 | 难度高 |
| `rand/srand` 乱序 | 顺序不定 ⇒ 抓包难复现，但也意味着**单次抓不到全量** | — |
| `SmOption.disableCollection` | **官方提供**的采集开关（`getDisableCollection():J` 位掩码） | 改了可能被识别为异常 |
| `addSubCollectors` | 官方扩展点 | 无害但是"接入方"而非"对抗" |
| `data 上报` | 压缩后 **走宿主自己的 https**（`getUrl`）⇒ 抓包能看（已解 AES/ECB，见 2.6.2 轮） | 响应 `shumei` 判定拿不到明文 |

### 8.1 动态 dump 的具体做法（下一步的入口）

```
1. 真机上让 smsdk 正常 load（打开宿主即可）
2. frida 等模块加载后：
     Module.findBaseAddress("libsmsdk.so")  → base
     读 [base + 0xc8084] 开始的方法名区（9 项 × 各自的 name/sig 指针）
   ⇒ 此时 datadiv_decode 已跑完，读到的是**明文**
3. 或者更省事：hook RegisterNatives 的第三个参数，直接在回调里
   dump 整个 JNINativeMethod 数组（name/sig/fnPtr 全明文）
```

> 注：`syscall` 直调 + `rand` 乱序会让 frida 检测有概率命中；
> 建议先确认 frida 是「不落地」形态（内存加载 / 改名），再上。
