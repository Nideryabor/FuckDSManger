## 二、Bug A（真凶）—— 分发链断了一环

### 2.1 错误代码（2.3.3 ~ 2.3.9）

```smali
:cond_79
const/16 v1, 0x10
if-ne v0, v1, :cond_be          # ❌ action != 0x10 → 直接跳到【方法末尾的 return】
invoke-static {}, GmDsDialog;->clear()V
return-void

const/16 v1, 0x11               # ← 这一块【没有标签】，没有任何分支能跳进来！
if-ne v0, v1, :cond_a6
:try_start_85
invoke-static {}, GmPromptDialog;->open()V
```

### 2.2 为什么能一眼看出是错的：分发链的「接龙」规律

`onClick` 用的是「**不等就跳下一个块**」的链式结构，每块的跳转目标 = **下一块的标签**：

| 当前块 | 不等时的跳转目标 | 下一块 | 对吗 |
|---|---|---|---|
| `0xe` | `:cond_71` | `0xf` | ✅ |
| `0xf` | `:cond_79` | `0x10` | ✅ |
| **`0x10`** | **`:cond_be`** | **`0x11`** | ❌ **应该跳 0x11 块** |
| `0x11` | `:cond_a6` | `0x12` | ✅ |
| `0x12` | `:cond_ae` | `0x13` | ✅ |
| `0x13` | `:cond_b6` | `0x14` | ✅ |
| `0x14` | `:cond_be` | 末尾 `return` | ✅ |

`:cond_be` 是**方法末尾的 `return-void`**（`0x14` 分支跳它是对的）。
`0x10` 那句跳到 `:cond_be`，**等于把 action≥0x11 的全部请求原地丢弃**。

### 2.3 完整症状解释（全部对得上）

| 现象 | 解释 |
|---|---|
| 点击无反应、无窗口 | `onClick` 在 `0x10` 那行就 `return` 了 |
| **LSPosed 无任何报错** | 没抛异常、没调 `open()`，真的「什么都没干」 |
| 2.3.4 / 2.3.5 在 0x11 分支塞 toast 永远不响 | 该块是**死代码**，永远执行不到（当时误判为「点击没传到」） |
| 2.3.6 在 `onClick` **最顶端**打 `action=17` 能响 | 顶端代码在死代码**之前**，所以能打出来 → **制造了「链路是通的」的假象** |
| 2.3.8 `[gm] shown=N` 探针不响 | 在 `open()` 内部，而 `open()` 根本没被调用 |

### 2.4 修复

```smali
:cond_79
const/16 v1, 0x10
if-ne v0, v1, :cond_11          # ✅ 指向 0x11 块
invoke-static {}, GmDsDialog;->clear()V
return-void

:cond_11                        # ✅ 新增标签，补齐断掉的一环
const/16 v1, 0x11
if-ne v0, v1, :cond_a6
:try_start_85
invoke-static {}, GmPromptDialog;->open()V
```

修复后链路：`0x10 → :cond_11 → :cond_a6 → :cond_ae → :cond_b6 → :cond_be` 环环相扣 ✅

## 八、教训（新增）

| # | 教训 |
|---|---|
| 10 | **手写 smali 的链式 `if-ne` 分发，每一块的跳转目标必须是「下一块的标签」**。若某块忘了打标签，前一块的跳转就会落到别处，整块代码变成**无入口死代码**——而且**不报错、不崩溃、静默失效**。 |
| 11 | **"顶端的日志能打出来" ≠ "分支执行到了"**。探针务必放在「想验证的那条路径内部」，而不是它之前的公共入口。 |
| 12 | **横向对比同类正常实现**是最快的定位手段（`GmBeautyDialog` / `GmDbDialog` 一比就现形）。 |
| 13 | 排查「静默失效」时，先怀疑**控制流**（跳转目标 / 死代码 / 反向前置判断），再怀疑异常。 |

## 九、附：`prompt_feature` 逆向结论（沿用，未变）

| 项 | 值 |
|---|---|
| 位置 | `model_configs` JSON 里每个模型对象的字段 |
| 有无独立 key | **没有**（全 APK 只出现 1 次，在 `Llx5` 序列化器里） |
| 元素类型 | `com.deepseek.chat.settings.ModelConfig.PromptTemplate` |
| 元素字段 | `id`(Int) / `scene`(String) / `content`(String) —— **三个都必填** |
| scene 取值 | `image` / `file` |
| 本地覆盖层 | **不存在** `kv_settings_*`，只能改写 `kv_remote_settings_model_configs_v1` |
| 服务端下发 key | `model_configs`，但 App 读的是 `model_configs_v1`（带 `_v1`） |

内置默认模板（`GmPrompt.DEF`）：

```json
[{"id":9,"scene":"image","content":"这是什么"},
 {"id":10,"scene":"image","content":"分析一下"},
 {"id":11,"scene":"image","content":"怎么办"},
 {"id":13,"scene":"file","content":"分析一下"},
 {"id":14,"scene":"file","content":"答案是什么"},
 {"id":15,"scene":"file","content":"总结"}]
```

`GmPrompt.patch()`：把 src 里所有 `"prompt_feature":[` … 首个 `]` 替换成用户 JSON。
> 局限：`content` 里别出现 `]`；会同时改写所有模型（default / expert / vision）。

## 十、2.10.52 / 2.10.67 的两处连带影响（2026-09-19）

### 10.1 2.10.52：编辑器终于能读到/写到宿主那份配置

**旧问题**：`apply()` 依赖一个"宿主配置快照"（模块侧 `MK` 键），而**那份快照从未被填充**（模块从没读过宿主 MMKV）⇒ `ok(src)` 恒假 ⇒ 保存报「未找到模型配置」。

**修法**：新增 `GmPrompt.host()` / `hostPut(String)`，走 **`MMKV.l()` → `nativeHandle` → `decodeString`/`encodeString`（native 本体）** ⇒ 既读到宿主真值，也把编辑结果**直写宿主**；且**绕开挂在包装 `k`/`q` 上的自家 hook**。

### 10.2 2.10.67：`prompt_feature` 不再被服务器下发覆盖

**关键事实**：`prompt_feature` 与 `switchable` **同在** `kv_remote_settings_model_configs_v1` 的 JSON 内部。

**2.10.67 在下发应用点（`p66.h`）把整项 `model_configs` 摘掉**（用同型副本替换参数）⇒
- 服务器**无法覆盖** `switchable`（模型切换 ✓）
- 服务器**同样无法覆盖** `prompt_feature`（**文件快捷选项 ✓**）

**⇒ 结论**：编辑保存后的内容会一直保留（生效需重启宿主，因宿主是"读一次就缓存"）。

> ⚠️ 已知副作用：服务器若**新增/调整模型列表**，本机不再跟随（可关掉「模型切换」开关恢复）。


### 10.3 2.10.68：`patch()` 从"精确字符串"改为"JSON 结构化"

**旧实现（坏）**：

```java
NEEDLE = "\"prompt_feature\":[";      // 无空格 ⇒ 实际 JSON 有空格就匹配不上
找 NEEDLE → 再找【第一个 ']'】收尾     // 数组含 ']' 还会截错
```

**⇒ 匹配不上就原样返回；而 `apply()` 即使没改动也会 `hostPut` 写回** ⇒ 界面「已保存」但内容没变。

**新实现（好）**：

```java
JSONArray arr = new JSONArray(src);
JSONArray ours = new JSONArray(ourJson);
for (每个元素) if (o.has("prompt_feature")) { o.put("prompt_feature", ours); changed = true; }
return changed ? arr.toString() : src;      // 异常也返回原串
```

⇒ **只要字段在就一定能改**（空格/换行/转义/嵌套都不怕）。

**真凶**：`GmSync.reapplyAll()`（每次 onResume / 下发都跑）里**确实调了** `GmPrompt.reapply`，
但它是**老线废码**：

```java
String v2 = read2(c, MK, "s");     // 读【模块快照】
String v3 = patch(v2, v0);
GmStore.write(c, MK, v3, "s");     // 写回【模块快照】← 宿主完全没被碰
```

⇒ **"持续保住"这一环一直是空的**（与 `GmModel` 当初同病）。

**新实现**：

```java
String user = get(c);              // 用户编辑的
String src  = host();              // 宿主真值
String out  = patch(src, user);    // JSON 结构化改写
if (out.equals(src)) return false;
return hostPut(out);               // ★ 直写宿主
```

**⇒ 每次进 App / 下发后都会把编辑内容重新写回宿主**，不再被打回服务器版本。

## 十五、2.10.72：hook 参数不要写死下标（扫描 + 类型判断）

**崩溃**：

```
IllegalArgumentException: method yb5.e argument 1 has type eb6, got java.util.ArrayList
	at nb5.c(r8-map-id-…:1595)
```

⇒ `yb5.e` 的第 1 参是 `eb6`，**List 在别的槽位**；而 71 版假设 List 在 `args[0]` ⇒ 塞错 ⇒ 崩。

**修法（两处 hook 统一）**：

```java
Object[] args = param.args;
for (int i = 0; i < args.length; i++) {
    if (!(args[i] instanceof List)) continue;     // 只处理真 List
    List<?> out = buildMut((List<?>) args[i]);
    if (out == null) break;
    args[i] = out;                                 // 替换到它实际所在的槽位
    logOnce("suggest.on", "[建议] 列表已接管（buildMut）");
    break;
}
```

**⇒ 位置无关 + 类型安全 + 更抗混淆。**

### 项目级规则（第 3 次类型不匹配后确立）

> **任何回写 `param.args` 的地方，都必须先 `instanceof` 判类型，绝不写死下标。**
> （案例：`p66.h` 要 `bx4`；`yb5.e` 第 1 参要 `eb6`；`yb5.f` 用 `args[0]`）

### 教训

| # | 教训 |
|---|---|
| 354 | ⭐⭐⭐ **hook 参数不要写死下标** ⇒ 扫描 + instanceof |
| 355 | ⭐⭐⭐ **"类型不匹配"已出现三次** ⇒ 回写 args 前必须判类型 |
| 356 | ⭐⭐ **崩溃信息很精确**（`argument 1 has type eb6` 直接给出改动点） |
