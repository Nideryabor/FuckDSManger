# 液态玻璃 · 「底图从哪来」方案研究

> 主人 2026-09-30：「要不不用 PixelCopy 了，你看看有没有别的方案，**先别急着做**」
> 研究者：尼得亚伯 🐲 · 依据：`chrisbanes/haze` + `skydoves/Cloudy` 的真源码 + 我们的真机日志

---

## 一、PixelCopy 到底烂在哪（逐条有据）

| 毛病 | 证据 |
|---|---|
| **后台就失效** | 真机日志：`Window doesn't have a backing surface!` —— 窗口没 surface 时必然失败 |
| **有延迟** | 它是**异步**的，拿到的是"上一帧"；快速滚动时玻璃会拖尾 |
| **连文字一起截进来** | 它是"整屏截图" ⇒ 才有了「擦内容」那个补丁 |
| **正反馈** | 会把自己画的玻璃也截进去 |
| ⚠️ **可能炸渲染线程** | Cloudy 的源码里专门写了这条（他们的 issue #112）：<br>`captureToImage / PixelCopy forces a full-tree prepareTreeImpl re-walk that has NO cycle guard and overflows the RenderThread stack` |

**第五条的原文（`BackdropClearBlurrer.kt`）**，值得完整读一遍：

> The obvious backdrop blur records `drawLayer(sky.backgroundLayer)` into a blur GraphicsLayer…
> But the backdrop node is a DESCENDANT of the sky recorder ⇒ **cyclic RenderNode graph**.
> On-screen HWUI walks it damage-scoped and survives, but a **`captureToImage` / PixelCopy forces a
> full-tree `prepareTreeImpl` re-walk that has NO cycle guard and overflows the RenderThread stack**.

⇒ **一句话：PixelCopy 会强迫整棵树重走一遍，而且没有环检测。** 我们只是碰巧还没撞上。

## 二、库们用的是另一条路：`GraphicsLayer.record {}`

**Haze 和 Cloudy 都是这个**（Cloudy 的 `CloudyBackground.android.kt`）：

```kotlin
override fun ContentDrawScope.draw() {
    val layer = context.createGraphicsLayer()
    sky.capturing {                 // ← 录制期间把"会反向采样我"的覆盖层标记为缺席
        layer.record { this@draw.drawContent() }   // ← 把内容录进图层（Compose 原生）
    }
    sky.backgroundLayer = layer
    drawContent()
}
```

**好处（全是 PixelCopy 的痛点）**：
- **同步**、**在绘制里 inline** ⇒ 零延迟（Cloudy 注释：`zero version lag`）
- 不依赖窗口 surface ⇒ 后台也能用
- 不强迫整树重走 ⇒ 没有那个爆栈风险
- 录的是"内容"不是"屏幕" ⇒ 不含玻璃自己

**再加一条 Cloudy 的实战教训**：
跨节点互相采样会形成**环**（A 采 B、B 又采 A）⇒ 录制期间必须用 `capturing` 标记把自己的覆盖层排除，
否则又是那个 RenderNode 环。

## 三、为什么这套我们用不了（诚实说）

| 门槛 | 说明 |
|---|---|
| `GraphicsLayer` / `GraphicsContext` | 在宿主里**全是混淆名**，只能结构定位 |
| **`toImageBitmap()` 是 `suspend` 函数** | 要协程续体才能驱动 —— **从反射式 Java 里几乎做不到** |
| `layer.record {}` 要一个 `DrawScope` 块 | 我们是**别人家**的 composition，没有自己的 `drawContent()` 可录 |

⇒ **照抄库的做法，在我们这个"寄生"场景里不成立。**

## 四、那还有什么？（按可行性排）

### 🥇 A. 「**底色做玻璃**」——**完全不要截图**

**核心想法**：我们本来就 hook 了**每一个元素的背景节点**（`uia.v` 造的那些）。
那个背景的**颜色 / 形状 / 透明度**我们是**已知的** —— 那为什么还要去截屏幕？

```
玻璃 = 元素自己的底色（或它派生出的柔和渐变）
        + 模糊（对纯色无意义 ⇒ 可以省）
        + 折射（边缘把"底色"掰弯）
        + 高光/色散
```

**优点**：
- ✅ **零截图** ⇒ 后台可用、无延迟、无正反馈、**不可能有文字叠影**
- ✅ 不碰任何 Compose 内部（我们已经在那个 hook 里了）
- ✅ 性能最好（一个 shader pass，不碰 Bitmap）
- ✅ API 33 以下也能退化成"底色 + 高光"

**代价**：
- ❌ 失去"透出背后的**内容**"那种真实感 —— 玻璃看到的只是**底色**，不是背后的照片/文字
- ⚠️ 但注意：宿主界面大片是**纯色** —— 在纯色上，A 和 PixelCopy **本来就长得一样**（这正是"改了看不出区别"的根因）

### 🥈 B. mortd 架构：**一次全屏 pass**

`mortd/GlassBox.kt` 的做法：**一个全屏 shader，把最多 10 个玻璃元素当参数传进去**（数组 uniform）。

```
根节点 draw
  └─ 给 root 的 RenderNode 设 renderEffect = chain(模糊, RuntimeShader(全屏玻璃))
        shader 内部：对每个玻璃矩形做折射/高光，其它像素原样透出
```

**优点**：一次 pass、**不需要截图**、天然解决"抓取作用域"。
**难点**：得拿到"根节点内容"当 shader 的 `content` —— **又是同一个死结**（我们不在自己的 composition 里）。

### 🥉 C. `Picture` + 同步栅格化

`android.graphics.Picture` 是**公开 API、名字永不变**，`picture.beginRecording()` → 画 → `endRecording()`，同步栅格化。

**难点**：还是"把宿主的绘制录进 Picture"这一步 —— 除非钩到 `AndroidComposeView` 的 `dispatchDraw` 去**替换 canvas**（侵入性大、风险高）。

### D. `ImageReader` + Surface（替代 PixelCopy 的"温和版"）

避开 `Window doesn't have a backing surface`：自己造一个 `ImageReader` 的 Surface，
把内容画上去再读回来。**但**：仍然要 `decor.draw()`（我们实测会**卡死**），且仍然是异步 + 正反馈。

## 五、我的建议

**先做 A，把 PixelCopy 降级成"可选的高保真模式"。**

理由：

1. **宿主界面大片是纯色** ⇒ A 和截图**在当前场景下观感几乎一致**（这就是"换了没区别"的真相）
2. A **一次性消灭**后台失效 / 延迟 / 叠影 / 正反馈 / 爆栈风险 **五个问题**
3. A 的实现在**我们已有的那个 hook 里**，不需要任何新的宿主 API
4. 真要"透出内容"的真实感，**那要等 B（全屏 pass）那个死结解开** ——
   而解开它需要"能录自己的 composition"，对寄生式模块来说代价很高

**具体到实现（等主人点头再动）**：
- 在 `uia.v` 的 hook 里**顺便把背景颜色读出来**（元素对象的字段，我们已经能拿到类）；
- 玻璃内容 = 该颜色 + 一点柔和渐变；
- 保留折射 / 色散 / 高光 / 浓度 / 颜色自定义；
- 新增一个「底图来源」开关：`底色` / `屏幕截图`（默认底色）。

## 六、还没排除的可能（留给下一轮）

- `RenderNode` + **硬件 RecordingCanvas** 重画视图树（我们只试过**软件** canvas，卡死可能是软件渲染导致）
- `AndroidComposeView` 的 `dispatchDraw` 钩子 + canvas 替换（风险高，但能拿到"真·页面内容"）
- 等 Compose 版本更新后，`GraphicsLayer` 的非 suspend 快照 API
