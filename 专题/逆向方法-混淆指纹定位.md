# 逆向方法 · R8 混淆下的「指纹定位法」

> **为什么有这篇**：宿主 2.5.2 把 **androidx 库类和业务类一起全量改名**
> （`dex_names` 里搜 `androidx/navigation` = **0 命中**），按类名找东西这条路基本废了。
> 但每次混淆都**还留着「幸存物」**。本方法就是从幸存物反推被混淆的角色。
> 本文是「界面导航管理器」线索的产物，**可复用于任何宿主 / 任何第三方库**。
> 建立：2026-09-24 🐲

---

## 一、核心命题

**R8 改「名」，但不改「形」。**

| 幸存物 | 说明 | 为什么活下来 |
|---|---|---|
| **字符串常量** | 错误文案、源码文件名、协议 key、资源 key | R8 无法证明它死（要参与运行时查找/日志） |
| **方法签名形状** | 形参类型组合 `(String,Object,Annotation[])V` | 类型系统的一部分，改名不改形 |
| **类合并后的合成桶** | `a:I` 字段 + `implements Function0` + `packed-switch` | R8 把几十个 lambda 塞进同一个类 |
| **调用链拓扑** | 谁调谁 | 改名动不了图结构 |

⇒ 结论：**用「形」定位，别用「名」定位。**

---

## 二、指纹分级（选指纹的优先级）

| 级 | 指纹类型 | 实例 | 稳定性 |
|---|---|---|---|
| **S** | 库/框架的**错误文案 + 源文件名行号** | `"androidx.navigation.compose.NavHost (NavHost.kt:490)"` | ★★★ 极稳，跨版本跨 App |
| **S** | 业务方的**协议/路由/键名字符串** | `"com.deepseek.chat.ui.pages.ChatRoute"` | ★★★ 稳定契约，他们不敢改 |
| **A** | **唯一形参组合的方法签名** | `Lia3;-><init>(Ljava/lang/String;Ljava/lang/Object;[Ljava/lang/annotation/Annotation;)V` | ★★☆ |
| **B** | **合成桶结构**（字段 `a:I` + switch） | `Lx98;` / `Lh;` / `Lk5;` / `Lx95;` | ★★☆ |
| **C** | **调用链反查**（从 S 级点顺链） | 由 `Lld6;->f` 反查 `Lbn7;` | ★☆☆ 兜底 |

> 实操：**先搜 S 级，一击命中 → 再用轮廓/反查补全周边角色。**

## 三、四步流程

```
1. 定靶   我要哪个"角色"（不是哪个类名）
          例：谁负责把路由对象转成字符串？

2. 选指纹 优先 S 级：这个角色有没有"必然会打印/保存"的字符串？
          例：报错文案 → "Destination with route " / "cannot be found in navigation graph "

3. 一击   一条 search 命中宿主类
          mt_apk_search target=dex_strings query=<文案> matchMode=contains

4. 顺链   命中点的 outline → 看形参/字段类型 → 反查它们的角色
          mt_apk_dex_outline_class → 用返回的 locator 链式下钻
```

**关键心法**：角色是「职责」，不是「名字」。
一篇锚点表里写的永远是 `角色 → 混淆名 → 旗舰指纹 → 重定位路径`，**混淆名列每版都会变，指纹列不会。**

## 四、R8 会「吃掉」什么（反直觉清单）★

这几条是这次真踩到的，以后**照抄别人模块前必须先验**：

1. **未被调用的 public 重载会被剪掉。**
   2.5.2 的 `NavController` 只剩 **23 个方法**，`navigate` 只剩一个 `navigate(route: Any, extras)`。
   ⇒ 别的版本/别的模块能用的 `navigate(String)`，在我们宿主上**根本不存在**。
   ⇒ **教训：抄功能可以先抄思路，但 API 存活必须先查。**

2. **androidx 库类名也会被改。**
   `androidx.navigation` 整包在 `dex_names` 里 **0 命中**（只有 `androidx/appcompat` 靠 keep 规则活着）。
   ⇒ 别指望用 `Class.forName("androidx.navigation.NavController")`。

3. **Kotlin 的「源文件名:行号」字符串会留。**
   Compose 的 source information（`"Xxx (Foo.kt:123)"`）是**最强的库指纹**，
   足以把 Compose 库函数一个个点出来。

4. **反射用的字符串一定留。**
   如 kotlinx.serialization 的 `serialName`（要参与运行时查找）。
   ⇒ **FQ 原名虽然类没了，字符串还在** —— 这是"能拿来用"的前提。

5. **合成 lambda 会被合并到同一个类。**
   `Lx98;` 一个类里塞了 29 个 case（Settings 路由 + 无关 lambda 混在一起）。
   ⇒ 读轮廓时**别看类，要看方法里的字符串/调用**，否则会把无关代码当成同一功能。

## 六、版本升级重定位 checklist（约 5 分钟）

宿主换版本后，按顺序跑一遍，把新混淆名填回锚点表：

```
# ① 确定库还在（S 级指纹）
mt_apk_search target=dex_strings queryType=literal query="androidx.navigation.compose.NavHost" ...

# ② 定位 NavController（S 级指纹）
mt_apk_search target=dex_strings query="android-support-nav:controller:deepLinkIntent"
→ 取命中类 → mt_apk_dex_outline_class limit=300
→ 核对是否仍有 getGraph / setGraph 报错串 / 回退栈字段

# ③ 看 navigate 重载还剩几个（决定能不能用字符串跳）
→ 轮廓里数一下收 Object/String 的 navigate，以及 $default 桥

# ④ 定位 route id / route 串生成（同一个静态工具桶）
mt_apk_search target=dex_strings query="Cannot locate NavType for argument ["
→ 同桶内找 serialName.hashCode() 与 generateRouteWithArgs

# ⑤ 穷举路由（换包名前缀即可复用）
mt_apk_search target=dex_strings queryType=regex
             query="com\.deepseek\.chat\..*Route" matchMode=exact
→ 命中类 = 路由承载类；比对是否有新增/删除

# ⑥ 核对 nested graph（无 Route 后缀的那两条）
```
