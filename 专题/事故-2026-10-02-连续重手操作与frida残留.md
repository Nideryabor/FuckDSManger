## 二、⭐ 真正的技术错误：`timeout` 硬杀 frida

**项目文档里早就写过这条**（`专题/2026-10-01-frida攻坚与适配新宿主-总复盘.md` 教训 337）：

> **「停」不是停一个进程，是停一整条链。** `-k` 只杀 `run.sh`，
> `timeout` 和 `frida-inject` 会活着。

**而我自己这么干了**：`timeout 34 frida -H ... -p <pid> -l x.js` ⇒
timeout 到点 **SIGTERM 掉 frida CLI** ⇒ **注进宿主的 agent 不会被卸载**，
它还在目标进程里挂着 hook。

连着跑 5 次 = **5 层 agent 叠在宿主上**。
⇒ 宿主变重、行为异常、连带把系统拖卡。

> **✅ 正确姿势（下次必须遵守）**：
> 1. **优先用网关 `frida-inject`**（`run.sh`），它是"跑完就退"的一次性注入器，
>    且**网关自己会清理**（`frida.sh -k` 会连子孙一起收）。
> 2. 如果一定要用 frida CLI attach：
>    - **不要让脚本长驻**：脚本里做完事就 `Java.perform` 结束后**主动退出**
>      （或 `setImmediate(() => Process.detach())` / 让 frida CLI 自己结束）；
>    - **绝不用 `timeout` 硬杀** —— 宁可手动 `Ctrl-C`（它会走正常 detach）；
>    - **一次只注一个**，注完确认没有残留再做下一个。
> 3. 收尾检查：`ps -A | grep -a -E "frida|inject"`（`[idle_inject/N]` 是内核线程，不是残留）。

## 三、⭐ 还有一个更严重的"方法论"错误

我把「**hook 挂上了但零调用**」当成了**事实**，并据此开始推断
（"FitHook 从未生效 ⇒ 图底用的是未缩放的 RuntimeShader"）。

**但这个观察根本不可信**，因为：

| 干扰源 | 后果 |
|---|---|
| 多个半死的 agent 叠加 | 后面几次的 "✓ 挂上" 可能只是假象 |
| `timeout` 杀掉 CLI 时 **stdout 块缓冲**可能丢 | 有输出也可能没写进文件 |
| 每次注入都换了一个"已经不太正常"的进程 | 观测对象状态已经漂了 |

⇒ **"零调用"不能作为结论。** 基于它做的整条推断链（包括"FitHook 没生效"）**全部作废**。

> **教训**：**在"工具可能不生效"的阶段，任何"负结果"都不能当证据。**
> 必须先做**一个干净的、正对照**（比如 hook 一个每次必被调的方法，
> 且确认它在**单次、干净的注入**下能打印），才可以开始解释"为什么没调到"。
