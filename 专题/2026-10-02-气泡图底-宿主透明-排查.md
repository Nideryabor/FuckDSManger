## ⭐⭐ 换人后的头号嫌疑：PaintHook 主逻辑的 "D 分支"（`inScope()` 方向反了）

## 一、头号嫌疑：GmAlphaHook（`eh0` = 宿主 BackgroundElement）

### 1.1 现役代码（`tmp/base130_261/sm/.../gm/GmAlphaHook.smali`）

```smali
.method private static apply(...)
    sget v2, sDepth
    if-lez v2, :cond_18      # sDepth <= 0 → 跳过
    obj = thisObject
    if-eqz obj, :cond_18
    setFloatField(obj, "c", alphaF())   # ★ 无条件写！没有"是不是我们的元素"判断
```

- 挂在：`eh0.<init>`（after）+ `eh0.c(...)`（before）——**每个 BackgroundElement 的创建/更新都会经过**。
- `alphaF() = sAlpha / 100f`，`sAlpha` = `fuckds_bubble_alpha`（gm 侧默认 **100**）。

### 1.2 历史脉络（为什么现在才有感）

| 版本 | 判据 | 效果 |
|---|---|---|
| 2.22.29（原始） | `b instanceof GmBmpShader ⇒ 写` | 只对我们图片底写；且当时 `if-gtz` 是死的（2.22.40 才修活） |
| 2.6.1 适配期（≈10/1） | **判据被删宽成 `sDepth>0` 就写** | **误伤面全开：窗口内所有背景元素** |
| 2.22.44 记录原文 | "删掉 `instance-of GmBmpShader ⇒ :end` 的跳过 ⇒ 图片透明度对图片底生效" | **开误伤面的那一步** |

> 注：2.6.1 里图片底的 brush 变成了我们自造的 `jq0(RuntimeShader)`，
> 原来 `b instanceof GmBmpShader` 在新宿主上**恒假**（所以当时"删掉"看似合理）——
> 但正确修法应该是**换一把新锁**（见 §四修复），而不是把门全拆了。

### 1.3 量纲问题（UI ↔ gm 不一致，会放大症状）

| 侧 | 值域 | 默认 |
|---|---|---|
| UI（Tree.kt） | 滑块 **0–255** | **255** |
| gm（GmBubble） | `setAlpha` 夹紧 10–100；`alphaF()=值/100f` | 100 |

⇒ 滑块 <100 ⇒ 实际 alpha<1 ⇒ 半透明；滑块 255 ⇒ alphaF=2.55（一般饱和，无视觉）。
**⇒ 只要主人为图片底调过"透明度"（尤其 <100），立刻全消息项半透明。**

## 二、意外发现：3.42.47 的 `fitInput` 是**死代码**（从未生效）

```smali
# GmBubbleFitHook（3.42.48 现役）：
invoke-static {p1, v0}, GmBubble->fitInput(Ljava/lang/Object;Landroid/graphics/Matrix;)V
#                ↑ p1 是 MethodHookParam！
```

而 `fitInput(Object brush, Matrix)` 内部是 `getObjectField(brush, "d")`——
**对 MethodHookParam 读 "d" 字段 ⇒ NoSuchFieldError ⇒ 被 catchall 吞** ⇒ **每次必抛、永不生效**。

**⇒ 3.42.47「上下好了」的真实功臣 = `GmBmpShader.baseMatrix(v0)`**（设 m0 后宿主逐片 `setLocalMatrix` 被合成为 M0∘T）。
**⇒ 3.42.47/48 文档里「输入 shader 才是真身、b(J) 返回值是陪跑」的定论【错】**——不要再照着它改。
（反推依据：3.42.48 改的 scale/贴顶在视觉上立刻生效 ⇒ 改的正是渲染链上的东西 ⇒ 渲染用 GmBmpShader。）

**修复草案**（待主人决定，不急）：
把调用改成传 **thisObject（brush）**：
```smali
iget-object vX, p1, ...->thisObject
invoke-static {vX, v0}, GmBubble->fitInput(...)
```
（需要在 FitHook 里找一个空闲寄存器；`.registers 16` 里 v14/v15 已被 p0/p1 占用，v3/v4 在调用点附近空闲，动手时再核算。）

## 三、另一条待定线：`inScope()` 的极性与历史语义相反

- **老版（9/25，`tmp/GmBubblePaintHook.smali`）主逻辑闸门** = `on() && sDepth>0`（"只在助手项内做"）。
- **现役**：改成调用 `inScope()`，而 `inScope() = (sDepth ≤ 0) && on()`（**符号反了**）。
- 它管的是 PaintHook 主逻辑："D 分支：把颜色刷 0（项内小卡透明化）" / "C 分支：换 brush（已被 `brush()` return null 掏空、无害）"。
- **矛盾点**：若这个反了的方向真在"项外"全量跑，全 app 颜色背景（76 处调用点）都会被刷透明——**与现状不符** ⇒ **它要么未真正命中、要么有缓冲** ⇒ **先不动它**，等 §一确认后再定。
