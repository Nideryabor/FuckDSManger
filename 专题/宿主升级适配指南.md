## 一、动手前的 8 条铁律（升级时最容易破的）

| # | 铁律 | 为什么（本项目实证） |
|---|---|---|
| **181** | ⭐⭐⭐ **安装 ≠ 生效**：覆盖安装模块后**必须强停宿主**（或重启手机） | 2.19.4：`handleLoadPackage` 只在进程启动跑一次 ⇒ 用旧 dex 注册，之后加载的类来自新 APK ⇒ **「逻辑自相矛盾」的假象**（自检行打印 null、钩子却响了）⇒ **前几轮结论全部被污染** |
| **614** | ⭐⭐⭐ 诊断行**自带版本号**，让 dex 自证 | 同上：`[通话] 通话守护已启动…v2.20.0`，一眼看出跑的是哪份代码 |
| **255/577** | ⭐⭐⭐ hook 回调**零异常外抛** | 2.17.9：`nn1.A` 钩子里反射抛异常 ⇒ 被打断的是宿主的**发送+接流协程** ⇒ 消息不落库、回复不来 |
| **266/268** | ⭐⭐⭐ 停功能要**整段停 + 删代码** | 2.10.47 只停 `buildMut` 漏了同段 `forceVis`；靠「某字段恰好恒 null」= 定时炸弹 |
| **反判断** | ⭐⭐⭐ `if-*z` 六兄弟逐字念，**每写一个分支立刻写出「跳过去代表什么」** | 本项目累计 **20+ 次**；2.14.11 一处连犯 3 处；2.17.4 首道守卫反向 ⇒ 全程静默 |
| **寄存器** | ⭐⭐⭐ 改方法体后同步核对 `.registers ≥ 最大寄存器号+1`，`invoke-*` 参数个数与签名一致 | 2.18.2 `tick()` 用 v6 但 `.registers 6` ⇒ **ART 拒绝整个类**；smali 汇编器**不校验**这两样 |
| **6** | ⭐⭐ `mt_apk_edit_check(runBuildChecks=true)` **不做字节码校验** ⇒ 插完 smali **必须回读产物人工复核** | VerifyError 会一路过到真机 |
| **590** | ⭐⭐ **「没有效果的新代码」= 纯风险**，零收益一律回退 | 2.18.5 撤回每秒轮询宿主 ⇒ 回到全绿 |

**另外三条工程习惯**（升级轮尤其重要）：

- ⭐ **hook 失败要隔离**：`hookM` 内部自建实例 + 自 try ⇒ **一条 hook 失败只废它自己**（历史 4 次「一个类拖垮全局」）。
- ⭐ **模块自保**：`handleLoadPackage` 里任何一处抛异常 = **后面所有 hook 全不注册** ⇒ 危险调用一律 `GmUtil.envSafe`。
- ⭐ **升级轮开工第一件事：先翻自家文档**（教训 543）。`wr.x()` 是空壳这条结论我们**踩了两版**才想起来。

## 二、五步 SOP

### 2.0 环境与证据准备

```text
① 拿到新宿主 APK
   → mt_apk_open(path=<新宿主>.apk, temporary=false)   # 长期用，别 temporary
   记录：versionCode / versionName / 类数 / dex 数     # 与基线对比，「变多少」定策略

② 基线（旧宿主）工作区保持可查：deepseek2.5.2 (273) 旧工作区 id 记在 交接文档 §1

③ 让主人装新宿主 + 装当前基线模块 + 【强停宿主】→ 跑一遍 → 要日志
   ⚠️ 没有「新宿主 + 旧模块」的坏法清单，就不知道该适配什么 ⇒ 别凭猜
```

> 🔴 **最重要的输入不是 APK，是「坏法清单」**。
> 「全坏」和「某个入口点不开」是两条完全不同的路。

### 2.1 锚点存活体检（核心环节，约 10 分钟）

**逐域跑 `§三` 的表格**。每条锚点的动作只有三种：

| 方法 | 用途 |
|---|---|
| `mt_apk_search target=dex_strings` | **旗舰指纹**（S 级字符串）一击命中 |
| `mt_apk_search target=dex_names` / `mt_apk_list view=dex_classes` | 按结构（签名 / 形参组合）找 |
| `mt_apk_dex_outline_class` | 命中后核对**方法签名 / 字段形状 / 明文常量** |
| `mt_apk_resource_read` / `view=resource_table` | 资源 id 核对 |
| `mt_apk_dex_xref` | 从调用点反查（教训 261） |

**判定只看一条：验结构，不看名字。**
（`p66.h` 参数 5→4、`MMKV.p` 被复用成 `p(String,F)V` —— 名字在、语义已换人。）

体检结论填进 `参考/数据/锚点总表-<新版本>.tsv`，每行标 ✅/⚠️/❌。

> ⚠️ **反编译侧的坑（多 dex 宿主必踩）**：`baksmali d <apk>` **默认只翻 `classes.dex`**。
> 2.6.1 只翻第一个 dex 时是 **11,709** 个类，**逐 dex 全翻后是 15,484**（与 MT 报的一致）；
> 漏翻 = 有一批类根本不在树里 ⇒ **匹配全在错误范围里跑**（本轮复核纠出 3 处结论偏差）。
> ⇒ **先数 dex 数、逐 dex 翻、翻完核对类数**；关键结论都要在"满树"上复验一遍。

### 2.2 分诊与处置

| 体检结果 | 处置 |
|---|---|
| ✅ 全在 | 问题**不在锚点** ⇒ 走 §五（灰度类型 / 常量 / 资源 id） |
| ⚠️ 签名变了（参数少/多） | **别急着改**：先看模块**有没有按位置读参数**。本模块 `GmDsHook` 只读 `args[0]` ⇒ 5→4 **免修**（教训 67） |
| ❌ 类改名了 | 用**旗舰指纹**重定位（S 级一击），见 §四 M2 |
| ❌ 类消失了 | 该类被 R8 内联/合并 ⇒ 回到**调用链上游**找新的载体（教训 252：diff 调用图） |
| ❌ 方法重载被剪 | 抄来的 API 必须重新验存活（教训 111）——`NavController` 只剩 23 个方法，`navigate(String)` 已被剪 |
| 🆕 宿主新增了键/页面 | 计入「纳管」待办（§5.3），**不属于适配 bug** |

## 四、四大高发故障模式（按升级后的实际概率排序）

### M1 · 灰度键「类型不符」 ⇒ 静默失效 ★★★★★

**症状**：UI 显示「已保存」、也有 toast，**宿主就是不认**（静默读回默认值）。
**判据**：**「键名对得上」≠「能生效」**（教训 2）。
**处置**：走 §5.2 类型核验流程。

**宿主读法 → 模块类型码对照**：

| 宿主 MMKV 解码方法 | 语义 | 模块 `GmDialog.TYPES` |
|---|---|---|
| `c(String)Z` | boolean | `b` |
| `g(String)I` | int | `i` |
| `e(String)F` | float | `f` |
| `j(String)String` | string | `s` |
| `k(String)String` | string（另一个域） | `t` ⚠️ **自定义码，要盯住**（既不进 `GmStore.write` 的 `b/i/f/l` 分支（落 `putString`），又要求宿主按 string 读） |
| `q(String)String` | string（TTS 域） | `s`（按 String 处理；**核验工具的解码表要认识 `q`** —— 本轮新识别的读法） |

**历史命中记录**：2.9.7（4× `b→t`、1× `f→i`）· 2.9.12（`input_default_voice` `s→b`、`edit_menu_item_config` `s→i`）。
**⇒ 三版里两版坏的根因都是它。升级第一件事就该核类型。**

### M2 · R8 重排：类名「还在」但已换人 ★★★★

R8 map 每版重排，**混淆名空间被整体重新分配**。2.5.1 一轮里九个旧名全部换人。
**处置**：§2.3 按旗舰指纹重定位。**永远不要凭记忆填类名。**

### M3 · R8 剪掉重载 / 参数个数变化 ★★★

- 未被调用的 public 重载会被**剪掉**（`NavController.navigate(String)` 就是这么没的）。
- 参数个数会变（`p66.h` 5→4）。
**处置**：先判断「模块有没有按位置读参数」——
`GmDsHook` 只读 `args[0]`、`hookAllMethods(cls,"h",…)` 按名字挂 ⇒ **签名变了也免修**（教训 67）。
**排查顺序：锚点在不在 → 签名变了没 → 模块用没用那个参数。**

### M4 · 自己的老毛病在升级轮集中爆发 ★★★

升级轮改文件多，最容易犯：

| 病症 | 判据 | 处置 |
|---|---|---|
| `if-*z` 反向 | 功能**静默失效** + **日志一行都没有** | 「日志缺失 = 那段代码没执行」⇒ 静默 return 一律补日志（教训 563） |
| `.registers` 越界 | LSPosed 日志 `VerifyError: Verifier rejected class` | 改方法体后同步核对（教训 583） |
| `invoke-*` 参数个数不符 | `VerifyError` / `NoSuchMethodError` | 汇编器不校验，人工数（教训 584） |
| 反射 `VerifyError` 被自己的 try 吞 | helper 恒返回 null | **反射 helper 的 catch 必须落盘**（教训 611）；`Object` 进 `Collection` 参数要 `check-cast` |
| 调了 bridge 不存在的重载 | `NoSuchMethodError` | **只用项目里已用过的重载**（教训 587）——本工程 bridge 只有三参变参版 `callMethod(Object,String,Object...)` |

## 五、灰度域专项（本模块的命脉）

### 5.1 三层优先级（决定「要不要加 hook」）

```
kv_settings_<k>      （本地覆盖层，优先级最高）  ← 我们优先写这里，零 hook
      ↓
内存缓存
      ↓
kv_remote_settings_<k>（服务端下发）          ← 没有本地键时才写这里 + 必须加 GmMmkvHook
```

**规律**：有 `kv_settings_*` 的键 ⇒ 写**裸键**即可，**零 hook**；
没有 ⇒ 写 remote 键 **+ 必须加 `GmMmkvHook`**。

**拦截下发要用影子键** `fuckds_pin_<key>`（`GmStore.write/remove` 自动镜像），空 = 不干预；
**绝不能用同键旧值当覆盖值**（会退化成「用户没设过的键被永久冻结」）。

### 5.2 类型核验流程（每次升级必跑）

```text
① 拿宿主「配置总表类」（如 Lo02 / Ln2a / pk9）
   mt_apk_dex_outline_class locator=dex_class:Lo02; limit=400
② 把每项的「类型串 + contains→decode 方法名」全部提取出来
③ 与模块 GmDialog.TYPES 逐键比对
④ 差异项：改 GmDialog <clinit> 里的类型码
⑤ 差集：宿主是否新增了灰度键？ → 决定要不要纳管
```

**产出**：三张分组核验表（总表 63 / 录音语音 7 / TTS 2）+ 下发域 11。

### 5.3 新键纳管（属「新增」不属「适配 bug」）

```text
① 从总表类里找出「模块 TYPES 里没有的键」
② 逐个确认：读法（MMKV->?）/ 类型串 / 默认值 / 是否有 kv_settings_ 本地覆盖
③ 加进 GmDialog 的键表 + 类型码
④ 真机验：改完重启宿主是否生效
```

| `kv_remote_settings_id_model_configs_v1` | 版本 id 键 |

## 七、常见误判 / 别信的东西

| 别信 | 真相 |
|---|---|
| 「旧类名还在，直接改回旧名不就行了」 | 名字在 ≠ 语义在。`p66.h` 参数变了、`MMKV.p` 被复用成 float 版 |
| 「功能没生效 ⇒ 我的 hook 没挂上」 | 也可能是**它在生效，只是你看不见**（教训 106，自绘 Dialog 能收点击却不可见） |
| 「日志没数据 ⇒ 数据源不对」 | 也可能是**那段代码没执行**（反判断反向 / 被自己的 try 吞 / 静默 return） |
| 「覆盖安装就好了」 | **必须强停宿主**（铁律 181）；否则新旧 dex 混用 ⇒ 前几轮结论全部作废（教训 626~628） |
| 「UI 显示已保存 ⇒ 生效了」 | 类型不符 ⇒ 静默读回默认值（铁律 2） |

## 9.1 ⭐ 成员名审计（v1.0 完全没覆盖的一类，也是本轮"功能全哑"的真凶）

### 为什么它最难查
R8 改**方法名/字段名**之后，模块里这种代码会**静默失效**：

```smali
const-string v3, "D"
invoke-static {v2, v3, v4}, XposedHelpers;->callMethod(...)   # 老名字，现在不存在
```
抛出的 `NoSuchMethodError` **被自己的 try/catch 吃掉** ⇒ 日志里什么都没有 ⇒
表现成"**设置开了、但一点儿效果都没有**"。**比崩还难查。**

### ⚠️ 但"静默失效"不是最坏的 —— 它有时根本不失败，而是"打到别的成员"（v2.1 修正）

R8 的**名字复用**会让**旧名字依然存在**（只是换了主人）⇒ 反射**不报错**，
一声不响地**返回另一个成员的值 / 调用到另一个方法** ⇒ 错误数据直接流进宿主。

本轮两个实锤（教训 334）：

| 案例 | 表现 |
|---|---|
| `GmUAvatarHook.setResult(String)` | 污染了"本该返回渲染列表"的方法 ⇒ 点「上传图片」触发重组 ⇒ `ClassCastException: String cannot be cast to dz9` ⇒ **宿主崩** |
| 消息域「角色判据」（按方法名 `"D"`） | 反射成功但打到**另一个方法**（返回 `mb9`）⇒ 判据失效 ⇒ 用户项走助手支线 ⇒ **"雷霆大横条"** |

**⇒ 比"哑火"危险一个数量级**，而且**不在异常日志里留痕**。抓它的两条路：
① 运行时"**点名 + 验类型**"（见下面扫法 ③）② 从崩溃签名反推（§9.5）。

### 处置：接管型钩子必须做"身份校验"（教训 333）

凡是**用 `setResult(...)` 覆盖返回值 / 写宿主字段**的钩子，接管之前必须先验**方法身份**：

```text
① 方法的声明类 / 名字在预期范围内
② 返回类型是我们期望的那族（不是 String、不是接口）
③ 判据用到的字段类型也核一遍
任一条不过 ⇒ 直接放行原方法（宁可不干活）
```

反例：`getIntField(obj,"a") == 0xf` —— "一个字段名 + 一个数值"就决定接管，**判据太弱**；
新宿主上（连同那个数值本身也版本耦合，见 §9.4）命中了不该命中的方法 ⇒ 污染宿主。

> 🧭 **设计取向（教训 327）**："钩住方法直接改返回值"最抗升级（自包含、不依赖宿主成员名）；
> "反射深挖宿主对象"最脆（成员名一改就废）。但前者必须配上面的"身份校验" —— **抗升级 ≠ 免校验**。

### 怎么扫（底座侧）
```sh
# ① 列出所有"带字面量的反射调用"
python3 - <<'PY'
# 扫 callMethod / callStaticMethod / get*Field / set*Field / findMethod*，
# 取调用行 `{...}` 里的寄存器，回溯寄存器里的 const-string 值
PY
# ② 对每一处，先判"对象是哪个宿主的类"，再查该类在新宿主的成员名
python3 tools/fp_method.py tmp/hold tmp/hnew 映射.tsv <老类名>

# ③ 运行时「点名 + 验类型」（10/1 新增）—— 不只查"存不存在"，更要查"类型对不对"
#    "存在但类型不对" = 名字复用的雷（比 NoSuchMethodError 危险）
#    产物：参考/数据/反射调用清单.tsv（102 处）→ 适配-待改清单.tsv（42 处已给新值）
#    工具：tools/frida/extract_reflect.py · tools/frida/gen_patch_list.py
```

### 已知对照（宿主 2.6.1，实测）

| 老类 | 新类 | 老成员 → 新成员 |
|---|---|---|
| `vq`（消息基类） | `mr` | `l`→`j`（正文）· `C`→`q`（拼接）· `D`→`C`（角色 USER/ASSISTANT）· `x`→`w`（序号）· `k`→`h` · `m`→`i` |

## 9.2 ⭐ 「名字诈尸」：门禁必须判形状，不能只判"类在不在"

**现象**：宿主升级后，旧锚点名**没消失**，而是**被别的类占用了**。

2.6.1 实测：
| 旧名 | 老身份 | 新身份 |
|---|---|---|
| `Lkf5;` | Compose 杂物间（painterResource） | **CameraX 的 lambda**（`MeteringRepeating`） |
| `Luia;` | Modifier 静态工具桶 | 一个 51 字段的巨类 |
| `Lh91;` | 消息列表 Composable | **一个 0 方法的空接口** |

**后果**：门禁 `findClass("kf5")` **成功** ⇒ 模块**不退出** ⇒
51 条钩子**全挂到无关的类上** ⇒ 轻则全哑、重则**把宿主咬崩**。

**处置（写进门禁）**：
```java
boolean ok = false;
try {
    Class<?> c = XposedHelpers.findClass(name, cl);
    // ★ 形状校验：必须真有那个方法（哪怕只判参数个数）
    ok = XposedHelpers.findMethodExactIfExists(c, "x", int.class, int.class, Object.class) != null;
} catch (Throwable ignore) {}
if (!ok) return;   // 宁可不干活，也别挂错类
```

## 9.4 ⭐ 探针定案法：「魔法数字」不要推，让运行时说

**适用**：case 号 / 索引 / 资源 id / 参数顺序 —— 任何"改一处就致命"的常量。

**两步**：
1. **静态缩小范围**（fp_match / 调用栈）
2. **插一行日志让它自证**：
```smali
new-instance v4, Ljava/lang/StringBuilder;
const-string v5, "[FDS] row case="
invoke-direct {v4, v5}, Ljava/lang/StringBuilder;-><init>(Ljava/lang/String;)V
invoke-virtual {v4, v1}, Ljava/lang/StringBuilder;->append(I)Ljava/lang/StringBuilder;
invoke-virtual {v4}, Ljava/lang/StringBuilder;->toString()Ljava/lang/String;
move-result-object v4
invoke-static {v4}, Lcom/nidyaber/fuckdsmanger/gm/GmUtil;->log(Ljava/lang/String;)V
```

**本轮战果**：
- 入口 case：静态推 `0x5` ❌ → 探针读出 **`0x1d`** ✅
- **★ 不知道"是哪个类"时，去 hook 它的"下游"，打印 Java 调用栈** ——
  本轮栈直接打出 `AndroidComposeView.dispatchTouchEvent → … → m01.w → t5.w → … → ll2.z → xu2.a`，
  一击锁定行桶是 `t5`（不是我先前误判的 `ew1`）。**这一招最值钱。**
- **⚠️ 判据里的"数值"也是版本耦合的**（教训 339）：`getIntField(obj,"a") == 0xf` ——
  类名/方法名/字段名**全核过**，照样咬在别人的分支上（正确值是 `0x12`，实测）⇒
  **弱判据 + 魔法数字 = 最危险的组合** —— 别核完名字就放心。

> **另一类"签名变了但名字没变"的坑**：`jn0.<init>` 从 `(int, long)` 变成 **`(long, int)`**（参数顺序换了）。
> ⇒ `newInstance` 抛 `NoSuchMethodError: jn0#[Integer, Long]`。
> **审计时不能只看"方法名在不在"，还要看形参顺序。**

## 9.7 ⭐ 「包名伪装」与「无壳判定」—— 反分析两件套

### 9.7.1 「包名伪装」：`android.app.Praimoork` 不是随机名、也不是伪造

崩栈/日志里如果出现"像系统类"的怪名：

```
android.app.Praimoork.w(Praimoork.java)
android.content.MootuntShedath.w(MootuntShedath.java)
```

**真相（本轮实锤）**：既不是随机类名、也不是被伪造 —— 是宿主把**自家混淆类搬进了 `android.*` 包**，
让逆行者一眼扫过去以为是系统代码（又一种反分析手法）。

- 排查姿势：`Java.enumerateLoadedClassesSync()` 默认看不到它（不在默认 ClassLoader 的可见范围）
  ⇒ **遍历全部 ClassLoader（本机 106 个），逐个 `loadClass("android.app.Praimoork")`，谁认它就是**
- 💡 **重要结论：真类名是稳定的 ⇒ 静态指纹配对（§2.3）依然有效。**
  别因为看到"怪名字"就怀疑整套静态方法（本轮差点因此推翻自己）。
- 📌 顺手反证：怀疑过的"造假器" `lk9` —— **是空的**，它就是个普通栈格式化器。

### 9.7.2 「无壳判定」：先确认"要不要上内存 DEX 转储"

**一句话判据：数 `InMemoryDexClassLoader`。**
- 只有**模块 + LSPosed** 的 2 个 ⇒ 宿主**没有壳 / 没有运行时解密** ⇒ 静态 dex 就是全部
- 只有宿主自己也在动态加载 dex 时，才需要考虑内存 DEX 转储（panda-dex-dumper 那类）

辅助判据：**"已加载类名"与"静态 dex 类表"做差集** —— 差集里才是"运行时才有的类"。

> 本机实测：ClassLoader 共 106 个（2 × InMemoryDexClassLoader + 102 × PathClassLoader + 2 其他）、
> 已加载类 41,354 —— **无壳**，内存转储不需要（省下一个晚上的功）。

## 9.8 ⭐ 「改动进包」的闭环与单一真相源

### 教训 332：工具磨得再亮，改动进不了包都是空的

本轮最贵的一课：`patch_261.py` 改好的 smali 树 —— **一直没人接**。
缺了"smali → classes.dex → 塞回底座 APK"的那一环 ⇒ **改多少都不进包**（白忙一晚）。

**⇒ 升级适配开工前，先把"改 → 进包 → 装机 → 回读"整条流水线走通一遍**（哪怕用一条无害小改动试走）。

本轮补上的环节：
```sh
python3 tools/重建底座.py --smali tmp/base130_261/sm --base <底座apk> --out <底座apk> --api 26
# 内含：临时文件 + os.replace、往返语义复核、关键替换复核
```

> ⚠️ **不要重跑 `patch_261.py`**（`rmtree+copytree` 会抹掉树里的手工改动，教训 341）。

### 教训 347：单一真相源 —— 改动风格"二选一"，混用必丢

```text
① 在 smali 树里改   → 走「重建底座」进包   ← 推荐，可复核、可回溯
② 字节级直接改 dex  → 不进树               ← 只适合应急
```

**混用必丢**：重建是用树**整个替换** dex —— 树里没有的（字节级）改动会被**覆盖回去**。
（本轮实例：一个 1 字节修复没写回树，重建后差点把"上传图片崩"放出来）

**⇒ 规矩：树是唯一真相源。** 字节级改动必须**写回树**（或台账里标死），否则下次重建即丢。

> 配套：改完必须**回读产物**（§2.5）—— 先有闭环，"回读"才有意义。

## 9.9 ⭐ 资源同步：既要"平移"，也要"拆雷"

资源 ID 每版都会**平移**（示例：`profile_check_for_updates` `0x7f0f021f → 0x7f0f0263`）。
但平移只是第一层 —— 下面还有一颗**方向相反的雷**：

**⚠️ "哨兵 ID"会变真资源（反向误伤）**
老代码有个安全习惯：拿"宿主里显然不存在的 ID"当哨兵（命中就返回空串，防 `NotFoundException` 崩）。
新宿主里那些 ID **可能变成真资源** —— 本轮：`0x7f0f0221/0222` 变成了**登录验证 toast 的两条文案** ⇒
"防崩溃的空串返回"变成**把登录提示清空**（龙把人咬了）。

**⇒ 资源同步的标准姿势（"平移 + 拆雷"两连）**：
1. 列出模块里**每一个宿主资源 ID**（含所有"哨兵 ID"；模块自造的合成区间如 `0x7f7f0000` 不用动）
2. 逐个读**它现在的真实资源名**（`mt_apk_resource_read` / `view=resource_table`）
3. 该平移的平移 · **哨兵 ID 有主了就废掉那条守卫** · 顺手核对 §三 锚点表的资源行
