## 一、位置是怎么定下来的（逆向路径）

宿主 DeepSeek **2.5.1** 全量 R8 混淆，但 Kotlin 会往 dex 里塞**源码位置字符串**，这是最好的路标。

1. 搜 dex 字符串 `drawer` → 命中 `com.deepseek.chat.ui.components.drawer.*` 与
   `com.deepseek.chat.ui.pages.chat.views.ChatNavigationDrawerContent (ChatNavigationDrawerContent.kt:145)`
   ⇒ 侧边栏内容就在 `ChatNavigationDrawerContent.kt`。
2. 搜「打码手机号」的字面量 `"****"` → 只有 2 处，都是
   `Llx8;->t0(IILjava/lang/String;Ljava/lang/String;)`（≈ `StringBuilder.append(seq,start,end)`）：
   ```
   if (mobile.length != 11) { log("MobileUtil", "mobileNumber.length should be 11"); null }
   else mobile.substring(0,3) + "****" + mobile.substring(7,11)   // 158****8888
   ```
   旁边带着 `Lu9a;->Y("MobileUtil")` 的 trace —— 那段逻辑的函数名就叫 **MobileUtil**。
3. 顺着 `Ls5;->v()`（上面两处打码之一所在的方法）反查：它是**合成 lambda 类**，
   `public final synthetic a:I` 就是 switch 分派下标。全库搜它的构造点，传 `0x8` 的**只有一个**：
   `Leb1;->h(Lld6;Lc76;Ley3;I)V` 里的 `new-instance Ls5; const/16 v11, 0x8`。
4. `Leb1;->h` 的 trace 字符串写着
   **`com.deepseek.chat.ui.pages.chat.views.UserInfoFooter (ChatNavigationDrawerContent.kt:632)`**
   ⇒ 这就是侧边栏底部那一行。

## 二、`UserInfoFooter` 里有什么

| 元素 | 落点 |
|---|---|
| 账号名（`Text`） | 取值自 `Ls5`(`a=8`) 的 state，最终由 `Lz89;->b(String;…)` 绘制 |
| 账号头像 | URL 经 `Ljt5;->N(…)` = **`coil3.compose.rememberAsyncImagePainter`**；无图时退到 `painterResource(0x7f07010f)` → `Lme4;->a(...)`（Icon） |
| 头像 URL | `Lp5`(`a=0xf`) 的 lambda → 返回 `Lit9->e:Ljava/lang/String`（全库只有 `UserInfoFooter` 构造 `0xf`） |
| 右侧小图标 | `0x7f0700bf` = `ic_ellipsis`，contentDescription = `0x7f0f02da` = `settings` |

### 账号名取值逻辑（`Ls5;->v()` 的 `a == 8` 分支）

```
1) id_profiles 里选中的 profile 有昵称 → 用它
2) 否则 Lgy.a() 非空                  → 用打码手机号 158****8888
3) 否则                              → 兜底字符串 sider_profile = "My Profile"
```

（`Lgy` = 账号模型，由 `com.deepseek.chat.account.model.KVAppUserInfo` 反混淆而来）

### 账号模型（`Lh45;` = `KVAppUserInfo`，序列化器 `Lf45;`）

`token` / `id` / `email` / `mobile_number` / `status` / `chat_status` / `id_profiles` /
`need_birthday` / `is_mainland` / `minor_mode_status`

> ⭐ **模型里没有头像字段** ⇒ 头像只能靠「换 URL」或「换资源」两条路（见 3.2）。

## 三、实现（2.9.9）

### 3.1 自定义账号名（留空 = 隐藏）

配置：`fuckds_gm` / **`accname_text`(String) + `accname_set`(boolean)**

hook **`s5;->v()`**（注意是 Java 名 `s5`）：

```
if (!GmName.isSet(ctx))        -> 什么都不做（跟随宿主原本显示）
else if (this.a == 8)          -> setResult(GmName.getText(ctx))   // 可能是 "" = 隐藏
```

- ✅ **全库唯一**：`Ls5;-><init>(Object,Object,Object,I)` 的调用点里，传 `0x8` 的只有 `UserInfoFooter`
- ✅ **留空就是隐藏**：返回空串，Compose `Text("")` 不显示内容，行仍在（头像 / 点击区不受影响）
- ✅ 「恢复默认」= `GmName.clear()` 清掉 `accname_set` ⇒ 回到宿主原样
- 交互：美化页一行 `EditText` + 「保存账号名」+「恢复默认」

### 3.2 修改账号头像（走 Coil）

hook **`p5;->v()`**（`a == 0xf`）→ 返回 `file://<私有目录>/fuckds_uavatar.png?v=<mtime>`。

| 项 | 值 |
|---|---|
| 落盘文件 | `fuckds_uavatar.png`（宿主私有 `filesDir`） |
| 开关键 | `fuckds_gm` / `uavatar_on` |
| 选图 | `GET_CONTENT` + `startActivityForResult(0x4359)` → `GmPickHook` 的第三分支落盘 |
| 破缓存 | `?v=<lastModified>`（Coil 以 model 字符串做 key） |

> 为什么不用「换资源」那条路 —— 见第五节真因 ②。

## 五、2.9.8 为什么「完全没效果」

### 真因 ① 账号名：`findClass` 写成了 dex 名

注册时写 `"Ls5"`，但 Xposed 要的是 **Java 名** —— `Ls5;` 的 Java 名是 **`s5`**。
`findClass("Ls5")` 抛异常 → 被 `hookM` 的 try/catch 吞掉 → **功能静默完全无效**。

> 项目里 app 类的 hook 一直用的是 Java 名（`h91`/`p66`/`m5`/`h02`/`bx4`/`kf5`），这次是自己写岔了。

### 真因 ② 账号头像：`painterResource` 对矢量 XML 不走 `getDrawable`

```
painterResource(id):
  value = resources.getValue(id)
  if (value.string endsWith ".xml")  -> loadVectorResource: resources.getXml(id) + 解析成 ImageVector
  else                               -> BitmapFactory / getDrawable 那条路
```

`ic_profile` = `res/BI.xml` 是**矢量** ⇒ 走 `getXml` 解析 ⇒ `Resources.getDrawable` **一次都没被调用**，
那个 hook 是**死代码**。

**改法**：别换资源，换「资源的前一步」—— 头像真正由 **Coil3** 加载，吃的是 URL 字符串，
hook 那个算 URL 的 lambda 返回 `file://` 即可。

## 八、附：助手头像的「蓝色方块」（2.9.10 → 2.9.11，**未完结**）

### 8.1 助手头像靠三条 hook 接力

1. `GmVectorHook` hook `Resources.getValue` → 把 `TypedValue.string` 置 null（骗掉 `painterResource` 的矢量分支）
2. `GmPainterHook` hook `painterResource`（`kf5;->K`）→ 用 `AndroidImageBitmap`(`le`) + `BitmapPainter`(`ok0`) 造 painter 塞回去
3. 宿主 `Lbka;->c` 用 **`Icon(painter, tint = 主题色)`** 画 ⇒ **`ColorFilter.tint`（`SrcIn`）把照片染成纯品牌蓝方块** ← 蓝方块的根因 ✓

> 关键点：`res/Fi.xml`（`assistant_message_avatar`）**是矢量**，所以「hook `getDrawable` 换图」那条路
> 对助手头像**根本不可能生效** —— 必须靠 ① 先把分支骗掉。这是 2.9.8 那次最容易误判的地方。

### 8.2 2.9.10 的修法与意外（⚠️ 重点）

**做法**：新增 `GmIconHook` hook `me4;->a`（`Icon`），身份命中我们的 painter 时把 `args[3]`（tint）
换成反射读到的 `Color.Unspecified`（`q32->h`）。

**结果**：蓝方块没了，**但头像整个消失了** 😵

**矛盾点**：我把绘制链读到最底层 ——
`Icon` → `PainterElement`(`Llu6`) / `PainterModifier`(`Lmu6->k0`) → `Painter.paint`(`Lku6->g`)，
其中 `Lku6->g` 内部有个 `b:Z` 标志（“需要 layer”）：

```
alpha != 1 ∨ colorFilter != null  ⇒ b = true  ⇒ saveLayer(rect, paint) + onDraw() + restore()
否则                              ⇒ b = false ⇒ 直接 onDraw()
```

**两条分支都会调 `onDraw()`** ⇒ 按代码「不染色」应当正常显示照片 ⇒ 与真机现象矛盾。

### 8.3 两个候选（互相可区分）

| 候选 | 内容 | 判据 |
|---|---|---|
| **A** | tint 中和这一步本身有问题（`b=false` 路径某环节） | 装 2.9.11 后头像**变回蓝方块** |
| **B** ⭐ | 与 tint 无关：我们的 painter 画出来的内容本来就不对（例如接近背景色/尺寸退化），**蓝 tint 只是把它显影了** | 装 2.9.11 后头像**仍然空白** |

> 候选 B 的直觉：`SrcIn` 保留 alpha、RGB 全换 ⇒「有 tint 可见、无 tint 不可见」很可能意味着内容本身有问题。

### 8.4 现状与续做入口

- **2.9.11 = 摘掉 tint 中和的回退版**（恢复 2.9.9 行为），`GmIconHook` 类保留、一行即可重启用
- **➡️ 完整的「已确证地图」+ 两个候选修法 + 需要的日志关键字，全部存档在 `版本/2.9.11.md` 第五节**

  - **A** ⇒ 自建 Painter 子类（继承宿主 `Lku6`）在 `onDraw` 里无视 `colorFilter`

### 8.5 本节教训（新增）

- **第 64 条：⭐「改了某参数 → 效果剧烈变化」时，先怀疑「原来那个参数在掩盖另一个 bug」。**
  蓝 tint 一去掉头像就整个不见 ⇒ 很可能内容本来就是错的。别急着再改同一个参数（会来回烧版本），
  先做**能二分的实验**（本次 = 2.9.11 摘钩回退）。
- **第 65 条：改不动就「先回退到可观测状态」再收工。**
  「彻底不可见」→「蓝方块」保住了可观测性与可排查性；回退 + 存档的成本远低于留个「什么都不显示」的版本过夜。

### 8.6 ✅ 2.9.26：换修法（不动 tint，只换 filter）—— **待真机验收**

**思路**：2.9.10 的错不在目标（去染色），而在手法 —— 把 tint 换成 `Color.Unspecified` 会连带把
`Painter.paint` 的 `useLayer` 从 `true` 翻成 `false`，**一次改了两个变量**。
2.9.26 改成 **值中性化、路径不变**：

```
tint 不动（主题色）      → Icon 照旧造 ColorFilter
useLayer 不动（true）    → 还是今天能出「蓝方块」的那条 saveLayer 分支
只把 filter 换成恒等     → BlendMode.Dst（Porter-Duff [Da, Dc] = 保留被绘制内容）
```

**落点**：`Lfh6;->N(...)`（= `Modifier.paint`，宿主 2.5.2 下已逐字核对：`args[5]` 会被原样塞进
`Llu6`(PainterElement)，mask 只管 alignment/alpha）——
`args[1]` 是 painter，可直接与 `GmPainterHook.sPainter` 比身份 ⇒ 天然只影响助手头像这一处。

**新增 / 改动**：`GmPaintModHook`（新类，+1 → 81 类）；`GmIconHook` 改纯观测（不再改 tint）。

> 完整改动、判读表（三行关键日志）、教训 110~113 见 **`版本/2.9.26.md`**。

### 8.7 顺带查清的两件事（避免下次重走）

| 项 | 结论 |
|---|---|
| `GmPainterHook` 到底挂在哪 | **`kf5.K`**（不是 `i65.x`）。`i65.x` 是 2.5.1 时代的老挂载点，2.5.2 里 `Li65;` 只剩 `<init>`/`A` 两个方法；头像调用点 `Lcka;` 是**直接** `invoke-static {…}, Lkf5;->K`。代码里那行日志 `Li65.x called` 只是**没跟着改的旧标签** ⇒ 教训 110 |

## 九、教训

- **第 55 条：Kotlin 合成 lambda 的 `public final synthetic a:I` 就是 switch 下标**，可以当「反查唯一构造点」的钥匙 ——
  先找到逻辑所在的方法 → 读出下标 → 全库搜 `new-instance` + 该下标，就能精确锁定**唯一调用点**。
- **第 56 条：`"****"` 是最省事的定位锚点**。想找「打码手机号」不要猜混淆类名，
  直接在 dex 字符串里搜这个字面量，再顺 `StringBuilder.append(seq,int,int)` 的调用点即可。
- **第 57 条：非 range 的 `invoke-*` 最多 5 个寄存器**。六参方法（如 `GmBeautyAdd.sw()`）必须用
  `invoke-static/range {v0 .. v5}`，且**参数寄存器必须连续升序**。
- **第 58 条：Xposed 注册用「Java 类名」，不是 dex 描述符。** `Lh91;`→`"h91"`，`Ls5;`→`"s5"`。
  写错不报错，只是被 try/catch 吞掉 ⇒ **功能静默失效**。挂完一定要确认 `hookM … count=N` / `hookM FAIL` 那行日志。
- **第 59 条：Compose `painterResource` 对矢量 XML 不调 `Resources.getDrawable`**（走 `getXml` + 解析）。
  「hook getDrawable 换图」这条老路**只对 PNG / 非-XML 资源有效**。
- **第 60 条：换不掉资源，就去换「资源的前一步」。** 头像真正的加载器是 Coil3，吃 URL 字符串 ⇒
  hook 算 URL 的 lambda 返回 `file://`，既绕开资源解析，也绕开 Icon 的 tint。
