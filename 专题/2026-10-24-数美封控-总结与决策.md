### 1.6 ★★ 掀桌级发现：`hookJava` 是**云控**的

```smali
invoke-virtual {p4}, l11l111l11Il;->l11l111l1lll()Z    ← 读 "hook_java_switch"
if-eqz p3, :cond_a7                                   ← false ⇒ hookJava 整段跳过
```

云控键：`hook_java_switch` / `hook_switch` / `risk_file_switch` /
`upload_checker_switch` / `white_apps` / `risk_dirs` / `all_atamper` / `core_atamper`

**⇒ 这是数美官方设计的「按组织配置检测强度」，不是对抗。**
**⇒ 理论最优解：伪造 `/v3/cloudconf` 响应，让它自己别采。**

### 1.7 云控解密链（已完整还原）

```
① AES/CBC/PKCS5Padding
   key = 32 字节（Base64 常量，见逆向档案）
   IV  = "0102030405060708"                          ← 硬编码
② Inflater（标准 zlib）
③ 按 ver 解析：
   ver=1 → upload_checker_switch / risk_file_switch / all_atamper / core_atamper / sensitive.*
   ver=0 → up_max / re_max / net_max / hook_java_switch / hook_switch
```

⚠️ **死结**：云控响应签名用 `SmOption.publicKey`，我们**没有私钥**
⇒ 伪造「合法通过」的响应不可能，只能**重放**或**改 `sm_sdk_host` 指向自己**。

## 二、今天真修的东西（3.71.19）

### 2.1 `device_id` 会重复生成 —— "一堆未知设备"的根源

**旧实现：**
```java
gen() {
    Random r = new Random();          // ★ 无种子 ⇒ 默认纳秒时间戳
    for (int i = 0; i < 16; i++) sb.append(hex(r.nextInt(16)));
}
```

**三个病：**

| # | 病 | 后果 |
|---|---|---|
| 1 | **无种子** ⇒ 两台设备同一毫秒会生成**同一个** device_id | 服务端当成同一台 ⇒ **连坐封号风险** |
| 2 | `shared_prefs` **跨进程**读写（模块 UI 进程 + 宿主进程都写同一个文件）| 丢值/读旧 ⇒ 重新 `gen()` |
| 3 | 每次丢值 = 服务端眼里**一台新设备** | 「登录设备管理」越滚越多（主人实测 **9 台**）|

**实测到过两个不同的值并存**（具体值不落盘）⇒ 证实了第 2 条。

**新实现（3.71.19）：**
```java
gen() {
    seed = Build.MODEL + "|" + Build.BRAND + "|" + Build.HARDWARE + "|" + firstInstallTime
    return MD5(seed) 前 8 字节 → 16 位 hex
}
```

**保证：**
- 同机永远同一个值（**丢了也能算回来**）
- 不同机不撞（`firstInstallTime` 精确到毫秒，覆盖"同型号硬件完全一样"）
- 系统升级不变（**刻意不用 `FINGERPRINT`**，它含 build 号）
- 出错兜底：FINGERPRINT.hashCode() 拼 16 位，**绝不返回 null**

**⚠️ 迁移注意**：`ensureFake` 是「读到就用」
⇒ 库里旧值还在用，新算法暂时不生效。
⇒ 要切新算法得**清一次**（UI 里「美化›设备›当前伪造 ID」本来就可编辑），代价是**多一台设备**，之后永久稳定。
