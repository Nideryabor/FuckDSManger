### 6.2 根因

```
libsmsdk.so           : 0 行   ✗ 没加载
l11l11l111Il.Context  = null   ★ 从未初始化
SmAntiFraud.option    = null   ★ 从未配置
SmAntiFraud 25 个重载  → 一次都没被调用
```

初始化入口 `SmAntiFraud.create()` 的唯一调用点在 `t3a`，
`t3a implements Lmc6`（**Worker 接口**），`<init>(...,Lbd3;)V`（`bd3` = WorkerParameters）。
⇒ **数美初始化是个 WorkManager Worker，从未被调度。**

### 6.3 `xpApp` 的真相

```java
读 /proc/self/maps → 找 /data/app/ → 抠包名
  → getApplicationInfo(pkg, 0x80) → metaData.get("xposedmodule")
  → 非 null 就上报「包名,应用名,true,82,简介」
```

**三重要素让它对我们无效**：
1. 引擎没启动 ⇒ 不采集
2. 即使采集，maps 里 `little_femaleboy` = **0 行**（`primaryCpuAbi=null`，LSPosed 用 `InMemoryDexClassLoader`）
3. Android 15 的 `/data/app/~~hash==/pkg-hash/` 前缀让它 `substring` 切错，**连自己都查不到**（`NameNotFoundException`）

**⇒ 不需要写任何对抗代码。**

> ⚠️ 但 `xpApp` **不在 `setNotCollect` 里**（只有 `ssid/sensor/bssid`）⇒ 万一哪天 Worker 跑了会采集。
> 监控哨兵：`adb logcat -s Smlog`（`SmAntiFraud.String = "Smlog"`）。

## 七、★ ttEncrypt 突破（不用逆密钥）

### 7.1 关键

```
EncryptorUtil.a(int size, byte[] data)
   IN  = 1f 8b 08 ...    ← gzip(JSON) 明文
   OUT = 12 39 20 20 ...  ← ttEncrypt 结果（不用管）
```

类名 `com.bytedance.applog.encryptor.EncryptorUtil` **未混淆**（JNI 按名注册）。
一处 hook 覆盖 **AppLog + APM + gator + AB**（7 个调用点）。

### 7.2 解出来的内容

**header（设备指纹）**：
```
device_model/brand  : <真机测试>（已脱敏）     resolution: <已脱敏>
package             : com.deepseek.chat.a      ← clone 包名原样上报
app_version         : 2.7.2  vc289
sig_hash            : e89b158e4bcf988ebd09eb83f5378e87   ← ★ 宿主 APK 签名 MD5
bd_did / install_id / clientudid / openudid / cdid      ← 五个设备标识
carrier: <真机测试>（已脱敏）   mcc_mnc: <已脱敏>
```

**event_v3（16 个事件）**：`send_button_click`（带 `chat_context_length`）/ `sse_request` /
`http_request`（completion、create_pow_challenge、history_messages）/ `sse_created` /
`sse_ready` / `sse_first_delta` / `sse_msg_status_updated`×3 / `sse_event` / `sse_finished` /
`fetch_history_messages`

### 7.3 对我们的意义

| 发现 | 影响 |
|---|---|
| `sig_hash` = APK 签名 MD5 上报 | ★ **绝不能改宿主签名** |
| `package` 原样上报 | clone 包在这条链上**有痕迹** |
| `chat_context_length` 上报 | **我们注入系统提示词会让它变大** |
| 5 个设备标识 | 改机需**五个一起动** |

## 十、事故与教训

### 10.1 ★ 我把宿主搞崩了一次

`sug272.js` 给 `h67` 全部 36 个重载挂 hook，并在**每帧组合的热路径里**做反射遍历字段：

```
FATAL EXCEPTION: main
java.lang.ClassCastException: k30 cannot be cast to go7
	at x98.d(...:541)
	at s21.q(...:1145)
	at r15.N(...)      ← Composer.endRestartGroup
```

**教训（新增硬规则）**：
> **Composable 是每帧重入的。任何 hook 里做「反射 / 字符串拼接 / try-catch」都会在帧内放大成灾难。**
> 探针一律：只读一次（static flag）+ 只读允许字段 + 绝不在 Composable 里反射。

### 10.2 ★ 我误报了一次「手机号泄露」

grep 到 `17311238834`，一口咬定是手机号。
实际是 `"ssid":"1731123883409535062"` 的**前 11 位**（19 位 session ssid）。

而主人问的侧边栏 `158******15` 是 **服务端下发的打码值**（`/users/current` 里就是打码的）。

**真正的问题是「昵称替换」功能挂了** —— 配置推过来了（`fuckds_nick=dxyabab`），
但**日志里没有任何「昵称 hook 已安装」** ⇒ 那个 hook 根本没装。

**教训**：看到「像手机号的数字」先看上下文和长度，别急着下结论。

### 10.3 网关三条坑

| 坑 | 表现 | 解 |
|---|---|---|
| **`timeout` 默认只有 12 秒** | `setTimeout(15000)` 的脚本永远拿不到输出 | 显式写 `timeout=N`（封顶 180） |
| `Unable to save SELinux policy ... Out of memory` | 看着像失败 | **无害警告**；首次真失败是内存不足（free 512MB → 清理后 1384MB 才成） |
| `resolve_pid` 遍历 /proc **6.97 秒** | 抢不到启动窗口 | 别抢窗口，去读内存 |

### 10.4 frida 17 的 Java wrapper

Java 对象显示成 `[object Object]`。判「有没有数据」必须：
```js
Java.cast(v, Java.use('java.util.Map')).size()
```
