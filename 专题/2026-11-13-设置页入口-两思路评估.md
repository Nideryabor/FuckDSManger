## 一、思路① 为什么历史上失败（你 11-07 的记录）

`FdmEntry.java:139` 原文：

```
「检查更新 / 复制 / 删除对话 / 重新生成」四个功能共用 pg7 的 e=22/23。
`e` 只是 R8 合并后的 switch 索引，不承载任何语义。
⇒ 没有任何可靠的运行时判据能区分这四件事。
```

你当时留的话：

```

   「在宿主自己的 onClick lambda 里注入」，而不是拦协程 resume。
```

**这个判断是对的** —— 但今天我发现了一个**更靠上游、且语义唯一**的落点。

## 二、★ 新判据：挂在「结果字符串」上，而不是 switch 索引

### 2.1 关键发现

「当前已是最新版本」这个字符串，全树**只有一个地方**取它：

| | 2.7.5 | 2.8.0 |
|---|---|---|
| 引用类 | **`ol2`** | **`xl2`** |
| 方法 | `j(Object)Object`（269 行） | `j(Object)Object` |
| **方法体相似度** | — | **0.935**（同一份代码） |
| 资源名 | `profile_check_for_updates_newest` | 同 |
| 资源 id | `0x7f0f0267` | **`0x7f0f0275`**（变了）|
| case 标签 | `:pswitch_73`（case **22**） | `:pswitch_6a`（case **23**）|

`ol2.x → xl2.j` 里的 case 分支就三行：
```smali
:pswitch_6a
check-cast p1, Landroid/content/Context
const p0, 0x7f0f0275
invoke-virtual {p1, p0}, Landroid/content/Context;->getString(I)Ljava/lang/String;
```

### 2.2 这为什么是干净判据

| 判据 | 语义 | 会不会误伤 |
|---|---|---|
| ~~`pg7.e ∈ {22,23}`~~ | ❌ 无（R8 switch 下标，四家共用）| **会**（四次误伤的原因）|
| ~~`ol2.j` 的 case 号~~ | 🟡 有，但 **22 → 23 会漂** | 不会，但版本一换就失效 |
| ✅ **`getString(profile_check_for_updates_newest)`** | ✅ **100% 唯一**：只有"检查更新已完成"才取这个串 | **不会**：复制/删除对话/重新生成永远不取它 |
| ✅ **`getString(profile_check_for_updates)`** | ✅ 只有"检查更新"这一行要显示标题 | 不会 |

### 2.3 新方案

```java
// hook Context.getString(int) / Resources.getString(int)
int idUpdate = res.getIdentifier("profile_check_for_updates",          "string", pkg);
int idNewest = res.getIdentifier("profile_check_for_updates_newest",   "string", pkg);

if (id == idUpdate) { p.setResult("FuckDSManger 插件"); return; }   // 改文案
if (id == idNewest) { p.setResult(""); 拉起我们的 UI; return; }      // 接结果
```

**收益**：
- **0 个 R8 名字依赖** —— 不用 `pg7`/`xl2`/`ol2`，宿主怎么改名都不怕
- **0 个 case 号依赖** —— 不用管 22 还是 23
- **语义天然唯一** —— 挂在"结果"而不是"分发的下标"
- 4 次误伤的根因（switch 下标无语义）被**从根上绕开**

**代价**：
- `getString` 是超热路径（每秒数千次）⇒ 第一句必须"比两个 int 就返回"
- `getIdentifier` 只在**安装时算一次**并缓存

## 三、⚠️ 顺带发现两个真实问题

### 3.1 资源 id 会漂移（`写死字面量坑` 活标本）

| 资源名 | 2.7.5 | 2.8.0 |
|---|---|---|
| `profile_check_for_updates` | 0x7f0f**0266** | 0x7f0f**0274** |
| `profile_check_for_updates_newest` | 0x7f0f**0267** | 0x7f0f**0275** |
| `profile_title` | 0x7f0f0285 | 0x7f0f0293 |
| `session_batch_entry_button` | 0x7f0f02f4 | 0x7f0f0303 |
| `cancel` / `confirm` | 0x7f0f009b / 0x7f0f00cc | **不变** |

⇒ **有的不变、有的全变**（因为新增 9 个字符串插进了排序）。
⇒ **绝不能写死 id**，必须 `getIdentifier(name, "string", pkg)` 运行时解析。

### 3.2 🐛 `GmResTextHook` 现在咬到别的东西了

现役代码写死：
```
0x7f0f021f  → setResult("FuckDSManger")
0x7f0f0221  → setResult("")
0x7f0f0222  → setResult("")
```

这两个版本里的真实身份：

| id | 2.7.5 | 2.8.0 |
|---|---|---|
| `0x7f0f021f` | `missing_pow_header_toast` | **`message_think_duration`** ← 「思考时长」 |
| `0x7f0f0221` | （不存在）| `message_thinking` |
| `0x7f0f0222` | `mobile_verification_account_exist_toast` | `message_tool_find_wip` |

⇒ 如果 `GmResTextHook` 还活着，**「思考时长」那个文案会被显示成 `FuckDSManger`**。
⇒ 建议：这个类整体退役，或改成按**资源名**（而不是 id）匹配。

## 四、思路② 为什么贵

### 4.1 设置页结构（2.8.0 实测）

```
SettingsPage.kt         → gz9（主 Composable，212 行处）
                        → sz6（547 / 95 / 341 行处）
                        → q43（21 个 lambda：194/351/355/390/424/439/442/455/462/468/474/479/491/493/499/504/506/514/519/521/532）
                        → r43（16 个 lambda：360/362/367/372/374/378/381/385/395/408/411/415/420/427/432/538）
                        → ne（191）、ym0（397/399）、zs9（485）
```

### 4.2 三条硬门槛

1. **设置行不是数据驱动的**
   - 它没有"一个 List 塞进去就渲染"的结构
   - 每一行是**硬编码在 Composable 里**的独立调用（所以才有 `q43` 那 21 个 lambda）
   - ⇒ 没有"往数组 append 一条"的便宜路径，只能**在旁边插一段 UI 构建代码**

2. **插 UI = 改 Compose 调用链**
   - 要么 hook 某个 `Composable` 并在中间插桩（要在帧内构造 Composer/LayoutNode）
   - 要么改宿主 smali 里的布局调用序列
   - 前者撞上你的教训 **X**：「绝不在 Composable 里做反射 —— 我给 `h67` 36 个重载挂 hook 并在帧内反射 ⇒ 宿主崩溃（`ClassCastException` at `Composer.endRestartGroup`）」

3. **Composable 每帧重入**
   - 任何"重活"（反射、findClass、new 对象）都会被放大成灾难
   - 而我们的 UI 拉起逻辑偏偏就是个"重活"

### 4.3 结论

思路②如果要做，本质上是"**在宿主的 Compose 树里塞一个我们自己的节点**" ——
这需要改宿主 smali 的布局调用，而不是 hook。而改宿主布局 = 版本一换就得重做。

## 五、建议的实施方案（思路①）

### 阶段 1：文案（不带任何 R8 依赖）

```
新增 GmGetStringHook
  hook: Resources.getString(int) / Context.getString(int)
  逻辑:
    int idUpdate = getIdentifier("profile_check_for_updates", "string", pkg)  // 装时算一次

```

### 阶段 2：接点击

```
同一个 hook 里:
    int idNewest = getIdentifier("profile_check_for_updates_newest", "string", pkg)
    if (id == idNewest) {
        setResult("");                 // 把「当前已是最新版本」吞成空
        FdmUiHook.launchWithFallback(ctx, ...);   // 复用现役逻辑
    }
```

**注意**：这个时机是"宿主检查更新**已完成**"，用户点完要等网络往返。
如果嫌慢，可以**在阶段 2 加一条**：同时挂 `ol2/xl2` 的 `j()` 方法，
用 `this.a` 的 case 号**动态探针**（第一次运行时打日志确认是 23），
再回到"按 case 号拦"——这就是"在宿主自己的 onClick lambda 里注入"。

但**阶段 1+2 已经能达到目的且零版本依赖**，建议先做这个。

# 附录 A：宿主是不是「单 Activity + 无显式 Compose 页面」？（2026-11-13 实测）

> 结论：**是单 Activity；而且没有任何「显式页面入口」**。
> ⇒ 想从宿主界面进我们的 UI，**只能 hook**，没有第二条路。

## A.1 Manifest 里能对外开放的组件（2.8.0）

| kind | 组件 | exported | 备注 |
|---|---|---|---|
| activity | **`com.deepseek.chat.MainActivity`** | **true** | singleTask(2)，**唯一业务 Activity** |
| activity | `ShareProxyActivity` | true | 只处理 SEND/share URI |
| activity | `wxapi.WXEntryActivity` | true | 微信回调 |
| activity | `TablePreviewActivity` | 默认 false | 不对外开放 |
| service | `OpenChatTileService` | true | 快捷磁贴（只能「打开聊天」）|
| service | `CameraAskTileService` / `PictureAskTileService` | true | 磁贴 |
| receiver | `ShareResultReceiver` | true | 分享结果 |
| provider | `AppFileProvider` | false | — |

⇒ **业务页面只有 MainActivity 一个**，其余都是「功能型」组件。

## A.2 MainActivity 接受的 deep link（全部，就这 3 个）

| scheme | host | pathPrefix | 用途 |
|---|---|---|---|
| `com.deepseek.chat` | `authorized_android` | — | 微信登录回调 |
| `dpsk` | `chat` | `/new` | 新建对话 |
| `dpsk` | `chat` | `/share` | 分享 |

**没有 `settings` / `profile` / `me` 之类的页面 deep link。**

## A.3 MainActivity 接受的 Intent extras（全部）

```
com.deepseek.chat.extra.WECHAT_ENTRY_PAYLOAD
authorized_android / code / nonce        ← 微信登录
android.intent.action.VIEW               ← 上面的 deep link
android.intent.action.SEND / SEND_MULTIPLE / PROCESS_TEXT
```

**没有任何「跳转到某页」的 extra**（比如 `navigate_to=settings`）。

## A.4 页面路由是「类型安全 Navigation」，无字符串路由

```
androidx.navigationevent_navigationevent.version   ← Navigation 2.8+ 的新 API
NavHost 相关巨型类：h37 (25,525 行) / t27 (19,715 行) / u27 (8,182 行)
```

全树扫「斜杠式路由字符串」的结果**只有 MIME 类型**（`image/png`、`application/json`…），
**没有任何页面 route 字符串**。

⇒ 路由是 `@Serializable` 对象（Kotlin Serialization）做 destination，
**外部进程无法构造、也无法指定**。

## A.5 ⇒ 对「设置页入口」的影响

| 想法 | 可行性 |
|---|---|
| 用 `am start` 直接打开设置页 | ❌ 没有对应 Activity / deep link |
| 用 deep link 跳设置页 | ❌ 只有 chat/new、chat/share |
| 用 Intent extra 指定页面 | ❌ 没有这个参数 |
| 改 Manifest 加一个我们的 Activity 代理 | 🟡 需重打包宿主 ⇒ **违反铁律** |
| **hook 设置行 + 改文案**（思路①）| ✅ **唯一干净的路** |

⇒ **附录 A 的结论反过来支持思路①**：既然没有显式入口，
那 `GmRemap` + `getString` 按资源名匹配那条路，就是成本最低、最不侵入的选择。
