## 二、初始化调用链（谁调 create）

```
Loy9;->a(Loy9;Lrgb;Lam8;)V          ← 静态方法，协程体
   ① 读下发配置里的 sm_sdk_host（空则用兜底）
   ② new SmOption() + setOrganization/PublicKey/AppId/NotCollect/Url/ConfUrl
   ③ new Lly9(lam8) → registerServerIdCallback(IServerSmidCallback)
   ④ 从 Compose CompositionLocal 里取 Context
   ⑤ SmAntiFraud.create(context, option)     ← ★ 唯一调用点
      return-void                             ← ★ 返回值被【完全忽略】
```

### 2.1 `create()` 返回值被忽略 —— 这是关键

```smali
invoke-static {p0, p1}, Lcom/ishumei/smantifraud/SmAntiFraud;->create(...)Z
return-void                        ← 没有 move-result、没有 if、没有任何判断
```

⇒ **让它返回 false，宿主完全不知道**。

### 2.2 但 `getDeviceId()` 会露馅

```java
static String getDeviceId() {
    synchronized (SmAntiFraud.class) {
        if (l11l11l111Il.l111l1111l1Il)  return "D";          // destroyed 标记
        String cached = l1l11l1I1Il.l111l11111I1l;
        if (TextUtils.isEmpty(cached))
            return l111l11I1IIIl->l111l11111Il();              // 正常：现算
        // ★ 缓存非空 = 疑似被篡改
        Log.e("Smlog", cached);
        throw new IllegalAccessException(cached);
    }
    // catch: → "D" + base64(异常描述)
}
```

**结论**：`create` 失败 ⇒ `getDeviceId()` 返回 **`"D"` + base64(异常信息)** 这种畸形串
⇒ 服务端一眼看出「这设备指纹不正常」⇒ **这就是痕迹**。

## 三、行为探针实测（`tools/frida/probes/shumei1.js`）

### 3.1 探针能做什么

| # | 抓什么 | 手段 |
|---|---|---|
| ① | syscall 号 + 路径/端口 | hook `libc.syscall`，只看 `returnAddress` 落在 `libsmsdk.so` 内的 |
| ② | 扫了哪些目录 | hook `opendir` + `readdir`（读 `dirent.d_name` @ offset 19）|
| ③ | 执行了哪些 shell | hook `popen` |
| ④ | 读了哪些系统属性 | hook `__system_property_get`（读输出缓冲）|
| ⑤ | 探了哪些端口 | hook `socket` |
| ⑥ | 9 个 JNI fnPtr 谁被调 | 按静态地址 `0xa07c`…`0xa764` 下钩 |

### 3.2 首次实测结果（job `shumei-102129`）

```
[shu] hook syscall @ 0x723457d170        ✓
[shu] hook opendir @ 0x7234559a88        ✓
[shu] hook popen @ 0x723457a1f4          ✓
[shu] hook __system_property_get @ ...   ✓
[shu] hook socket @ 0x7234555c34         ✓
[shu] ✗ libsmsdk.so 还没加载      × 24 次（12 秒）
note=rc=137                              ← 进程被杀
```

**结论 1**：`libsmsdk.so` **在本轮 attach 期间从未加载** ⇒ 数美是**懒加载**，只在特定动作触发。

**结论 2**：`rc=137`（SIGKILL）⇒ attach 期间进程被杀，**下次要注意**（可能是探针太重 / 或宿主自己重启）。

**结论 3**：验证了 `cat /proc/<pid>/maps | grep smsdk` = **0 条** ⇒ 确认没加载。

## 四、三条路线的权衡（给决策用）

| # | 方案 | 做法 | 痕迹 | 可行性 |
|---|---|---|---|---|
| **A** | **让 `create()` 失败** | hook `SmAntiFraud.create` → `setResult(false)` | ❌ **大**：`getDeviceId()` 返回 `"D"+base64(异常)`，服务端一眼看穿；且 `Log.e("Smlog","smsdk init exception!")` 刷日志 | 简单 |
| **B** | **堵上报端口** | 改 `sm_sdk_host` → 黑洞（`127.0.0.1` / 无效域名） | ⚠️ 中：smid 正常算出来（本地），但**从不回传** ⇒ 服务端看到「设备指纹从未上报」 | 简单（用现有 pin 机制）|
| **C** | **假服务端** | 改 `sm_sdk_host` → 我们自己的服务器，返回"通过"响应 | ✅ **最小**：服务端以为正常上报 | ⚠️ 难：响应是 AES（用上面那个 publicKey）加密的，要模拟 |
| **D** | **改 JNINativeMethod 表** | native 层把 9 个 fnPtr 换成我们的 | ✅ 小 | ⚠️ 难：要注入 native 代码（mprotect `.data.rel.ro` @ `0xc6ec8`）|
| **E** | **让它扫到干净数据** | hook `opendir`/`readdir`/`popen`/`syscall` 返回净化后的结果 | ✅ 小 | ⚠️ 中：hook 点被扫到（`/proc/self/maps` 出现 frida 段）|

### 推荐组合（按优先级）

```
① 先用 B 快速验证：改 sm_sdk_host → 127.0.0.1:1（必失败）
   看服务端是否因此拒绝/降权（如果没事，B 就够用）
② 若服务端因此判风险 ⇒ 上 C（假服务端）
   需要先解出 v4/protocol 的响应格式（用上面 publicKey 对应的私钥？不可能）
   ⇒ 更现实：直接返回历史抓到的**真实成功响应**（重放），但要处理 nonce/时效
③ 真正彻底：D（native 改表）
```
