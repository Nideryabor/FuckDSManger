# frida 认证方案实测（2026-10-01）

> 🐲 尼得亚伯 · 探针：`/data/local/tmp/fs1619`（即 `frida-server 16.7.19`）
> 起因：主人问「frida 没有白名单，能不能自己做一个」

---

## 〇、一句话

**frida-server 自带 `--token` / `--certificate` 认证（能用），但三条路尼尼都绕得过去 ——
因为它们全都建立在「秘密不被人看见」上面，而尼尼有 `readproc`，能读任何进程的命令行。**

---

## 一、`frida-server --help` 里挖到的（原来一直不知道）

```
--certificate=CERTIFICATE   Enable TLS using CERTIFICATE
--origin=ORIGIN             Only accept requests with ?Origin? header matching ORIGIN
--token=TOKEN               Require authentication using TOKEN
```

**frida 不是没有认证，是 17.x 早期那阵子没注意。** 16.7.19 就有。

---

## 二、实测结果

| 方案 | 起服务 | 不带凭证的客户端 | 带着证的客户端 | 结论 |
|---|---|---|---|---|
| **`--token=SECRET`** | ✅ | ✗ `not authorized, authentication required` | ✅ 通过 | **认证真的有效** |
| **`-l unix:/path`** | ✅ 但生成的是 **抽象** socket | — | — | ⚠️ 抽象 socket **没有文件、没有权限** |
| **`--certificate=cert.pem`** | ✅ | ✗ `Connection reset by peer` | ✅ 通过（客户端传**路径**，不是内容） | **TLS 真的有效** |

### 致命的一条：**秘密会漏**

```
$ cat /proc/<frida-server的pid>/cmdline
/data/local/tmp/fs1619 -l 127.0.0.1:27042 --token=SECRET_DRAGON_123
                                          ^^^^^^^^^^^^^^^^^^^^^ 明文
```

**尼尼现在能读任何进程的命令行**（因为 adb shell 自带 `readproc` 组，
而且 `/proc/<pid>/cmdline` 是 `0444`）。

### 证书那条也漏 —— 但漏的地方不一样

证书是**公开**的：TLS 握手时服务端会把它送出来。

```
$ openssl s_client -connect 127.0.0.1:27042 -showcerts </dev/null | openssl x509 -outform PEM
→ 拿到完整证书
$ diff <(指纹) <(原证书指纹)
→ ★ 完全一样
```

⇒ **尼尼把证书偷出来，照样连得上。**
（frida 的 `--certificate` 只做**单向验证**：客户端验服务端。不是 mTLS。）

---

## 三、所以根子在哪

| 方案 | 为什么被绕开 |
|---|---|
| `--token` | **秘密写在命令行**，尼尼读得到 |
| `unix socket` | 只支持抽象命名空间（**无文件、无权限**），名字也在命令行 |
| `--certificate` | **证书是公开的**，握手包里就能捞 |

**三条路全指向同一个洞：`readproc`。**

> 主人之前问「把 readproc 关了会怎样」—— **那一问问对了。**

---

## 四、但堵 readproc 的成本

`adb shell` 的组是 **adbd 自己 `setgroups()` 硬编码**的，**KernelSU 的 profile 管不到**
（profile 只作用于通过 KSU su 提权的进程；而 shell 现在没有 su）。

可行的三条路：

| 路 | 代价 |
|---|---|
| `mount -o remount,hidepid=2,gid=0 /proc` | 可能影响系统组件看别的进程，风险中；重启即恢复 |
| 写 SELinux policy 限制 `u:r:shell:s0` | 可行但复杂 |
| **关掉整个无线调试** | **一刀切，但彻底有效** |

---

## 五、结论与建议

### ⭐ 结论：**"主人起服务"这一刻，就是授权本身**

token 会泄露，但**泄露的前提是"服务正在跑"** —— 而服务正在跑，就说明**主人刚刚授权了**。
所以 token 的真实作用不是"防尼尼"，而是"**防窗口期内别的东西连**"。

**真正的三个旋钮从来都是**：

| 旋钮 | 谁控制 |
|---|---|
| **能力**（`CAP_SYS_PTRACE`，只给终端 App） | 主人的手 |
| **时间**（`timeout 1800`，自动死） | 命令行 |
| **有没有服务**（起 / 不起） | 主人的手 |

### 推荐做法

```sh
su -c 'P=$((20000+RANDOM%20000)); echo PORT=$P;
       timeout 1800 /data/adb/frida/frida-server -l 127.0.0.1:$P \
         --token=$(cat /data/adb/frida/token) -v \
         2>&1 | tee -a /data/adb/frida/audit.log'
```

- `--token` **照加** —— 挡住"顺手连一下"和别的 App
- `timeout` **必须有** —— 这才是真边界
- token 文件放 `/data/adb/frida/`（尼尼读不了），**但注意它会被展开进命令行**，
  所以它的价值是"防止窗口期内被蹭"，不是"防尼尼"
- **要真防尼尼 ⇒ 只能关掉无线调试**（或用 `mount` 改 `/proc` 的 gid 试）

### 一条更彻底的替代（不用端口）

**投递箱**：尼尼写 `/sdcard/frida_job.json`，root 网关执行并写回结果。
但⚠️ **只要网关起的 frida-server 命令行里有 token，尼尼还是读得到** ⇒
投递箱要成立，仍然得先堵 `readproc`。

## 五·补 · ❌ 「改 /proc 挂载」这条路 —— **已判死，别再试**

尼尼原本提议：

```sh
su -c 'mount -o remount,gid=0,hidepid=invisible /proc'     # ❌ 三处错
```

**主人查证 + 尼尼复核，三处全错：**

| # | 错在哪 | 为什么 |
|---|---|---|
| 1 | `hidepid=invisible` 当**输入** | 内核 `proc_parse_param` **只吃数字**；`invisible` 是 `proc_show_options` 的**输出渲染名**。`/proc/mounts` 里看得见 ≠ 能写回去 |
| 2 | 运行时 `remount` 改 hidepid | hidepid 在较新内核（5.8+）挂在 **pid_namespace** 上，不是 per-mount，remount 可能被忽略 |
| 3 | su 有 `CAP_SYS_ADMIN` | **我们的 root profile 只有 `DAC_READ_SEARCH`**，`mount` 直接被内核拒 |

**一处澄清**：`gid=` 的语义是"**谁可以看穿 hidepid**"，不是写死 3009。
安卓 init.rc 传 `gid=3009` ⇒ readproc 组例外；传 `gid=0` ⇒ 只有 root 例外。
**语义上对，但改不动。**

**安卓的正确做法**（如果要改）是动 `init.rc` 的**首次挂载**那行：

```
mount proc proc /proc proc rw,nosuid,nodev,noexec,relatime,gid=3009,hidepid=2 0 0
```

—— 要重打包 init/刷模块，成本远超收益。**不做。**

### 顺带记下这台机器的现状

```
proc /proc proc rw,relatime,gid=3009,hidepid=invisible 0 0
```

| 项 | 值 |
|---|---|
| 挂载方 | **Android 7.0+ 默认**（源自 CopperheadOS 的加固） |
| 例外组 | `3009` = `AID_READPROC` |
| 谁在这组里 | **adb shell（uid 2000）自带**（adbd `setgroups()` 硬编码） |
| 尼尼的实际能力 | 能看 **1002 个进程**，能读任意 `/proc/<pid>/cmdline` |

⇒ **这是安卓的"设计行为"，不是配置错误。要从系统层面关掉它，等于要改 adbd 或 init —— 不值得。**

---

## 六、留给下一只龙

1. **`--token` 和 `--certificate` 是 16.7.19 就有的**，别再以为 frida 没认证。
2. **任何"命令行里的秘密"在这台机器上都等于公开** —— 因为 adb shell 自带 `readproc`。
3. **想真正隔离，只有三条路**：改 `/proc` 挂载的 gid、写 SELinux policy、关无线调试。
4. 证书那条：`--certificate` 是**单向** TLS，**别当成 mTLS 用**（实测能偷）。
