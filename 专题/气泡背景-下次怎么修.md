## ★ 核心原则：一次只改一处

我上一轮连续三版（3.73.10/11/12）都同时改好几处，
**根本分不清是哪处弄崩的** ⇒ 只能全部回滚。这次必须一次一处。

---

## 方案 B（推荐，风险最低）：只改 `args[1]`，不碰返回值

既然 `x98.t(mod, color, shape)` 的**第 2 参就是颜色**，
在 `beforeHookedMethod` 里直接改 `args[1]` 即可：

```smali
# 位置：GmBubblePaintHook.ub()，作用域判断通过之后
const/4 v2, 0x1
aget-object v3, v0, v2            # args[1] = Long(颜色)
# → 换成 GmBubble.uColorLong() 包装后的 Long
invoke-static {}, Lcom/nidyaber/fuckdsmanger/gm/GmBubble;->uColorLong()J
move-result-wide v4
invoke-static {v4, v5}, Ljava/lang/Long;->valueOf(J)Ljava/lang/Long;
move-result-object v3
const/4 v2, 0x1
aput-object v3, v0, v2            # 写回 args[1]
invoke-virtual {p0, v3}, XC_MethodHook$MethodHookParam;->setResult(...)  # ✗ 不需要！
```

**为什么这条路最安全**：

| 风险点 | 方案 A（换 Modifier） | 方案 B（改颜色） |
|---|---|---|
| 返回 null ⇒ 宿主 NPE（事故 #4） | ✗ 会发生 | ✅ 不可能（不改返回值） |
| 新 Modifier 语义不对 ⇒ 盖不住（"被 v24 打回来"） | ✗ 会发生 | ✅ 不产生新对象 |
| 需要 GmPrims 按签名找原语 | ✗ 需要 | ✅ **完全不需要** |
| 改错影响范围 | 整条 Modifier 链 | 只有一个颜色值 |

## 但前置条件：`ub()` 的门必须能进来

现状（3.73.13）：`ub()` 的 `caller().startsWith(wb0.e)` 恒假 ⇒ 里面什么都不执行。

### 第一步改动（**只改这一处**）

```smali
# 位置：GmBubblePaintHook.ub()，替换 caller 门
# 原：
invoke-static {} GmUtil->caller() : String
move-result-object v2
invoke-static {} GmBubblePaintHook->uCaller() : String
move-result-object v3
invoke-virtual {v2, v3} String->startsWith(String)Z
move-result v2
if-eqz v2, :cond_a3

# 新：
sget v2, Lcom/nidyaber/fuckdsmanger/gm/GmBubble;->sUBub:I
if-lez v2, :cond_ub_ok          # sUBub > 0 ⇒ 用户气泡 lambda 里
sget v2, Lcom/nidyaber/fuckdsmanger/gm/GmBubble;->sUDepth:I
if-gtz v2, :cond_a3             # sUDepth <= 0 ⇒ 两个都不是 ⇒ 跳过
:cond_ub_ok
```

**改完立刻验**：装机 → 滑一下 → 日志里应该出现
```
[DIAG] ubMod 进来了
```
或（如果走方案 B）`[气泡] 用户气泡 颜色已换`。

**如果 `ubMod 进来了` 还是不出现** ⇒ 说明 `ub()` 更早的地方就返回了，
加一行无条件日志确认卡在哪个门槛（`uOn()` / `isColorVer` / `args.len`）。

### 第二步改动（确认门通了之后）

按方案 B 改 `args[1]`。**这一处改完就该能看到效果**。

## 🚨 绝对不要做的

| 禁令 | 原因 |
|---|---|
| ❌ 在 `catch` 处理器里用 `try` 区内的局部变量 | ⇒ `VerifyError` ⇒ 整个类不加载（事故 #2） |
| ❌ 手写 `invoke-*` 不核对寄存器个数 | ⇒ `VerifyError` ⇒ 整个类不加载（事故 #3） |
| ❌ 改动"失败路径"后不检查返回值 | ⇒ 返回 null ⇒ 宿主 NPE（事故 #4） |
| ❌ 一次改多处 | 分不清哪处崩的（事故 1/4/5 全都因为这个） |
| ❌ 在 `wrap()` 里塞 background | `wrap` 处理的 `y6a` 是 layout 元素，不是背景 |

### 已知的坑

| 坑 | 表现 | 解 |
|---|---|---|
| `const/16` 小数值被判成资源 id | 出包自检 ④ 报 `0x7e680000` | 用 `const/4`（只能 -8..7）；或确认是 `call_site_ids` 数据区的误报（`find_res_ids` 是字节级扫描） |
| 底座/树同步检查误报 | `⓪ 同步检查` 报"1 个方法体不同" | 加 `ALLOW_STALE_BASE=1`（前提：已确认底座里真的有你的改动） |
| `重建底座` 与 `做包` 并行 | 互相踩，包是旧的 | **严格串行**，别放在同一个 tool block 里 |

## 如果方案 B 也失败

那就说明 `x98.t` 改了 `args[1]` 也不生效（可能宿主内部又覆盖了）。
下一步：**hook `x98.t` 的 `afterHookedMethod`，读 `getResult()` 看看宿主实际用了什么颜色** —— 这是"宿主打回来"假设的直接验证。

再不行就考虑完全另一条路：
- `drawBehind` / `drawWithContent`（自己画，不碰颜色）
- 或者承认"用户气泡背景在 2.7.2 不可改"，把开关隐藏掉
