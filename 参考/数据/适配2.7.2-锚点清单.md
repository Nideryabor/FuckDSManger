## 八、★「包名检测（查 data/app）」定案

> 主人情报：「这次的新版本有了包名检测（查 data/app）」。**挖到底了，结论如下。**

### 8.1 它是什么（完整还原）

调用链：

```
l111l1111llIl;->l1111l111111Il(l11l11IIII1l, Set, l11l1111lIIl, …, int, …)   ← 总采集器
  └ 键名 "xpApp"（老键 "a102"）
  └ if (!notCollect.contains("xpApp") && !notCollect.contains("a102"))
        l1111l111111Il;->l111l1111llIl()Ljava/util/List;
        l11l1111lIIl;->l111l1111lIl(List)        ← 塞进上报包
```

`l111l1111llIl()` 逐字还原：

```java
List<String> out = new ArrayList<>();
Set<String> seen = new HashSet<>();
Context ctx = l11l11l111Il.ctx;
if (ctx == null) return out;
BufferedReader r = new BufferedReader(new FileReader("/proc/self/maps"));
while ((line = r.readLine()) != null) {
    int i = line.indexOf("/data/app/");
    if (i == -1) continue;
    int j = line.indexOf("-", i);              // 有的是 ".../base.apk-0x..."
    if (j == -1) j = line.indexOf("/", i + 10);
    String pkg = line.substring(i + 10, j);     // ← 抠出目录名（= 包名）
    if (pkg.equals(ctx.getPackageName())) continue;   // 跳过自己
    seen.add(pkg);
}
// ↓ 关键：不是「拼包名就上报」，而是去查这个包的 meta-data
for (String pkg : seen) {
    ApplicationInfo ai = pm.getApplicationInfo(pkg, 0x80 /*GET_META_DATA*/);
    Bundle md = ai.metaData;
    if (md == null) continue;
    Object m  = md.get("xposedmodule");        // ★★ 判据
    Object mv = md.get("xposedminversion");
    Object d  = md.get("xposeddescription");
    if (m == null) continue;                   // 没有 xposedmodule ⇒ 放过
    String label = (Build.VERSION.SDK_INT >= 29) ? "" : ai.loadLabel(pm).toString();
    out.add(TextUtils.join(",", new Object[]{ pkg, label, m, mv, d }));
}
```

**它报出去的是逗号五元组**：`包名,应用名,xposedmodule,xposedminversion,xposeddescription`

⇒ **我们一被扫到，报上去的就是 `com.little_femaleboy.cannot_show.the_big_won_whale,FuckDSManger NL,true,82,FuckDSManger …`**
（我们 `pipeline/build_single.py` 第 142~144 行就是写这三个 meta-data 的）

### 8.3 真问题：它到底打不打得到我们？——**未证**

链条上唯一不确定的一环是：**我们的 `base.apk` 路径会不会出现在宿主进程的 `/proc/self/maps` 里。**

| 情形 | 会不会中 |
|---|---|
| LSPosed 把模块 dex 以 `InMemoryDexClassLoader` 注入、**不 map 模块 apk** | ✅ 不中 |
| 模块 apk 被 map（哪怕只为 `nativeLibraryDirectories`） | 🔴 **中，且带名字** |

已知线索（我们自己进程的日志）：
```
DexPathList[[dex file "InMemoryDexFile[cookie=[…]]"],
            nativeLibraryDirectories=[/data/app/~~c1UY…/com.little_femaleboy…/base.apk!/lib/arm64-v8a, …]]
```
⇒ **dex 是内存里的，但 `nativeLibraryDirectories` 指向了 apk 内的 `!/lib/`** —— 这种路径在某些 ROM 上会以
`/data/app/…/base.apk` 形式出现在 maps 里。**所以这条必须实测，不能靠推理。**

**实测被卡住**：`adb shell` 读宿主 `/proc/<pid>/maps` → `Permission denied`；
`ro.sh`（su）→ `su: inaccessible or not found`（SUSFS 藏的）；
`run-as com.termux` → `package not debuggable`（主人给它关了调试）。
⇒ **三条路都断了**，需要一个**在宿主进程内**的观测点（frida 或加一行诊断日志）。

### 8.4 建议的处置

| 优先 | 动作 | 说明 |
|---|---|---|
| ① | **先测**：frida 挂宿主，跑 `cat /proc/self/maps \| grep -c little_femaleboy` | 不动产物、最快出答案 |
| ② | 若命中 ⇒ **hook `BufferedReader.readLine`** 只过滤 `/data/app/` 行（方案 D） | 一行过滤，比改检测类更稳（不碰数美类名，R8 重排无关） |
| ③ | 或 **`xpApp` 列入 notCollect** / 让 `l111l1111lIl(List)` 收空表 | 需知 `notCollect` 来源（远端下发） |
| ④ | **降级方案**：把 `xposedmodule` meta-data 的 value 从 `true` 改成别的 | 判据是 `get()!=null` **不是** `==true` ⇒ **没用**，别浪费 |

> ★ 教训：**判据是「键存在」不是「值为 true」**。想靠改 value 蒙过去是空的。
