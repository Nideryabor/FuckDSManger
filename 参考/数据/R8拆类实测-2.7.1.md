# R8 「拆类 / 合并类」实测报告 · 宿主 2.6.2 → 2.7.1

> 记于 2026-10-24 · 尼得亚伯 🐲 · 纯静态实测数据
> 树：`tmp/h262`（15559 类）· `tmp/h271`（15216 类）

---

## 〇、一句话

**2.7.1 这轮 R8 同时做了「拆」和「合」两件事，而且都是按「调用域」重组的。**
一个 51 方法的旧类，在新版里散成 3 个类、共 175 个方法（**3.4 倍膨胀**）；
反过来两个旧类（48+62=110 方法）被合成一个 68 方法的类。

---

## 一、拆分类的实测数据

| 旧类（2.6.2）| 方法数 | 新类（2.7.1）| 方法数 | 膨胀比 |
|---|---|---|---|---|
| `us6`（Modifier 扩展桶）| **51** | `p68` + `dz7` + `r0b` | 52 + 61 + 62 = **175** | **3.4×** |
| `jtb`（气泡/对话框 Composable）| **96** | `szb` + `x4c` + `fxb` | 53 + 104 + 62 = **219** | **2.3×** |
| `e3c`（Modifier.paint）| **62** | `kmc`（**合并**了 `pic`）| **68**（`pic`48+`e3c`62=110 里的 68）| — |
| `qn7`（ChatPage 作用域）| 48 | `jr7` | 55 | 1.1×（稳定）|
| `by4`（Composer）| 73 | `n05` | 72 | 0.99×（稳定）|
| `kh2`（会话接口）| 66 | `oj2` | 68 | 1.03×（稳定）|

> ⭐ **关键**：`us6` 和 `jtb` 是**「合并出来的大杂烩」被重新切开**；
> `qn7`/`by4`/`kh2` 这类**语义单一的类**几乎不动（±2）。
> ⇒ **膨胀的只有大杂烩，不是所有类**。

## 二、拆的依据：按「调用域」重组

`us6`（51 方法）拆出来的三个碎片，各自覆盖的 SourceInfo 域：

| 碎片 | 覆盖的 `.kt` 文件域 | 典型域 |
|---|---|---|
| `dz7` | **36 / 36**（全覆盖）| `AppTabRow` / `FullScreenImage` / `ZoomableAsyncImage` / `DragHandle` / `ComponentModifiers` |
| `p68` | **31 / 36** | `AccountDeletionPage` / `UserChatMessageBubble` / `ChatInputAddActionButton` / `ChatWelcomeLogo` |
| `r0b` | **14 / 36** | `PagerSemantics` / `LazyLayoutPager` / `PagerMeasurePolicy` |

`jtb`（96 方法）拆出来的三个碎片：

| 碎片 | 典型域 |
|---|---|
| `szb` | `ChatMessageCell` / `MessageSelectableModifier` / `ConfirmClearSessionDialog` / `DeleteSessionConfirmDialog` |
| `x4c` | `AppBanner` / `CallSettingsBottomSheet`（整族）/ `MarkdownCodeBlockHeader` / `InputModeToggleButton` / `AsrLanguageSettingItem` |
| `fxb` | `AppAlertDialogV2` / `MarkdownCodeBlockContent` / `AgeVerificationScreen` / `ChatInputToggleableToolView` / `ChatSessionList` / `CallRatingBanner` |

> 💡 **结论：拆分不是「按方法平均分三份」，而是「按业务域聚簇」。**
> 而且 `dz7` 覆盖 36/36 个域 —— 说明**同一个 SourceInfo 串会在多个碎片里出现**
> （Compose 函数的 inline/lambda 被复制），所以**不能靠「某个串在哪个类」来判断全部方法归属**。

## 三、合并类：`e3c` + `pic` → `kmc`

| 2.6.2 | 内容 | 2.7.1 |
|---|---|---|
| `e3c`（62 方法）| `Modifier.paint`（`a0(Lgc7;Ll18;Lca;Lc83;FLon0;I)Lgc7;`）+ 大量 Compose 工具 | → **`kmc`**（68 方法）|
| `pic`（48 方法）| `AppButton` / `AppFullWidthButton` / `AppButtonDefaults` | → **`kmc`**（同一类）|
| 合计 110 | | **68**（R8 又剪掉了 42 个）|

**证据**：
- `kmc` 里有 **6 处 `AppButton.kt` 串**（2.6.2 的 `e3c` 里 **0 处**）
- `kmc` 的域列表同时含 `AppButton.kt` / `AssistantChatMessageIncompleteView.kt` / `CallTransitionLayout.kt` / `FluidBlobStaticFrame.kt` / `Crossfade.kt`
- `kmc.e0` = 2.6.2 的 `e3c.a0`（六类型逐位唯一命中）
- `kmc.b/c/d` = 2.6.2 的 `pic.b/c/d`（13 条按钮锚点里的 #1~#3）

## 四、对 hook 的实际影响（清单）

| # | 影响 | 表现 | 判据 / 处置 |
|---|---|---|---|
| **1** | ⭐⭐⭐ **`hookAllMethods` 只挂到 1/N** | 原来 `hookAllMethods("us6","*")` 一次全覆盖；现在挂 `p68` 只覆盖 52/175 | **不会报错、count 也不为 0** ⇒ 必须**多类遍历挂** + 每类单独打 count |
| **2** | ⭐⭐⭐ **`findClass` 拿到的类「变了但名字像」** | `a6` 名字还在，但已是 `r(Object,Object)Object` | 类级映射值必须**允许数组**；`cls()` 返回 `String[]` |
| **3** | ⭐⭐ **方法名跨碎片不连续** | `us6.y→p68.B`、`us6.z→p68.C` 但 `us6.t→dz7.t`、`us6.s→r0b.q` | `MTH` 表必须**同时记「新类名」**，不能只记方法名 |
| **4** | ⭐⭐ **注释/代码不一致会被放大** | `GmGlassSink` 注释说挂 `qk7.C`（4参），代码挂 `us6.z`（3参）| 拆类后两个原语可能落在不同碎片 ⇒ 两处都要显式改 |
| **5** | ⭐ **diff 会爆炸** | 51 方法 → 175 方法，逐个 diff 无意义 | 验收不能靠「全量 diff」，只能靠**逐条锚点回读** |

## 五、工程建议（写进 `GmRemap`）

```java
// 允许一个旧名映射到多个新类（拆类），按顺序尝试
private static final String[][] CLS = {
    //  {2.5.2, 2.6.1, 2.6.2, 2.7.1}
    {"uia", "qk7", "us6", "p68,dz7,r0b"},   // ★ 拆成 3 个
    {"pn9", "i93", "jtb", "szb,x4c,fxb"},   // ★ 拆成 3 个
    {"fh6", "w2b", "e3c", "kmc"},           // ★ 合并了 pic
    ...
};

/** 返回数组：findAll 型钩子遍历挂，findClass 型取第一个命中的 */
public static String[] clsAll(String key) { ... }
```

**配套改动**：
1. `GmRemap.cls()` 保留（返回第一个）以兼容现有单类调用
2. 新增 `clsAll()` 给 `hookAllMethods` 型钩子
3. **每个 hookAll 点必须打 `类名 + count`**，否则拆类漏挂看不见
