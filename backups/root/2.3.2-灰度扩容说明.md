# 2.3.2 变更说明（2026-09-12）

## 一、修的 bug：`GmDialog.save()` 分支反向 ⭐

```smali
# 修改前（错误）
if-eqz v7, :cond_62     # v7 = (新值 == 初始值)；为 0(改了) 就跳过写入 ← 反了
# 修改后（正确）
if-nez v7, :cond_62     # 改了才继续走写/删分支
```

**影响面**：从 **1.6.1**「只写改动过的项」那次改动起，
`保存` 实际写入的是**没改动的项**，真正改过的项被跳过。
toast 依然弹「已写入覆盖」，所以长期没被发现。

修好后逻辑：
| 情况 | 行为 |
|---|---|
| 值被改动 | 写 bak（备份原值）→ 写入新值 |
| 值清空 | `remove()` 删除覆盖（bak 保留） |
| 值未变 | 跳过，不产生任何写入 |

## 三、为什么这 8 项要用「远程键」

**实证**（DeepSeek 2.4.5 `Luv1;->e()F`）：

```smali
# 1. 查内存缓存 ConcurrentHashMap h["camera_compress_ratio"]
# 2. 未命中 → MMKV: kv_remote_settings_camera_compress_ratio，默认 0.8
# 3. 再查 kv_remote_settings_id_camera_compress_ratio
```

**没有** `kv_settings_camera_compress_ratio` 这一层（全 APK 0 命中）。
所以老的「写 `kv_settings_*`」机制对它们无效，必须直接改写远程键。

## 四、实现方式

### 4.1 `addRow` 支持「全 key」

```smali
# KEYS 里的字符串若自带 "kv_" 前缀 → 原样使用；否则自动拼 "kv_settings_"
const-string v2, "kv_"
invoke-virtual {p2, v2}, Ljava/lang/String;->startsWith(Ljava/lang/String;)Z
...
:gm_add_full
    "kv_settings_" + p2
:gm_add_key
```

### 4.2 `GmStore` 新增方法

| 方法 | 作用 |
|---|---|
| `bak(ctx,key,type)` | 首次保存时把**原值**备份到 `fuckds_bak_<key>`（已是空值/已存在备份则跳过） |
| `restore(ctx,key,type)` | 有备份 → 写回原值并删备份；无备份 → `remove(key)` |

### 4.3 `GmDialog` 接线

- `save()`：写之前先 `GmStore.bak(ctx, key, type)`
- `resetAll()`（全部恢复灰度）：`remove` → `restore`，并同步取 `sTypes`

### 4.4 类型扩展

`GmStore.read2/write` 新增 `"l"`（long）：`getLong` / `Long.parseLong` + `putLong`。

## 五、残留风险

1. **服务端重新下发会覆盖** —— `kv_remote_settings_*` 是服务端设置的落地层，
   下次拉 `/api/v0/client/settings` 若包含该键，覆盖会被冲掉。
2. **需重启 App** —— `Luv1` 有 `ConcurrentHashMap` 内存缓存，改完必须重启。
3. `bak` 只在**首次**保存时记录，若先改了 A 再改 B，恢复时都回到最初值（符合预期）。
