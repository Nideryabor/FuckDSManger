# 2.5.0 —— 美化 › 修改背景（2026-09-12）

> 新增：图片 / 动态渐变背景，可开关、可调透明度。方案选型：**蒙层式**（用户选定）。

---

## 一、技术背景（为什么不能做「真·底图」）

DeepSeek 是**纯 Compose 单 Activity** 应用：

| 事实 | 证据 |
|---|---|
| 主 Activity = `com.deepseek.chat.MainActivity`（extends `Lds`） | AndroidManifest |
| 主题 `Theme.DeepSeek` 的 `android:windowBackground` 只是**启动闪屏色** `@color/splashscreenBackground` | `resource:0x7f100110` |
| 页面底色由 Compose 自己绘制 | `MainActivity.onCreate` 里 `Ly03;->a(Lds;Lxr8;)`（setContent） |
| **Compose 类被 R8 完全混淆** | 模块里 `painterResource` 的混淆名是 `Li65;` |

⇒ 给 `DecorView` 设背景会被 Compose 整个盖住。
要「真·底图」必须透明化 App 的页面底色，而 Compose 的 Theme/ColorScheme 类名已混淆，
需要额外逆向定位，**有失败风险**。

⇒ 因此本版采用 **蒙层式**：在 App 上层叠一层可调透明度的图片/渐变。

## 三、实现

### 3.1 新增类

| 类 | 作用 |
|---|---|
| `GmBg` | 数据层：`isOn/setOn`、`mode/setMode`(0=图片 1=渐变)、`alpha/setAlpha`(0~100)、`grad/setGrad`、`file/hasImage/bitmap/saveImage`、`pick/takePicking`、**`ensure()`** |
| `GmBgView` | 自定义 `View`：`onDraw` 里画图片（center-crop）或渐变；用 `SystemClock.uptimeMillis()` 算相位 + `postInvalidateOnAnimation()` **自驱动动画**（不用 ValueAnimator） |
| `GmBgSwitch` | 开关监听 |
| `GmBgDialog` | 设置界面 |

### 3.2 挂载方式

`GmBg.ensure(ctx)`：
1. 取 `GmEntry.sAct`
2. 未开启 → 把旧 view 从 DecorView 摘掉
3. 已开启 → 算签名 `mode*1000000 + grad*10000 + alpha*10 + hasImage`；
   与 `sSig` 相同且 view 已挂 → 直接返回（**避免重复重建**）
4. 否则 `removeView` 旧的 → `new GmBgView` → `addView` 到 **DecorView（FrameLayout）**，`FrameLayout.LayoutParams(-1,-1)`

调用点：
- `GmResumeHook.afterHookedMethod`（每次 onResume，覆盖重建 Activity 的情况）
- `GmBgSwitch` 开关变化时
- `GmBgDialog` 各参数变化时
- `GmPickHook` 选图成功后

**触摸穿透**：`GmBgView` 不设 clickable、不监听触摸 → `onTouchEvent` 返回 false → 事件继续传给下层 ✓
**与模块对话框不冲突**：Dialog 是独立 Window，始终在 Activity 之上 ✓

### 3.3 渐变动画原理

```
onDraw:
  phase = (uptimeMillis % 9000) / 10000.0      # 9 秒一轮
  matrix.setTranslate(-phase * width, 0)
  gradient.setLocalMatrix(matrix)
  canvas.drawRect(...)
  postInvalidateOnAnimation()                  # 下一帧继续
```

渐变色数组做成 `[c0,c1,c2,c3,c0]`、横向跨度 `2*width`，
平移一个 `width` 后首尾色相同 ⇒ **无缝循环**。

### 3.4 复用的机制

- 选图：`GmBg.pick()` 置标记 → `GmPickHook`（挂在 `Activity.onActivityResult`）识别 →
  `GmBg.saveImage()`。**GmPickHook 里先问 GmBg，再问 GmAvatar**，两者互不干扰。
- 用户偏好存储：`GmStore`（MMKV 反射桥）
- UI 风格：与其它对话框一致的 `GmUtil` 调色板 + 圆角卡片

## 七、已知限制 / 后续可优化

1. **蒙层式 = UI 会被蒙一层**。这是用户选定方案的固有代价，靠调低透明度缓解。
   若想要「真·底图」，需要把 App 的 Compose 页面底色透明化（要逆向定位混淆后的
   Compose Theme/ColorScheme 类），可作为后续独立任务。
2. 作用范围为 **MainActivity**（聊天页 / 设置页都在这一个 Activity 内）。
   其它 Activity（如图片预览）不加背景。
3. 图片未做内存限制（超大图会占用较多内存），可后续加 `inSampleSize` 降采样。
4. 渐变背景会持续 `invalidate`（约 60fps），有一定耗电；图片模式不动画、不耗电。
5. 4 套配色写死在 `GmBgView.P`，想加配色改这里即可。

## 八、2.5.1 —— 修复「没有效果」+ 真底图位置（2026-09-12）

### 8.1 用户反馈「没有效果」的真正原因：**又是反向判断** ⚠️

```smali
.method public static ensure(Landroid/content/Context;)V
    sget-object v0, ...GmEntry;->sAct:Landroid/app/Activity;
    if-nez v0, :ret        # ❌ sAct 非空 → 直接 return！
```

本意是「没有 Activity 就返回」，写成了「有 Activity 就返回」。
⇒ **`ensure()` 一次都没执行过**，背景从未被挂载。**反向判断家族第 11 次。**

修复：`if-nez` → `if-eqz`。

> 📌 这不是方案问题，是龙龙的实现 bug。教训：**写完 `if-*z` 后，用一句话把语义读出来**
> ——「如果 sAct 不为空就返回」听着就不对。

### 8.2 新增「位置」开关（走真底图）

`GmBg.pos(ctx)`：`0 = 蒙层（addView 到最后，盖在内容上）` / `1 = 底图（addView 到 index 0，在内容后面）`，**默认 1（底图）**。

```smali
invoke-static {p0}, GmBg;->pos(Context)I
move-result v8
const/4 v9, 0x1
if-ne v8, v9, :top
const/4 v8, 0x0
invoke-virtual {v6, v5, v8, v7}, Landroid/view/ViewGroup;->addView(Landroid/view/View;ILandroid/view/ViewGroup$LayoutParams;)V
goto :fin
:top
invoke-virtual {v6, v5, v7}, Landroid/view/ViewGroup;->addView(Landroid/view/View;Landroid/view/ViewGroup$LayoutParams;)V
```

对话框新增一行：`[ 蒙层（盖在上层） ] [ 底图（在内容后面） ]`（动作 `0x24` / `0x25`）。

UI 签名相应扩充为：
```

```

## 九、2.5.2 —— 修复 `GmBg.ensure` 的 NPE（连带修掉两处反向判断）

### 9.1 崩溃

```
NullPointerException: Attempt to invoke virtual method
  'android.view.ViewParent android.view.View.getParent()' on a null object reference
    at GmBg.ensure(Unknown Source:77)
    at GmBgDialog.setPosBehind
    at GmClick.onClick
```

### 9.2 根因：**同一段里两处 `if-*z` 写反**

```smali
:ni
if-nez v2, :mk          # ❌ 语义应为「v2 == null（还没挂）→ 去重建」
                        #    实际是「v2 != null 才跳走」
invoke-virtual {v2}, Landroid/view/View;->getParent()   # ← v2 为 null 时直接 NPE
...
if-nez v4, :mk          # ❌ 语义应为「getParent() == null（没挂上）→ 重建」
```

修复后：

```smali
if-eqz v2, :mk          # ✅ 未创建 → 重建
...
if-eqz v4, :mk          # ✅ 未挂载 → 重建
```

### 9.3 为什么 2.5.0 没崩、2.5.1 才崩

2.5.0 的 `ensure()` 开头 `sAct` 守卫写反 ⇒ **整个方法从不执行**，
把这两处 bug **挡在后面**了。修掉第一个后它们才露头。

> 📌 这正是第六节/第十一节记过的「**多个 bug 会互相掩盖**」：
> 修一个不见效，不一定是修错了，可能是后面还有。

### 9.4 修复后的完整守卫复核

| 位置 | 写法 | 语义 | 判定 |
|---|---|---|---|
| 开头 | `if-eqz v0, :ret` | 无 Activity → 返回 | ✅ |
| 关闭分支 | `if-eqz v2, :ret` | 无旧 view → 返回 | ✅ |
| 关闭分支 | `if-eqz v1, :clr` | 父不是 ViewGroup → 跳过 removeView | ✅（`instance-of` 对 null 返回 false，不会 NPE） |
| 重建判定 | `if-eqz v2, :mk` | 未创建 → 重建 | ✅ |
| 重建判定 | `if-eqz v4, :mk` | 未挂载 → 重建 | ✅ |
| 重建判定 | `if-eq v3, v4, :mk` | 签名变了 → 重建 | ✅ |
| 重建内 | `if-eqz v2, :newv` | 无旧 view → 跳过移除 | ✅ |
| 重建内 | `if-eqz v5, :newv` | 父不是 ViewGroup → 跳过移除 | ✅ |
| 挂载 | `if-eqz v7, :ret` | DecorView 不是 ViewGroup → 返回 | ✅ |

## 十、2.5.3 —— 真底图：把 Compose 页面底色透明化 ⭐

### 10.1 用户反馈

> 蒙层有效，但底图无效，LSPosed 无报错。

**结论**：我们的渲染完全正常 ✓，**是 App 的 Compose 页面底色不透明，把 index 0 的底图盖住了**。

### 10.2 找到混淆后的 `ColorScheme`

Compose 类被 R8 重打包，但 `ColorScheme` 是 **Kotlin data class**，
其 `toString()` 会引用字段名字符串 ⇒ 用字段名反查即可：

| 搜索串 | 命中类 |
|---|---|
| `ColorScheme(primary=` | **`Laz1;`** |
| `surfaceContainerHighest=` | **`Laz1;`** |

`Laz1;` 的结构完全印证了它是 `ColorScheme`：

- **48 个 `J`(long) 字段** —— 每个 Compose `Color` 在字节码里就是一个 `long`，
  而 Material3 1.3 的 `ColorScheme` 恰好是 **48 个颜色角色** ✓
- 构造函数 `<init>(JJJJ…×48)V`（instructionCount 91）
- `toString()` 里 48 个字段名（`primary=`、`background=`…）

### 10.3 参数索引推算

按 Material3 的声明顺序（`primary, onPrimary, primaryContainer, onPrimaryContainer,
inversePrimary, secondary, …, tertiaryContainer, onTertiaryContainer, **background**,
onBackground, **surface**, onSurface, …`）：

```
args[13] = background
args[15] = surface
```

数值上 48 个参数 / 48 个字段完全吻合 ✓

### 10.4 Compose `Color.Transparent` 的机器表示

`Color` 是 `value class Color(val value: ULong)`，`Color(0x00000000L)` 打包后就是 **`0L`**。
所以把参数换成 `Long.valueOf(0)` 即得到全透明 ✓

### 10.5 实现：`GmCsHook`

```smali
.method protected beforeHookedMethod(...)V
    args = param.args
    if (args == null) return
    if (args.length < 16) return                 # 不是 ColorScheme
    ctx = GmSync.ctx(); if (ctx == null) return
    if (!GmBg.isOn(ctx)) return                  # 背景未开 → 不动
    if (GmBg.pos(ctx) != 1) return               # 只在「底图」模式下透明化
    Long z = Long.valueOf(0L)
    args[13] = z                                 # background → 透明
    args[15] = z                                 # surface    → 透明
```

注册（在 `GmSync.ensure` 里）：
```smali
findClass("az1", cl)
XposedBridge.hookAllConstructors(cls, new GmCsHook())
```

> ⚠️ 构造函数**不能用 `hookAllMethods`**（它遍历 `getDeclaredMethods()`，不含 `<init>`），
> 必须用 `hookAllConstructors` / `findAndHookConstructor`。这条坑在第十节 10.2 记过。

### 10.6 已知限制

**切换后需重启 App**：`ColorScheme` 在组合期构造一次并缓存，
启用/关闭「底图」不会立刻重建主题 ⇒ 已把提示文案改为
「背景已开启（图片模式）— 底图模式需重启 App 生效」。

## 十一、2.5.4 —— 修选图分流（反向判断第 12 次）+ 扩大透明化范围

### 11.1 「蒙层只有渐变有效」的真因

```smali

move-result v0
```

## 十二、2.5.5 —— 换思路：用「混合模式」做真底图

### 12.1 10 项实验结论

用户：**10 项吐司弹了，但完全没有区别。**

⇒ 把 `background` + `surface` + 全部 `surfaceContainer*` 都改成透明，界面**毫无变化**
⇒ **DeepSeek 的界面根本不用 Material3 的 `ColorScheme`**（它有自己的配色系统），
`az1` 只是被某些 M3 组件顺带构造出来的。

**结论：继续在 ColorScheme 上打转没有意义。**

### 12.2 新方案：内容视图混合模式（不动 Compose）

把 **`android.R.id.content`** 的混合模式改成：

| 模式 | 条件 | 效果 |
|---|---|---|
| `MULTIPLY` | 浅色模式 | 页面白底 × 底图 = **底图显形**；黑字 × 底图 ≈ 黑字，仍可读 |
| `SCREEN` | 深色模式 | 近黑底 ⊕ 底图 = **底图显形**；白字 ⊕ 底图 = 白字，仍可读 |
| `null`(SRC_OVER) | 未开启 / 非底图 | 恢复正常，无副作用 |

实现：`GmBg.setBlend(ctx, act)`
```smali
if (SDK_INT < 29) return                     # setBlendMode 是 API 29+
view = act.findViewById(0x1020002)           # android.R.id.content
if (view == null) return
BlendMode m = null
if (isOn && pos == 1) m = isNight ? SCREEN : MULTIPLY
view.setBlendMode(m)
```

调用点：`ensure()` 的关闭分支（恢复 null）+ 挂载完成处（设置混合）。
