## 二、`switchable` 字段的逆向结论

### 2.1 位置

在 `kv_remote_settings_model_configs_v1` 的 JSON 里，**每个模型对象**都有一个布尔字段：

```json
{"model_type":"default","name":"快速模式","enabled":true, "switchable":true , ...}
{"model_type":"expert", "name":"专家模式","enabled":false,"switchable":false, ...}
{"model_type":"vision", "name":"识图模式","enabled":false,"switchable":false, ...}
```

> 来源：本机 `ds_raw.txt`（服务端下发快照）

### 2.2 含义

`switchable` = **该模型能否被切换过去**。
服务端默认只放开「快速模式」，**专家模式 / 识图模式都是 `false`** ——
所以用户在会话里切不到它们。

**→ 这正是本次新功能要改的东西。**

## 三、顺手修的第 3 批同族 bug：`GmStore.bak / restore` 反向 ×3 ⭐

新功能依赖「备份原值 → 改 → 还原」，结果一查发现**备份功能从建立起就是坏的**：

```smali
# ❌ 错（GmStore.bak）
invoke-virtual {v0}, Ljava/lang/String;->isEmpty()Z
move-result v1
if-eqz v1, :cond_31     # 非空 → 跳走（不备份）；空 → 继续往下写备份。完全反了
```

| 位置 | 后果 |
|---|---|
| `GmStore.bak()` ×2 | **备份永远存不下来** → 2.3.2 上线的「备份还原」形同虚设 |
| `GmStore.restore()` ×1 | 有备份时**不还原**，反而走 `remove(key)` 把键删掉 |

**影响面（重要）**：`GmPrompt.apply()` 与「灰度项保存」都调 `bak()`，
所以它们的「恢复默认」实际是**把整个键删掉**（回落默认值），而不是还原成原值。
2.4.2 一并修复，三处 `if-eqz` → `if-nez`。

> 📌 至此，本项目已累计发现 **9 处** `isEmpty()` 判断反向
> （1.6.1 保存 / 2.3.2 保存 / 2.4.0 弹窗 / 2.4.1 display×2 + apply×2 / 2.4.2 GmStore×3）。
> **教训升级见第四节。**

## 四、新功能：聊天 › 模型切换

### 4.1 位置

```
管理器 → 菜单页 → 「聊天」
   ├── [●] 防撤回
   ├── [●] 模型切换        ← 🆕 本次新增
   ├── 本地数据库管理 ›
   └── [返回]
```

### 4.2 交互

| 操作 | 行为 |
|---|---|
| 打开开关 | 备份原始 `model_configs` → 把所有模型的 `"switchable":false` 改成 `"switchable":true` → 写回 MMKV；toast「模型切换已启用…（重启 App 生效）」 |
| 关闭开关 | 有备份 → 还原原始 `model_configs`；无备份 → 把 `"switchable":true` 改回 `false`；toast「模型切换已禁用」 |
| 找不到模型配置 | 直接失败并提示「修改失败：未找到模型配置，请先在 App 内打开一次设置页」 |

> ⚠️ 会话中的模型列表**有内存缓存**，改完必须**重启 App** 才生效。

### 4.3 实现

**新类 `GmModel`（数据层）**

| 字段 / 方法 | 说明 |
|---|---|
| `MK` = `kv_remote_settings_model_configs_v1` | 目标键 |
| `KEY` = `fuckds_model_switch` | 开关状态（bool） |
| `FALSE` / `TRUE` = `"switchable":false` / `"switchable":true` | 替换用的字面量 |
| `isOn(ctx)` | 读开关状态 |
| `setOn(ctx, on)` | 写开关 + 打补丁，返回是否成功 |
| `hasBak(ctx)` | 是否已有 `fuckds_bak_<key>` 备份 |

补丁用的是 **`String.replace(CharSequence,CharSequence)`**（不是手写 indexOf 循环），
单次替换不会级联（搜索串和替换串不同），所以 `false→true` / `true→false` 都能一次到位。

**新类 `GmModelSwitch`（监听器）** —— 仿 `GmSwitch` 写法，`CompoundButton.OnCheckedChangeListener`。

**`GmChatDialog.open()`** —— 在「防撤回」行之后插入分割线 + 新行（标题「模型切换」+ 副标题 + `Switch`）。

## 八、风险 / 说明

1. **需重启 App** —— `Luv1` 有 `ConcurrentHashMap` 内存缓存。
2. **服务端重新下发会覆盖** —— 下次拉 `/api/v0/client/settings` 若含 `model_configs`，覆盖会被冲掉（备份仍在，可再次打开开关恢复）。
3. 本模块只改 **MMKV 里的落地值**，不动 App 代码，所以依赖 App 真的会读 `switchable` 字段。
   若开了开关仍切不了，说明真正闸门是 `enabled` 字段（服务端对 expert/vision 也是 `false`），可再做一版一起放开。
4. `setOn` 关闭时优先走「备份还原」，只有在**从未备份过**的情况下才退化为「true→false」全量改写。

## 九、2.4.7 —— 修复「模型切换」提示消息反向（2026-09-12）

### 9.1 现象

用户：开启「模型切换」后提示 **「修改失败：未找到模型配置」**。

### 9.2 真相：**消息判断反了，开关其实成功了**

```smali
    invoke-static {v0, p2}, GmModel;->setOn(Context;Z)Z
    move-result v1
    if-eqz v1, :ok          # ❌ v1==0（失败）反而跳进「成功分支」
    const-string v1, "修改失败：未找到模型配置，……"
```

| `setOn` 实际结果 | 旧版显示的消息 |
|---|---|
| **成功**（1） | ❌「修改失败：未找到模型配置」 |
| 失败（0） | ❌「模型切换已启用」 |

**⇒ 用户看到"找不到配置"，恰恰证明 `setOn` 执行成功了**，
也反证了 `kv_remote_settings_model_configs_v1` 这个键**确实存在且有值** ✅

### 9.3 修复

```smali
    if-nez v1, :ok          # ✅ 成功才进成功分支
```

### 9.4 顺带复核同类消息判断（都对）

| 位置 | 写法 | 判定 |
|---|---|---|
| `GmPromptDialog.save()` | `if-eqz v3, :fail`（v3 = apply 结果） | ✅ 0→失败 |
| `GmHelloDialog.save()` | 无条件成功提示 | ✅ |
| `GmModelSwitch` | 本次修正 | ✅ |
