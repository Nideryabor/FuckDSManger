# 2.4.5 —— 服务端下发后自动重应用自定义（2026-09-12）

> 解决「自定义内容保存后只生效一次，之后被服务端下发覆盖」的问题。

---

## 一、问题

用户反馈：招呼语（以及同类的 `prompt_feature` / `switchable`）保存后**只生效一次**，
之后被服务端重新下发的内容替换掉；但模块里存的用户文本还在。

**根因**：模块走的是「改写 MMKV 落地层」的方案 ——
`kv_remote_settings_*` 是服务端设置的落地层，**下次拉设置时会被整个覆盖**。

---

## 二、逆向后拿到的两个关键事实（用本体 APK 实证）✅

本次终于把 **`DeepSeek2_2.4.5.apk`（12915 个类）** 打开做了实证，
不再靠猜：

### 2.1 `welcome_msg` 的真实本地键名

`Laz5;` 中直接含字符串：

```
"welcome_msg"
"kv_remote_settings_id_welcome_msg"
"kv_remote_settings_welcome_msg"      ← 值落地键（2 处）
```

→ **`kv_remote_settings_welcome_msg`**，与模块的猜测完全一致 ✓
（`GmHello.find()` 的第一候选就是它，所以能立即命中，不会退化到全量扫描）

### 2.2 下发应用点的行为（`Luv1;->u`）

```smali
v7  = map.get("normal_history_and_file_token_limit")            # 服务端值对象 xn4
v8  = "kv_remote_settings_normal_history_and_file_token_limit"   # 值落地键
v14 = "kv_remote_settings_id_normal_history_and_file_token_limit" # id 落地键
...
if (id != null) { 写 v14 = id;  cache.put(key, id); }
else            { mmkv.u(v14); cache.remove(key); }
value = v7.get("value");   # 真正的值 → 写 v8
```

结论：**服务端推送格式是 `{"id":…,"value":…}` 信封**，App 把它拆成
「值键」+「id 键」分别落到 MMKV。所以模块只要在**推送之后**把值键再改回来即可。

## 三、方案：hook 下发应用点，推送后自动重应用

```
服务端推送 → Luv1;->u / Laz5;->h（逐项落地到 MMKV）
                    ↓ afterHookedMethod
              GmSync.reapplyAll()
                    ├── GmPrompt.reapply()  提示词快捷项
                    ├── GmHello.reapply()   招呼用语
                    └── GmModel.reapply()   模型切换 switchable
```

### 3.1 为什么不会打架

三项 `reapply` 都采用 **「先比后写」**：

```java
用户覆盖为空        → 跳过
当前值 == 要写的值  → 跳过（不产生任何写入）
否则               → bak 备份 + 写入
```

所以即使 `uv1.u` 在一次下发里被调用几十次（每个配置项一次），
也只有**第一次**会真正写 MMKV，其余都是「读一次 + 相等即返回」，开销极小。

而且因为该项被推送覆盖后 hook 会再触发一次，**无论我们的键在推送序列的哪个位置，最终都会是自定义值**。

### 3.2 双保险

| 触发点 | 作用 |
|---|---|
| `GmSyncHook`（hook `uv1.u` / `az5.h` 的 `afterHookedMethod`） | 主路径：推送落地后立即改回来 |
| `GmResumeHook.afterHookedMethod`（Activity.onResume） | 兜底：万一推送发生在 Activity 之前（`sAct` 为空），下次进前台时补一次 |

两者都调用同一个 `GmSync.reapplyAll()`。

## 七、遗留 / 注意

1. **仍可能「需要重启 App 才在界面上体现」** —— 若 App 把该配置缓存在
   `Luv1` 的 `ConcurrentHashMap` 里（`u()` 里确实会 `cache.put`），
   我们改的是 MMKV，内存缓存要到下次读取/重启才刷新。
   但**MMKV 层已经不会被服务端永久覆盖**了。
2. 若日志里没有 `reapply hooks ensured`，说明 `uv1` / `az5` 类名变了（App 更新），
   需要重新定位下发应用点。
3. `hookAllMethods("uv1", "u")` 会挂上该类所有名为 `u` 的重载，属有意为之（更抗混淆变动）；
   因为「先比后写」，多挂几个也不会造成额外写入。

## 八、2.4.6 —— 修复 2.4.5 的 VerifyError（同类错误第二次 ⚠️）

### 8.1 崩溃

```
VerifyError: Verifier rejected class ...GmPrompt:
  reapply(android.content.Context) failed to verify:
  [0x1E] register v4 has type Precise Reference: java.lang.String
         but expected Reference: android.content.Context
    at GmSync.reapplyAll → GmResumeHook.afterHookedMethod
```

**连带症状**：`GmPrompt` 整类被拒 → 所有用到它的地方全废 →
「文件快捷选项」点了没反应（异常被 `GmClick` 的 try/catch 静默吞掉）。

### 8.2 根因：**又是「参数寄存器被当局部变量」**

```smali
.method public static reapply(Landroid/content/Context;)Z
    .registers 5            # ❌ 1 个参数 → p0 = v4
    ...
    const-string v4, "s"    # ❌ 把 Context 参数覆盖成 String
```

`GmModel.reapply` 同样：`.registers 6` ⇒ p0 = v5，却写了 `const-string v5, "s"`。

### 8.3 修复

| 方法 | 需要的局部寄存器 | 正确 `.registers` |
|---|---|---|
| `GmPrompt.reapply` | v0..v4（5 个） | `1 + 5 = 6` |
| `GmModel.reapply` | v0..v5（6 个） | `1 + 6 = 7` |

另外给 `GmResumeHook` 里新增的调用**套上 try/catch**，避免以后再拖垮宿主。

### 8.4 ⭐ 定死一条铁律（务必遵守）

```
.registers = 局部寄存器个数 + 参数寄存器个数
局部只允许用 v0 .. v(局部个数-1)
```

**参数寄存器个数 = 形参个数 +（实例方法 ? 1 : 0，`this` 也算）；
`long`/`double` 各占 2 个。**

于是 `p0` 恒等于 `v[局部个数]`，**永远不会和局部变量重叠**。

自检公式（写完一个方法立刻算一遍）：

```
最高用到的 vN  <  .registers − 参数寄存器个数      ← 必须成立
```

| 方法 | 最高 vN | .registers | 参数寄存器 | 判定 |
|---|---|---|---|---|
| `GmPrompt.reapply` | v4 | 6 | 1 | 4 < 5 ✅ |
| `GmModel.reapply` | v5 | 7 | 1 | 5 < 6 ✅ |
| `GmHello.reapply` | v3 | 5 | 1 | 3 < 4 ✅ |
| `GmSync.ensure` | v3 | 5 | 1 | 3 < 4 ✅ |
