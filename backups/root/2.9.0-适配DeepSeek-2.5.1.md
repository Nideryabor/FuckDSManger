## 四、本轮踩坑（与历史教训呼应）

1. **smali 零比较跳转语义再次踩坑**（本项目第 N 次）：
   - `if-ltz` = **`< 0` 才跳**
   - `if-gez` = **`>= 0` 才跳**
   - `if-gtz` = `> 0` 才跳 / `if-lez` = `<= 0` 才跳
   
   > 写成「为空就返回」时务必先默念一遍。本次 `GmClickHook` 两处守卫第一版都写反，靠人工复核抓回。

2. **R8 lambda 合并容器**：`k72` / `tia` / `on1` / `hka` 等类是「一个类装几百个 lambda」的容器
   （字段 `a:I` / `e:I` 做 switch）。**不要 hook 这类巨型方法**，要找它内部调用的**具体小方法**
   （如 `vc5.Z`）或**明文常量**（如 API 路径）当锚点。

3. **明文常量是最好的锚点**：
   - API 路径 `/api/v0/check_client_update`
   - 资源名 `profile_check_for_updates` / `assistant_message_avatar`
   - `kv_remote_settings_*`（下发键名）
   R8 改不了字符串字面量（业务可读性需要），反查极其高效。

4. **data class 的 `toString()` 是身份证明**：`ok0.toString()` 直接写着 `BitmapPainter(image=`，
   这次正是靠它确认 BitmapPainter，无需读构造逻辑。

## 七、2.9.1 —— 修「点击不响应」（2026-09-12）

**现象**：文案已正确替换为 `FuckDSManger`，但点击后仍执行原「检查更新」，模块管理器弹不出来。

**分析**：2.9.0 的 `GmClickHook` 沿用了旧版的双重门槛：

| 门槛 | 条件 | 作用 |
|---|---|---|
| `sLast` 防抖 | 距上次打开 > 3s | 防止连点重复弹窗 |
| `sTick` 触摸 | 距上次触摸 ≤ 1.5s | 证明「是用户刚点的」，同时排除 App 自动检查更新 |

`sTick` 由 `GmTouchHook` hook **`android.app.Activity.dispatchTouchEvent`** 刷新。
2.5.1 的 Activity 继承链为：

```
MainActivity → gs(AppCompat/AppCompatActivity) → br3(FragmentActivity) → k62(ComponentActivity) → Activity
```

实测 `MainActivity`、`gs`、`k62` 均未声明 `dispatchTouchEvent`，但**若链上任一层重写且不调 super，虚方法分派就绕开了被 hook 的 `Activity` 版本** ⇒ `sTick` 恒为 0
⇒ `uptimeMillis - 0` 永远 > 1500 ⇒ **`if-gtz` 每次都 return** ⇒ 点击被门槛拦死。

> ⚠️ 这与小窝 6.2 的教训同源：**「hook 挂父类可能被中间层覆盖」**。

**修法（2.9.1，versionCode 88）**：

1. `GmEntry` 新增静态字段 **`sSet:J`**
2. `GmResTextHook` 命中 `0x7f0f021f` 时刷新 `sSet`（`Resources.getString` 的 hook **已验证有效**——文案替换成功就是证据）
3. `GmClickHook` 门槛改为 **「任一成立即放行」**：
   - `now - sTick <= 1.5s`（触摸信号，可能失效但保留作快路径）
   - `now - sSet <= 600s`（10 分钟内设置页渲染过该行 ⇒ 用户在设置页）
4. 命中时额外 `Toast("FDS: hit check_client_update")` 作为可视化诊断

**判定表（下次复现时按此判断）**：

| 现象 | 结论 |
|---|---|
| Toast 出现 + 管理器弹出 | ✅ 修复成功 |
| Toast 出现但管理器未弹 | `GmMenuDialog.open()` 自身问题 |
| 无 Toast、无反应 | 点击未经过 `vc5.Z` 的 `check_client_update` 路径 ⇒ 需换锚点 |

**备选锚点（若上表第三行成立）**：
- `Resources.getString(0x7f0f0220)`（`profile_check_for_updates_newest`）→ 结果文案渲染即「检查更新」被触发
- 自绘悬浮入口（`GmFab`，不依赖任何宿主内部结构，保底方案）

## 八、2.9.2 —— 修 2.9.1 引入的「全局失效」（2026-09-12）

**现象**：2.9.1 装上后，「检查更新」行的文案**连替换都没了**，变回原样（比 2.9.0 更差）。

**根因（2.9.1 是我自己写坏的）**：
在 `GmResTextHook` 里插入 `sSet` 刷新代码时用了 `v2/v3` 做 long，
但该方法的 `.registers 4` ⇒ **`p0 = v2`、`p1 = v3`**（实例方法 + 1 个参数）。

```
move-result-wide v2      # 覆盖了 p0(this) 和 p1(param)！
...
invoke-virtual {p1, v0}, MethodHookParam;->setResult(...)   # p1 已被破坏 ⇒ 类型错误
```

⇒ ART verifier 拒绝整个 `GmResTextHook` 类 ⇒
`handleLoadPackage` 里 `new-instance GmResTextHook` 抛 `NoClassDefFoundError` ⇒
**`handleLoadPackage` 当场中断，后面所有 hook 全都没注册**。
（文案变回去 = GmResTextHook 没注册；其余功能同样全废。）

> 这是 2.4.4 / 2.4.6 / 2.3.0 之后**第 4 次**栽在「寄存器落点」上。
> 教训升级：**插入代码前必须先算 `.registers` 与 p 寄存器落点**：
> `p0 = v(.registers-1)`，`p1 = v(.registers-2)`，…（实例方法）；
> 可用「局部寄存器」= `v0 .. v(.registers - 参数个数 - 1)`。

**修法（2.9.2，versionCode 89）**：

1. `GmResTextHook` 里改用 **`v0/v1`**（真正的局部寄存器），不再碰 p0/p1
2. **加固 `hookM`**：签名从 `(ClassLoader, String, String, XC_MethodHook)` 改为
   **`(ClassLoader, String, String, String hookClassName)`**，把 hook 实例的创建挪进 `hookM` 自己的 try 内：

```smali
invoke-static {p3}, Ljava/lang/Class;->forName(Ljava/lang/String;)Ljava/lang/Class;   # 用模块自己的 loader
invoke-virtual {v1}, Ljava/lang/Class;->newInstance()Ljava/lang/Object;
check-cast v1, Lde/robv/android/xposed/XC_MethodHook;
```

   调用点随之简化为三行 `const-string` + 一次 `hookM`。
   好处：**以后任何一个 hook 类加载/验证失败，都只会让那一条 hook 失效，不会拖垮全局**
   （失败会写进 `GmDiag`：`hookM FAIL <host>.<method> hook=<class>`）。

> ⚠️ 注意：hook 类必须用 `Class.forName(String)`（走模块自身 ClassLoader）加载，
> **不能**用 `XposedHelpers.findClass(name, 宿主loader)` —— 宿主 loader 看不到模块的类。

**复核记录**：本轮把 9 个改动类的 `.registers` / p 落点全部人工核对一遍
（`GmClickHook` 12/实例1参、`GmRevokeHook.asList` 5/静态1参、`GmSync.ensure` 5/静态1参、
`DisableFlagSecure.hookM` 9/静态4参、`handleLoadPackage` 9/实例1参 —— 均无冲突）。

## 九、2.9.3 —— 找到真正的「检查更新」点击入口（2026-09-12）

**2.9.2 实测**：文案恢复正常（说明全局 hook 已注册），但点击仍然无 Toast、无管理器
⇒ **证明点击「检查更新」根本不会调用 `/api/v0/check_client_update`**（App 用的是启动时缓存的结果）。
⇒ `vc5.Z` 这个锚点选错了，必须换。

### 9.1 定位过程（可复用的套路）

1. 找设置页主 Composable：搜字符串 `pages.settings.SettingsPage `
   → **`La18;`**（`com.deepseek.chat.ui.pages.settings.SettingsPage (SettingsPage.kt:94)`）
2. 找「检查更新」文案 lambda 的持有者：
   `Ltia;`（ComposableSingletons 容器）的 `<clinit>` 里 `const/16 0xf → new Lk72(0xf)`
   → `sput-object → Ltia;->H:Lt62;`
3. 在 `La18;` 里搜 `Ltia;->H:` → 命中设置项构造点：

```smali
new-instance v1, Lm5;
const/16 v0, 0x14
invoke-direct {v1, v2, v0}, Lm5;-><init>(Lsv3;I)V   # 经 remember{} 包一层
check-cast v17, Lhv3;
...
sget-object v24, Ltia;->G:Lt62;
sget-object v26, Ltia;->H:Lt62;      # ← 「检查更新」文案
invoke-static/range {v16 .. v29}, Lob8;->b(...)V
```

4. `Lob8;->b` 的 source 信息直接写明身份：
   **`com.deepseek.chat.ui.pages.settings.components.SettingItem (SettingItem.kt:149)`**
5. `SettingItem` 第 2 个参数类型是 **`Lhv3`**，而 `v17 = Lm5(p0, 0x14)` 是它唯一的来源
6. 确认 `Lhv3` = **Kotlin `Function0`**（`v()` 即 `invoke()`）：
   全局搜 `Lhv3;->v()` 命中 `AndroidComposeView` / `AndroidViewHolder` / `PopupLayout` 等 Compose 内部回调，
   且 `Lt62`（Composable lambda 包装器）的 implements 列表里**没有** `Lhv3`
   ⇒ `Lhv3` 是非 Composable 的 `Function0`，即 **`onClick`**（Composable 内容 lambda 会带 Composer 参数）

### 9.2 结论：点击入口 = `Lm5;->v()` 且 `this.a == 0x14`

```smali
:pswitch_29  #0x14
sget-object v0, Lad8;->a:Lad8;              # 发送「检查更新」事件
invoke-interface {p0, v0}, Lsv3;->g(Ljava/lang/Object;)Ljava/lang/Object;
return-object v4                            # v4 = Llp9;->a  (Llp9 = kotlin.Unit)
```

`Lm5` 是 R8 合并的 lambda 容器（`a:I` 存 lambda id），`0x14` 全局唯一。

### 9.3 实现（2.9.3，versionCode 90）

- **新增类 `GmEntryHook`**：hook `Lm5;->v()Ljava/lang/Object;`
  - 读 `thisObject.a`，`!= 0x14` 直接返回
  - 命中：`GmMenuDialog.open()` + Toast `FDS: hit check-update row`
  - **阻断**：`setResult(Llp9.a)`（通过宿主 ClassLoader `findClass("lp9").getStaticObjectField("a")` 取），
    这样原「检查更新」事件不会发出，行为变成纯粹的「打开模块管理器」
- `DisableFlagSecure` 注册 `hookM(loader, "m5", "v", "GmEntryHook")`
- 保留 `vc5.Z` 的旧 hook 作为兜底（无害）

### 9.4 新知识

| 混淆名 | 真实身份 |
|---|---|
| `Lhv3` | Kotlin `Function0`（`v()` = `invoke()`） |
| `Lwv3` / `Lxv3` / … | Compose `@Composable` lambda 家族（FunctionN + Composer） |
| `Llp9` | `kotlin.Unit`（`Llp9->a` 是 Unit 单例） |
| `Lob8` | `SettingItem` 组件（SettingItem.kt:149） |
| `La18` | `SettingsPage`（SettingsPage.kt:94） |
| `Ltia` | ComposableSingletons 容器（`H` = 检查更新文案 lambda） |
| `Lm5` | R8 合并的 Function0 容器（`a=0x14` → 检查更新 onClick） |
| `Lad8` | 「检查更新」事件对象 |

> 方法论：**Compose 页面的 onClick 找法** ——
> 主 Composable → SettingItem 组件 → 第 N 个 `Function0`（非 Composable）参数 → 追它的构造点。
> `Function0`（无 Composer 参数）一定是回调，`Function2<Composer,Int,Unit>` 才是可组合内容。

| **2.9.4** | **文案又变回「检查更新」** + 点击弹出 **「当前已是最新版本」** |

第 2 条直接锁定了两个答案：
1. **点击确实走了「检查更新」流程**，并且最终走到「已是最新版本」的结果分支
2. 结果文案 = **资源 `0x7f0f0220`**（`profile_check_for_updates_newest` = "You are already on the latest version."）

### 10.2 为什么 2.9.4 文案又坏了（第 3 次全局失效）

2.9.4 我给 `hookM` 的 catch 加了一句「注册失败就 Toast」。
**但 `hookM` 是在 `handleLoadPackage` 里跑的，不保证在主线程** ——
非主线程 `Toast.show()` 会抛 `RuntimeException`，而它抛在 catch 块内部
⇒ 异常直接冒出 `hookM` ⇒ `handleLoadPackage` 中断 ⇒ 后续 hook 全没注册（含 `GmResTextHook`）。

> 教训：**catch 块里只做「不会抛异常」的事**（写日志、记内存缓冲），
> 绝不要在 catch 里做 Toast / UI / 反射这类可能二次抛异常的操​作。
> 这是本项目第 3 次「一个 hook 类/一段诊断代码拖垮全局」。

**修法**：去掉 `hookM` catch 里的 Toast（错误信息仍写入 `GmDiag`）。

### 10.3 新锚点：hook「已是最新版本」的文案

`0x7f0f0220` 在整个宿主里**只有一个引用点**：

```smali
# Lc12;->g(Object)Object  (第 350 行附近)
check-cast p1, Landroid/content/Context;
const p0, 0x7f0f0220
invoke-virtual {p1, p0}, Landroid/content/Context;->getString(I)Ljava/lang/String;
```

`Context.getString(int)` 内部必然经过 **`Resources.getString(int)`** —— 而我们**已经** hook 了它
（文案替换成功就是证据）⇒ 零成本复用。

**实现（`GmResTextHook`）**：
- `id == 0x7f0f021f` → 照旧：刷新 `sSet` + 返回 `FuckDSManger`
- `id == 0x7f0f0220` → 调用 `hitLatest()`：
  - 先判断当前线程是主线程（`Looper.myLooper() == getMainLooper()`），非主线程直接放弃
  - 主线程 → `GmMenuDialog.open()`
  - 整个过程包在 try/catch 里（`getString` 可能在各种线程被调用，绝不能把异常抛回宿主）

**语义**：用户点「FuckDSManger」→ 宿主走检查更新 → 命中「已是最新版本」的渲染
→ 我们顺势打开模块管理器。（原对话框仍会显示，属可接受的副作用）

### 10.4 顺带清理

- `GmSettingHook`（hook `SettingItem`）改为**只在 `a == 0x14` 时提示一次**，不再刷屏
- 保留 `Lm5.v()` / `vc5.Z` 两条旧路径作兜底

### 10.5 寄存器复核（本版改动 3 处）

| 方法 | .registers | p 落点 | 局部可用 | 结论 |
|---|---|---|---|---|
| `GmResTextHook.beforeHookedMethod` | 4 | p0=v2, p1=v3 | v0,v1 | ✅ 只用 v0/v1 |
| `GmResTextHook.hitLatest` | 3 | 静态无参 | v0..v2 | ✅ |
| `GmSettingHook.beforeHookedMethod` | 6 | p0=v4, p1=v5 | v0..v3 | ✅ |

> 标签汇合处的寄存器类型也复核过：各 `:ret` 的前驱类型一致，无 int/Object 冲突。

## 十一、2.9.6 —— 修「主线程判断把自己拦掉」+ 双通道兜底（2026-09-12）

**2.9.5 实测**：文案正常，点击仍只走原逻辑、无 Toast、无管理器。

**分析**：2.9.5 的 `hitLatest()` 里加了「非主线程直接放弃」的判断。
但宿主的 `Lc12.g` 大概率是**在后台/协程线程**里调 `context.getString(0x7f0f0220)`，
再把字符串交给 UI ⇒ 我们的判断把自己拦掉了。

**修法（2.9.6，versionCode 93）**：

1. **去掉主线程判断**，改为**无条件 `GmEntry.sH.post(...)`**（`sH` 是模块已有的主线程 Handler）
   - 新增 `GmOpenRun implements Runnable`：`run()` 里 Toast `FDS: latest-version hit` + `GmMenuDialog.open()`
   - 这样无论 `getString` 在哪个线程被调用，管理器都在主线程打开
2. **加 Toast 诊断**：命中时必弹 `FDS: latest-version hit`，方便确认是否命中
3. **加 3 秒防抖**（`GmResTextHook.sLast`），避免重组导致多次弹窗
4. **双通道兜底**：新增 `GmLatestHook`，hook `Lc12;->g(Object)Object` 的 after，
   若返回值是含 `latest` / `最新` 的字符串 → 同样 post `GmOpenRun`
   （防止 `0x7f0f0220` 这条路因某种原因没走到）

**寄存器复核**：
- `GmResTextHook.hitLatest` `.registers 5`（静态无参，局部 v0..v4）— 标签 `:go` 单一前驱，无类型冲突
- `GmResTextHook.openNow` `.registers 3` — `:ret` 前驱同为 Handler 类型
- `GmLatestHook.afterHookedMethod` `.registers 6`（实例 1 参 → p0=v4,p1=v5，局部 v0..v3）
- `GmOpenRun.run` `.registers 3`

> ⚠️ 这次特别注意了：**同一标签被「不同类型寄存器状态」的多条路径跳入会 VerifyError**
> —— 解法是让每条路径各自 `return`，或把处理逻辑拆成独立方法。

### 下一步（若 2.9.6 仍不生效）

启用**保底方案：自绘悬浮入口**

- 动作：在 Activity 的 `DecorView` 上 `addView` 一个小按钮（主线程 post）
- 点击 → 打开模块管理器
- **完全不依赖宿主的任何点击链路**，只要模块能 hook 到 `Resources.getString` 就一定可用
- 代价：UI 上多一个小控件

## 十二、2.9.7 —— 保底方案：自绘悬浮入口（2026-09-12）

**背景**：2.9.6 的双通道（`0x7f0f0220` + `Lc12.g`）实测仍无反应 ⇒
宿主那个「当前已是最新版本」的文案**很可能根本不由 `Resources.getString` 提供**
（大概率是 `CheckClientUpdateShowContent` 服务端下发的字符串）。
⇒ 所有"从宿主内部找点击链路"的尝试到此为止。

**采用保底方案：完全绕开宿主点击链路，自绘入口。**

### 12.1 实现

| 新增类 | 职责 |
|---|---|
| `GmFab` | `implements Runnable`；静态 `show()` 把自身 post 到主线程；`run()` 在 `DecorView` 上加一个小按钮 |
| `GmFabClick` | `implements View$OnClickListener`；`onClick` → `GmMenuDialog.open()` |

**触发点**：`GmResTextHook` 命中 `0x7f0f021f`（设置页渲染「检查更新」行）时调用 `GmFab.show()`。
这个 hook **已经验证有效**（文案替换成功就是证据），所以按钮一定能挂上。

**按钮样式**：`TextView`，文字 `FDS`，白字 + 半透明黑底，右下角，24dp 边距。
**去重**：静态 `sView`，若 `getParent() != null` 说明还在屏上，不重复添加；
Activity 重建后旧 DecorView 被回收（parent 变 null），会自动重新挂上。

**线程安全**：`show()` 只做 post；真正碰 View 的代码全在主线程 `run()` 里，
整段包在 try/catch 内（绝不把异常抛回宿主）。

### 12.2 定位

- 装好后**进一次设置页**（触发文案渲染）
- 屏幕**右下角**会出现一个 `FDS` 小按钮
- 点它 → 打开模块管理器

### 12.3 结论与遗留

- ✅ 模块入口问题**彻底解决**（不再依赖宿主任何内部结构）
- ⚠️ 交互从「点设置条目」变成「点悬浮按钮」；原「检查更新」条目仍是宿主原生行为
- 遗留：若日后宿主混淆名稳定下来，可再回到 `SettingItem` 那条路恢复原交互

### 12.4 本轮方法论总结（写给下次适配）

1. 宿主升级后**所有混淆名都会变**，先验结构再看名字
2. **明文常量**（资源名/API 路径/字符串）是最可靠的锚点
3. 找到 `SettingItem` 这类组件后，其 **`Function0`（非 Composable）参数就是 onClick**
4. 但**服务端下发的文案**会让「结果文案」这条路彻底断掉 —— 必须有兜底入口
5. **catch 块内只做不会抛异常的事**（本项目已因此翻车 2 次：2.9.4 的 Toast）
6. **同一标签被不同类型的多条路径跳入会 VerifyError** —— 每条路径各自 `return`
7. 保底方案的价值：**只要还有一个已验证有效的 hook（如 `Resources.getString`），就能挂 UI**
