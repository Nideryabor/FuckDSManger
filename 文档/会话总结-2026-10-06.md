## 三、Layout Inspect 的 MCP（新工程，不入库）

`/workspace/layoutinspect-mcp/`（源码 + 解析 + 打包/签名脚本，本地保留）

| 项 | 值 |
|---|---|
| 目标 | `com.flass.layoutinspect` 1.1.5 (vc19) · **libxposed 新 API 模块** |
| 端点 | App 侧 `127.0.0.1:8790/mcp` · 注入侧 `8800 + abs(pkg.hashCode()%100)`（deepseek=**8860**） |
| 代码 | `src/com/nidyaber/limcp/`：`Json` `McpServer` `Mcp` `Views` `Dex` `L` `McpBootstrap`（纯 Java 零依赖） |
| 工具 | `views` `clickables` `hit`(performClick) `acc*` `cls_find` `apk_dump` `fs_*` `sh` `log_tail` `pkgs` |
| 出包 | `sh 出包.sh`（javac→d8→换 dex→自研 zipalign→签名→**卸载重装**） |
| 客户端 | `/workspace/tools/limcp.sh <端口> <工具> '<json>'` |

### ⚠️ 四个必记坑

1. **入口是 `ModernHook`，不是 `Hook`** —— 新 API 模块走 `java_init.list`；塞进老 `IXposedHookLoadPackage` 一次都不会被调（端口永远起不来）。
2. **LSPosed 认模块 = 包名 + 签名** ⇒ 换签名后必须 **卸载重装**，`install -r` 无效。
3. **apktool 打不了这个包**（资源里有带 `$` 的 AVD 中间产物，aapt1/aapt2 都拒）⇒ 改用「只换 dex」的 `pack.py`；`lib/**/*.so` 必须 **STORED + 4096 对齐**（`extractNativeLibs="false"`）。
4. **工作区进程活不过一次工具调用**（`nohup`/`setsid` 都会被收）⇒ 沙箱常驻 HTTP 服务走不通，这正是必须塞进 APK 的理由。

### 两条「眼睛」的分工

| 界面 | 走哪条 | 工具 | 权限 |
|---|---|---|---|
| 传统 View | **进程内 MCP** | `views`/`clickables`/`hit` | 零权限 ✅ |
| Compose/自绘 | **adb uiautomator** | `tools/ui.py` · `tools/devmcp/` | adb 即可 ✅ |

> 进程内自造的 `AccessibilityNodeInfo` **走不了子树**（要真无障碍服务）⇒ Compose 只能靠 uiautomator。
> 进程内那条的独门价值：能看见**别人的悬浮窗**、`performClick()` 免权限、能读 `/data/app` 的 APK（adb 读不到）。

### 实测战果
- DeepSeek 进程内读到完整视图树（含 `GmBgView` = FDM 的注入视图、Layout Inspect 悬浮圆点）
- `cls_find mmkv` → 15484 个类里精确定位 3 个
- `apk_dump` → 把 22MB 的 DeepSeek APK 拉到它自己的私有目录

## 四·七、PyGuy2 之谜（2026-10-06）

**现象**：贡献者列表里冒出一个不相干的账号 `PyGuy2`（18 次提交）。

**真因**：GitHub 的贡献者列表**按作者邮箱匹配 GitHub 账号**。
`2.10.11 ~ 2.10.13` 那 18 个提交用了**占位邮箱** `noreply@example.com`，

**他对本仓没有任何权限**（非协作者 / 不能推 / 非 fork），纯显示归类。

**处理**：
1. ✅ 加 `.mailmap`（推上去了，不动历史、不用 force push）—— 把 9 种历史身份归一
   到 `Nideryabor <338461957+Nideryabor@users.noreply.github.com>`，含被冻结的老账号 `dxyabab`
2. ✅ 本地 `git config user.*` 也改成规范身份 ⇒ 以后提交不会再冒占位邮箱
3. ⏸ 备用脚本 `修邮箱.sh`（重写那 18 个提交的邮箱 + 强推）—— 只在 mailmap 一天后仍不好使时用

## 四·八、🩹 一个真 bug：仓库「克隆不出来」（2026-10-06 晚）

**发现**：准备打包备份时，顺手做 `git clone . /tmp/verify` 验证 —— **直接失败**：
```
warning: failed to stat '.git/objects/pack/.l2s.tmp_idx_iayDr80001': Operation not permitted
fatal: failed to iterate over '.git/objects/'
```

**真因**：proot 的 `--link2symlink` 把硬链接改造成「软链 + 实体」，在 `.git/objects/` 里留下
**1622 个 `.l2s.*` 残渣**。它们让 git **连对象目录都遍历不了** ⇒ **clone / 备份还原全部失效**。
👉 也就是说：**在这之前，那份备份就算拷出去，也是克隆不回来的。**

**处理**：
1. 删掉 `.git.broken-20261002/`（**9748 个断链**）——先把 27 个元数据文件归档成
   `backups/git-broken-20261002-元数据.tar`（2.1MB，**含 63KB 的 reflog**，记录了 10-02 那次 git 修复全过程）
2. `git gc --prune=now` → 再把剩余 `.l2s.*` 挪到 `/tmp/l2s_stash`（464 项，可回滚）

**结果**：

| | 修前 | 修后 |
|---|---|---|
| `.git` 大小 | 117 M | **47 M** |
| `.l2s` 残渣 | 1622 | **0** |
| 断链 | 9749 | **1**（只剩 `抓日志.sh`） |
| `git clone .` | ❌ 失败 | ✅ 成功（272 提交 / 15594 文件 / HEAD 一致） |
| `git fsck --full` | — | ✅ 0 error |

**教训**：
- ⭐⭐⭐ **"能 commit" ≠ "能克隆"** —— 要验证仓库健康，跑 `git clone . /tmp/x`，不是只看 `git log`
- ⭐⭐⭐ **备份完必须做「还原演练」**（不演练 = 不知道备份能不能用）
- ⭐⭐ `du` 报的 `Operation not permitted` 是**信号**，不是噪声

## 四·九、📦 打包带走（给外接盘）

`打包带走.sh`（已写、已实测）：
```sh
sh 打包带走.sh <目标目录>                # 单包（exFAT/NTFS/ext4）
sh 打包带走.sh <目标目录> --split 3500m  # 拆卷（FAT32）
sh 打包带走.sh <目标目录> --slim         # 精简版（去 out/ tmp/ 缓存，1.5G）
```

**为什么要先打 tar 再拷**（不能直接拖）：
1. proot 的软链 → 直接拷到 FAT 会报「没有这个文件」
2. **560 个文件名含 `:`**（`tmp/lsp/log/` 时间戳）→ FAT/exFAT 拒收
3. 15G / 12.8 万文件逐个拷极慢；tar 是顺序读写

**实测**（精简版）：**67 秒**出包 1.5G → 解包还原 → 272 提交 / fsck 0 error ✅
**完整版预估**：约 10~12 分钟，15G

**排掉的雷**：无 >4G 单文件 ✅ · 无超长文件名 ✅ · 最大单文件 116MB（node 二进制）

## 四·十、💾 备份到外接盘（2026-10-06 傍晚，**完成**）

盘：`/storage/42C2F8EAC2F8E359`（58G · exFAT/NTFS 经 FUSE）→ 目录 `rikkahub工作区备份/`

| | 个数 | 大小 |
|---|---|---|
| 源 `/workspace` | 128156 | 13.97 GB |
| 盘上 | 127603 | 12.82 GB |
| **覆盖率** | **99.5630%** | — |

**唯一缺的 560 个**：文件名含 `:`（`tmp/lsp/log/` 时间戳）。
**这块盘的 FUSE 层直接拒收**，实测连 `mv` 都不行：
```
can't create .../test:colon.log: Operation not permitted
mv: bad '.../.ni_t': Operation not permitted
```
⇒ **文件系统限制，不是拷贝姿势问题**（它们只是 LSPosed 日志，可再生）。

### 踩的四个坑（都实测过）

| # | 现象 | 真因 | 解法 |
|---|---|---|---|
| 1 | 直接拷文件报「没有这个文件」/ 0 字节 | `fdm-app/work/b_used_aars/*.aar` 等 **53 个软链指向 `/workspace/...`**，手机视角读不到 | — |
| 2 | 560 个文件拷不进去 | 名字含 `:` | 无法解，只能放弃 |
| 3 | tar 报 `bad symlink`，42 个文件丢了 | **proot l2s 伪装**：`lstat` 被拦成普通文件，`readlink` 没被拦 ⇒ tar 存成软链条目 | **`-h --hard-dereference`** |
| 4 | 盘不支持软链（`Function not implemented`） | — | 用 `-h` **实体化**成真文件 |

### 速度（重要经验）

**瓶颈是"文件数"不是"字节数"**：`tools/` 14245 个文件跑了 411s（≈35 文件/秒），
而 100MB 大文件测试是 15 MB/s。⇒ 4.3 万个文件的 `tmp/` 必须**按文件数分块**
（按大小分会分出一块 3 万个碎文件，跑到超时）。

### 「大小元数据不符」是假象

盘上 **612 个文件** `ls` 报的大小和源不一致（如源 25603、盘上显示 4344）。
**内容是对的** —— 抽验 **25/25** 全量 md5 与源文件完整 md5 **一字不差**。
⇒ exFAT/FUSE 驱动返回的 `stat` size 是旧的，读取时数据是完整的。

### 交付的脚本

| 脚本 | 用途 |
|---|---|
| `推到盘.sh` | 分块流式推送（预算分块计划 / 逐块推 / 收尾） |
| `tools/出笼隧道/adb.sh` | **修了一个 bug**：`exec adb "$@"` 没带 `-s` ⇒ 多设备时报 `more than one device`，现自动取 `127.0.0.1:<port>` |
