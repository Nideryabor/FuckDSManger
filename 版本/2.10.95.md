## 一、读源码定位：`vq.l()` 自己不干活

```smali
.method public final l()Ljava/lang/String;
    invoke-virtual {p0}, Lvq;->D()Ljava/lang/String;    # ← 抽象方法（子类实现）
    …
    invoke-virtual {p0}, Lvq;->r()…  / C()…             # ← 又是抽象方法
```

**⇒ `l()`/`t()`/`k()` 这些都是"壳"，真正取数据靠子类的抽象实现；而 `vq` 的字段全是 Compose 状态对象（`Lz09;`/`Lrs8;`）**

**⇒ 我的调用时机在"设置页按钮回调"里（主线程、非 Compose 作用域）—— 大概率踩到了「快照/状态」的读限制 ⇒ 抛异常**（而且 `getCause()` 为 null，更说明是环境而非实现的问题）。

## 二、本版：把"抽文本"搬到 hook 里做

**核心思路：不在点按钮时抽，而是在 `wr.z` 触发的**那一刻**（还在宿主的调用栈上）就把文本抽好、存起来。**

| 新增 | 作用 |
|---|---|
| **`sCtx:String`** | 缓存"抽好的上下文" |
| **`grab(List)`** | 遍历列表 → 逐个 `one()` → 拼串（复用现有逻辑，同样 try/catch） |
| `z_take` 分支 | 存完 `sList` 后**立即调 `grab(args[1])`** |
| `ctxText()` 开头 | **优先返回 `sCtx`**（有就直接用，不再碰元素） |
| `pick()` 的 catch | 改为 **`GmUtil.logE(Throwable)`** ⇒ 打**完整堆栈**（含 `Caused by`），比 `getCause()` 靠谱 |

**⇒ 这样即使"点按钮时读不了状态"，文本也已经在 `wr.z` 那一刻被抓下来了。**

## 四、教训

| # | 教训 |
|---|---|
| **434** | ⭐⭐⭐ **同一个方法，在不同时机调用结果可能完全不同**：Compose 状态对象的读有"快照上下文"要求 ⇒ **拿数据要趁"宿主自己在跑"的时候（hook 里）拿，别拖到"自己的时机"** |
| **435** | ⭐⭐⭐ **`getCause()` 返回 null ⇒ 别死磕，换 `logE`（完整堆栈）**：`getStackTraceString` 会打印嵌套链，信息量比 `getCause` 高一个量级 |
| **436** | ⭐⭐ **"在 hook 里就地加工"是通用手法**：宿主递过来的原始数据（`List`、`Map`）往往只在那一刻"可访问"，**顺手就把它翻译成我们想要的形式**存起来 |
