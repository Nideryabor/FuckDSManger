## 二、动手前先修掉的**第二道坑**（文档里没写）

`GmCallDialog.stream(String)` 原来有一道守卫：

```smali
sget-boolean v0, ...->sThink:Z
if-eqz v0, :cond_18        # !sThink ⇒ 直接 return（静默）
```

而 **`sThink` 只在 `tick()` 的「思考中超过 6s 无自动回待机」里被清成 false**；
AI 回复要 **~11s** 才来 ⇒ **`um1` 到达时 `sThink` 早就是 false**
⇒ 就算接上数据源，`stream()` 也会**静默 no-op**。

**本版处理**：拆掉 `stream()` 的这道守卫（只留 `p0 != null`）。
理由：`stream()` 全程只有本模块调用，而 `apply()` 自己会判 `sText != null`（通话页没开时自然无效）；
「思考中」这个语义不该由 `stream()` 兼职当门闸。
> ❌ 没有采用「在 `um1` 分支里补调 `think()` 把 `sThink` 顶回 true」——那会让 6s 兜底在之后误把状态刷成「待机」，
> 若主人此时正好在录音，会看到状态被顶掉。

## 三、宿主机理侦查（本轮新结论，宿主 2.5.2 / vc273）

### 3.1 `vq`（消息，抽象基类）

| 成员 | 结论 |
|---|---|
| `c:Lrs8` | **文本状态**（Compose MutableState）；`S(String)V` 就是往它写 `new cy5(text)`（`S` = public final，8 条指令） |
| `C()Ljava/lang/String;` | **拼接全部文本块**：遍历 `s()`（`b41` 集合），元素 `instanceof gg0` ⇒ `gg0.j()`，串起来 |
| `l()Ljava/lang/String;` | ★ **展示文本**：`D()`（角色）== `"USER"` ⇒ `r()`，否则 ⇒ `C()` |
| `x()I` | **本地序号**；`>0` 才是真消息（见 `wr.y()` 的扫描条件） |
| `z():Integer` / `K()` | 服务端消息 id（`z().intValue()`），被 `wr.a()` 用来找「父消息」 |
| 其它 | `D()`=角色串、`G()`=状态串（`CONTENT_FILTER`/`INCOMPLETE`） |

### 3.2 `wr`（会话/消息容器）

| 成员 | 结论 |
|---|---|
| `a:String` | 会话 id（2.14.9 已证） |
| `f:LinkedHashMap` | **消息主存储**，key=`vq.x()`（序号→Integer）、value=`vq`（见 `wr.a(Lvq;Z)V`） |
| `q:HashMap` | ⚠️ **不是消息表**！value 是 **`hv1`**（`hv1.c:Lgv1` / `hv1.e:o52` / `hv1.f:Integer` / `hv1.g:o52`）＝**在途流记录**；`wr.u(Lvq,String)` 是「停流」时按 id `remove` 并上报 `stop_stream_success` ⇒ **`专题/流式回复捕获.md` 里候选 C 把 `q` 当消息表是错的** |
| `x():hp8` | **渲染列表**（`j` 状态为 `nr` 时才有值，否则 null）；全宿主 13 处引用（`dm0.n` 巨型 Composable、`tga.F`、`ao1.g`…） |
| `y():Integer` | 从 `x()` 末尾倒扫，返回**第一条 `x()>0`** 的消息序号（说明**末尾可能有 `x()<=0` 的占位消息**） |
| `z(Lwr,List)` / `A(List,Integer,Z)` | 写列表 / 应用流式补丁 |

### 3.3 `hp8`（= `SnapshotStateList`）

`toArray()[Ljava/lang/Object;`、`size()`、`get(I)`、`iterator()`、`isEmpty()` **都是它自身声明的 public final**
⇒ `XposedHelpers.callMethod(list, "toArray", new Object[0])` **能直接命中**（不需要 `get(int)` 那种「基本类型参数」的反射坑）。

## 七、教训

| # | 教训 |
|---|---|
| **595** | ⭐⭐⭐ **「管道已就绪、只缺数据源」这种结论最容易漏掉「管道自己的守卫」**：`stream()` 的 `sThink` 门闸在 11s 后才到达的 `um1` 上**必然为假** ⇒ 接上数据源也会静默无效。**接数据源之前，先把「投递口」的每个前置条件在真实时序上过一遍。** |
| **596** | ⭐⭐ **「文档里的候选数据源」也可能指错对象**：候选 C 说 `wr.q` 是「消息表」，实测它是**在途流记录表**（value 是 `hv1`）。**照抄文档也要落地核一次类型。** |
| **597** | ⭐⭐ **反射挑「自身声明」的方法**：`hp8` 是 `SnapshotStateList`，`toArray()/size()/get()` 都自身声明 ⇒ `callMethod` 直接命中；而 `LinkedHashMap.values()` 声明在父类 `HashMap` ⇒ 换 `f` 通道时要另写 `getDeclaredMethod`（同时绕开「基本类型参数」的反射坑）。 |
| **598** | ⭐⭐ **同一方法的「门闸」类改动要一次说清归属**：`stream()` 的门闸该由调用方（`grabAi`）负责判断，而不是把「是否思考中」硬编码进投递函数。**门闸与语义不一致 ⇒ 必然在某个时序下静默失效。** |
| **599** | ⭐ **MCP 通道对「含 `.catchall` 的方法中段插入嵌套 try」会拒**（本次第 4 次复现）⇒ 解法：**去掉嵌套 try 再插**（外层已有 catchall，`grabAi()` 自身也全程 try 住，无需再包一层）。 |
