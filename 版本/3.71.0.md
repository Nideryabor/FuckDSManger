## 二、★★ 本轮最重要的一个概念：拆类

### 现象

R8 在 2.7.1 把「合并出来的大杂烩类」**按业务域重新切开**：

| 旧类 | 方法数 | 新类 | 合计 |
|---|---|---|---|
| `us6`（Modifier 扩展桶）| 51 | `p68` + `dz7` + `r0b` | 175 |
| `jtb`（气泡/对话框）| 96 | `szb` + `x4c` + `fxb` | 219 |

反方向也有**合并**：`e3c`(62) + `pic`(48) → `kmc`(68)。

### 最阴的一条：方法会跑到别的碎片

> **`qn7` 的 48 个方法里，47 个在 `jr7`，只有 `s`（GotoBottomButton）跟着
> `ChatFloatingToolViewV2` 这个域跑到了 `dz7`。**

`hookM` 原来是：
```java
String cls = GmRemap.cls(oldCls);        // "qn7" → "jr7"
String mth = GmRemap.method(oldCls, m);  // "s" → "o"
findClass(cls); hookAllMethods(cls, mth, hook);   // ← jr7 里没有 o ！静默失败
```

### 解法

新增 `clsFor(类, 方法)`：按**方法**查它真正在哪个类（MTH 表的 owner 列）。
`GmEntry.hookM` 里把 `cls(p1)` 换成 `clsFor(p1, p2)` —— 寄存器不变（p1/p2 都是参数寄存器），
`.registers 8` 不变，只是 invoke 参数从 1 个变 2 个。

### 附带：`clsAll()` 给 hookAllMethods 型钩子

`uia` → `{"p68","dz7","r0b"}`、`pn9` → `{"szb","x4c","fxb"}`。
**拆类后 hookAll 型钩子必须遍历这个数组**，否则只挂到 1/N 且**不报错、count 也不为 0**。

> 本轮实际排查：`GmEntry` 里所有 `hookM` 都是挂**具体方法**（不是 `*`），
> 所以 `clsFor` 就够用，遍历逻辑留作后续（`clsAll` 已就位）。
