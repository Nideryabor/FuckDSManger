## 一、两个根因（都是我的错，且是同一个家族）

### 根因 1 ⭐ `GmCallHook` 守卫写反 ⇒ 从来就没捕获过 `ao1`

```smali
# 2.13.0（错）
if-nez v0, :ret        # v0 = thisObject；「非空就跳走」⇒ 每次都跳过 sput
sput-object v0, ...sAo1

# 2.13.1（对）
if-eqz v0, :ret        # 「空才跳走」
sput-object v0, ...sAo1
```

⇒ 于是 `sAo1` 永远是 null ⇒ `send()` 走「还没捕获到发送入口」分支 ⇒ **主人看到的提示完全对得上**。
⇒ **教训 494 是我自己在 2.13.0 文档里写的**（「`if-eqz`=等于0跳、`if-nez`=不等于0跳」），写完 5 分钟就犯 ⇒ **写完守卫必须回读一次**，不是口号。

### 根因 2 ⭐ `GmCallBtn.show()` 被塞进了「别人家的 try 块」⇒ 被静默吞掉

2.13.0 我把调用插在 `GmResumeHook.afterHookedMethod` 里：

```smali
:try_start_1f
GmSync.ensure(ctx); GmSync.reapplyAll(); GmBg.ensure(ctx)
invoke-static {v0}, GmCallBtn;->show(Activity)V   ← ❌ 在 try 里
:try_end_28  .catchall {…} :catchall_29           ← 前面任何一句抛异常，我的代码就永不执行
```

`GmBg.ensure()`（背景/相机那套）一旦抛异常，**我的调用直接被跳过**，而 catchall 只做 `move-exception` + `goto` ⇒ **静默**。
⇒ 2.13.1：**把调用移出 try**，并且**自己再包一层独立 try/catch**（防我自己新类校验失败时顺着 `onResume` 崩宿主）。

## 五、教训（本轮）

| # | 教训 |
|---|---|
| **495** | ⭐⭐⭐ **别把「我新加的调用」插进别人已有的 try 块里**（尤其块内还有 camera/MMKV 这种爱抛异常的家伙）—— **成功路径会被别人的异常吞掉，而且 catchall 把你的死因也一起吞了**。要么放块外，要么自带 try。 |
| **496** | ⭐⭐⭐ **守卫方向写完必须回读**（`if-eqz` / `if-nez` 一字之差 = 功能全哑）。本轮 `GmCallHook` 就是这么废掉的，且**完全静默、无日志**（因为它在 sput 之前就跳走了）⇒ 守卫类代码 = 本项目历史第一大 bug 家族，没有之一。 |
| **497** | ⭐⭐ **诊断代码自己也会瞎**：本次 catch 用的 `logE` **不落盘** ⇒ 出事等于没记。**「记录」类代码一律用 `GmUtil.log`（落盘）**；要看堆栈就 `Log.getStackTraceString(t)` 再 `log`。 |
| **498** | ⭐ **报错要能一眼分流**：把「调用入口 / 中间步骤 / 成功」三段都打点（`进入` / `decorView 已拿到` / `已挂上`），失败时不用猜是哪一段；hook 里记**方法名**，一次就分清走了 `I` 还是 `J`。 |
