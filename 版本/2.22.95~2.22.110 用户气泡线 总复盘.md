## 二、已确认的技术事实（下一轮直接用）

### 1. 宿主结构
| 事实 | 值 |
|---|---|
| **消息项 composable** | `pn9.c(ILpe5;Ljb1;Lwr;Lvq;Lc76;Ley3;I)V`（**static**，678 条指令，宿主用它自己判"用户/助手布局"） |
| 参数位 | `p0`=int · `p1`=pe5 · `p2`=jb1 · `p3`=wr · **`p4`=`args[4]`=消息本体(`vq`)** · `p5`=`args[5]`=**Modifier(`c76`)** · `p6`=Composer · `p7`=flags |
| **角色 API** | `Lvq;->D()Ljava/lang/String;` ⇒ 返回 **`"USER"` / `"ASSISTANT"`（大写，与模块判据一致）** ✓ |
| 两个消息项的运行时类名 | **都是 `nx`** ⇒ **类名不能当身份证** |
| 助手气泡的**背景调用点** | **`ob2.b:168`**（`uia.v(modifier, 色, zc.o)`） |
| **用户气泡的背景调用点** | **`ls9.f:670`**（同一个 `zc.o` 形状；`sd=0 ud=0` ⇒ **在布局/绘制阶段**） |
| 用户气泡 lambda | **`ls9.f`**（`hookM ls9.f` 已有；用户项走用户支线时才会被调用） |
| 用户气泡的宿主色 | `-9208960518906183680`（未设图时的宿主色） |
| 宿主气泡形状对象 | `Lzc;->o`（探针里显示为 `形=c84`） |
| `pn9` 里其它 composable | `a`/`b`/`e`/`f`/`h`（带 `hv3`=布局节点，属于 measure-policy，不是项） |

### 2. 模块内部机制（务必记住）
| 项 | 说明 |
|---|---|
| `sDepth` / `sUDepth` | 助手 / 用户**项级**组合期计数（`pn9.c` before++ / after--） |
| after 钩子逻辑 | `if (sDepth>0) dec sDepth else if (sUDepth>0) dec sUDepth`（串行时正确） |
| **`GmUtil.logOnce(tag,msg)`** | ⚠️ **只按 `tag` 去重**（`HashSet.add(tag)`），打印的是 `msg` ⇒ **"每个状态一行"必须 `logOnce(s,s)` 或 tag 带状态** |
| **探针门 vs 重写门** | **探针门要宽**（否则漏整类调用）；**重写门要严**（否则误伤）。两者千万别绑同一个条件 |
| **`sImgName`** | 全局"当前图片文件"；原本只由 `wrap()`（项级注入）维护 ⇒ **用户侧不走 `wrap()` 时必须自己设** |
| 图片文件名 | AI = `fuckds_bubble.png` · 用户 = `fuckds_ububble.png` |
| 配置键 | `fuckds_bubble_*`（AI）/ `fuckds_ububble_*`（用户：`_on` / `_color` / `_radius` / `_img`） |
| 配置分流 | `GmBubbleDialog.sUser` ⇒ `applyColor/applyRadius/applyOn/armPick/setImgOn` 全部正确分流 ✓（**已排除"键串"**） |
| `ub()` 重写门（110 后） | `uOn()` && 方法名=="v" && （`sUDepth>0` **或** `caller` 以 `ls9.f` 开头）&& `args[2]==宿主 zc.o` ⇒ `useUImgName()` → `ubMod()` → `setResult` |
| `GmBubbleFitHook` | **已按实例取图**（`GmBmpShader.bmp` 的 `iget/iput`）⇒ 不是串图源 |

### 3. 诊断用的"可靠通道"
- **`GmUtil.log(String)`**：**绝不去重**、必打（`[CELL]` / `[HOOK]` / `[ROLE]` / `[UB]` 全走它）
- **探针内联**到"已证明会打印"的位置旁边（如 `[HOOK]` 标记下一行）⇒ 少掉"子函数是否被调用/参数是否正确/是否静默 catch"三整类不确定性
- 子函数里的 `findClass`/反射**可能静默失败**（`catchall` 只写 logcat，不进 DIAG）⇒ 探针能少一步就少一步

## 五、教训精选（本线 269 ~ 297）

| # | 教训 |
|---|---|
| **269** | ⭐⭐⭐ **`logOnce` 的 tag 就是"身份"**：两条互斥分支的自检共用 tag ⇒ "分支明明在跑"被读成"从没跑"（我据此连错 5 版） |
| **276** | ⭐⭐⭐ **"计数器"比"存在性日志"值钱**：`5 个消息项了但一次都没注入成功` 一行就推翻了我"主人没喂到数据"的结论 |
| **277/278** | ⭐⭐⭐ **"分支从未执行" ≠ "对象不存在"**：日志必须带**对象身份**（类名/角色值）才能区分 |
| **283/284** | ⭐⭐⭐ **探针要内联在"已证明会打印"的位置旁边**；**子函数的 `catchall` 是沉默的黑洞**（`logE` 不进 DIAG） |
| **285** | ⭐⭐ **同一现象连续三版未解 ⇒ 换"证据载体"，别继续推断** |
| **286** | ⭐⭐⭐ **互斥分支的自检绝不能共用 tag** |
| **287** | ⭐⭐⭐ **探针必须打印"判据真正用的那份数据"**（106 的探针在覆盖前、判据在覆盖后 ⇒ 白推一轮） |
| **289** | ⭐⭐⭐ **"作用域计数"会把绘制阶段的调用整类漏掉**（助手底在组合期、用户底在绘制期） |
| **292** | ⭐⭐⭐ **"探针门要宽、重写门要严"，两者别绑成一个条件** |
| **294** | ⭐⭐⭐ **调用点（caller）是最稳的身份证之一**（形状相同 `c84` 时分不开，靠 `ls9.f` 一次分清） |
