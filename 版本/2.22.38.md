# NL 2.22.38 —— 🕐 修「日志从来没被删过」：清理时机从 `handleLoadPackage` 挪到「第一次真正写日志」

> 产物：**`FuckDSManger_NL_2.22.38_for_ds2.5.2.apk`**（**vc369 / 125 类 / V1+V2+V3 / sha256(partial) `0a83a04b…`**）
> 基线：`FuckDSManger_NL_2.22.37_for_ds2.5.2.apk`（vc368 / `66742d81…`）

---

## 0. 主人回执

> 「不行，你这个 **dsmlogs 压根没删掉过**」

**完全正确** —— 2.22.36 / 2.22.37 两版的清理**一次都没执行到 `delete()`**。

---

## 1. 🔴 真根因：调用时机太早，`GmUtil.app()` 返回 null

```smali
# GmUtil.app()
sget-object v1, Lcom/varuns2002/disable_flag_secure/gm/GmEntry;->sAct:Landroid/app/Activity;
if-eqz v1, :cond_6
return-object v1                                  # ← sAct 只在 MainActivity.onResume 之后才有
:cond_6
... ActivityThread.currentApplication() ...       # ← 进程最早期通常还没 Application
```

而 `handleLoadPackage` 是**进程最早期**跑的（Application 还在创建中）⇒ **`app()` 返回 null**
⇒ `clear()` 第一句 `if-nez v0, :end` **直接吞掉** ⇒ 什么都没做。

**佐证**：文件日志本身能被写出来 ⇒ 说明**稍后** `app()` 是可用的 ⇒ 问题纯粹是**时机**。
（`GmLog.dir()` 有 `sDir` 静态缓存，所以「第一次失败之后」它还会再试 —— 而 `clear()` 没有这层容错。）

---

## 2. 修法：把清理绑到「第一次真正要写日志的那一刻」

```
GmLog.w(内容):
    ① v0 = dir()                    ← 用 GmUtil.app()，拿不到就返回 null
    ② if (v0 == null) return        ← 连日志都写不了 ⇒ 什么都别做
    ③ if (!sCleared) { sCleared = true; clear(); }   ← ★ 清理挪到这里
    ④ …原有轮转 + 写文件…
```

**为什么这样最稳（三个要点）**：

| 要点 | 说明 |
|---|---|
| **时机精确** | 走到 ③ 时 `dir()` 已非空 ⇒ **`app()` 必然可用** ⇒ `clear()` 一定打得中 |
| **不丢日志** | 清空发生在**本次这条日志写出之前** ⇒ 本次日志照样落盘；被清掉的正是**上一轮会话**的 `dsm.log` |
| **只清一次** | `sCleared` 标志 ⇒ 不会每条日志都去删一次文件 |

> ⚠️ 中途踩过一个小坑（同版内已修正）：第一版把 `sCleared = true` 写在 `dir()` 判断**之前** ——
> 那样「第一次 `w()` 时 `app()` 还不可用」会把标志提前置真 ⇒ **以后永远不清**。
> ⇒ **现在标志只在「`dir()` 非空」之后才置位**（见 §2 的 ③ 位置）。

同时：`handleLoadPackage` 里 2.22.36/37 加的那句 `GmLog.clear()` 调用**已删除**（它在那一刻必然无效，留着只会误导）。

## 5. 教训（807~808）

| # | 内容 |
|---|---|
| **807** | ⭐⭐⭐ **「静默吞掉」很容易把「失败」也一起吞掉**：`clear()` 为了「没日志就静默」写成 `if (ctx == null) return`，结果**每次调用都静默地什么也没做** —— 从日志、从行为上**完全看不出来**。⇒ **凡是「允许静默失败」的分支，至少要能回答「它到底执行了没有」**（本例的最好验证方式就是主人那句「**压根没删掉过**」—— 用户的朴素观察比任何日志都直接）。 |
| **808** | ⭐⭐⭐ **「什么时候调用」和「调用什么」一样重要**：`handleLoadPackage` 看着像「进程启动时」的天然锚点，但那一刻**连 Application 都还没创建**，任何依赖 `Context` 的操作都会哑掉。⇒ **在 Xposed 里选锚点时，先问「我要用的依赖在这个时刻存在吗」**；拿不准就往「**第一次真正用到它**」的地方挂（本例：第一次写日志时），那样依赖必然已就绪。 |
