## 一、从 `a=105 M=105 x=3` 推出的结论

（OCR 读到的截图关键行：`AI 未捕获（a=105 M=105 x=3）`）

三个数摆在一起，有个**刺眼的一致性**：

| 数 | 含义 | 异常点 |
|---|---|---|
| `a=105` | `h91.a` 有效调用（有参数）105 次 | ✅ 说明它**其实一直在跑**（之前那版"没调用"是采样窗口问题） |
| `M=105` | `sWr` 被写入 105 次 | ⚠️ **和 `a` 一模一样** ⇒ 说明写入者**就是 `h91.a`** |
| `x=3` | `wr.x()` 返回非 null 3 次 | ⇒ `sList` 本应被赋值过 |

**可 `sList` 却是空的** ⇒ 矛盾。

**推理**：`h91.a` 是 `static`（`thisObject == null`）、返回 `void`（`getResult() == null`）—— 两个分支都**不该**进。既然 `M` 每次都 +1，只剩一种可能：

> **`getResult()` 返回的不是 null** —— Compose 编译后的函数返回 `kotlin.Unit` 实例，
> 于是它被 `:aft_other` 分支当成"消息容器"**存进了 `sWr`**。

接下来 `sync()` 里 `sWr.getClass().getMethod("x")` 当然找不到 `Unit.x()` ⇒ 抛异常被 catch 吞掉 ⇒ **`sList` 永远是 null**。

**⇒ 根因：`afterHookedMethod` 的分派只按"方法名"分，没校验"对象类型" —— 任何非 null 返回值都会被当成 `wr`。**

## 二、修复

### 1. `sWr` 只接受真正的 `wr` 实例

新增 `sClsWr:Ljava/lang/Class;`，用 `XposedHelpers.findClass("wr", loader)` 解析（只解析一次），然后：

```smali
candidate = result != null ? result : thisObject
if (candidate != null) {
    if (sClsWr == null) sClsWr = findClass("wr", loader)      // 解析失败则宽松放行
    if (sClsWr != null && !sClsWr.isInstance(candidate)) return   // ★ 不是 wr ⇒ 丢弃
    sWr = candidate; M++
}
```

> ⚠️ 中途我自己还埋了个雷：写成 `if-nez v4, :aft_store`（"解析过就跳过校验"），
> 等于**校验只在第一次生效** ⇒ **读回自检时抓出来并当场改成 `if-eqz v4, :aft_verify`**。

### 2. Toast 增加三个状态位

```
AI 未捕获（a=? M=? x=? w=? l=? e=?）
                        ↑   ↑   ↑
                     有sWr 有sList  sync()异常
```

| 位 | 含义 |
|---|---|
| `w` | `sWr`（消息容器）是否已拿到 |
| `l` | `sList`（消息集合）是否已拿到 |
| `e` | `sync()` 的异常摘要（null 显示 `-`）⇒ **新增 `sErr` 字段** |

**⇒ 下次不管成不成，这一行就能把问题钉死，不用再翻日志。**

## 四、教训

| # | 教训 |
|---|---|
| **389** | ⭐⭐⭐ **hook 回调里拿到对象一定要验类型，不能只按"方法名/来源"分派**：Compose 函数返回 `Unit`（非 null！）⇒ 被误当业务对象存下 ⇒ 后续反射全炸且被 try/catch 静默吞掉，**最难查的一类 bug** |
| **390** | ⭐⭐⭐ **诊断数字之间的"巧合相等"就是线索**：`a=105` 和 `M=105` 完全一致 ⇒ 立刻指向"两者是同一次调用产生的" |
| **391** | ⭐⭐ **自检读回能救命**：`if-nez`/`if-eqz` 写反那次（校验只生效一次）在构建前就被抓到了 |
| **392** | ⭐⭐ **异常要留痕**：`catch` 里只 `return` 不留信息 ⇒ 出问题时完全瞎。**本版起 `sync()` 的异常进 `sErr` 并显示在 Toast 上** |
