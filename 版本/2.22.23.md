## 0. 主人回执与一句话结论

**回执**：修完之后 **图片能用了**，但——
> 「只显示在消息左上角，剩下的是图片边缘颜色拉伸」

**结论**：**这不是图的错，是「铺法」缺了一层**。
我们交给宿主的是 `tn0(android.graphics.Shader)`（`tn0` = 宿主的 `ShaderBrush` 子类，**原样返回你给的 shader，忽略 size**）
⇒ Skia 用**单位矩阵**画 `BitmapShader` ⇒ 图以 **1:1 像素** 贴在**节点(气泡)左上角**，
比气泡小 ⇒ 剩下的地方被 `TileMode.CLAMP` 用**最后一行/列像素拉伸**填满 ✓ 与回执完全吻合。

⇒ 本版：**把图按气泡的真实像素尺寸做「居中裁剪铺满」**（就是 Compose 官方 `Brush.Bitmap` 干的事），
借宿主的 `ShaderBrush.createShader(size)` 这一步，在它拿到 size 的瞬间算矩阵。

## 2. 改动清单

| # | 位置 | 改动 |
|---|---|---|
| 1 | **新类 `GmBmpShader`** | `extends android.graphics.BitmapShader`（**框架类**子类，只透传三参构造器）—— 用来给「我们的图刷」打**不可能撞车**的身份标记（宿主不可能有这个名字的类；且不依赖任何宿主混淆名） |
| 2 | **新类 `GmBubbleFitHook`** | 挂 `tn0.b(J)Landroid/graphics/Shader;`（`hookAllMethods`）。`beforeHookedMethod` 里：`thisObject.d instanceof GmBmpShader` + `sBmp != null` ⇒ 取 `args[0]`（打包的 `Size`）⇒ **`w=高位float` / `h=低位float`** ⇒ `s = max(w/bw, h/bh)`（cover）⇒ `Matrix.setScale(s,s)` + `postTranslate(-(bw*s-w)/2, -(bh*s-h)/2)` ⇒ **`new GmBmpShader(bmp, CLAMP, CLAMP)` + `setLocalMatrix` ⇒ `param.setResult(新shader)`** |
| 3 | `GmBubble.imgBrush` | 图刷改用 **`GmBmpShader`**（同一签名）；顺手把解码出的位图记进新静态字段 **`sBmp`** |
| 4 | `GmBubble` | 新字段 `sBmp:Landroid/graphics/Bitmap;` |
| 5 | `DisableFlagSecure` | 注册 `hookM(cl, "tn0", "b", GmBubbleFitHook)`（紧挨 `uia.v`/`uia.u`）+ 注册完成日志加 `tn0.b` |
| 6 | 版本 | manifest `353→354`、`2.22.22→2.22.23`；自检串 → `模块 NL 2.22.23 生效` |

**为什么必须「每次尺寸新建一个 shader」而不能共用一支**：
Compose 会把 `paint.shader` 记进**显示列表**（RenderNode）——同一个 shader 对象被两个尺寸不同的气泡引用时，
后设的 `localMatrix` 会**污染先画的那个**（同帧内 A/B 都按最后一次的矩阵渲染）⇒ 每个 (刷, 尺寸) 各一支才是对的。

**为什么用「子类」而不是「集合去重」**：列表里每个气泡各造一支 brush，
`imgBrush` 只记得住「最后一次」的 shader 引用 ⇒ 集合/单引用都会漏掉别的项；
而 `instanceof GmBmpShader` 对**所有**我们的刷都成立 ✓（且宿主自己的 `tn0` 包的是渐变/RuntimeShader，天然排除）。

## 5. 教训（749 起）

| # | 要点 |
|---|---|
| 749 | ⭐⭐⭐ **`android.graphics.Shader` 是「无尺寸感知」的**：`BitmapShader` 默认按**单位矩阵 + CLAMP** 画 ⇒ 永远是「1:1 贴左上角 + 右/下拉伸边缘」。**任何「当背景/铺满」的需求都必须自己按绘制尺寸算 `localMatrix`**（这就是 Compose `Brush.Bitmap` 存在的理由） |
| 750 | ⭐⭐⭐ **「借宿主现成实现」也有粒度之分**：`tn0` 只借到了「Shader→Brush 的包装」，**没借到 `Brush.Bitmap` 的按尺寸缩放**（本宿主 R8 把 `Brush.Bitmap` 剪掉了 —— 全 dex 只有 4 个 `ShaderBrush` 子类，无一包 `ImageBitmap`/`Bitmap`）⇒ **借之前先确认「要借的那一步」在不在** |
| 751 | ⭐⭐⭐ **共享 shader = 共享可变状态**：Compose 把 shader 记进显示列表 ⇒ 一支 shader 服务多个尺寸时，`localMatrix` 会互相污染（同帧全按最后一次渲染）。**按尺寸新建**才安全 |
| 752 | ⭐⭐ **给对象打标记的最稳做法 = 用「只有我有的类型」**（本文 `GmBmpShader extends` 框架类），比「全局集合/字段比对」稳（列表多项、brush 实例多份时都不漏），也不碰宿主混淆名 |
| 753 | ⭐⭐ **hooking「无尺寸感知」的中间层要选对方法**：`ShaderBrush.applyTo` 是 final 且被**全 App 每个渐变**调用（热路径）；而 `createShader` 只在**尺寸变化**时调用（冷路径）⇒ 钩后者 |
| 754 | ⭐⭐⭐ **MT 的 smali 汇编器把方法寄存器数卡在 16**：`.registers 18` + `p1`（= v17）直接被拒（`Invalid register: v17. Must be between v0 and v15`）⇒ 需要更多寄存器时，**把参数按绝对寄存器别名引用**（`.registers 16` ⇒ **`v15` 就是 `p1`**）并把局部压进 v0..v13 |
| 755 | ⭐⭐ **`const/high16 vX, 0x3f000000` 直接喂 `mul-float` 是合法的**（宿主 d8 产物里 `const/high16 0x3f800000` + `cmpl-float` 就是常态）⇒ 别为了「类型洁癖」多写 `int-to-float` |
