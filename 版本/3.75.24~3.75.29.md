## 二、真凶链（每一步都是证据，不是推断）

### ① 先证明 hook 是好的（排除"没挂上"）
```
[FDS] row case=5              ← GmEntryHook 命中了
【FdmUiHook】显式 拉起失败…    ← 我也拦到了
```
⇒ hook 机制没问题，问题在**挂错了入口**。

### ② 现场取证：设置页那一行到底是谁渲染的
`uiautomator dump` 得到那一行的真实文本是 **「FuckDSManger 插件列表」**
（= `GmResTextHook` 把 `profile_check_for_updates` 改了，**改字成功了**）。

静态追到 `h43`（`ComposableSingletons$SettingsPageKt`）：
```
SettingsPage.kt:493 → const v2, 0x7f0f0266 (profile_check_for_updates)
                    → Lzwa;->b(...)  ← onClick 参数传的是 null
```
**那一行的 onClick 不在 `zwa.b` 里** ⇒ 改字和点击确实是两条路。

### ③ 上一版的 hook 为什么形同虚设
`GmEntryHook` 挂的是 `m5/t5/z5` = 设置行 → **路由桶**。
它的 29 个 case 是「批量管理 / 语言 / 外观 / 退出登录」这类**有路由键**的行：
```
:pswitch_6b  const-string "logout_all_sessions_click"
:pswitch_d2  const-string "batch_management_click"
```
「检查更新」**根本不在这张 switch 里** ⇒ 永远碰不到。
（这条和 `专题/写死字面量坑` 第 1 条「case 号」是同一个坑的另一种形态：
 **别假设一个 switch 里有你要的东西，要看它的表**。）

### ④ frida 抓真身（决定性证据）
锚点：Toast 文案必然从 `Context.getString(int)` 出来。
```
[u2] CW.getString 0x7f0f0267 => 当前已是最新版本
      android.content.Context.getString(Native Method)
      ol2.j(:121)                    ← 通用 lambda 分发器
      pg7.z(:428)   ★★★★★            ← 点击逻辑本体
      sj0.h(:5)                      ← 协程 ContinuationImpl.resumeWith
      wy3.run(:112) / Handler.post
```
再读 `pg7.z` 的 `this.e`（R8 把一堆 suspend lambda 合并进 **一个** 类，
`e:I` 是 packed-switch 索引）：
```
[u3] pg7.z e=23 → 命中"当前已是最新版本"（路径A: pg7.z:428）
[u3] pg7.z e=22 → 命中"当前已是最新版本"（路径B: jv.a → n2a.m → m2a.z）
```
两次点击分别落 **23 / 22**，都直通同一句 ⇒ 同一功能、同一条路。

## 三、修法

新增 `bridge/FdmUpdateRowHook.java`：挂 `pg7.z`，只在 `e ∈ {22,23}` 时动作。

| 步 | 做什么 |
|---|---|
| 1 | `caseOf(thisObject)` 读 `this.e`，不是 22/23 ⇒ **原样放行**（别人的 lambda 不碰） |
| 2 | 800ms 去抖（连点不重复拉） |
| 3 | `FdmUiHook.openComposeFromHook(ctx)` ⇒ 拉起 Compose UI（复用同一条链，不复制） |
| 4 | `setResult(kotlin.Unit)` ⇒ **跳过宿主"检查版本"逻辑**（不再弹"已是最新版本"） |
| 5 | 取不到 `Unit` ⇒ **不 setResult**（宁可弹提示，也不要把协程搞坏） |
| 6 | 全程 `try/catch` 吞异常（热路径铁律） |

`GmRemap` 加一行锚点：
```java
{"settings.row.update.z", ..., null, null, "pg7", "z"},   // e=22/23
```
`FdmEntry` 里在 `isHost()` 成立时 `FdmUpdateRowHook.install(lp.classLoader)`。

## 四、这一夜踩的五个坑（全部有日志血证）

| # | 坑 | 证据 |
|---|---|---|
| **1** | **`new_elem()` 写带子节点的元素** ⇒ 吐出 `<receiver/>` + 游离 `</receiver>` ⇒ intent-filter 变兄弟 ⇒ PMS 直接丢掉 | `cmd package query-receivers -a …OPEN_UI` → **No receivers found**（而 base.apk 里明明有）。这正是 3.75.22「广播无效」的**真因**，我上次把锅甩给了 ROM / 包可见性 |
| **2** | **改完包不重启宿主** ⇒ 跑的还是旧 dex | `动作 open_ui_pi → （该动作暂未接通）` —— 新代码里根本没这句，说明进程里的桥是旧的 |
| **3** | **`MTH` 表的键是「类.方法」拼串**，我却写成了不含方法名的 `settings.row.update` | `✗ 挂载失败 settings.row.update.settings.row.update：ClassNotFoundException: settings$row$update`（3.75.28 血证） |
| **4** | **`remap_selftest.py` 要求每行一条记录**（跨行写会 `ValueError: substring not found`） | 工具直接抛异常 |
| **5** | **日志只看一条通道** ⇒ 查了三轮都"没有日志" | `GmUtil.log` 只进 dsm.log，而 `install` 那行我一开始没去 LSPosed 日志找。改成**双通道**（GmUtil + XposedBridge）后一眼就看见 |

### 教训（接在教训清单后面）

| # | 教训 |
|---|---|
| **270** | ⭐⭐⭐ **改文案 ≠ 接管点击**。文案是 Resource / Composable 参数；点击是 onClick lambda。改了一个不能假设另一个跟着动 |
| **271** | ⭐⭐⭐ **别假设 switch 里有你的 case**。先 `dump` 出 `packed-switch` 的表和分支首行，看它到底管哪几件事（`z5` 的 29 个 case 全是"有路由键"的行） |
| **272** | ⭐⭐⭐ **AXML 里带子节点的元素，绝不能复用只吐 start+end 的 helper**。现已加 `check_manifest_tree()` 机械闸门，出包前强制校验标签配对 |
| **273** | ⭐⭐⭐ **「dumpsys 查不到组件」先查清单编码，再怀疑 ROM**。`aapt2 dump` / 自己 decode 一遍，比猜快一百倍 |
| **274** | ⭐⭐ **装完包必须强停宿主**。（这条已写过，今天又栽一次 —— 因为"看起来"在跑） |
| **275** | ⭐⭐ **验证 hook 挂载，要去看 LSPosed 日志**（`XposedBridge.log`），不能只看自家文件日志 |
| **276** | ⭐⭐ **R8 会把一堆 suspend lambda 合并成一个类**，靠 `this.<int 字段>` 的 switch 索引区分 ⇒ 定位时**必须**同时抓到 case 号，否则"改了同一类的别的方法"风险极高 |
| **277** | ⭐⭐ **frida 找锚点用"必然发生的副作用"**：这次用 `Context.getString(resId)` —— Toast / 提示文案必经此处，比猜方法名可靠得多 |
