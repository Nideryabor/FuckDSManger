## 一、为什么换 PopupWindow 反而"没了"

`PopupWindow.showAtLocation()` 需要**目标窗口的 token 有效**；而它是在 `MainActivity.onResume` 里被调用的 —— **此时 activity 的窗口往往还没 attach**（窗口是在 onResume 之后由 `handleResumeActivity` 才加上去的）

⇒ 抛 `BadTokenException: Unable to add window -- token … is not valid; is your activity running?` ⇒ 挂载失败 ⇒ 没按钮。

而 **DecorView `addView` 不需要 token** —— 这正是 2.13.3 能显示的原因。
（两个方案的取舍：DecorView = 看得见但可能点不到；PopupWindow = 点得到但需要 token）

## 二、2.14.1 的做法：**双通道**

```
show()
 ├─ 通道 A：GmCallBtn.pop() → PopupWindow.showAtLocation()
 │    成功 → 日志「已挂上（PopupWindow）」
 │    失败 → 落盘堆栈 + 日志「PopupWindow 失败 ⇒ 回退 DecorView」
 └─ 通道 B（回退）：decorView.addView(view, FrameLayout$LayoutParams + gravity=0x33 + margins)
       → 日志「悬浮钮已挂上（DecorView 回退）」
```

两个通道**只要有一个成功，按钮就在**。

## 三、顺带修掉一个隐藏杀手：守护线程每秒重建

`ensure()` 原来只看 `sPop`：

```smali
# 2.14.0（错）
sget-object v0, sPop
if-eqz v0, :rebuild        # 走 DecorView 回退时 sPop 恒为 null ⇒ 每 1s 重建一次！
```

⇒ **每秒 dismiss + 重建**，不仅闪，还会**打断触摸流**（这正是 2.13.3「点了没反应」的头号嫌疑：那一版守护线程每秒 `bringToFront()`，而 `bringToFront` 内部就是 remove + re-add）。

**2.14.1**：`ensure()` 改成「**只要 view 还挂在 view 树上（`getParent() != null`）就算活着**」，两个通道都死透了才重建：

```
activity 变了 → 重建
sView == null → 重建
有 popup → isShowing() 就活着；不在显就再看 view 是否还挂树上
无 popup → view 有 parent 就活着
否则 → 重建
```

`hide()` 也补上了「从 view 树摘下来」（回退通道用得到）。

## 六、教训

| # | 教训 |
|---|---|
| **510** | ⭐⭐⭐ **`PopupWindow.showAtLocation()` 不能挂在 `onResume` 那一刻**：activity 窗口还没 attach ⇒ `BadTokenException`。**DecorView.addView 不需要 token**（代价是可能收不到触摸）⇒ 两者是"能显示"与"能点击"的取舍，**要按场景选，或两条都上**。 |
| **511** | ⭐⭐⭐ **守护/复检逻辑必须把"所有存活形态"都算作活着**：2.14.0 的 `ensure()` 只认 `sPop`，于是回退通道下**每秒重建一次**，把按钮变成"闪一下 + 点不动"。**判活条件漏一种形态 = 兜底代码自己变成故障源**。 |
| **512** | ⭐⭐ `ViewGroup.bringToFront()` 内部是 **remove + re-add**（会打断触摸流）⇒ **`bringToFront` 不能放进高频循环**（尤其别放守护线程）。 |
