# 3.43.5 → 3.43.7 —— 「图片底缩放」两真凶 + **logcat 通道打通**

> 主人定规（2026-10-03）：「**以后走 adb 抓 logcat，不可用再往私有目录写文件**」
> ⇒ 本轮的**基础设施收获**比 bug 本身重要：模块日志终于能从 logcat 直接读。

## 一、logcat 通道（为什么以前看不见 + 怎么打通的）

- **为什么看不见**：我们的日志走 `XposedBridge.log` → **LSPosed 写它自己的日志文件**
  （`/data/adb/lspd/log/`，**要 root**）——**压根不经过 logcat**（不是被吞，是不走这条路）。
- **打通**：给 `GmUtil.log` / `GmUtil.logE` 各加一句 **logcat 镜像**（tag `FDM`）。
  因为 `logOnce` / `logFail` / `logE` 都汇到这两个 ⇒ **一处补丁，全套模块日志进 logcat**。
- 探针（GmFitProbe）改成 **只写 logcat**（tag `GMFIT`），**私有目录写文件的代码整段删除**。
- 读法：`adb shell logcat -d -b all | grep -a FDM`（**别用 `\|`**：设备上的 toybox grep 不支持，
  害我白看两次"空的"）。
- 抓启动全过程：`logcat -c; (logcat -s FDM:V GMFIT:V > /data/local/tmp/x.txt &); 重启宿主`（shell 临时文件，非私有目录）。

## 二、两个真凶（logcat 一次全交代）

### 真凶①：`jq0.b` 通道**从来没装上**
```
hookM FAIL jq0.b
E FDM : java.lang.VerifyError: Verifier rejected class ...GmBubbleFitHook:
        beforeHookedMethod ... [0xA5] register v6 has type Float but expected Integer
```
⇒ 该类的手改 smali **过不了 ART 校验**（历史遗留的类型混用）⇒ `Class.forName` 就抛 ⇒ 装不上。
**"FitHook 从未生效"的老悬案到此结案。**
→ 处置：**停用该通道**（im9.a 那条不 setResult、更安全），并在 GmEntry 里写明原因。

### 真凶②：第二通道 `im9.a` 装上了，但**尺寸解码错**
它进了钩子、也动作了，可 scale 是 **1740197.9**（1.7e6 倍）——
因为 Size 打包里存的是**浮点位模式**（`1440.0f` = `1152647168`），我当整数读了。
→ 处置：`Float.intBitsToFloat()` 解宽高（与宿主 Size 打包一致）。

## 三、3.43.7 实测（logcat 自证）

```
hookM im9.a count=1                                   ← 装上了（jq0.b 的 FAIL 消失）
APPLY im9.a 生效 scale=2.174  target=1440x4158 bmp=616x640   ← 整页那次
APPLY im9.a 生效 scale=0.536  target=512x161  bmp=888x888    ← 气泡那次
```
- scale 公式 = **目标宽/图宽 × 「缩放」倍率**（日志反推出主人当前倍率 ≈93% ⇒ 滑杆真的在起作用了）。
- 也证实：我们的图刷子会被用在**两种尺寸**上（整页级 + 气泡级），各自套各自的铺满比例。

## 五、教训（接 881）

| # | 教训 |

| **881** | ⭐⭐⭐ **"日志看不见"先分清"没日志"还是"日志走了别的路"。** 我们一直在找"logcat 里为什么没有"——真相是**根本不走 logcat**（XposedBridge→LSPosed 文件，要 root）。**打通一条日志通道 = 一次性的解放**（后面几轮全靠它）。 |
