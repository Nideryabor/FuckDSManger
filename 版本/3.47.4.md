## 一、★ 链路（全部 frida 实证，不是推断）

```
```html 代码块（AI 输出）
  │
  ├─ ① 语言闸门   o01（MarkdownCodeKt）里：
  │      v7a.M(代码块语言, "mermaid", true)Z
  │      ⇒ 我们让 "html" 也返回 true ⇒ 宿主把它当成 Diagram
  │
  ├─ ② 建 WebView  new MermaidGeneratorWebView(Context)
  │      ★ 内联渲染用的是 **Generator**，不是 Viewer
  │        （Viewer 是"点图表全屏预览"那条路 —— 我在它身上 hook 了好几轮，一条都不中）
  │
  ├─ ③ 加载页面   loadUrl("file:///android_asset/generator.html")
  │      ⇒ ★ 我们把它换成自建页的 data: URL
  │
  ├─ ④ 投递内容   evaluateJavascript(
  │        "if (window.generateMermaid) { window.generateMermaid(源码, "dark"); }")
  │      ⇒ 命中**我们页面里**的 generateMermaid
  │
  └─ ⑤ 渲染 + 回执
         我们的实现：HTML → <svg><foreignObject> → Image → canvas → PNG dataURL
         → window.AndroidBridge.onImageRendered(png, "")
         ⇒ 宿主拿到 PNG，显示在代码块位置
```

### 从资产里逐字读出来的协议（`assets/generator.js`）

| 项 | 值 | 写错的后果 |
|---|---|---|
| 接口名 | `window.generateMermaid(src, theme, maxW, maxH)` | 宿主那句 `if (…)` 不成立 ⇒ 什么也不发生 |
| 成功回执 | `window.AndroidBridge.onImageRendered(dataURL, type)` | — |
| 失败回执 | `window.AndroidBridge.onImageRenderFailed("RENDER_FAILED", msg)` | — |
| **回执对象** | **`AndroidBridge`**（不是 `NativeBridge`！） | 永远等不到回执 ⇒ 卡在「生成中」 |
| 全屏那条路 | `window.JSBridge.requestRenderMermaid(src,id)` → `NativeBridge.onMermaidRendered("FINISHED",id)` | 点全屏黑屏 |

> `NativeBridge` 是 **viewer**（全屏预览）用的，`AndroidBridge` 才是 **generator**（内联渲染）用的。
> 两个页面协议不同 —— 这是最容易搞混的一处。

## 二、★★★ 五个坑（每个都烧掉了好几轮）

### 坑 1：`am force-stop` 在这台设备上**完全无效**

```
$ ps -A | grep deepseek          → 1 个进程
$ am force-stop com.deepseek.chat.a
$ ps -A | grep deepseek          → 还是 1 个！  ← 进程没死
```

**⇒ 宿主一直是同一个进程 ⇒ LSPosed 加载的还是旧 dex ⇒ 我中间那几版（3.46.1~3.46.3）从头到尾没生效过**，
而我还一直在纳闷"为什么探针一条都不打"。

**✅ 正解：`am start -S`**（它内部走的是另一条路，实测有效：进程 11171 → 14813）。

> ⚠️ 项目里所有部署脚本用的都是 `am force-stop` —— **以后统一换成 `am start -S`**。
> 这大概也是过去好几次"装了没反应"的隐藏原因之一。

### 坑 2：现场日志根本抓不住（logcat 256 KiB 环形）

```
main: ring buffer is 256 KiB (254 KiB consumed)   ← 实测
```

而模块自己每帧都在打 `PHook: kh7.x id=…`（你日志里 8 秒 150 条）⇒ **几分钟滚一整圈**。
DIAG 也是 256 KiB，同样的问题；而且来回"回读→摘抄"还容易在缩短时切掉关键几行。

**✅ 正解：改用 frida 白名单网关（投递式）**

```
尼尼写 /data/local/tmp/frida_job.txt  →  run.sh（root，校验白名单）→  frida-inject
                                          →  /data/local/tmp/frida_out/result.txt  →  尼尼读
```

**没有端口、没有常驻进程、尼尼碰不到任何秘密**。
`title=网页无法打开` 这条决定性证据，就是它 **35 秒**抓出来的 —— 而靠 DIAG 来回对了七八轮都没看见。

### 坑 3：`file://` 被 `targetSdk>=30` 默认禁掉

第一版我把自建页写进 `filesDir` 再 `file://` 加载，frida 拿到的是：

```
url   = file:///data/user/0/com.deepseek.chat.a/files/fdm_generator.html
title = 网页无法打开                                    ← ★ 页面根本没加载
```

**⇒ `window.generateMermaid` 不存在 ⇒ 宿主那句 `if (…)` 跳过 ⇒ 卡在「生成中」。**

宿主自己能用 `file:///android_asset/…` 是因为 `android_asset` 走**特权通道**，不吃这条限制。

**✅ 正解：`data:text/html;charset=utf-8;base64,…`** —— 不是文件访问，不受管。

### 坑 4：★★★ `<br>` 会毁掉整份 SVG（"复杂文档渲染失败"的真凶）

SVG 是 **XML**。XML 里 `<br>` / `<img>` / `<hr>` 这类空元素**必须自闭合**。
我早期是把 `el.innerHTML` 直接拼进 `<foreignObject>` ⇒ 文档里一有 `<br>` 就是格式错误
⇒ **整份 SVG 解析失败** ⇒ `img.onerror` ⇒ 渲染失败。

**⇒ 这解释了"简单表格能过、复杂文档过不去"**（表格里没有空标签，而 AI 写的介绍页里到处都是 `<br>`）。

**✅ 正解：`new XMLSerializer().serializeToString(holder)`** —— 它按 XML 规矩输出
（`<br>` → `<br />`），顺带处理好 `&`、属性引号。CSS 另做一次转义（`&`→`&amp;`）。

### 坑 5：`<script>` 不会执行

`innerHTML` / `XMLSerializer` 插进 DOM 的 `<script>` **都不会跑**（浏览器安全规则）
⇒ 打字机、数字滚动、滚动显现这些**回调驱动的元素渲染出来全是空白**。
真机症状就是主人那句：「打字机……打字机没有字」。

**✅ 正解：把 `<script>` 抠出来手动执行一次**（`new Function(code)()`），
并把截图前的等待从 40ms 提到 **260ms**（给动画时间打出几个字）。

## 三、其他几处"要记一笔"

| # | 事 | 说明 |
|---|---|---|
| 1 | **宽度要取内容宽度** | 用容器宽 ⇒ 表格只占图里一小条，铺满后显小。包一层 `inline-block`，它的 `offsetWidth` 就是内容自然宽 |
| 2 | **透明底** | canvas 不 `fillRect` ⇒ 保留 alpha，让内容自己的背景（或气泡背景）透出来（主人提的） |
| 3 | **尺寸保护** | 超 4000×8000 直接拦下报 `TOO_LARGE`（那种尺寸下 SVG→图片必失败，与其黑屏不如报清楚） |
| 4 | **预览被裁剪是宿主的行为** | frida 测到宿主给的 `contentHeight=352`，而内容上千像素 ⇒「预览看个大概、全屏看完整」是当前架构下的合理分工 |
| 5 | **诊断出口：`document.title`** | 页面把状态写成 `FDM\|xxx` 放 title ⇒ frida 一句 `getTitle()` 就读到。（`Java.registerClass` 做回调在 attach+25s 窗口下**不稳**，实测 `status=empty`） |
| 6 | **WebView 方法必须在主线程调** | frida 里 `getUrl()` 直接调会抛 `All WebView methods must be called on the same thread` ⇒ 塞进 `Java.scheduleOnMainThread` |

## 四、⚠️ 两次"差点翻车"

### ① 编译失败但 `做包.sh` 没拦住，出了个旧 dex 的包

`GmHtml` 重写时把 `looksLikeHtml` 删了，而 Hook 里还在调 ⇒ `javac` 报错 ⇒ 但打包脚本照样出包了。
**⇒ 出包后必须核对 `build/dex/classes.dex` 的时间戳 / sha256 是不是新的**，不能只看"✅ 好了"。
（3.47.2 因此重出过一次。）

### ② 主人明确否决了"往外部存储写文件"

我一度实现了 `dump()`：把日志写到 `/sdcard/Android/data/<包>/files/`（adb 读得到，绕开缓冲）。
主人：**「我宁愿你 frida 插桩，也不允许你往外部存储写文件」** —— **这个否决是对的**：
那个目录虽然 adb 读得到，但**任何能读 SD 卡的东西**都读得到，而且"模块往存储里写日志"本身就是个风控特征。
⇒ 全部撤掉（`dump()` + 7 处调用），改走 frida。

## 五、方法论：这一轮真正的收获

**前 4 个包全在"猜"** —— 猜是 Viewer 还是 Generator、猜宿主用哪个方法投递、
猜为什么没命中。每猜一次就是"改代码 → 出包 → 装 → 重启 → 让主人测 → 回读日志"，
一轮十几分钟，而且**经常连关键日志都拿不到**。

**从 frida 网关接通那一刻起，节奏变成了**：

```
写 job  →  35 秒  →  result.txt 里有答案
```

三条关键证据全是它给的：

| 证据 | 一句话解决 |
|---|---|
| `title = 网页无法打开` | 页面压根没加载（FILE 权限） |
| `WebView#1 class = …MermaidGeneratorWebView` | 内联用的是 Generator，不是 Viewer |
| `evalJS 头 = … window.generateMermaid("<table", "dark")` | 投递函数名 + 参数序 |

**教训：能用「观测」拿到的事实，绝不要用「推断」代替。**
推断的代价是**每次都要让主人陪着跑一轮**；观测的代价是 35 秒。
