## 一、2.14.4 错在哪：判据本身不可靠

我拿 `M()` + `wr.a` 当"会话是否就绪"的判据。但宿主的 `I()` 里是这么写的：

```java
v1 = this.v.getValue() → ho1
if (v1 instanceof fo1) return;     // ⭐ 先挡掉"未就绪"状态
v1 = ho1.b() → wr                  // 只有就绪了才敢调 b()
```

而 `M()` 内部**不做这个保护**（直接 `((ho1)v.getValue()).b()`）⇒ 遇到未就绪状态会抛 ⇒ 我的 `sid()` 全 try/catch 成 null ⇒ **两个候选都被判"空" ⇒ 直接不发**。
（教训复读：**兜底判据自己不可靠时，"宁可不发"就变成了"永远不发"**。）

## 二、2.14.5 的做法：**配对**，不再猜

**关键事实**：`Lao1;-><init>` 里会 `new Lyp1()` —— **每个 component 都自带一个属于它的输入状态**。

于是把两者绑成一对：

| 钩子 | 动作 |
|---|---|
| `hookAllConstructors("ao1")` → `GmCallCtorHook` | **before**：`sCtor = thisObject`（正在构造的 component）<br>**after**：`sNewA = thisObject`，清空 `sCtor` |
| `hookAllConstructors("yp1")` → **新类 `GmCallYpHook`** | **after**：若 `sCtor != null` ⇒ **`sPairA = sCtor`、`sPairY = 刚建好的 yp1`**（＝"这个 component 的输入状态"） |

**发送时选人（优先级从高到低）**：

```
① sPairY == sYp1（活的输入状态）  ⇒ 用 sPairA  ⭐ 这才是"当前对话的 component"
② sid(sNewA) 非空                 ⇒ 用 sNewA
③ sid(sAo1) 非空                  ⇒ 用 sAo1
④ sNewA 非空                      ⇒ 兜底用它
⑤ 否则                            ⇒ 弹提示（不发）
```

每条路径都会落盘一行说明走的哪条（`[通话] 发送：用配对 component（输入状态匹配）` / `…sid=…` / `…兜底…`）⇒ 下次日志能直接读出判据命中情况。

## 五、教训

| # | 教训 |
|---|---|
| **523** | ⭐⭐⭐ **"就绪判据"必须和宿主自己的守卫一致**：宿主用 `instanceof fo1` 挡未就绪，我却在外面用 `M()` 盲调 ⇒ 判据本身会抛 ⇒ 全判成"空"。**判断"可不可用"要用宿主承认的那套条件。** |
| **524** | ⭐⭐⭐ **对象之间的关系，能"现场配对"就别"事后猜"**：`ao1` 造 `yp1`（构造器里 new）⇒ 直接挂两个构造器钩子把它们绑起来，一次配对终身受用；比"按 sid 非空挑一个"这种启发式可靠得多。 |
| **525** | ⭐⭐ **"宁可不发"必须配"判据可靠"**：保守策略在判据错时会退化成"永远不发"（本轮就是）。**保守 + 错误判据 = 功能消失**，比"发错地方"更难排查。 |
