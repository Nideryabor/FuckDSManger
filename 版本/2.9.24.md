## 一、为什么放弃「靠弹窗操作」这条路

本轮 OCR 日志再次显示：

```
FuckDSManger: prompt ENTER
FuckDSManger: prompt SKIP done-flag
```

`fuckds_dev_ask3` **只能由 2.9.23 的系统 AlertDialog 按钮写入**，但它已经是 `"done"`
⇒ **系统对话框也弹了、按钮也被点了，主人依然"什么都没看到"**。

⇒ 结论：**在这个宿主/环境里，任何弹窗形式的交互都不可靠**
（自绘 `Dialog` 不可见 ⇒ 换系统 `AlertDialog` 仍不可见）。
既然如此，就**彻底不依赖 UI**。

## 二、本版改动：默认开启

### 2.1 `GmDevice.refresh` 的开关判定反转

```
改前： sOn = "true".equalsIgnoreCase(fuckds_device_on)      // 只有显式 true 才开
改后： sOn = !("false".equalsIgnoreCase(fuckds_device_on))   // 除非显式 false，否则开
```

对应 smali：把比较串换成 `"false"`，结果 `xor-int/lit8 v0, v0, 0x1` 取反。

⇒ **新用户（从未设置过）默认就是启用状态**；只有用户主动在设置页关掉（写 `"false"`）才停。

### 2.2 效果

```
装 2.9.24 → 强停宿主 → 重新打开
   ↓
GmDevice.refresh → sOn = true（默认）
   ↓
ensureFake → 没有伪 ID 就生成一个（16 位 hex）
   ↓
GmDeviceHook 命中 Settings$Secure.getString("android_id") → 返回伪值
   ↓
Lex2.b() 自己算 AES ⇒ 请求头 x-device-id 变成全新值
```

**全程不需要点任何按钮、不需要任何弹窗。**

### 2.3 弹窗逻辑保留但不影响功能

`promptIfNeeded` 里新增的「设备身份已启用 ⇒ SKIP」正好让弹窗**不再打扰**
（默认启用后它自然就不弹了）。

### 2.4 版本

`AndroidManifest.xml`：`110/2.9.23` → `111/2.9.24`

## 四、教训（补充第十一节）

| # | 教训 |
|---|---|
| 109 | ⭐⭐ **当交互通道被证明不可靠时，应当重新设计"触发模型"，而不是继续换交互控件**：自绘 Dialog → 系统 AlertDialog → 仍然不可见。真正该做的是**取消交互依赖，让功能默认生效**。<br>"需要用户点一下才能生效"本身就是**可选的设计**，不是必须的 |
| 110 | ⭐ **"默认开"对这个功能才是正确默认值**：模组的目的是绕过风控，用户装它就是为了生效；把开关默认设为关、再要求用户去打开，等于把主流程变成了额外步骤 |
| 111 | **判定字符串要选"少数派"那一侧**：`sOn = "true".equals(x)` 与 `sOn = !"false".equals(x)` 在默认值上完全不同。**改默认值时，改比较串比加分支更不容易出错** |
