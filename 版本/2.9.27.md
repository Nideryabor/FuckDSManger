## 一、这一版修了什么（真 bug）

**`GmVectorHook` 的兜底缺口** —— 它会清空头像资源的 `TypedValue.string`（让 `painterResource` 走位图分支）。
门槛只有 `isOn && hasImage`：

```
isOn ✔ && hasImage ✔  →  破坏矢量加载
                          ↓
        然后 GmPainterHook 的替换「不一定成功」
        （解码失败 / sAct 空 / 抛异常 ⇒ 直接 return，没有 setResult）
                          ↓
        那条被破坏的加载路径**没人兜底** ⇒ 头像 = 什么都不画（不是蓝方块，是空白）
```

这正好解释了「**头像整个渲染都没了**」——**空白与蓝方块是两种不同的失败状态**：

| 现象 | 含义 |
|---|---|
| **蓝方块** | painter 替换**成功**了，只是被 `Icon` 的 tint（SrcIn）染成纯色 |
| **空白** | painter 替换**没成功**，而矢量加载已被我们破坏 ⇒ 没有兜底 |

**修法**：给 `GmVectorHook` 再加一道门槛 —— **只有 `GmPainterHook.sPainter != null`（替换用的 painter 已就绪）时才破坏矢量加载**。
⇒ 从此「替换不成功」时最多退回**宿主默认头像**，不会再出现「空白」。

> 顺带一个好处：首次调用时不再破坏，`painterResource` 走原生矢量分支正常返回，
> 我们的 `setResult` 照旧覆盖它（Xposed 的 `setResult` 会连原方法抛出的异常一起清掉）⇒
> **结果与资源加载路径解耦**，更稳。

## 四、★ 验收步骤（这次的关键：**必须先把聊天窗口打开**）

「头像」是在**消息列表渲染**时才合成的，所以在设置页/抽屉里取日志**永远看不到**相关行
（2.9.26 的回执就是这个情况）。

1. 装 2.9.27 → 重启宿主
2. **打开一个能看到 AI 回复的对话**（头像位置要有内容），停留几秒（滚动一下让消息列表重新合成）
3. 取 LSPosed 日志（过滤 `FuckDSManger`），或直接看头像

### 4.1 日志判读

```
PHook: kf5.K id=0x7f070059          ← ★ 头像合成确实发生了（只有 Lcka; 会请求这个 id）
PHook: ID MATCH avatar 0x7f070059
PHook: painter built OK             ← 照片解码 + BitmapPainter 造好了
GmVectorHook fired (painter ready)
GmIconHook: our painter reached Icon layer
GmPaintModHook: ColorFilter -> Dst(hengdeng) replaced, avatar should show original photo
```

| 日志情况 | 结论 | 下一步 |
|---|---|---|
| 全套都在 + **头像=彩色原图** | 🎉 完结 | 摘 `修改助手图片` 的 WIP、更新文档 |
| 全套都在 + 头像仍蓝 | 替换生效了，恒等 filter 没生效 | 查 `GmPaintModHook`（`fh6.N` 是否命中） |
| 有 `ID MATCH` 但没有 `painter built OK` | 卡在解码/开关 | 看紧随其后那行（`decode NULL` / `isOn FALSE` / `hasImage FALSE`） |
| **`PHook: kf5.K id=` 里根本没有 `0x7f070059`** | 头像合成根本没跑（宿主这一版不再用这条路径 / 这个 id） | 搜宿主里还有没有别的地方画助手头像（资源/URL）⇒ 换落点 |
| 头像变回**默认头像**（不再是空白） | 兜底修复生效 ✓ | 说明替换环节仍未成功，按上一行继续查 |

**注意**：`kf5.K id=` 只打前 16 次，够用（头像 id 只可能出现在消息列表渲染那几次调用里）。

## 五、教训（补充）

**第 114 条：⭐「功能没生效」要先分清是「A 环节失败」还是「A 失败后被 B 拖累成更糟的现象」。**
本轮之前一直以为头像问题是「染色」，但真机现象是**空白**——空白 ≠ 蓝方块：
蓝方块 = 替换成功（只是被 tint），空白 = 替换失败**且**我们事先破坏了原生加载路径。
先用日志把「替换成功/失败」这个二值确定下来，现象的两种形态立刻各有归宿。

**第 115 条：「破坏别人的方案」必须自带兜底条件（幂等/前置就绪判断）。**
`GmVectorHook` 清 `TypedValue.string` 属于典型的「先破坏、后替换」两段式：
只要替换段有任何一个 early-return，破坏段就成了净损失。
正确写法 = **破坏段的前置条件里，必须有「替换段的产物已就绪」**（本次：`sPainter != null`）。

**第 116 条：诊断日志要打在「用户能拿到的地方」，并且要能回答「到底跑到没有」。**
2.9.26 回执里一个头像相关行都没有，无法区分「hook 没挂上」和「头像没合成」。
本次改成：**按 id 记录前 N 次调用**（不是只记录命中）—— 这样「没命中」也变成一条可判读的信息。
