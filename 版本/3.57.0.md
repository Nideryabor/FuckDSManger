> 这样模型就知道我们在听哪里了」

---

## 〇、一句话

**给「系统提示词」加了一组会自己变的占位符** —— `{music}` `{song}` `{artist}` `{lyric}` …
在宿主**构造 completion 请求的那一刻**当场替换成真值。于是模型读到的永远是「此刻」在听什么、
唱到哪一句，而不是会话开头那一刻的**快照**。

---

## 一、为什么做成「变量」，而不是再灌一段提示词

「系统提示词」本质是**静态文本**：写进去什么样，发出去就什么样。而「我在听什么」是**时变**的。

三条路，只有第三条对：

| 方案 | 为什么不行 / 行 |
|---|---|
| ① 每次换歌就重写系统提示词 | 要把歌名写进**配置** ⇒ 等于每换一首歌改一次设置；还会和主人自己写的正文互相覆盖 |
| ② 发消息前用广播/轮询同步一次 | 绕远路。宿主**本来就在发消息时经过一个 hook 点**，直接在那儿取内存状态就行 |
| ③ **占位符 + 发消息那一刻替换** ✅ | 替换点 = 已有的 `GmSysPrompt.inject()`（挂 `ChatFullCompletionRequest` 构造器）⇒ 零新增挂点、零轮询、天然实时 |

**关键认识：`inject()` 被调用的时刻，正好就是「信息最新鲜」的时刻。**
歌词行、播放进度这类东西的「实时性」不是靠推送做出来的 —— 是**取数时机**决定的。

## 二、变量表

| 变量 | 有歌时 | 没在放歌时 |
|---|---|---|
| `{music}` | `《稻香》 - 周杰伦 (1:23/3:42)` | 空串 |
| `{song}` / `{artist}` / `{album}` | 歌名 / 歌手 / 专辑 | 空串 |
| `{music_pos}` / `{music_dur}` / `{music_left}` | 已听 / 总长 / 剩余（`m:ss`） | 空串 |
| `{music_state}` | `playing` / `paused` | 空串 |
| `{lyric}` / `{lyric_prev}` / `{lyric_next}` | 当前唱到的这一句 / 上一句 / 下一句 | 空串（**且需歌词开关**） |

**匹配口径**：只认 `{变量名}` 这种**精确形态** ⇒ 主人提示词里别的花括号（写 JSON 例子、写模板）
一律不会被误伤。

## 三、空值语义（主人 2026-10-07 拍板）

> 主人选项原文：「替换成空字符串 —— 整句自然断掉」

1. **变量一律变空串** —— 如实表达「此刻没有这个信息」，而不是编一句「（未在播放）」占位。
2. 配套给一个「糖」：`[[ … ]]` 包起来的整块，**块内至少有一个我们的变量、且它们全部为空**
   ⇒ **连块带括号整段删掉**。

```text
[[正在听：{music}]]
```
* 在放歌 ⇒ `正在听：《稻香》 - 周杰伦 (1:23/3:42)`
* 没放歌 ⇒ **整行消失**（不会留下一条「正在听：」的断尾巴）

规则边界（写死，避免误伤）：
* **只认一层**，不支持嵌套；
* 块内必须**至少有一个**我们的变量 —— 否则 `[[普通内容]]` **原样保留**（连壳都不脱）。

## 四、★ 与「注入模式」的关系：有变量 ⇒ 强制每轮

> 主人选项原文：「音乐提示词忽略这个设置」

「仅首条」的语义是「只在本会话第一条消息注入，token 只花一次」。它和时变内容是**天然冲突**的：

> 会话开了两小时、歌换了三十首，模型还在聊第一条消息时的那首 —— **这比不注入更糟**，
> 因为它是在用**过期事实**误导模型，而模型会当成当前状态。

⇒ 判定：`GmPromptVars.hasAny(正文)` 为真 ⇒ 无视 `fuckds_sysprompt_mode`，**每轮都注入**。
UI 上「注入模式」那一项的说明里加了警告，并且日志会打出 `pvar=true` 以便分辨。

> 代价（明说）：整段提示词会**每轮随消息发送** ⇒ token 持续消耗。
> 这正是「每轮」模式原有的代价，只是现在由「有没有变量」自动决定，而不是由主人记着去切。

## 五、⚠️ 版权：歌词单独开关、默认关

项目对音乐的既有铁律（`GmMusicPlayer` 文件头，2026-10-06 主人明确要求）：
**音频只流式不落盘 · 封面/歌词只在内存 · 落盘的 `state.json` 只有事实性元数据。**

但这一次的性质**不一样**，必须写清楚：

| | 内存里显示给自己看 | **塞进提示词** |
|---|---|---|
| 去哪了 | 屏幕 | **上传给服务器** + **留在对话历史里** |
| 谁能看到 | 主人 | 服务端、换设备、导出聊天记录的人 |

⇒ 所以分成两个开关：

* **「音乐变量」总开关** —— 控制歌名/歌手/专辑/进度（**事实性元数据**）
* **「允许歌词变量」** —— 控制 `{lyric}` 系列，**默认关**

**不是技术上做不到，是性质变了就得由人来决定。**

**三条纪律**（写在 `GmPromptVars` 文件头，也是本版最容易踩的地方）：

1. **热路径零异常** —— 调用点在「每次发消息」上，任何异常必须吞掉并原样放行（教训 255）。
2. **绝不联网、绝不阻塞** —— 歌词缓存没命中时只做一次**异步预热**（同一首 60s 内只试一次），
   绝不在发消息的线程上等网络。
3. **替换失败就原样放行** —— 宁可不替换，也不能把 `{music}` 这种字面量发给模型。

## 八、教训

**978 · ⭐⭐⭐ 「实时」不是靠推送做出来的，是靠「取数时机」决定的。**
　　别急着加轮询/广播/监听 —— 先问「这个信息被用到的那一刻，谁在手边」。

**979 · ⭐⭐⭐ 时变内容 + 「只注入一次」= 用过期事实误导模型。**
　　过期的信息比没有信息更糟：**没有是个洞，过期是个坑**。
　　所以本版让变量**自己**去否决注入模式（有变量 ⇒ 每轮），而不是指望主人记得手动切。

**980 · ⭐⭐ 同一份数据在两处算出两个答案，比算错更难看。**
　　`{lyric}` 的判定口径必须与迷你卡高亮**同一套**（最后一个 `ms[i] <= pos`），
　　否则用户会看到「卡片高亮这句、提示词说那句」—— 那时候你会怀疑人生，而不是怀疑口径。

**981 · ⭐⭐ 「内存里给自己看」和「发给服务器」是两种性质，别用同一把尺子量。**
　　歌词在屏幕上滚，是版权内容但风险可控；歌词进提示词，就是**上传 + 留档**。
　　⇒ 拆成两个开关、默认关，让**人**来决定，而不是替人默认。
