## 一、主人回执里有**两个**崩溃（一个我的、一个不是我的）

### 🅰️ 我引入的（严重：每次绘制都炸）

```
java.lang.ClassCastException: java.lang.Long cannot be cast to q32
	at c73.b(…:72)     ← c73 = LinearGradient.b(J)Shader
	at dd8.a(…:42)     ← dd8 = ShaderBrush
	at xv0.c(…) … → AndroidComposeView.dispatchDraw
```

**根因**：`Compose` 的 `Color` 是 **Kotlin inline value class** ⇒ 运行时装箱类型是宿主里的 **`q32`**（有自己的 `J a` 字段），
而我在 `GmBubble.brush()` 里往 `List<Color>` 塞的是 **`java.lang.Long`**。
泛型被擦除 ⇒ 编译/校验都看不出来 ⇒ **一到 `check-cast … Lq32;` 就炸**（在绘制线程里！）。

**为什么这版才炸**：`GmBubblePaintHook` 直到 2.21.7 才真正装上（注册名 `Luia`→`uia` 那处漏改），
所以这个坏 brush 直到 2.21.7/2.21.8 **第一次真正进入 modifier 树** ⇒ 2.21.9 这一版才把雷引爆。

**处置（止血）**：`GmBubble.brush()` **先直接 `return null`** ⇒ 替换路线不换 brush（宿主原样）⇒ **不再崩**。
代码里留了注释：修好装箱后删掉那两行即可恢复渐变。

**恢复渐变的正确做法（下一版）**：把 `Long` 换成 `q32` 装箱体：
- 静态搜索确认 `q32` 里**没有** `(J)Lq32;` 形式的静态装箱方法（`(J)Lq32;` 与 `;J)Lq32;` 都是 0 命中）
- ⇒ 应该是**构造器装箱**：`new-instance Lq32;` + `invoke-direct … <init>(J)V`
- ⇒ 下一版用**反射扫描 `q32.getDeclaredConstructors()`**（找「1 个 `long` 参数」那个）+ `setAccessible(true)` + `newInstance(Long.valueOf(px))`，
  **不依赖方法名**，版本升级免疫。

## 五、教训

| # | 要点 |
|---|---|
| **666** | ⭐⭐⭐ **Kotlin inline value class（如 Compose `Color`）在运行时有独立装箱类**：往 `List<Color>` 里塞 `Long`，**擦除后完全看不出来**，只在 `check-cast` 时炸。**凡是往宿主集合里塞「值类」的场合，必须先确认装箱体是谁、怎么装箱。** |
| **667** | ⭐⭐⭐ **「新装上的钩子」会把潜伏的坏数据首次送进热路径**：坏 brush 写了 3 个版本，直到 paint hook 真正装上才开始炸。⇒ **修复「钩子没装上」之后，要立刻预判「它一装上去会做什么」**。 |
| **668** | ⭐⭐ **止血优先于完善**：崩溃发生在 **绘制线程**（`dispatchDraw`）⇒ 先把危险路径 `return null` 停掉，把「渐变」留到能把装箱做对的那一版。**能一版修好是运气，能一版停住才是指标。** |
| **669** | ⭐⭐ **看崩溃栈要分清「谁引入的」**：这次两条栈一条是我的（`c73/LinearGradient`）、一条是老 bug（`GmSuggestAi`）；**用 `changedClassCount` + 「我有没有碰过这个类」两条一比即可定性**，不要混在一起改。 |
| **670** | ⭐⭐ **老 bug 常常解释掉「悬案待办」**：`dbSid` 那条⚪待办一直等 `END v4=` 读数，真相是**这个类验证都过不去、钩子从未装上**。**「日志从来没出现」要先怀疑「代码从来没跑」。** |
