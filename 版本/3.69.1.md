但**内置卡片本来就不能展开**：

```kotlin
// SysPromptV2.kt · 卡片渲染
noExpand = c.isBuiltin || c.type == T_TEXTSRC,     // ← 内置三张（含音乐）恒为 true
```

⇒ `expanded` 永远是 `false` ⇒ 那段「展开区」**一次都不会被渲染** ⇒
尼尼写的 `if (card.type == T_MUSIC) MusicDjRow(ctx)` **等于不存在**。

> ★ 这是"**我把功能写进了不可达分支**"——代码是对的，位置是死的。
> 而且 3.69.0 的核验还"通过"了（包里有 `MusicDjRow`、有资源、有桥）

## 三、"默认开"那处取反要照抄

搬动时最怕把键的语义搬歪。这个键是**反面**的（`fuckds_dj_off`：

| 实际 | 键 | 界面 |
|---|---|---|
| 从没碰过 | （没写过） | **开** ✅ |
| 拨开 | `false` | 开 |
| 拨关 | `true` | 关 |

⇒ 读的时候**必须**写成"没写过 ⇒ false（= 没关）"：

```kotlin
var djOff by remember {
    mutableStateOf(sp.getString("cfg.$K_DJ_OFF", null)?.let { Bridge.boolOf(it) } ?: false)
}
```

★ 注意**不能**照抄别处的 `sp.getString(..., null) ?: sp.getString(..., null)` 写法 ——
那种写法在"没写过"时会落进 `Bridge.boolOf(null)` ⇒ 读成 false ⇒ **开关显示成关**
（其它键的"没写过 = 关"正好是想要的默认，**这一个偏偏是反的**）。
⇒ 这是本次唯一有"陷阱"的一行，代码里写了长注释。

## 六、教训

**1075 · ⭐⭐⭐ 「内置卡片不可展开」这件事，我自己在 3.62 就写进代码了，转头就忘。**
　　`noExpand = c.isBuiltin` 是**自己定的规矩**，结果 3.69.0 把新按钮放进"展开区"。
　　★ 加 UI 时的第一问应该是：**这段代码在运行时会真的被走到吗？**
　　（判据：顺着触发路径点一遍，而不是"我写了这一行"。）

**1076 · ⭐⭐⭐ 核验要问「走得到吗」，而不是「符号在不在包里」。**
　　3.69.0 的核验 4 项全过（桥有 `GmMusicDj`、UI 有 `MusicDjRow`、arsc 有文案、装机成功），
　　但**用户永远点不到**。⇒ 以后凡是"新增入口"的改动，核验必须包含
　　**"这条入口从哪儿点进去"** 这一步，写进版本文档的「怎么试」。

**1077 · ⭐⭐ 搬家时，键的**语义方向**要跟着一起搬，别只看键名。**
　　`fuckds_dj_off` 是"反面键"，别的键都是正面 ——
　　照抄邻座的读法（`?: sp.getString(k, null)`）就会把默认值读反。
　　★ 做法：搬家时**把原处那几行注释一起搬**，并把"为什么这么读"写在新位置旁边。

**1078 · ⭐ 「音乐相关的东西放音乐页」是主人 3.57.1 就说过的。**
　　尼尼这次凭"功能属于提示词"的直觉放进了系统提示词页 ⇒ 被拽回来。
　　★ 判据：**按"人找它的时候脑子在哪"分类，而不是按"它在技术上属于哪一层"分类。**
