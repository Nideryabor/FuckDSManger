## 一、这一轮把「上一轮结论」推翻了一条关键的

### 1.1 新日志里那条被忽略的字段值

```
[建议] g56 字段 → a:int=9 | b:java.lang.String=image | c:java.lang.String=能再展开讲讲吗？ | d:java.lang.Integer=2131690015
```

`2131690015 = 0x7F0F021F`。查代码：**这是我们自己写的**（`buildMut2` 里 `d = 0x7f0f021f + i`），不是宿主的。

⇒ 也就是说：末端列表接管（`yb5.f`）**一直在把 d 写成"宿主资源 id 段的后继 id"**（`0x7f0f021f+i`，i≥1 时指向宿主别处资源甚至不存在）—— 这是个**越界隐患**，一直没人发现。

### 1.2 `GmResIdHook` 的引用数是 **0**

```
mt_apk_dex_xref dex_class:Lcom/varuns2002/disable_flag_secure/gm/GmResIdHook; → refs: []
```

⇒ 这个"假资源 id → 我们的文字"的拦截器**从来没有被注册过**（教训 254「类在 ≠ 生效」第二次应验）。
⇒ 于是 2.10.38 那次「排除 d 通道」的对照实验**证据无效**：hook 根本没跑，当然没有「按资源 id 接管」的日志。

**代价**：从 2.10.37 起，四五个版本都在"d 通道到底行不行"上打转。

### 1.3 ⭐ 决定性发现：`MMKV.q` 是**写**，`MMKV.k` 是**读**

在宿主 vc273 里逐个查引用（不是猜）：

```smali
# 读：p66.f() 取 model_configs
invoke-virtual {p0, v1, v2}, Lcom/tencent/mmkv/MMKV;->k(Ljava/lang/String;Ljava/lang/String;)Ljava/lang/String;   # v2 = null(defValue)

# 写：p66.h() 把服务器下发的配置落盘
invoke-virtual {v3, v7, v6}, Lcom/tencent/mmkv/MMKV;->q(Ljava/lang/String;Ljava/lang/String;)Z                 # (key, value) → encodeString
```

| 方法 | 语义 | 谁在用 |
|---|---|---|
| `MMKV.k(String,String)→String` | **读**（decodeString） | `p66.f()` 读 `kv_remote_settings_model_configs_v1` |
| `MMKV.q(String,String)→Z` | **写**（encodeString） | `p66.h()` 写 `kv_remote_settings_model_configs_v1` / `..._welcome_msg` |

⇒ **老线 hook `q` 完全正确**：它在宿主**把服务器配置写盘的瞬间**，把值里的 `"prompt_feature":[…]` 换成我们的模板池 ⇒ 落盘即我们的 ⇒ 之后宿主自己读、自己解析、自己造 chip ⇒ 文字+点击全正常。
⇒ 这是"**在源头接管**"的教科书形态（教训 253）。

### 1.4 那 2.10.41 为什么崩？

老 `GmMmkvHook` 里引用了 **老线专有类**：

```java
GmSync.ctx()      // 模块侧 Context
GmModel.isOn()    // 模型改名开关
GmTts.fix()       // TTS 修正
GmHello.get()     // 欢迎语
```

新线是重写的，**这些类不复存在** ⇒ hook 一执行就 `NoClassDefFoundError`，而它跑在 **MMKV 写盘热路径**上、且**老版无 try/catch** ⇒ 直接带崩宿主。
（这解释了「2.10.41 生效但崩」和「2.10.46 全撤了却仍崩」之间的别扭：46 撤的是**注册**，而 46 之前的崩是**注册+老类依赖**；46 之后的残留崩因需堆栈，见第五节。）

## 二、本版改动（三处）

| # | 改动 | 目的 |
|---|---|---|
| 1 | **`GmMmkvHook` 重写**：`before` 管 `q`（写）、`after` 管 `k`（读），自包含、全程 try/catch、JSON 校验通过才写回 | 落地"源头接管"，且**零异常外抛** |
| 2 | **注册两处**：`hookM(…, "com.tencent.mmkv.MMKV", "q", GmMmkvHook)` + `… "k" …` | 老线只挂了 `q`，现在**读也兜一层**（写入若尚未发生，读时也能补上） |
| 3 | **停掉末端列表接管**：`GmSuggestHook.beforeHookedMethod` 不再调 `buildMut`（改打一行 `[建议] 末端列表接管已停用`） | ① 消除 `d=0x7f0f021f+i` 越界隐患 ② 避免末端把宿主**按我们的配置造好的**列表又换掉（自相残杀） |

### 2.1 接管链（新）

```
宿主收到服务器配置
   └─ p66.h() ──► MMKV.q("kv_remote_settings_model_configs_v1", 服务器JSON)
                    └─★我们的 hook(before)：patch(prompt_feature → 模板池) → JSON 校验 → 写回 args[1]
   └─ 落盘（已是我们的）
宿主渲染 chip
   └─ p66.f() ──► MMKV.k(key, null)
                    └─★我们的 hook(after)：若值里没有 prompt_feature 就放弃；有则 patch + 校验 + setResult
   └─ 宿主自己 w46/g56 解析 → 自己渲染 → 文字 + 点击全部是宿主原生行为
```

### 2.2 8 条形状对齐（并修掉写反的 scene）

```java
id   = 9 + i                     // 9..16，与宿主一致
scene= i < 4 ? "image" : "file"  // ★ 宿主原样：9~12=image，13~16=file
content = 模板池[ i % size ]      // 循环取，条数不足就重复
```

上一版安全版写的是 `i<4 → "file"`（**反的**），本版修正。

## 三、代码（smali 关键片段）

```smali
.method static handle(Ljava/lang/String;Ljava/lang/String;)Ljava/lang/String;
    # 返回改好的 JSON；null = 不改（任何一步不满足都返回 null）
    :try_start_0
    if-eqz p0, :nul                       # key 空
    if-eqz p1, :nul                       # 值空
    const-string v0, "kv_remote_settings_model_configs_v1"
    invoke-virtual {v0, p0}, Ljava/lang/String;->equals(Ljava/lang/Object;)Z
    move-result v1
    if-eqz v1, :nul                       # 不是目标键
    sget-object v0, …GmPrompt;->NEEDLE:Ljava/lang/String;
    invoke-virtual {p1, v0}, Ljava/lang/String;->indexOf(Ljava/lang/String;)I
    move-result v1
    const/4 v6, 0x0
    if-lt v1, v6, :has                    # 有 prompt_feature 段
    …logOnce("mmkv.noneedle")… ; goto :nul
    :has
    …app() / GmSuggest.on() / rows() / GmPrompt.build() / GmPrompt.patch()…
    new-instance v6, Lorg/json/JSONObject; invoke-direct {v6, v5}, …-><init>(Ljava/lang/String;)V   # ★校验
    move-object v0, v5
    goto :end
    :nul
    const/4 v0, 0x0
    :end
    :try_end_0
    .catchall {…} :catchall_0
    return-object v0
    :catchall_0            # 任何异常只记日志、不改写
    move-exception v0 ; …logE… ; const/4 v0, 0x0 ; return-object v0
.end method
```

`beforeHookedMethod`（写）：`args.length==2` + 两个 `instanceof String` + `handle()` 非 null 才 `args[1]=结果`。
`afterHookedMethod`（读）：`args[0]` 是 String + `getResult()` 是 String + `handle()` 非 null 才 `setResult(结果)`。

**两个方法体都在 `:try_…` / `.catchall` 里** ⇒ 无论宿主传什么奇怪的键值组合，最坏也只是不改写。

## 六、教训（续编号）

| # | 教训 |
|---|---|
| **261** | ⭐⭐⭐ **混淆方法名必须"从调用点反查"，不能从方法名猜语义**：`p66.f()` 读 → `MMKV.k`；`p66.h()` 写 → `MMKV.q`。老线 hook `q` 是对的，我第一轮凭 grep 失误误判成"q 不存在" |
| **262** | ⭐⭐⭐ **"依赖不存在的类"是热路径上的隐形炸弹**：老 `GmMmkvHook` 引用老线专有类，注册即 `NoClassDefFoundError` ⇒ 崩。搬老代码必须先**查依赖闭包** |
| **263** | ⭐⭐ **未注册的 hook = 从未验证的假设**：`GmResIdHook` xref=0，导致 2.10.37~38 的结论全废。**加 hook 后第一件事：查 xref / 看注册日志 count** |
| **264** | ⭐⭐ **同一版本的"接管"要分清是源头还是末端**：末端接管会把源头接管造好的结果再改一遍，二者**同时存在 = 自相残杀** |
| **265** | ⭐ **越界 id 这种隐患不会立刻炸**，但会在"某个场景（上传图片）"才触发 —— 看见 `d=0x7f0f021f+i` 这种"宿主真实 id + 偏移"就该警觉 |
| 258 | （复用）"哪一版不崩"是二分黄金信息 |
| 254 | （复用）类在 ≠ 生效 |
