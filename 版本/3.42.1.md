## 一、这一轮最贵的发现：R8「名字诈尸」

新宿主 2.6.1（vc279）把混淆名空间**整体重排**，而且——

> **旧名字没有消失，是被别的类占用了。**

| 旧锚点名 | 2.5.2 里的身份 | **2.6.1 里变成了什么** |
|---|---|---|
| `Lkf5;` | Compose 杂物间（painterResource） | CameraX 的 lambda（`MeteringRepeating`） |
| `Luia;` | Modifier 静态工具桶（85 字段） | 一个 51 字段的巨类 |
| `Lh91;` | 消息列表 Composable | **一个 0 方法的空接口** |

⇒ 底座的**门禁** `findClass("kf5") → findClass("uia") → 都失败才 return` **会"成功"通过**，
⇒ 51 条钩子**全部挂到不相关的类上**。

> 🔴 **这比「模块静默全灭」更坏**：全灭只是没反应；挂错是**拿钩子去咬无关代码**。

**产物里已经把门禁改成 `kh7` / `qk7`**（并保留旧门禁的语义）。

## 四、改动实现：把映射放到**运行时**（关键设计）

### 为什么不能"纯文本替换"

底座的 `GmEntry` 里**寄存器被复用**——同一个字符串 `"v"` 同时服务三个锚点：

```
m5.v  → 要变成 ew1.w
uia.v → 要变成 qk7.D
s5.v  → 要变成 a6.w
```

**同一个字符串要映射到三个不同的新名字** ⇒ 任何基于文本的替换都会串味。

### 做法

新增 `mod-src/src/.../bridge/GmRemap.java`（进我们的桥 dex），
在 `GmEntry.hookM` / `hookC2` 的入口**插入一次查表调用**：

```smali
.registers 6 → 8                       # 腾出 v2/v3（pN 别名自动顺延）
invoke-static {p1}, …GmRemap;->cls(String)String
move-result-object v2
invoke-static {p1,p2}, …GmRemap;->method(String,String)String
move-result-object v3
move-object p1, v2 ; move-object p2, v3
```

**未定位的锚点**：`GmRemap.cls()` 返回 `com.gm.gone.<旧名>` ⇒ `findClass` 抛异常
⇒ 被 `hookM` 自带的 `catchall` 吞掉 ⇒ **那一条 hook 不注册**。
> **宁可不干活，也不要挂到错误的类上乱咬宿主** —— 这是本轮最贵的教训。

其余 14 个 gm 类（GmSync / GmSuggestAi / GmBubble / GmResumeHook / GmEnv …）
**只做类名字符串的 1:1 替换**（这些文件里一个名字只服务一个用途，无冲突）。

> ✅ 实测底座**从不用直接类型引用宿主**（全树只有 `List;/Long;/Log;`）⇒ 纯字符串改写是安全的。

## 七、教训（编号接上）

| # | 教训 |
|---|---|
| 300 | **R8「名字复用」是新故障模式**：旧名还在 ≠ 还是那个类。门禁必须判"**类在 **且** 形状对**"，不能只判类在。 |
| 301 | `baksmali d <apk>` **默认只翻 classes.dex**。多 dex 必须 `app.apk/classesN.dex` 逐个翻，否则静默少四分之一类，所有结构结论都失真。 |
| 302 | 多 dex 漏翻的后果是**结论"看起来对"**（kf5→kh7 确实对），但**最优解可能在漏掉的 dex 里** ⇒ 必须重跑复核。 |
| 303 | **SourceInfo 里的行号会变**，只搜"文件名 + 冒号"不够，要搜"文件名"再定位。 |
| 304 | 底座 `hookM` 的**寄存器复用**让"字符串替换"这条路走不通 ⇒ 映射要放运行时。 |
| 305 | **插桩要覆盖所有注册入口**：第一轮只插了 `hookM`，漏了 `hookC2`（jd8/se0 走它）⇒ 靠**回读产物**抓出来。 |
| 306 | **未定位的锚点要"安全跳过"而不是"保留原名"** —— 保留原名 = 挂到诈尸的类上。 |
