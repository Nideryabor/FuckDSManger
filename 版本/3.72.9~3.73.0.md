## 一、先纠正复盘里的一处误判

`专题/2026-10-31-一日总复盘.md §十一 #2` 写的是：

> 「已定位：选中层在祖先节点注册 `detectTapGestures`，单次 tap 被吃掉」

**这个结论至少不是第一真凶。** 真正先炸的是这一条：

`GmRichLink`（负责把 `<Suggestion>` 渲染成**可点击链接**的桥）里五个宿主混淆名
全部是 2.7.1 的：

| 用途 | 2.6.2 / 2.7.1（旧候选） | **2.7.2 实际** | 证据 |
|---|---|---|---|
| `AnnotatedString.Builder` | `kn` / `jn` | **`qn`** | `implements Appendable` · `a:StringBuilder` · `b/c:ArrayList` · `h(Lho6;)I`(pushLink) · `e(String)` · `f()` · `k()Lsn;` |
| `LinkAnnotation`（父类） | `gm6` / `yi6` | **`ho6`** | `qn.h(Lho6;)I` 的参数类型；`.implements Lon;` |
| `LinkAnnotation.Clickable` | `em6` / `wi6` / `xi6` | **`fo6`** | 串 `LinkAnnotation.Clickable(tag=`；`.super Lho6;`；字段 `a:String` / `b:Lgxa;` / `c:Lio6;` |
| `TextLinkStyles` | `tra` / `vna` | **`gxa`** | `fo6.b` 的类型；`<init>(tba×4)` |
| `LinkInteractionListener` | `hm6` / `zi6` | **`io6`** | `fo6.c` 的类型；`public interface abstract` + 唯一方法 `a(Lho6;)V` |

⇒ 五个里**一个都不对** ⇒ `prepare()` 必然 `bail` ⇒ `GmRichTextHook.emitSuggest` 走降级分支
「只把标签剥掉」⇒ `<Suggestion>` 变成**点不动的死文字**。

所以「点了没反应」的第一原因是**能力压根没就绪**，而不是手势被吃。
（手势层是否也吃 tap，要等 3.72.9 装上去点一下才知道 —— 见第五节）

## 二、3.72.9：把「猜名字」改成「结构派生」

一次升级死五个名字，这个维护方式本身就是 bug。改成：

```
① Builder      ← 候选名 + **指纹校验**（Appendable / a:StringBuilder / 有 h(X)I）
② LinkAnnotation ← pushLink 的**参数类型**（不猜名字）
③ Clickable    ← 候选名里唯一「是 ② 的子类 + 有 (String,?,?) 构造器 + 第三参是接口」的
④ TextLinkStyles / Listener ← 直接从 Clickable 构造器的第 2、3 个参数推
```

只留两条候选名（`qn/kn/jn/in`、`fo6/em6/wi6/xi6`），**其余四个全是算出来的**。
下次宿主改名，至多影响一条候选。

自检日志也换了写法，直接把认出来的类名打出来（以后一眼就能看出挂的是不是对的东西）：

```
richLink 自检 OK：自检全过（Builder=qn · Link=ho6 · Clickable=fo6 · Styles=gxa · Listener=io6）
```

## 三、3.73.0：建议条旁路（主人 2026-10-31 的 iOS 思路）

主人的原话：

> **「hook AI 类，把气泡里的回复建议内容抹掉，单独几个气泡以最后一条 AI 气泡为基准跟在后面（iOS 原本思路）」**

### 3.1 Android 这边做不到的那一半

iOS 能「单独几个气泡」，是因为 UIKit 那边能往 `UICollectionView` 里**插 cell**。
Android 这边宿主是 **Compose 的 LazyColumn** —— 我们没有 compose 编译器
（`@Composable` 的调用顺序是编译期算好的，javac 手写必然破坏 composition，这条是 3.x 一路的铁律）。

所以「往列表里插条目」这条路封死。改成**窗口上自己的一层 View**：

| 要求 | 落地 |
|---|---|
| 气泡里**抹掉**建议 | `GmRichTextHook.emitSuggest`：建议条模式下一个字节都不往气泡里写 |
| **跟着最后一条 AI 气泡** | 落点 = 输入框上沿（最后一条气泡下面那个位置）；靠右下、离底 `fuckds_sugbar_h` 可调 |
| **点得动** | 自己的 View 是窗口里独立一层，事件先到它手里；宿主的手势层碰不到 |

### 3.2 新增文件

| 文件 | 作用 |
|---|---|
| `bridge/GmSugBar.java` | 管理器：开关 / 挂窗口 / 收建议 / 点击转发 / 去重与"用过就收" |
| `bridge/GmSugBarView.java` | 那个 View：一排圆角 chip，可横滑，靠右 |

键（都在模块自己的存储里）：

| 键 | 默认 | 含义 |
|---|---|---|
| `fuckds_sugbar_on` | **false** | 总开关。关 ⇒ 走气泡内链接（老路）；开 ⇒ 气泡里抹掉 + 这条显示 |
| `fuckds_sugbar_h` | 120 | 距屏幕底边多少 dp（大致就是输入框上沿） |
| `fuckds_sugbar_ttl` | 180 | 多少秒后自己收（0 = 不收） |

`cfg_put` 通道已经接上（`fuckds_sugbar_on` 拨一下当场长出来 / 收掉，见 `FdmBridge.dispatch`），
`FdmEntry` 里也装了钩子（跟便签 / 迷你卡同一套路数：`Activity.onResume/onPause`）。

### 3.3 两个必须记住的设计点

**① 默认关，它是"旁路"不是"替代品"**

两条路都在：链接能点就用链接（更省事，跟气泡滚在一起），点不动就切这条。
**谁好用留谁** —— 这也是本轮最好的验证方式（同一个包，拨一个开关就能对照）。

**② 「用过就收」必须记签名**

宿主每重组一次就把消息文本重过一遍 `rebuild` ⇒ `<Suggestion>` 又被解析、又调 `publish`
⇒ 建议条会**刚发完又冒出来**。
所以点掉 / 超时收起时，把这组建议的**签名**记进 `sSuppressed`，
同一条消息后续的 `publish` 直接丢弃；等**另一条**消息的建议进来才换。

## 五、主人验收（一个包验两条路）

装 **3.73.0**（vc759）→ **重启宿主一次**。

### 第一步：验「链接那条路」（默认状态，开关关着）

1. 让 AI 回一条带 `<Suggestion>` 的（或者直接用老对话）
2. **点一下那个建议**
3. 看日志：
   - 出现 `richLink 自检 OK：…（Builder=qn · Link=ho6 · Clickable=fo6 · Styles=gxa · Listener=io6）`
     ⇒ 名字全对上了 ✅
   - 点了之后出现 `[建议] ★★ 被点了！要回复的内容 = 「…」`
     ⇒ **链接那条路就通了**，不用开旁路（建议就这么用）
   - 点了没这条日志 ⇒ 手势层确实吃了 tap ⇒ 进第二步

### 第二步：验「建议条那条路」

```sh
# 拨开（也可以从 cfg_put 通道走）
am broadcast -a com.nidyaber.fuckdsmanger.CMD --es cmd cfg_put --es arg 'fuckds_sugbar_on<0x1f>b<0x1f>true'
```

（`<0x1f>` = 那三个字节里的分隔符 `\u001f`，按你平时发广播的方式给就行）

拨开后：对话里那条建议应该**从气泡里消失**，改成右下角一排 chip（输入框上沿）。
点一下 ⇒ 日志 `【GmSugBar】★ 点到了：「…」→ 回复「…」` + 消息发出去 + 这条自己收起。

### 第三步：微调位置（要是不在输入框上沿）

`fuckds_sugbar_h`：默认 120（dp）。太小会压在输入框上，太大就跑到半空了。
