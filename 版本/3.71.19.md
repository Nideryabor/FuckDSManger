## 一、病

主人：「新版本宿主有登录设备管理，然后我在里面看到了一堆未知设备（我们伪造了 deviceid）」

实测确认 **9 台设备**（具体清单属主人隐私，**不落盘**）。

**判定依据（脱敏后）**：
- 其中 1 台的「设备名」不是机型名而是一个**通用占位串** ⇒ 典型的重置产物
- 另有 2 台的 `device_name` / `os` / `client_platform` **全为 null**
- ⇒ 「客户端每次重置都生成新 ID」这个推断成立

模块里也**真的找到两个不同的值**（`fuckds_device_id` 曾经并存过两份，具体值不落盘）：
```
fdm_ui.xml      → XXX（当前生效）
另一次快照       → YYY（旧值）
```

### 真因：`gen()` 用无种子的 `Random`

```java
static String gen() {
    Random r = new Random();                     // ★ 无种子
    StringBuilder sb = new StringBuilder();
    for (int i = 0; i < 16; i++) {
        sb.append(Integer.toHexString(r.nextInt(16)));
    }
    return sb.toString();
}
```

**三个病**：

| # | 病 | 后果 |
|---|---|---|
| 1 | `new Random()` **无种子** ⇒ 默认用纳秒时间戳 | 两台设备同一毫秒初始化会生成**同一个** device_id ⇒ 服务端关联成同一台 ⇒ **连坐封号** |
| 2 | 种子来自 `shared_prefs`，而**模块 UI 进程和宿主进程都写同一个文件** | 跨进程一致性问题 ⇒ 读空/读旧 ⇒ 重新 `gen()` ⇒ 新设备 |
| 3 | 每次丢值都变成服务端眼里的一台新设备 | **登录设备管理里越滚越多** |

## 二、修法：确定性派生

```java
static String gen() {
    seed = Build.MODEL + "|" + Build.BRAND + "|" + Build.HARDWARE
         + "|" + ctx.getPackageManager().getPackageInfo(pkg, 0).firstInstallTime;
    return MD5(seed) 前 8 字节 → 16 位 hex（小写，逐字节补 0）；
}
```

### 为什么选这几个字段

| 字段 | 为什么 |
|---|---|
| `Build.MODEL` / `BRAND` / `HARDWARE` | 同型号手机一样 —— **所以不够，必须加时间** |
| `firstInstallTime` | ★ **每机不同、同机稳定、无需权限、系统升级不变**。精确到毫秒 ⇒ 同型号也不会撞 |
| ~~`Build.FINGERPRINT`~~ | ❌ **刻意不用** —— 它含 build 号，系统一升级值就变 ⇒ 又成新设备 |

### 兜底

```java
catch (Throwable) {
    // 绝不返回 null；仍确定性
    return Integer.toHexString(Build.FINGERPRINT.hashCode()) 重复两遍;
}
```

## 四、⚠️ 迁移注意（重要）

`ensureFake()` 的逻辑是「**读到就用，读不到才算**」：

```java
saved = GmStore.read2(ctx, "fuckds_device_id", "s");
if (saved 有效) { sFake = saved; return; }     // ← 你还在用旧的随机值
sFake = gen();                                  // ← 新算法只在丢失时生效
```

**⇒ 库里那个旧值还在用，新算法暂时不生效。**

要切新算法有两条路：

| 选项 | 结果 |
|---|---|
| **A. 保留旧值** | 设备列表暂不增长，但那个值是随机的；**将来若丢失，会变成新算法的值（还是多一台）** |
| **B. 清空一次**（UI 里「美化 › 设备 › 当前伪造 ID」本来就可编辑）| **会多一台设备**（最后一次），之后**永久稳定、永不增长** |

尼尼推荐 **B** —— 一次性付清。

## 五、教训

| # | 教训 |
|---|---|
| **AG** | ⭐⭐⭐ **`new Random()` 无种子 = 潜在碰撞源**。需要「稳定标识」时**绝不能用随机**，要用确定性派生 |
| **AH** | ⭐⭐⭐ **派生用的字段不能含会变的东西** —— `Build.FINGERPRINT` 含 build 号，系统升级就变；`firstInstallTime` 才是稳的 |
| **AI** | ⭐⭐ **SharedPreferences 跨进程不可靠** —— 模块 UI 进程和宿主进程各有一份缓存，写同一个文件必然打架。稳定值要能**算回来**，不能只靠存 |
| **AJ** | ⭐⭐ **"设备列表增长"是症状，根因往往在客户端** —— 先去查自己是不是每次都生成新 ID，别急着怪服务端 |
