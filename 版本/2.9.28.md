## 一、先补一个「已确证」：头像 painter 到底从哪来

为了排掉「2.5.2 改用 URL/Coil 画助手头像」这条怀疑，本版前**逐行读完了**
`Lcka;` 里 `AssistantIcon` 那个 composable（smali 4984 → 5290）：

```
trace: "…message_items.assistant.AssistantIcon (AssistantIcon.kt:22)"   ← .line 22
  → sget Lkd1;->d:F + LocalDensity 换算 → Modifier.size(<float>) *(.line 41~72)*
  → ColorSchemeV2 取色 + Modifier.clip *(.line 77~116)*
  → invoke-static {composer}, Ljt5;->B(Ley3;)J    ← ⚠️ coil3，但只用来算 **group key**
        ushr-long/xor-long → hash → 交给 Lxd5;->A(…, boxed)（sourceInformation，调试用）*(.line 123~188)*
  → const v1, 0x7f070059 → Lkf5;->K(IILey3;)Lku6;   ← **头像 painter 就是这条** *(.line 191/194)*
  → Lul8;->l(modifier, float) → Modifier.size *(.line 198)*
  → Lup2->e:Llv;->a:J（主题色）* (.line 211~228)*
  → Lme4;->a(painter, null, modifier, tint, composer, 0x38, 0)   ← Icon(...) *(.line 235)*
```

**结论（关键）**：
1. 这个 composable 是**线性的**，`painterResource(0x7f070059)` **没有任何前置分支**（不存在「有 URL 就用 Coil、没有才用 painterResource」那种写法）；
2. 那里的 `coil3` 调用**只产出一个 key**（拿去做 Compose 的 group key / sourceInformation），**不产 painter**；
3. ⇒ **只要助手头像被渲染，`kf5.K(0x7f070059)` 必然被调用**。

所以「搜不到 0059」只能解释为：**那段日志没被看到**（截图正好只覆盖启动那 10 条）。

## 二、本版改动（四步自检 Toast + 日志不再截断）

| 步骤 | 落点 | 判定含义 |
|---|---|---|
| **1) PHook: hit avatar id** | `GmPainterHook` 命中 `0x7f070059`（`sAct` 非空后、`isOn` 判定**之前**） | 头像合成**确实跑了**（最关键的二分） |
| **2) painter ready (replaced)** | `GmPainterHook` 成功造出 `BitmapPainter` 并 `setResult` | 替换**成功**（解码 + 建 painter 都过了） |
| **3) painter reached Icon** | `GmIconHook` 身份比对命中（我们的 painter 到了 `me4.a`） | 我们的 painter 真的被 `Icon` 用了 |
| **4) identity filter (Dst) installed** | `GmPaintModHook` 把 `Modifier.paint` 的 `ColorFilter` 换成恒等 `BlendMode.Dst` | 染色解除**已落地**（彩图就该出来了） |

其它：

- `GmPainterHook` 的「前 N 次 `kf5.K` 资源 id」日志上限 **16 → 600**（启动那批图标会吃掉前十几条，**截断会导致「搜不到 0059」这种假阴性**）；
- 每个 Toast 都有 `sTold*` 一次性开关（不会刷屏）；
- `AndroidManifest.xml` `114/2.9.27` → **`115/2.9.28`**；入口日志 → `v2.9.28`。

## 四、★ 验收（看 Toast，不用翻日志）

1. 装 2.9.28 → 重启宿主
2. **打开有 AI 回复的对话**（头像区块在屏幕上）
3. 看屏幕弹了几个 Toast

| 观察 | 结论 | 下一步 |
|---|---|---|
| **四个都弹**，头像=彩色原图 | 🎉 完结 | 摘 WIP、更新文档 |
| 四个都弹，头像仍蓝/空白 | 四个环节都对了 ⇒ 问题在 filter 的**渲染语义**（或 painter 尺寸） | 换 filter 方案（`Modulate + 白`）或改 painter 的 `dstSize` |
| 只有 **1、2**，没有 3/4 | painter 造出来了，但**没走到 Icon** | 查 `Lcka;` 那处 `Icon` 是否被 `remember` 缓存了旧 painter |
| 只有 **1**，没有 2 | 卡在「解码/建 painter」 | 看日志紧随的 `decode NULL` / `isOn FALSE` / `hasImage FALSE` |
| **一个都没有** | 头像合成**根本没跑**（对话里没有走 `AssistantIcon`） | 换落点（见下） |
| 头像变回**默认头像**（不再空白） | 2.9.27 的兜底生效 ✓ | 结合上面各行继续 |

> 「一个都没有」时请顺手确认：`输出` 里有没有 `PHook: kf5.K id=0x…` 这类行出现（现在不再截断，最多 600 条）；
> **一个 `id=` 行都没有** ⇒ `painterResource` 在这个进程里一次都没被调用（那就是别的层级问题了）；
> **有 `id=` 行但没有 `0x7f070059`** ⇒ 助手头像确实没走 `painterResource`，需要重新定位绘制点（反证第 1 节）。

## 五、教训（补充）

**第 117 条：⭐ 诊断手段要匹配「用户能稳定提供的信息」。**
连续两轮都卡在「拿不到我要的那段日志」：日志是长列表、要滚动/搜索、还要过滤 tag。
本版改用 **Toast 四步自检**（屏幕上一次给全），把「取证成本」从「翻日志」降到「瞄一眼」——
诊断方案本身也要按可用性设计。

**第 118 条：日志截断（cap）会制造假阴性。**
「前 16 次 `kf5.K` id」的上限在启动期就被图标占满了，导致用户「搜不到 0059」却无法区分
「真的没有」与「被截掉了」。**任何 `first N` 型诊断日志，都要在文档里写明 N 和它的代价**，否则它会骗人。

**第 119 条：⭐ 怀疑「某调用点已废弃」时，逐行读完那个 composable，别靠推断。**
`Ljt5;->B(composer)` 一看像 Coil 加载，实际只是**算 group key**；这条若有误判，
整条「头像走 Coil」的路线会把排查带偏一整个版本。
