## 1. 三条 bug **同源**：判据「按层数 + 限流」太脆弱

| 现象 | 技术解释 |
|---|---|
| ① 悬浮 / 自带填充色**挡住背景** | 上一版只透明「最外 6 层」⇒ **内层容器、悬浮按钮、输入框的填充色仍在** |
| ② **进设置返回背景消失，滑动又出现** | `sPageCnt` 用完（`>=6`）⇒ 返回后**不再透明**；一滑动 ⇒ ChatPage 重组 ⇒ `cnt` 重置 ⇒ **又能透明** ← **与现象严丝合缝** |
| ③ **浅色模式切换后必须重启** | 颜色**只在首次记录一次** ⇒ 切主题后没更新 ⇒ 重启才重记 |

⇒ **问题不是"透明哪几层"，而是"判据记不住、还搞限流"。**

## 2. 本版改动：三槽颜色白名单 + **去掉限流**

```
GmBubble 新增字段：
    public static sPageColor:J      ← 槽 1（页面底色）
    public static sSurfaceColor:J   ← 槽 2（内容区 surface）
    public static sExtraColor:J     ← 槽 3（余量：悬浮/容器填充色）

GmPageHook.before（每次进 ChatPage）：
    三个槽全部清 0                    ← ★ 每次进页面重新记忆（解决 ③）

pg：
    ① 方法名 == "v"
    ② args[1] 是 Long
    ③ sDepth == 0                    ← 排除助手项内的气泡底
    ④ 颜色命中三槽之一        ⇒ 透明化 ✓（不再看层数、不再限流）
    ⑤ 否则若有空槽            ⇒ 记进空槽 + 透明化
    ⑥ 三槽都满且不命中        ⇒ 跳过（那不是底色）
```

**为什么能一次解决三条**：

| bug | 解决方式 |
|---|---|
| ② **返回后消失** | **彻底去掉 `cnt` 限流** —— 只要颜色还在记忆里，**任何时刻都透明** |
| ③ **切主题要重启** | `before` 每次都清空 ⇒ **进一次页面就重新记当前主题的颜色** |
| ① **悬浮层挡住** | 槽位增加到 **3 个**（页面底色 + surface + 一类容器填充色）⇒ 同色的内层会被**一起透明** |

**`why=` 编号（本版）**

| `why=` | 含义 |
|---|---|
| **1** | 方法名不是 `v` |
| **2** | `args` 问题 |
| **3** | 在助手消息项内（`sDepth > 0`） |
| **4/5** | 进入"记录新颜色"分支（4=准备记，5=正在记） |
| **0** | ✅ 通过（已透明化） |
| **6** | `GmBg.real()` 为 false |

## 5. 教训（831~833）

| # | 内容 |
|---|---|
| **831** | ⭐⭐⭐ **「滑动才出现 / 返回就消失」= 典型的"限流计数器"症状**：`sPageCnt < 6` 这种"只数前几次"的判据，**一旦计数用完就永久失效**，而任何一次"重新组合"又会把它重置 ⇒ 表现为**间歇性生效**。⇒ **凡"有时有效有时无效"的功能，先检查有没有"计数/配额"类判据。** |
| **832** | ⭐⭐⭐ **「必须重启才生效」= 典型的"只读一次"症状**：配置/颜色在**首次使用时缓存一次**，之后不再刷新。⇒ **凡是"重启才对"的问题，都在"缓存了但没有失效机制"那一步**。 |
| **833** | ⭐⭐ **判据要选"稳定且可重复识别"的东西，而不是"顺序号"**：层数（第 1~6 层）随页面重组而变，**颜色却是稳定的**。⇒ **能用"内容特征"识别时，别用"出现次序"。** |
