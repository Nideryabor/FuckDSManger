### 2.2 ⭐⭐⭐ 整页打不开的真因：**循环依赖**（3.108.0 → 3.108.1）

3.108.0 装到真机上，点「打开模块 · 整页」——**弹保底卡片**。

日志（`devlog`，LSPosed modules 组）：

```
14:57:56.137  选择页：主人点了「打开模块 · 整页」
14:57:56.146  已关闭当前 Dialog（为弹保底让位）
14:57:56.250  ✗ 整页内容装不上 ⇒ 退回保底
              （拿不到模块 Resources（模块 APK 路径没找到 / addAssetPath 失败） · inHost=true）
14:57:56.253  选择页：整页没装上 ⇒ 自动退回「模块本体」（跨进程）
14:57:56.257  显式 拉起失败：ActivityNotFoundException …
14:57:57.263  判据：宿主仍在前台、也没收到 UI_OPENED ⇒ 拉起失败，弹保底
```

**原来的取路径链**：

```
模块进程跑一次 → getPackageCodePath() → 广播 → 宿主存键 → 整页读键
        ↑                                            ↑
   要人先开模块本体                            整页才有路径
```

而整页存在的**唯一目的**就是「不用开模块本体」⇒ 这是**循环依赖**。
`grep "已记下模块 APK 路径"` 在 lspd/modules + dsm.log 里 **0 次**，坐实了。

**修法：问框架要（LSPosed 官方 API）**

源码实证（`core/src/main/java/de/robv/android/xposed/XposedInit.java`）：

```java
if (moduleInstance instanceof IXposedHookZygoteInit) {
    StartupParam param = new StartupParam();
    param.modulePath = apk;                        // ← 模块 APK 绝对路径
    ((IXposedHookZygoteInit) moduleInstance).initZygote(param);
}
```

它在**每个目标进程**加载模块时都会跑，且**早于** `handleLoadPackage`。
⇒ 我们实现 `IXposedHookZygoteInit` 就有路径了：**不用存储、不用跨进程、不用反射**。

```java
@Override
public void initZygote(StartupParam startupParam) {
    FdmBridge.setModuleApkFromZygote(startupParam.modulePath);
}
```

**最终 `HostPage.moduleResources()` 是四级链**：

| # | 来源 | 性质 |
|---|---|---|
| 1 主路 | `FdmEntry.initZygote(StartupParam.modulePath)` | LSPosed 官方 API，每进程必调 |
| 2 | `ClassLoader.getResource("AndroidManifest.xml")` → 截出 `jar:file:…apk!` | 纯公开 Java API |
| 3 | 宿主存储里模块上报的那条（旧路） | 兼容 |
| 4 | 反射 `BaseDexClassLoader.pathList` | 最后兜底 |
| 5 | `createPackageContext` | 包可见性允许时 |

**探到就回存**并打日志 `模块 Resources 已装载（via=zygote/classloader/...）`。

真机（3.108.1）：
```

15:11:38.812 ✅ Compose 整页已塞进宿主
15:11:38.812 选择页：整页 ⇒ 已显示
```

### 2.3 ⭐⭐⭐ 资源表：一份 `Resources` 到底能不能认两张表（3.108.2 → 3.108.3）

主人：「点一下宿主 compose 的**灰度**会炸」。

崩溃（dropbox，`data_app_crash@1794640533807`）：

```
android.content.res.Resources$NotFoundException: String resource ID #0x7f0a0059
    at android.content.res.Resources.getText(Resources.java:498)
    at androidx.compose.material3.internal.Strings_androidKt.getString-2EP1pXo
    at androidx.compose.material3.OutlinedTextFieldKt$OutlinedTextField$3.invoke
    at com.nidyaber.fuckdsmanger.RowsKt.SettingText(SourceFile:318)
    at com.nidyaber.fuckdsmanger.PagesKt.GrayRow(SourceFile:609)
```

`aapt2 dump resources` 查 `0x7f0a0059` = **`default_error_message`**（Material3 的字符串，**我们 aapt2 编出来的**）。

**真因**：我们编的 Material3 通过 `LocalContext.getResources()` 去**宿主**资源表查自己的 id ⇒ 找不到 ⇒ 宿主整个进程崩。

主人追问「包括下面的菜单项目也是这样的」—— 对，音乐 / 过检 / 帮助全走同一条路。

#### 3.107.0 的结论「一份 Resources 只能认一张表」，只在特定前提下成立

`javap android.content.res.Resources`：

```
public CharSequence getText(int)                            ← 不是 final
public String getString(int)                                ← 不是 final
public Drawable getDrawable(int)                            ← 不是 final
public int getColor(int)                                    ← 不是 final
public final ... newTheme() / getAssets()                   ← 只有这俩是 final
```

3.107.0 真正卡住的是 **`Context.getString`**（那句 `'getString' in 'Context' is final`），**不是 `Resources`**。
⇒ 结论下早了：**子类化 `Resources`，一次查不到就换另一张表** 是可行的。

#### `BridgeRes`（`HostRes.kt`）

```kotlin
class BridgeRes(base: Resources, private val mod: Resources)
    : Resources(base.assets, base.displayMetrics, base.configuration) {
    override fun getText(id: Int): CharSequence =
        try { mod.getText(id) } catch (e: Resources.NotFoundException) { super.getText(id) }
    // getString / getDrawable / getColor / getColorStateList / get*Array 同理
}
```

- `assets` / 密度 / 配置**全部来自宿主** ⇒ 宿主自己的解析、主题一点没动
- 只有「模块表抛 `NotFoundException`」才回落；别的异常原样抛（教训 807：别把「真坏了」伪装成「找不到」）
- 常态是**模块表直接命中**（不抛异常），catch 只发生在库/宿主的 id 上，且不在绘制热路径

#### ⚠️ 但主界面好了，**彩蛋照样炸**（3.108.3）

主人：「点七下的彩蛋又炸了」。

```
Resources$NotFoundException: String resource ID #0x7f0a017a   ← m3c_dialog（也是我们编的）
    at android.content.res.Resources.getText        ← **不是 BridgeRes**
    at androidx.compose.material3.DefaultBasicAlertDialogOverride$BasicAlertDialog$1
    at androidx.compose.ui.window.AndroidDialog_androidKt.DialogLayout
    at androidx.compose.ui.platform.ComposeViewContext.ProvideCompositionLocals$ui   ← ★
```

`0x7f0a017a` = `m3c_dialog`，**在模块表里**。所以不是「查不到」，是 **BridgeRes 没被用上**。

**真因**：Compose 的 `Dialog` 是**独立 window**：

```
Dialog 内部 → DialogWrapper.setContent → new ComposeView(dialog.context)
                                                ↑
                     ComposeViewContext.ProvideCompositionLocals$ui
                     用 **View 自己的 context** 重新覆盖 LocalContext/LocalResources
```

那个 context 追根溯源是**根 ComposeView 的 context = 宿主 Activity**。
⇒ 在 `setContent` 里 provide 一层 `LocalContext`，**管不到 Dialog 里新建的 View 树**。

**修法**：在**建 ComposeView 的时候**就换成包过的 Context：

```java
Context cvCtx = act;
if (FULL_MODE.equals(hostClass)) {
    Object wrapped = HostPage.wrapContext(act);   // = ResCtx(act)，getResources() = BridgeRes
    if (wrapped instanceof Context) cvCtx = (Context) wrapped;
}
Object cv = cvCls.getConstructor(Context.class).newInstance(cvCtx);
```

只对 `FULL_MODE` 做 —— 保底弹窗/选择页的文案全是写死的字符串，别给它们增加失败面。

## 三、⚠️ 顺带确认的一件事：`Xposed API 调用保护` 不用关

主人问过：「这条路是不是要关闭 lsp 的钩子调用保护」。

查了 LSPosed 主仓：

| 层 | 事实 |
|---|---|
| 开关内部键 | `enable_dex_obfuscate`（`app/src/main/res/xml/prefs.xml`） |
| 默认值 | `android:defaultValue="true"`，`ConfigManager` 里 `bool == null \|\| (boolean) bool` ⇒ **默认开** |
| 真正干活 | `ObfuscationManager`：`native SharedMemory obfuscateDex(SharedMemory)` —注释写着 **"For module dexes"**；`native HashMap<String,String> getSignatures()` |
| 下发 | `LSPApplicationService` 的 `OBFUSCATION_MAP_TRANSACTION_CODE`，受 `dexObfuscate()` 闸门控制 |

**机制**：开关 ON 时，LSPosed 在加载模块 dex 的那一刻把里面**所有 `de.robv.android.xposed.*` 的类名/方法签名**换成随机名，并把映射表塞给进程。

- 静态编进模块 APK 的代码 → 一起被重写 → 调用照常成功 ✅
- **运行时动态加载**的 dex（assets 里、网络下载的）→ 没被重写 → 里面写 `XposedBridge.log` 就 `ClassNotFoundException` ❌

**我们的单包是 5 个 dex、同一个 APK、统一过 LSPosed**；
`grep -r "DexClassLoader\|InMemoryDexClassLoader\|instantiateClassLoader" mod-src/src fdm-app/src` = **0**。
⇒ 这条路既不是 Xposed API，也没有动态加载，**跟那个开关无关**。

小窝里 2026-09-25 就有过同样结论（`tmp/chatdb/export/2026-09-25 2329 …md:16`）。

## 五、教训（接 340）

| # | 教训 |
|---|---|
| **341** | ⭐⭐⭐ **「循环依赖」往往是因为忘了框架已经知道答案** —— 整页要模块 APK 路径，而路径只有「开模块本体」才有，可整页存在的意义就是不开本体。绕了一大圈才发现 LSPosed 的 `StartupParam.modulePath` 本来就是**白送**的（每个目标进程、早于 `handleLoadPackage`）。**要一个东西之前先问：拿到它的那条路，是不是正好依赖我要解决的那个问题？** |
| **342** | ⭐⭐⭐ **`Resources.getString` 不是 `final`，`Context.getString` 才是** —— 3.107.0 撞到 `'getString' in 'Context' is final` 就得出「一份 Resources 只能认一张表」，**结论下早了**。`javap` 一次能省一天：`getText/getString/getDrawable/getColor` 全可覆写，只有 `newTheme/getAssets` 是 final。**「A 不行」不等于「这一类都不行」，要看清到底是哪个 A。** |
| **343** | ⭐⭐⭐ **Compose 的 `Dialog` 是独立 window，`CompositionLocal` 管不到它** —— `ProvideCompositionLocals$ui` 会用 **View 自己的 context** 覆盖 `LocalContext`/`LocalResources`，而 Dialog 内部 `new ComposeView(dialog.context)` 追根溯源到根 View 的 context。⇒ 想让 Dialog 里的 Material3 拿到对的资源，必须在**建 ComposeView 时**就换 context，`setContent` 里 provide 没用。 |
| **344** | ⭐⭐ **量纲闸要按「认法可靠性」分流，不能一刀切** —— 用户气泡靠 `clip(Shape)` 引用相等认，会误标 ⇒ 需要尺寸闸；AI 气泡靠 `sAssistPending`（我们自己刚注入的元素）认，身份确定 ⇒ 量纲闸只会误伤（宿主 AI 回复天然满屏宽）。教训 338 要**反过来用**：已经有可靠身份的地方，别再用量纲卡。 |
| **345** | ⭐⭐ **跨 uid 的状态必须由那一侧上报，不能「伸手去查」** —— SAF 持久授权记在 uid 上。整页跑在宿主进程，无论怎么查 `persistedUriPermissions` 都只能看到宿主的；而我们自己的 `ui_saf_tree` 在 `sp(ctx)` 里也变成了 `HostStore`（宿主表）⇒ 恒「未授权」。**「查不到」和「没授权」是两件事，别混。** |
| **346** | ⭐ **「算得准」不等于「放得对」** —— 悬浮关闭钮的位置我算到「状态栏 + 68dp、右对齐 12dp」，任何页面都不重叠，精度没问题；但主人一眼就看出它不该在那儿。**位置是语义问题，不是几何问题。** |
