## 一、主人的观察把链路补完整了

| 现象 | 含义 |
|---|---|
| 开关后第一次重启，**卡闪了一下** | ✅ **`GmModel.setOn` 直写宿主"生效过"**（宿主读到了 `switchable:true`） |
| 随后**被服务器下发覆盖** | ❌ 服务器重写 `false`；而我们的"重应用"（`reapplyAll → reapply`）**没能改回来**（卡在"匹配不上"） |
| **第二次重启**卡不显示 | 磁盘上已经是 `false` 了 |

**⇒ 结论：写入链路是通的，唯一卡点就是"匹配"**（把 `false` 改成 `true` 那一步）。

---

## 二、本版：不再和字符串格式纠缠

| # | 改动 | 说明 |
|---|---|---|
| 1 | 新增 **`GmModel.fix(String)`** | 用 **JSON 结构化改写**：`new JSONArray(src)` → 遍历每个元素 → 若 `has("switchable")` 且当前为 `false` → `put("switchable", true)` → 有改动才 `toString()` 返回；**任何异常一律返回原串**（绝不破坏数据） |
| 2 | **`reapply` 双保险** | ① 先试正则 `"switchable"\s*:\s*false`；② 没改动就调 **`fix()`**；③ 两者都没改动 ⇒ 打"样本(前300)" |
| 3 | **`handle`（读写接管）同样双保险** | 保证"启动首次读取"和"服务器写盘那一刻"两条路都能改 |

**⇒ 只要宿主的这份 JSON 里存在 `switchable` 字段（无论空格、换行、转义如何），`fix()` 都能改到它。**

## 四、教训

| # | 教训 |
|---|---|
| **314** | ⭐⭐⭐ **文本层面的"结构化数据"改动，要用解析器而不是字符串替换**：字段存在就一定改得到，且不会因空格/转义/顺序失败 |
| **315** | ⭐⭐⭐ **双保险要有明确失败出口**：正则 → JSON → 才报"没改动"，并把**输入样本**一并打出来 |
| **316** | ⭐⭐ **结构化改写可能改变 JSON 形态**（字段顺序/转义）⇒ 仅在有改动时才替换，且改写函数**任何异常都返回原串**（宁可不改，不许改坏） |
| **317** | ⭐⭐ **"闪一下就没了"再次证明**：写入是通的，问题在**重应用**这一侧 —— 报症状时要区分"写没写进去"和"改没改回来" |
