## 二、⭐ 这一版的决定性实证（不需要真机，直接从宿主读出来的）

去 `DeepSeek_2.6.1.apk` 里把 `jq0` 和它父类 `Lim9` 反编译出来，一次定死三件事：

### 2.1 `jq0` 就是 Compose 的 `ShaderBrush`

```smali
.class public final Ljq0;
.super Lim9;
.field public final synthetic c:I      # tag
.field public final d:Ljava/lang/Object;

.method public constructor <init>(Landroid/graphics/RuntimeShader;)V
    const/4 v0, 0x1
    iput v0, p0, Ljq0;->c:I           # tag = 1  ← **就是我们 imgBrush 走的那条**
    iput-object p1, p0, Ljq0;->d:Ljava/lang/Object;   # d = 那个 RuntimeShader 本体
```

⇒ **`thisObject->d` 与我们 `sBmpShaderMap.put()` 的 key 是同一个对象**（IdentityHashMap 语义天然成立）。

### 2.2 `b(J)` 里的 J **确实是 size**，而且宿主拿它当缓存键

```smali
.method public final b(J)Landroid/graphics/Shader;
    .registers 3
    iget p1, p0, Ljq0;->c:I           # ← J 被直接覆盖（jq0 自己不用它）
    ...
    :pswitch_e  #0x1
    check-cast p0, Landroid/graphics/RuntimeShader;
    return-object p0                   # tag=1 ⇒ 原样返回 d
```

关键在**调用方** `Lim9`：

```smali
.field public b:J                       # 缓存的 size，初值 0x7fc000007fc00000（NaN,NaN）

.method public final a(FJLsf;)V        # (alpha, size, paint)
    iget-object v0, p0, Lim9;->a:Ljub
    if-eqz v0, :cond_d
    iget-wide v2, p0, Lim9;->b:J
    invoke-static {v2, v3, p2, p3}, Lhv9;->b(JJ)Z    # Size.equals(缓存size, 新size)
    if-nez v2, :cond_36
    :cond_d
    ... invoke-virtual {p0, p2, p3}, Lim9;->b(J)Shader;   # ★ 把 size 原样传给 b(J)
    ... iput-wide p2, p0, Lim9;->b:J                      # ★ 缓存这个 size
    ...
    invoke-virtual {p4, v1}, Lsf;->i(Landroid/graphics/Shader;)V   # 装进 Paint
```

⇒ `b(J)` 的 `J` = **packed Size（高 32 = width / 低 32 = height）**，这点我们原来解对了。
⇒ 而且宿主**只在 size 变化时**才重建 shader（冷路径，钩它是对的）。

### 2.3 `b(J)` 有 4 个调用点（不是 1 个）

`mt_apk_dex_xref` 结果：`Lci;->w()` · `Lim9;->a(FJLsf;)` · `Lob7;->i(...)` · `Lti7;->w()`。

⇒ 其中 `w()` 那种大概率不是绘制路径。**"谁在调"比"尺寸多大"更值得当判据** —— 这正是身份判据的立足点。

## 三、⭐ 因此被推翻的（3.42.37 那版是误判）

原判断（写在 `专题/图底串图-排查中.md` §7.2 / `交接文档.md` 顶部）：

> 怀疑 **`GmBubbleFitHook` 管太宽**：判据放宽成"任意 Shader"之后，
> 把宿主的**列表级 `ShaderBrush`** 也接管了 ⇒ 把气泡图 shader 画到列表区域。
> 铁证：`[FIT] 目标=(1440,25349)`。

**真相**：`1440` 宽 = **屏幕宽** ⇒ 那**不是**"宿主的列表级 brush 被误接管"，
而是**我们自己的 brush 被用在一个大节点上**（整页/整列表尺寸）。

而 3.42.34 起 `sBmpMap.get(thisObject)` 返回 null 就会 `:cond_7a` 放行 ——
**宿主的 brush 根本进不来**，闸门从一开始就在挡正常调用。

⇒ **「尺寸闸门（目标 > 2500 就放行）」是错的方向，本版删除。**
它只会让"大区域"退回不缩放（图 1:1 贴左上角 + `CLAMP` 边缘拉伸）⇒ **制造新的错位**。

## 四、这一版改了什么（3 处）

| # | 位置 | 改动 |
|---|---|---|
| **①** | `GmBubble` 新字段 | `sBmpShaderMap:Ljava/util/IdentityHashMap;` —— **第二把钥匙**：RuntimeShader 实例 → 位图 |
| **②** | `GmBubble.imgBrush()` | 造出 RuntimeShader 后，把它也配一张图（`put(runtimeShader, sBmp)`）<br>+ **两处配对表都加限容**（size > 64 就 clear） |
| **③** | `GmBubbleFitHook.beforeHookedMethod` | 取图改成**两把钥匙**：先按 shader 配对，再按 brush 配对；**都配不上就放行**（并打一条 `logOnce`）<br>+ **删掉尺寸闸门** |

### 4.1 为什么"两把钥匙"

| 钥匙 | 键 | 为什么 |
|---|---|---|
| ① | `thisObject->d`（RuntimeShader） | **一定配得上** —— 这个 shader 是我们亲手 new 的，`jq0.<init>(RuntimeShader)` 原封不动存进 `d`。宿主中间复制/包装过 brush 也影响不到它。 |
| ② | `thisObject`（brush 实例） | 3.42.34 的老路，保留兜底（万一宿主某个版本不再把 shader 明放在 `d` 里）。 |

⇒ **两把都不中 ⇒ 这不是我们造的 brush ⇒ 一律 `return-void`，绝不 `setResult`。**
⇒ 这就把"串图"的入口从根上关掉了：**宿主的 brush 永远进不来**。

### 4.2 顺手修的：配对表内存泄漏

`sBmpMap` / `sBmpShaderMap` 都是**每次重组就 put 一个新对象**的 `IdentityHashMap`，
而 value 是 `Bitmap`（大对象）⇒ 滚一会儿列表就是 OOM 的路。

⇒ 两处都加：`size() > 64` 就 `clear()`。
清空只会让"当帧正在显示的那些 brush"配不上 ⇒ 那一帧放行不做裁剪，
下一次重组又配上了 —— **最多一帧没铺满，比 OOM 便宜得多**。

### 4.3 诊断（临时，下一版可删）

配对失败时打一条 `logOnce`：

```
[FIT] 两把钥匙都没配上  —— 这个 ShaderBrush 不是我们造的 ⇒ 放行。
```

**正常情况一条都不出现。** 一旦出现 ⇒ 说明宿主的某个 brush 确实走进了这个钩子，
那就是"串图 / 跑到别人底下"的候选来源 —— **一次真机就能定性**。

原来的 `[FIT] 图=… 目标=(…) scale=…` 保留（主人已经熟悉，出问题能立刻看出图对不对）。

## 六、遗留（需要主人拍板的 1 件）

### ⚠️ `zoomF` 封顶会造成"盖不满"——这是**设计取舍**，不是 bug

```
scale = min(max(w/bw, h/bh), zoomF)     # zoomF = fuckds_bubble_maxz / 100（默认 2.0）
```

当**目标区域远大于图片**时（例如整页 1440×25349 铺一张 1440×3168 的图），
`max()` 算出 8.0 会被 `min()` 砍到 2.0 ⇒ 图只盖住上面一小块 ⇒ **剩下"连像素延伸都没有"**。

这正是主人描述过的「下半截透明 / 下面连像素延伸都没有」。

**两条路（各有代价）**：

| 方案 | 效果 | 代价 |
|---|---|---|
| **A. 保留封顶**（现状） | 图不会被拉糊 | 大区域**盖不满**，出现空白 |
| **B. 封顶后改用 `CLAMP` 边缘色补满** | 永远铺满 | 回到 2.22.23 主人抱怨过的"**边缘颜色拉伸**" |
| **C. 只在"气泡"上封顶，大区域不封顶** | 两头都要 | 需要先能可靠区分"气泡 brush / 别的 brush" |

> 本版**没动它**（改视觉设计要主人点头）。
> 但现在**身份判据已经就位** ⇒ 方案 C 已经变得可行（配对时把 `sImgName` 一起存下来即可）。
