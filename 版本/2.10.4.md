## 一、🐛 铁证 bug：菜单那行「回复建议」点了等于没点

`GmClick.onClick` 是一条 `if-ne v0,v1,:cond_xx` 链。我把 0x33~0x37 插在链尾，**但没改上一条（0x32）的「不匹配」跳转目标**：

```smali
    :cond_18e
    const/16 v1, 0x32
    if-ne v0, v1, :cond_196     ← 不是 0x32 就跳到方法末尾的 return-void
    ...pickUserImage()V
    return-void
                                ← 我插的 0x33~0x37 在这后面 ⇒ 永远到不了！
```

⇒ 点「回复建议」直接 `return-void` ⇒ **`GmSuggestDialog.open()` 从没被调用** ⇒ 没有日志、没有界面、当然也没有吐司。

**修法**：把 0x32 分支的跳转目标改成我这条链的入口标签 `:c33`。✅

> 教训 148：**往「if 链尾」追加分支时，必须同时把「上一条的 else 分支」重新指向新链入口**，
> 否则新分支是死代码（编译器不会报错，因为语法完全合法）。

## 二、第二记杠杆：劫持文案解析 `pd5.I`（不管列表换没换成）

档案里用 `dex_xref` 查过：字段 `c` 的**读点只有 `pd5.H` / `pd5.I` 两处**。
⇒ 不管 chip 渲染的是哪份列表（宿主的 / 我们的 / remember 缓存的），**文字都要经过这两个函数**。

新增 **`GmPromptTextHook`**（挂 `pd5.I`）：

```
命中 pd5.I(g56, ctx)
 ├─ 开关关 → 放行
 ├─ id = getIntField(g56,"a")
 │    ├─ id ≥ 0x2329 → idx = id - 0x2329      （我们改过的对象）
 │    └─ 否则按宿主内置 id 映射：9→0 10→1 11→2 13→3 14→4 15→5
 ├─ idx < 0 → 放行（不是提示词对象）
 └─ setResult(模板池[idx % 模板数])            ← ★ 直接决定 chip 显示什么字
```

**为什么这招比换列表更硬**：绕过「列表有没有被替换 / `remember` 有没有锁死 / `d` 是不是 0」全部变量，
**一处直接定文案**。同时点击发送取的就是这个文本 ⇒ 发送内容也一起正确。

日志：`[建议] g56.id=<宿主真实id>`（一次）· `[建议] 文案已接管 <文字>`（一次）
