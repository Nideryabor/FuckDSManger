## 一、这一版治的是什么

**症状**：灰度面板里改了值，UI 显示变了，**宿主没变**。

**根因（C0 查出来的两条）**：

1. `grayWrite` 只写 `fuckds_pin_*` 影子键，而且**键形一律用 `kv_remote_settings_`**
   —— 而宿主 2.5.2 对 63 项读的是 `kv_settings_<纯名>`
2. **全底座里没有任何地方读那个影子键**（`GmStore` 只在 write/remove 两处提到它）
   ⇒ 影子键写进去就躺在 MMKV 里，**没人认**

⇒ 修法：**给底座装一张 pin 表，并在它已有的"读 MMKV"钩子里查表替换**。

## 二、改动

### 底座 `GmMmkvHook`（一个类，三处）

```smali
+ .field private static sPins:Ljava/util/HashMap;          ← ① pin 表

+ .method public static setPins(Ljava/util/HashMap;)V      ← ② 桥把【同一个 map 实例】塞进来
+ .method private static pin(Ljava/lang/String;)Ljava/lang/String;   ← 查表
+ .method private static logPin(Ljava/lang/String;)V        ← 带 try/catch 的日志

  afterHookedMethod:                                       ← ③ 已有的读侧钩子里加一次查表
      check-cast v1, Ljava/lang/String;      ← 拿到 key
  +   invoke-static {v1}, GmMmkvHook;->pin(...)   ← 命中？
  +   if-eqz v4, :cond_pinmiss
  +   setResult(v4) / logPin / return-void         ← 命中就直接换掉返回值
  +   :cond_pinmiss
      invoke-virtual {p1}, ...->getResult()        ← 原有的 handle() 逻辑【一个字不动】
```

**为什么落在这里**：`GmEntry` 早就把 `GmMmkvHook` 挂在 `com.tencent.mmkv.MMKV` 的
`k`（读字符串）/ `q`（写字符串）上了，`afterHookedMethod` 的骨架本来就是
"读到值 → 调 handle → setResult(新值)"。B1 只是**往这个已有骨架里塞一次查表** ——
不新建机制、不新增 hook 注册点。

### 桥（3 个文件）

| 文件 | 改动 |
|---|---|
| `FdmBridge.grayWrite` | 影子键**三种键形都写**（`kv_settings_` / `kv_remote_settings_` / 裸名）+ **同时塞进内存 pin 表** |
| `FdmBridge.pins()` | 懒建 `HashMap` 并**反射**调 `GmMmkvHook.setPins(m)`（桥在 `bridge` 包、hook 在 `gm` 包，直接调会 `IllegalAccessError`）。**交的是同一个实例** ⇒ 之后 `put` 立刻对底座可见 |
| `FdmBridge.syncPins()` | 宿主重启后内存表是空的 ⇒ 在收到推送时把**存储里已有的影子键**全量灌回内存表 |
| `FdmUiHook.BASE_ENTRY` | 🐞 修 3.13.0 的 bug：`sAct` 在 **`…gm.GmEntry`**，不是 `…GmEntry`（日志里那句 `NoSuchFieldError` 就是它） |

**为什么"三种键形全写"**（C0 实测）：

| 宿主实际读的键 | 项数 |
|---|---|
| `kv_settings_<纯名>` | 63 |
| `kv_remote_settings_<纯名>` | 18 |
| `<纯名>` 裸名 | 2 |

—— 不知道宿主读哪个？**那就三种全塞进表**，反正只是查表命中。

## 三、链路（这一版之后）

```
UI 改一个灰度值
  → sendCmd("gray_put", …)
  → 宿主进程 FdmBridge.onCmd → grayWrite()
       ├─ 写影子键 ×3（持久化，跨重启）
       └─ pin 表 put ×3 ──────────┐
                                   │  （同一个 HashMap 实例）
                                   ▼
                          底座 GmMmkvHook.sPins
                                   ▲
宿主某处读 MMKV.k("kv_settings_x")  │
  → afterHookedMethod 拿到 key ────┘
  → pin 命中 ⇒ setResult(我们的值)  ⇒ **宿主当场读到我们的值**（不必重启）
```

**日志关键字**：

| 日志 | 含义 |
|---|---|
| `🔗 pin 表已交给底座（读侧替换生效）` | ✅ 表注册上了 |
| `pin 表全量同步 N 条` | ✅ 重启后把旧 pin 灌回来了 |
| `pin 表 +3（<纯名> = <值>）` | ✅ 改值时写进表了 |
| `[mmkv] pin 命中（读时替换）` | ✅ **宿主真的读到我们的值了** |

**这一轮同时是那道判定实验**（一举两得）：

| 现象 | 结论 |
|---|---|
| 值变了 **且** 有 `pin 命中` | 🎉 缓存不挡 ⇒ **B 通吃**，B2 铺类型即可 |
| 有 `pin 命中` 但**值没变** | ⚠️ 宿主那个 `ConcurrentHashMap` 缓存挡住了 ⇒ **这几个键转 C 补** |
| **没有** `pin 命中` | ⚠️ 宿主读的不是字符串路径（或读的是别处）⇒ 拿日志再定位 |
