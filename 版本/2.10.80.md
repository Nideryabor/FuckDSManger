## 二、本版：换一条"必然发生"的腿 —— `wr` 构造器

| 方案 | 为什么更稳 |
|---|---|
| ~~`h91.a` args~~ | 要它恰好渲染（已证伪） |
| ~~`wr.x()`~~ | 要它恰好被业务动作调用 |
| **`wr` 的构造器** ✅ | **`wr` = 会话消息容器（`ChatSessionComponent` 持有）** —— **进会话时必然被 new 一次**，与渲染节奏无关 |

实现：

```smali
findClass("wr", loader)
new GmSuggestAi()                                  # 新建 hook 实例
XposedBridge.hookAllConstructors(wr.class, hook)   # 挂所有构造器
```

`afterHookedMethod` 里新增 **构造器分支**：

```
param.getResult() == null（构造器无返回值）
  ⇒ 取 param.thisObject  ⇒ 存 sWr   ← ★ 关键
```

拿到 `wr` 实例后，`probe()` 里的 `sync()` 会反射调 `wr.x()` **现取**最新消息列表 —— **只要进过一次会话，点按钮就能拿到数据**。

### 现在的四条腿（谁先到用谁）

| # | 路径 | 触发条件 |
|---|---|---|
| 1 | **`wr` 构造器 → `thisObject`** | **进会话（必然）** ★ 本版新增 |
| 2 | `ao1.M()` 返回值 | 会话组件被取用 |
| 3 | `wr.x()` 返回值 | 业务动作 |
| 4 | `h91.a` args 扫 `hp8` | 消息列表渲染 |

## 三、三态计数：Toast 一眼看全

`probe()` 失败时显示：

```
AI 未捕获（a=0 M=3 x=5）
            ↑   ↑   ↑
         h91.a  M/ctor  wr.x
```

| 字段 | 含义 |
|---|---|
| `a` | `h91.a` 有效调用次数（有参数才算） |
| `M` | **`ao1.M()` / `wr` 构造器** 拿到实例的次数 |
| `x` | `wr.x()` 拿到返回值的次数 |

**⇒ 一眼分清哪条腿通、哪条腿死，不用再猜。**

## 五、教训

| # | 教训 |
|---|---|
| **385** | ⭐⭐⭐ **Composable 不等于"每帧必调"**：Compose 有跳过（skippable）机制，参数未变就整段跳过 ⇒ **别把渲染函数当"必然发生"的注入点** |
| **386** | ⭐⭐⭐ **优先挂在"对象被创建"的地方，而不是"被使用"的地方**：构造器只跑一次、时机确定、与 UI 节奏无关 ⇒ **是 hook 里最可靠的锚点** |
| **387** | ⭐⭐ **"之前命中过"不等于"这个点有效"** —— 我上一轮把 `wr.x` 的计数当成了 `h91.a` 的战果，直接导致两版方向错误。**多点共用回调时，计数必须分开**（本版 `a / M / x` 三计数） |
| **388** | ⭐⭐ **`param.thisObject` 是构造器 hook 的标配**：构造器没有返回值，拿实例只能靠它 |
