## 三、⚠️⚠️ 两个真机踩出来的坑（务必记住）

### 坑 1 · **别用 `gh2.S(...)`** —— 它会**开新会话**

`S` 不带会话参数，走的是"兜底"逻辑。**每发一次 ⇒ 一个新空会话**（本轮连开 5 个）。

对照 2.5.2 底座 `GmCallDialog.send()` 里的注释，写得明明白白：
```
"发送：用有会话的 component（sid 非空）"
"发送：兜底（没有候选带会话 ⇒ 可能新开）"     ← ★ 就是这个坑
```

### 坑 2 · **必须挑「当前会话」的那个 `gh2` 实例**

宿主进程里**同时活着多个 `gh2`**（每个打开过的会话一个）。本轮实测同时有 4 个：
```
sid="ff420901-…"  3 条
sid="c64bb7d0-…"  3 条
sid="d9efadb8-…"  76 条    ← 当前会话（消息最多）
sid=""            1 条     ← 空会话
```

**判据 = `W().a` 非空 且 消息数最多**。拿错了就会开新会话。

> `GmSender` 的做法：hook `gh2` 的所有构造器，把实例收进弱引用表，发送时按上面的判据挑。

## 四、★ `<Suggestion>` 语法

```
<Suggestion>▸ 再详细讲讲</Suggestion>              显示与回复同一句
<Suggestion>▸ 说说看|请从原理上详细解释一下</Suggestion>   显示与回复分开
⟦SUG⟧▸ 再详细讲讲⟦/SUG⟧                           保险写法（⟦⟧ 已验证能穿过宿主 markdown）
```

**渲染**：借宿主 `pushLink`（`in.h(si6)` = `Builder.pushLink`）⇒ 宿主自己的链接样式（主题色 + 下划线）。
**点击**：`ti6`(LinkInteractionListener) 接口用 `Proxy` 实现 ⇒ 回调里调 `GmSender.send(payload)`。

## 五、★ 怎么让 AI 写这个标签

模型不会凭空知道这套标记 —— 要告诉它。两种办法：

**① 直接要求**（最快）：
> 请原样输出这一行，不要放进代码块：`<Suggestion>▸ 再详细讲讲</Suggestion>`

**② 写进系统提示词**（一劳永逸）。在「聊天 › 系统提示词」里追加：
```
【追问建议】当你想让用户继续追问时，在回复的最后另起一行输出：
<Suggestion>▸ 你的建议问题</Suggestion>
可以写多行，每行一个建议。不要在代码块里写。
```

## 七、教训（933~938）

- **933 ⭐⭐⭐ 老代码的注释是金子** —— 底座里 `"发送：兜底（没有候选带会话 ⇒ 可能新开）"`
  一句话就点破了尼尼折腾好几轮的那个坑。**读透了再动手，比试错快十倍**。
- **934 ⭐⭐⭐ 「能调通」≠「是对的」** —— `gh2.S` / `x42.s` 都能调用成功、都不崩，
  但一个会开新会话、一个根本不发。**验证要看到"结果"，不能停在"没报错"**。
- **935 ⭐⭐⭐ 参数语义要从"默认值"反推** —— `gh2.S` 里 `m1a` 的默认值是
  `new m1a(elapsedRealtime, randomUUID())`；`h0` 则要求显式传 `ns`。
  **看默认值怎么造，就知道这个参数是"什么角色"**。
- **936 ⭐⭐ 同一个类可能有多个实例** —— `Java.choose('gh2')` 拿到"第一个"是不靠谱的；
  要**按业务判据挑**（这里 = 消息最多的那个）。
- **937 ⭐⭐ frida 投递式和"人的反应时间"天生对不上** ——
  30 秒窗口 vs 人看到消息再操作的几分钟延迟。⇒ **能让脚本自己触发的，别等人**。
  （本轮最终靠"脚本自己调用"才闭环）
- **938 ⭐⭐ 试探性调用要控制爆炸半径** —— 尼尼连开 5 个空会话才收敛。
  ⇒ **每次试探前先想好"最坏结果是什么、能不能收拾"**。
