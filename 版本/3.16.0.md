⇒ **写侧没问题，读侧一次都没命中。**

## 二、真因（逐字节核出来的）

我把宿主读一个设置的地方（`Lqa5.D`）反编译读了：

```java
if (mmkv.contains("kv_settings_search_state_on_login")) {          // ★ 先问「存储里有没有」
    return mmkv.j("kv_settings_search_state_on_login");            // ★ j = getString(key)「1 个参数」
} else {
    if (remoteMap.containsKey("search_state_on_login"))            // 远程下发 map
        return remoteMap.get("search_state_on_login");
    return 默认值;
}
```

而 `GmEntry` 只把 `GmMmkvHook` 挂在了：

- `MMKV.k(String,String)String` —— **2 个参数**的 getString
- `MMKV.q(String,String)Z` —— encode

⇒ **宿主用的是 1 个参数的 `j`，我们挂在 2 个参数的 `k` 上 —— 根本够不到。**

> ⚠️ 我的错在**猜了签名**。3.14.0 时代我从"hook 的参数是 (String,String)"推断"这是字符串读"，
> 当时没去核**宿主究竟调哪个**。教训：**"宿主调哪个方法"必须从字节码里抄，不能从签名猜。**

### 并且顺手发现：光挂 getter 还不够

`Lo02.<init>` 里每一项都是：

```java
if (mmkv.contains("kv_settings_x")) {
    new m02( mmkv.g("kv_settings_x") );   // Int  → g = getInt
}                     // String → j = getString(key)
```

`contains` 为**假**时，宿主**根本不读存储**（走远程 map / 默认值）。
而实测：宿主 MMKV 里 `kv_settings_*` 只有 **7 个键物理存在**……

⇒ 所以「覆盖一个键」需要**两件事**：
1. 让 `contains` 回答 **true**
2. 拦对应的**类型化 getter**

## 三、这一版改了什么

### 底座 2.22.122 → 2.22.123（`patch_base_123.py`，两个类）

**① `GmEntry`：给 `com.tencent.mmkv.MMKV` 补挂两个方法**

```smali
const-string v1, "j"          ← getString(key)，1 个参数
… hookM(…)

const-string v1, "contains"   ← 让"存储里有没有"这个问题能被我们接管
… hookM(…)
```

**② `GmMmkvHook.afterHookedMethod`：重写成「按返回类型分派」**

```
取 key = args[0]（守卫从 args.length==2 放宽到 >=1）
结果 = getResult()
├─ 是 String（j / k）
│   ├─ pin 命中 ⇒ setResult(pin) + 日志「[mmkv] pin 命中（读时替换）」+ return
│   └─ 没命中   ⇒ 落回原有的 handle() 逻辑（model_configs 那套，一个字没动）
└─ 是 Boolean 且为 false（contains 说"没有"）
    └─ 我们有 pin ⇒ setResult(true) + 日志「[mmkv] pin 命中（contains 提为 true）」
```

> 用**返回类型**分派而不是去比对方法名 —— 少一次字符串比较，也不用担心 `j`/`k` 两个名字。

### 桥（一处稳健性）

`syncPins(ctx)` 从"只在收到 UI 推送时跑"提前到 **`probe()`（宿主一启动就跑）**：

> 否则 UI 一直没起来 ⇒ 内存 pin 表永远是空的 ⇒ 重启宿主后"上次改过的值"会突然失效。

## 五、⚠️ 真机验收（和 3.15.0 同一套动作，这次该成了）

1. 装 **3.16.0** → **让宿主重启一次**
2. UI 里改 **登录搜索态**
3. 看日志：

| 日志 | 含义 |
|---|---|
| `pin 表全量同步 N 条` | 宿主启动时把存储里的 pin 灌进内存表 ✅ |
| `🔗 pin 表已交给底座` | 表注册上了 |
| **`[mmkv] pin 命中（读时替换）`** | ✅ **这次应该有了** |
| `[mmkv] pin 命中（contains 提为 true）` | 说明这个键在存储里原本不存在，被我们"提"上来了 |

**依旧是那道判定实验**：

| 现象 | 结论 |
|---|---|
| `pin 命中` 有了 **且** 宿主值变了 | 🎉 B 通了 ⇒ 开 **B2** 铺 `g/d/i/e` |
| `pin 命中` 有了 **但值没变** | ⚠️ 宿主还缓存了一层 ⇒ 转 **C** |
| **仍然没有** `pin 命中` | 说明宿主连 `contains`/`j` 都绕过了 ⇒ 拿日志定位别的读入口 |
