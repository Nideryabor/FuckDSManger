# 3.28.0（vc538）· 底座 2.22.130 —— 「雷霆大横条 + 卡成 PPT」一箭双雕

> 2026-09-30 · 尼得亚伯 🐲 · 装机：`com.little_femaleboy.cannot_show.the_big_won_whale` / 537→538
> 主人复述：「**用户气泡下面那个雷霆大横条跟随了 AI 气泡图片，用户气泡本身是好的；AI 气泡也是好的；但一更新界面就卡成 PPT**」

## 一句话

**两个症状、一个根因链**：`GmBubbleCellHook` 里角色分派的 `if-nez` 写反 ⇒ **用户项也走"助手支线"** ⇒ ① 用户那行的**项级 Modifier** 被 `wrap()` 套上 **AI 档的图片底**（= 跟着 AI 图的大横条）② 每个消息项都要跑一遍 `imgBrush()`，而它**每次都 `BitmapFactory.decodeFile` 一张 16MP 原图（~60MB 分配）** ⇒ 一重组就卡成 PPT。

## 证据

| # | 证据 | 来源 |
|---|---|---|
| 1 | 用户气泡本身好看 ⇒ `ub()` 定点重写（`ls9.f` 门）没问题 | 主人回执 |
| 2 | 横条**跟着 AI 的图** ⇒ 那条横条只可能来自 **`wrap()`**（它才用 `sImgName=fuckds_bubble.png`；`ub()` 用的是 `fuckds_ububble.png`） | 主人回执 |
| 3 | 而 **`wrap()` 只在"助手支线"里被调用**（`:cond_d8 → goto :goto_f6`）⇒ 用户行出现 AI 图 = 用户行走了助手支线 | `GmBubbleCellHook.smali` 341~355 行 |
| 4 | `instance-of v4, v3, String` + **`if-nez v4, :cond_b2`** ⇒ 角色**是 String 就跳助手块**（判据整体失效） | 原文（`if-nez` = 非零才跳） |
| 5 | `imgBrush()` 里 `BitmapFactory.decodeFile(...)` **每次都执行**，只有 `sput sBmp` 没有命中判断 | `GmBubble.smali` 550~666 行 |
| 6 | 原图 `fuckds_bubble.png` = 4096×3584（5.9MB）· `fuckds_ububble.png` = 3072×4608（3.9MB） | 真机拉取 |
| 7 | 开关"真值"在宿主 **MMKV**（`files/mmkv/mmkv.default`），不是 `fuckds_gm.xml`：`fuckds_bubble_on=01 00(false)` / `fuckds_ububble_on=01 00(false)` | 真机爬取 |

## 改动（底座 2.22.129 → 2.22.130，两类三处）

| # | 位置 | 改法 |
|---|---|---|
| 1 | `GmBubbleCellHook` 角色分派 | `if-nez v4, :cond_b2` → **`if-eqz v4, :cond_b2`**（一行）⇒ 是 String 才继续比 `"USER"`；`USER` ⇒ 走用户块（**只计数、不注入**）；其余/非 String ⇒ 助手块 |
| 2 | `GmBubble` 新字段 | `sBmpCache:Ljava/util/concurrent/ConcurrentHashMap;` |
| 3 | `GmBubble.imgBrush` | 入口先查 `sBmpCache.get(sImgName)`（表不存在就新建）⇒ 命中直接 `goto :cond_62`，**跳过 decodeFile**；主路径解码成功后 `put` 进去 |
| 4 | `GmBubble.saveImage` | 方法开头清空 `sBmpCache`（图片被重写 ⇒ 旧缓存作废，避免"换了图还是旧图"） |

> 两张图 ⇒ 表里两条（`fuckds_bubble.png` / `fuckds_ububble.png`），**不再互相把对方挤出缓存**（单槽缓存会被"两档交替"打成永远 miss）。
> 产物回读：`if-eqz v4, :cond_b2` ✓ · `sBmpCache` 4 处 ✓ · 底座 `classes=137` 不变 ✓
