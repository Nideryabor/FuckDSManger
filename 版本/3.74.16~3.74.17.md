## 一、灰度有两条通道，都真的在跑

查了 `FdmBridge.grayWrite()` 的实际路径，一次改键写 **4 个地方**：

| 顺位 | 写到哪 | 生效 |
|---|---|---|
| ① 主写 | `kv_settings_<键>`（宿主**真实键**·本地覆盖层，优先级最高） | ✅ **主通道** |
| ② 副写 | `kv_remote_settings_<键>`（宿主真实键·缓存层） | ✅ 但被 ① 压住 |
| ③ | 影子键 `fuckds_pin_*`（三种键形各一份） | ✅ **读时替换通道** |
| ④ | 内存 pin 表 `sPins` | ↔ ③ 的实际数据源 |

### 影子键是怎么生效的（★ 这轮第一阶段我判错了，这里是更正）

一开始我看的是 `mod-src/work/sm_new/` 那份**旧副本**（10287 B，没有 `setPins`），
断言"影子键是死代码"。**错了。** 底座正本 `tmp/base130_261/sm/` 那份是 **14730 B**，
含 `setPins` / `pin` / `logPin` / `rows`，真机日志也有命中的铁证。

真正挂载（`GmEntry`）：

```
hookM(cl, "com.tencent.mmkv.MMKV", "q", GM + "GmMmkvHook");   // encodeBool（写）
hookM(cl, "com.tencent.mmkv.MMKV", "k", GM + "GmMmkvHook");   // decodeString（读）
```

| 挂点 | 真身 | 时机 | 干什么 |
|---|---|---|---|
| `MMKV.k(String,String)String` | `decodeString`（**读**） | `afterHookedMethod` | `pin(key)` 查表 → 命中就 **`setResult`** ⇒ **读时替换** |
| `MMKV.q(String,Z)Z` | `encodeBool`（写） | `beforeHookedMethod` | `handle(key,value)` 拦截写入 |

`afterHookedMethod` 里的关键三行（smali 实测）：

```java
invoke-static {v1}, GmMmkvHook;->pin(String)String   // 查 pin 表
invoke-virtual {p1, v3}, setResult                   // ★ 替换返回值
logPin("[mmkv] pin 命中（读时替换）")
```

真机日志铁证：

```
[mmkv] pin 命中（contains 提为 true）
[mmkv] pin 命中（读时替换）
[mmkv] switchable false→true 已替换
```

### 那 `handle()` 里只认一个键是怎么回事

`handle()` 里的 `kv_remote_settings_model_configs_v1` 判断是**写侧的特化处理**
（把下发的 JSON 里 `"switchable":false` 改写成 `true`），**不是** pin 机制的全部。
`pin()` 那条路对**任何键**都生效，只要 pin 表里有。

### 局限（写清楚，免得下次又想当然）

- 只对**字符串类型**的键值有效（`instance-of String`）；数字/布尔型走真值通道
- 所以两条通道是**并存互补**的，不是"一条主一条废"

## 二、重置灰度 = 删 MMKV，让服务器重下发

### 旧做法（假的）

`gray_restore_all` 原来做三件事：撤影子键 → **把备份写回真实键** → 清内存 pin 表。

问题：备份记的是「**我们第一次改之前**」的值，而那份值本身可能已经被我们改过；
而且 `kv_settings_*` 这种"本地覆盖层"写进去以后**服务器再下发也压不住**。

### 新做法（主人定的原理）

> **重置灰度 = 直接删掉 MMKV，服务器会重新下发一份。**

```
① 删宿主真实键  kv_remote_settings_* / kv_settings_*（按 GRAY 表逐项删）
② 删我们的中间物  fuckds_pin_* + fuckds_bak_*
③ 清空内存 pin 表（否则底座读侧替换还活着）
⇒ 宿主下次启动发现本地没有 ⇒ 向服务端重新拉
```

**为什么更彻底**：删掉就是真的没有了，服务器给什么就是什么；
备份还原只能回到"我们改之前"，而那个值来源本身就不可靠。

UI 文案同步改：`全部恢复灰度` → **`重置灰度（服务器重下发）`**。

## 五、★ 通话页留驻（勾住）真的修好了

主人实测第一轮：「**通话按钮选项成功，勾住失败**」。

### 真因：锚点停在 2.7.1

`GmCallPin` 写死 `CLS_VM = "ps1"`（2.7.1 的名字）。在 2.7.2 里：

| 名字 | 2.7.2 实况 |
|---|---|
| `ps1` | **不存在** |
| `sq1`（2.6.2 的名字） | 还在，但**已被复用成别的类**（只剩一个 `serializer()`） |
| **`it1`** | ✅ **就是它** |

铁证在 `g83.smali:15658`（= `ChatCallHost.kt:32`，那个「要不要渲染通话页」的闸门）：

```smali
:cond_38
invoke-virtual {p0}, Lit1;->a()Z      ← ★ 闸门
```

### 改法：名字只当入口，结构才是判据

```java
CAND_VM = { "it1", "ps1", "sq1" }   // 顺序试
```

每个候选都要过**结构校验**：

1. 必须有 `a()Z`（0 参返回 boolean）
2. 必须有 Compose State 字段（`zda`）—— 闸门读的就是它

`sq1` 会被第 1 条挡掉（它没有 `a()Z`）。

真机：**主人确认「钩住了」** ✅

## 七、教训（1074 ~ 1079）

1. **⭐⭐⭐ 「我们有两条路」不等于「两条都在用」** —— 影子键那套机制写得很完整
   （三种键形 / 内存表 / 备份 / 撤销），看代码会以为它在工作。
   **要问的是"谁在读它"**：读侧钩子没挂 ⇒ 写了等于没写。
2. **⭐⭐⭐ 日志会撒谎，而假日志比没日志更坏** ——
   「ASR 探针已挂」这行跟上一行「已停用」自相矛盾，却在那儿挂了好几个版本。
   **同一件事的两行日志必须互相印证**。
3. **⭐⭐ 「删掉」比「还原」更干净** —— 备份还原回到的未必是原始状态
   （备份本身可能是改过的）。删掉让权威方（服务器）重新给一次。
4. **⭐⭐ R8 短名「还在」最坑** —— `sq1` 在 2.7.2 里确实存在，
   `findClass` 会成功、不抛异常，但它是**另一个类**。
   ⇒ **名字只当候选入口，结构校验才是判据**。（这条在 `GmSender` 上刚用过一次，这次又用上）
5. **⭐ 顺序：候选名要按"最新在前"排** —— `{it1, ps1, sq1}` 而不是 `{sq1, ps1, it1}`，
   否则撞到被复用的旧名会先失败一轮。
6. **⭐ 改 UI 控件类型时要连带看文案编号冲突** —— 我加 `pg_045` 撞了已有的，
   得先扫一遍已用编号再取。
