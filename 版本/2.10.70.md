> 产物：`FuckDSManger_NL_2.10.70_for_ds2.5.2.apk`（**221 / NL 2.10.70**，91 类，V1+V2+V3，sha256(partial) `e39f1645…`）
> 触发：主人 69 版 DIAG —— 「还是不行」

---

## 一、日志把链路证明成"全通"，但结果仍不对

```
[prompt] reapply 已把编辑内容写回宿主              ← ✅ 我们确实写进宿主了
[ds] 已用同型副本替换下发 Map（去掉 model_configs）  ← ✅ 下发覆盖也挡住了
[建议] 宿主列表 list=4                            ← 宿主读到的仍是 4 条（旧的）
```

**⇒ 写入通、防覆盖通，宿主却还是旧内容** ⇒ 说明**我们改的位置不是宿主真正读的位置**。

## 二、根因：改了一个"不存在的字段"

回看主人给的模型配置片段：

```json
"is_default":false,"enabled":false,"switchable":false,"show_model_name_in_session":false,
```

**⇒ 里面没有 `prompt_feature`！** ⇒ 服务器下发的 `model_configs` **不含这个字段**（客户端用**内置默认表** `m66.b` 补足）。

而 68 版我写的 `patch()` 是这样的：

```java
if (!o.has("prompt_feature")) continue;   // ★ 没有这个字段就跳过
o.put("prompt_feature", ourArr);
```

**⇒ 于是它"什么都没改"，却依然返回了 `arr.toString()`** ⇒ 上层以为成功、实际内容没变。

---

## 三、本版：无条件写入（没有就新增）

```java
for (每个模型元素) {
    o.put("prompt_feature", ourArr);      // ★ 无条件写：没有则新增，有则替换
    changed = true;
}
```

**⇒ 这样 `kv_remote_settings_model_configs_v1` 里每个模型都会带上我们编辑的 `prompt_feature`**，宿主反序列化（`w46` 里确实有这个字段）后就会用它 ⇒ chip 显示我们的文字。

## 四、验证

1. 装 `NL 2.10.70`
2. 设置 → 文件快捷选项 → 改一条（如「这是什么」→「这是啥」）→ **保存**
3. **强停 DeepSeek → 重开** → 传一张图 ⇒ chip 应显示**你改后的文字**
4. 若**仍不行** ⇒ 说明宿主显示用的是**编译进 APK 的内置默认表**（`m66.b`），那么下一步改为 **hook 列表渲染点 `yb5.e/f`，直接注入我们的列表**（2.10.51 时这套已验证可行，代码还在）

## 五、教训

| # | 教训 |
|---|---|
| **348** | ⭐⭐⭐ **"修改型操作"必须能区分"改到了"与"没改到"**：`has()` 判断后跳过、却又返回新字符串 ⇒ 上层完全无法察觉（本版已让"跳过"变成"新增"） |
| **349** | ⭐⭐⭐ **要改的字段可能"本来就不存在"**：服务端只下发**差异字段**，其余靠客户端默认值 ⇒ **"写入"应该是"覆盖/新增"而不是"仅替换已有的"** |
| **350** | ⭐⭐ **线索藏在用户给的原始数据里**：就是那段配置片段里**没有 `prompt_feature`** 这一点，才让方向瞬间明确 |
