## 一、这条回报暴露的真相

| 现象 | 推论 |
|---|---|
| 设置界面能打开 | ✅ 2.10.4 修的「if 链死代码」生效了 |
| **改了数量，按钮仍是 4 个** | ⛔ **渲染的列表根本不是我们的** —— `yb5.e` 的列表被 **`remember(key=常量)` 缓存的 lambda 锁死**（档案 B.2 #3 早就记过） |
| 文字仍空 | 说明屏上「取文字」这条路**不是 `pd5.I`**（大概率是 Compose 版 `pd5.H`），或宿主配置里 `content` 本来就是空 |

⇒ **别再跟 Compose 的列表/缓存硬碰**。屏幕上的「4 个」＝宿主 `prompt_feature` 里 **image 场景的 4 条**。

## 二、🎯 改走本项目的铁律：**直接写宿主自己的配置**

宿主那排 chip 的文字来自 **`kv_remote_settings_model_configs_v1` → `prompt_feature`**。
而这套读写机制**本项目早就有并且已验证过** —— 就是「**文件快捷选项**」（`GmPrompt` / `GmPromptDialog`）：

```
GmPrompt.build(rows)   rows = [id, scene, content]
GmPrompt.put(ctx, json)      → 写模块键 fuckds_prompt_feature
GmPrompt.apply(ctx)          → 备份宿主原值 + 把 "prompt_feature":[…] 替换进宿主 MMKV
GmPrompt.restore(ctx)        → 还原宿主原值 + 删模块键
```

**2.10.5 的做法**：`回复建议` 的「保存」现在**同时**写宿主配置 ——

```
每条模板 → 两行（image / file 各一条）
   image：id = 9 + i ，scene = "image"
   file ：id = 13 + i，scene = "file"
⇒ 宿主读到的 prompt_feature 就是我们的模板池（条数＝模板池条数）
⇒ 宿主用它原生的 chip 渲染、原生的点击发送 —— 零 hook、零 Composer 对抗
```

| 诉求 | 本版怎么满足 |
|---|---|
| 文字显示 | ✅ 宿主从自己的配置里读，必然有字 |
| 数量可变（默认 3） | ✅ 我们写几条就是几条（改数量 = 改写入条数） |
| 点击即发送 | ✅ 宿主原生行为，我们完全不插手 |
| 位置在输入框上方 | ✅ 宿主原生位置 |
| 一键还原 | ✅「恢复默认」同时 `GmPrompt.restore()` 把宿主原值还回去 |

保留的旧钩子（`buildMut` / `GmPromptTextHook` / `forceVis`）**不冲突**：配置路线生效后它们只是「同文案的冗余保障」。

## 四、教训

| # | 教训 |

| 149 | ⭐⭐⭐ **Compose 侧改不动时，回到「宿主配置」层** —— 本项目的看家本领就是「往宿主 MMKV 写键值」，遇到渲染墙应该**先想配置键**，而不是继续在 Compose 里凿 |
