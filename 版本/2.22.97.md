## 1. ⭐ 本轮最值钱的发现：**宿主 APK 就在手边**

`mt_apk_list_available_apks` 里躺着 **`deepseek2.5.2 (273).apk`**（宿主包本体 · 13311 类）。
之前 2.21.x 能 `xref Lc30;->a` 找到 `pn9.c`，就是因为有它 —— **本会话重新发现了它**。

> 🔑 **宿主 R8 没删 `SourceFile`/source-info 字符串** ⇒ `dex_strings` 搜 `ChatMessageBubble` 直接命中：
> `...components.message_items.user.MessageBubbleLayout (UserChatMessageBubble.kt:348)` · `MessageBubbleContentLayer (…:385)` · `MessageOverflowButton (…:481)` · `<anonymous> (…:239/268/308/322)`
> ⇒ **"文件级类 + 行号"可直达**：`Lzl9;` = `UserChatMessageBubble.kt` 的合并类，`Lls9;` = 该文件里 239 行那个 composable lambda。

### 1.1 用户气泡的"底"到底画在哪（**这就是靶子**）

`Lls9;->f(Ljava/lang/Object;Ljava/lang/Object;Ljava/lang/Object;)Ljava/lang/Object;`（384 指令 · 唯一的非构造方法）里：

```
.line 655  invoke-static {}, Lj92;->d()Z          ; 调试通道
.line 647  sget-object v5, Lma9;->c:Ldv8;         ; 读一个 CompositionLocal
.line 664  iget-object v5, v5, Lup2;->i:Ltp2;     ; → 主题色对象
.line 666  iget-wide  v5, v5, Ltp2;->a:J          ; → 颜色
.line 668  sget-object v8, Lzc;->o:Lc84;          ; ★ 形状 = 宿主 zc.o
.line 670  invoke-static {v1, v5, v6, v8}, Luia;->v(Lc76;JLmd8;)Lc76;   ; ★★★ 气泡底色
```

**判据链（四条独立证据）**：
1. 该 lambda 的 source-info 指向 **`UserChatMessageBubble.kt`** ✅
2. 形状是 **`zc.o`** —— 正是我们模块 `shape()` 的 fallback 常量（当年写 `shape()` 的人就是拿它当"宿主气泡形状"）✅
3. 类的字段是 `a/b/c:String` + `:uuid:` 字串 ⇒ **一条消息项** ✅
4. **`UserChatMessageBubble.kt` 那 4 个 lambda（`ig8`/`ls9`/`s71`/`zf5`）里，只有 `ls9` 有 `uia.v`**（其余三个 0 处）✅

> ❌ **差点踩雷（记录一下）**：先看中 `Lzl9;->K(Lc76;Ley3;I)V`（它做 `background(qv.f, tt7.a)`），但**它的 source-info 是 `DefaultUserAvatar (FullTextSearchItemAvatar.kt:112)`** ⇒ **source-info 是"这里调用了谁"**，所以 `K` 是**搜索页的头像**，不是气泡。**没有盲目下刀**。
> ❌ **形状不能当身份证**：`zc.o` 全宿主 **40+ 处**在用，**助手气泡也在用**（`pn9` line 2016 就是 `uia.v(mod, qp2.g, zc.o)`）。

### 1.2 `Lls9;->f` 是**接口分发**调用 ⇒ 静态 xref 查不到调用者

`Lls9;` 实现 `Lxv3;`，`f` 是被 `invoke-interface` 调的 ⇒ `dex_xref` 返回 0 条。
⇒ **不能靠 `caller()` 锚点**（而且 `GmUtil.caller()` 取的是**第 2 个宿主帧** = 调用者的调用者，语义上也不对口）。
⇒ **正解：给 `Lls9;->f` 自己挂一个钩子，用"作用域计数"当身份证**（和助手的 `sDepth` 完全同构）。

## 2. 新架构（v2.22.97）

| 层 | 做法 |
|---|---|
| **新类 `GmUBubbleHook`** | 挂宿主 **`ls9.f`**（`hookM(cl,"ls9","f","…GmUBubbleHook")`）⇒ `before`: **`GmBubble.sUBub++`** / `after`: `--`（带 `if-lez` 保护） |
| **作用域身份证** | **`sUBub > 0`** = "当前正在组合用户气泡本体"。**结构性、零猜测**（不是颜色、不是形状、不是值） |
| **定点重写** | `GmBubblePaintHook.ub(param)`：`sUBub>0` + 方法名 `v` + `args≥3` ⇒ **`GmBubble.ubMod(cl, args[0])`** ⇒ 拿返回值 **`param.setResult(...)`** |
| **`GmBubble.ubMod`** | `shape(cl)`（用 `uRadius()`）· 若 `uImgOn()`：`useUImgName()` + `imgBrush(cl)` ⇒ **自己调 `uia.u(mod, brush, shape, 0)`**；否则**自己调 `uia.v(mod, uColorLong(), shape)`**。⇒ **颜色 / 圆角 / 图片底 一次全覆盖**，且**不新增请求码、不改读取链** |
| **撤掉的（2.22.96 的错误）** | ① 用户项**项级注入**（→"一整条带"） ② 用户作用域内**把项内背景刷透明**（→"不该透明的透明了"） ③ `pg()` 里的 **`sUDepth>0 ⇒ 早退`**（→ 它让**用户项的绘制不再计入 `sPageCnt`** ⇒ "本页前 6 层"的兜底窗口**被拉长** ⇒ **更多东西被吃掉**，这正是"又双叒叕"的算术级真因） |
| **修崩溃** | `GmBubbleDialog.open()` 里把 `sBox` 加进新对话框前，**先看 `getParent()`，有父就 `removeView`**（`sBox` 是"建一次、两处复用"的容器 ⇒ 第二次 `addView` 必抛 `IllegalStateException: The specified child already has a parent`）|
| **`radius()`** | 用户档判据从 `sUDepth>0` 扩成 **`sUDepth>0 \|\| sUBub>0`**（保证 `shape()` 在 `ls9.f` 作用域里取到用户圆角） |
| **`inScope()`** | 收回成**只认助手**（`sDepth>0 && on()`）；用户侧完全交给新的 `ub()` 分支 |

### 2.1 `sUBub` / `sUDepth` 现状

- `sUBub`：**唯一真正干活的用户侧判据**（定点重写）
- `sUDepth`：**降级为"备用信号"**（`GmBubbleCellHook` 的用户支线仍计数，但**不再 inject**；只有 `radius()` 的 OR 条件还引用它）
- `colorLong()/imgOn()` 的双档逻辑**保留但不被依赖**（助手路径 `sUBub==sUDepth==0` ⇒ 永远返回助手值）

## 3. 2.22.96 三个回归的根因对照（写清楚，别再犯）

| 主人现象 | 真因 |
|---|---|
| **一整条带** | 用户项在 `pn9.c` 拿到的 **Modifier 是"项级/整行"**（含左侧留白），不是右边那个气泡 ⇒ 项级注入必然是横带。**助手项要整块、用户项要气泡本体 ⇒ 两者挂点不同，不能一套走到底** |
| **不该透明的又双叒叕透明了** | ① `inScope()` 把**用户作用域**也算进"助手替换路线" ⇒ 用户项内**每一个 `uia.v` 都被刷成透明**（引用块/卡片/图标一起中招） ② **`pg()` 的早退**让用户项绘制不再递增 `sPageCnt` ⇒ `sPageCnt<=6` 兜底窗口变长 ⇒ 页级实化**多吃层** |
| **两张图互相串** | `imgOn()/colorLong()` 靠 `sUDepth` 双档，而**项级注入的取名时机**与"当前档"耦合在一条 `sImgName` 上 ⇒ 任何一处档位读错就串图。**新架构把两条路彻底分家**：用户气泡只走 `ubMod` → `useUImgName()` → `fuckds_ububble.png` |
| **先开用户面再开 AI 面必崩** | **2.22.96 之前就存在的潜伏 bug**：`sBox` 复用容器第二次 `addView` 抛异常。以前没人"连开两个气泡对话框"，本版把它暴露了 ⇒ 本版修 |

## 5. 主人三步测

1. 装 **2.22.97** → **强停宿主**
2. **先验收"不再崩"**：美化 → **用户气泡美化 ›** → 关闭 → **AI 气泡美化 ›** → 关闭 → 再各开一次 ⇒ **不该崩**
3. **验收用户气泡**：随便发一条消息 → **划一下列表** ⇒ 自己那条应该是**右边一个圆角气泡**（**不是整行一条带**）染色/圆角；换色块 / 圆角 ±8 / 选图 都应只作用在**自己那条**
4. **验收没回归**：AI 气泡三件套照旧 · **引用块/卡片/文件那种"不该透明的"应该恢复**（这条最关键）
5. **日志判读**：
   - `hookM ls9.f count=1` ⇒ 钩子挂上了（**count=0 ⇒ 类名/方法名不对，立刻告诉我**）
   - `[气泡] 自检` → **`ls9.f 用户气泡 lambda 已调用（模块 NL 2.22.97 生效）`** ⇒ 真机上确实走到用户气泡了
   - `[气泡] 用户气泡` → `颜色/圆角已定点重写（ls9.f 作用域内）` 或 `图片底已定点重写（ls9.f 作用域内）` ⇒ 重写生效

### ⚠️ 若第 3 步"没变化"，请把日志里这三行发我
1. `hookM ls9.f` 那行（count 是多少）
2. 有没有 `ls9.f 用户气泡 lambda 已调用`
3. 有没有 `[气泡] 用户气泡` 那两行

（**有 1 无 2** ⇒ 宿主版本/类名不符 ⇒ 我换锚点；**有 2 无 3** ⇒ `uia.v` 的调用点变了 ⇒ 我加一条 `uia.u` 分支；**三行全有但画面不变** ⇒ `setResult` 被覆盖 ⇒ 我改成"直接改 args"。）

| **245** | ⭐⭐⭐ **"宿主包就在手边"要主动确认**：本轮所有突破都来自 `mt_apk_list_available_apks` 里那个 `deepseek2.5.2 (273).apk`。**开工前先扫一遍可用目标**，能省掉一整轮真机试错 |

| **247** | ⭐⭐⭐ **source-info 是"这里调用了谁"，不是"我是谁"**（本轮靠这条避免了把"搜索页头像"当成"用户气泡"下刀）。**看到字符串先问：它描述的是"目标"还是"自己"** |

| **249** | ⭐⭐⭐ **接口分发调用的方法，静态 xref 查不到调用者** ⇒ 此时**不要去找 `caller()`**（更别说 `GmUtil.caller()` 取的是第 2 个宿主帧，语义就错了）⇒ **正解是"给这一层自己挂钩子 + 作用域计数"**（= 教训 620/662 的"能判就别赌"、也是 `sDepth` 同构） |
| **250** | ⭐⭐⭐ **项级 Composable 的 Modifier ≠ 视觉容器**：助手项=整块（对），用户项=**整行**（错）。**"某个气泡要好看"必须挂在"那个气泡自己"的那次 `uia.v` 上** |
| **251** | ⭐⭐⭐ **加新判据时，别忘了它会把"既有计数/配额"算歪**：`pg()` 那 4 条 `sUDepth` 早退本身无害，**但它让用户项绘制不再计入 `sPageCnt`** ⇒ 兜底窗口变长 ⇒ 别处多吃层。**"不该透明"的算术级真因往往在"计数被漏加"上** |
