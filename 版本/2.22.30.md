## 0. 一句话结论

**路由导航能用 —— 但它的用处不在「实化」，而在「给我们一个只在聊天页成立的作用域锚点」。**

「实化」的真正障碍从来不是找不到聊天页，而是：
> **「底图」模式早就在内容下层了，却被 Compose 自己画的不透明底色挡死**

⇒ 所以本版只做一件事：**让聊天页那一层 Compose 底色透明**。

## 2. 现状机制（为什么「真背景」看起来像透明度调整）

| 角色 | 事实 |
|---|---|
| `GmBg.pos` | `0`=蒙层（上层）/ **`1`=底图（内容层 index 0）** / `2`=混合（上层 + 自绘混合） |
| `GmBg.setBlend` | 走 **`View.setBlendMode`** —— **View 级混合**，这就是「混合（真背景）」的全部实现 |
| `GmBg.ensure` | 负责挂载/摘除（`getParent` / `removeView`） |

⇒ **「底图（index 0）」这个位置本身是对的**（真的在内容下面），
但它**永远看不见** —— 因为 Compose 在自己的 `ComposeView` 里画了不透明底色，把它整个盖住。
所以历史上一路退化成「混合」：把图叠到上层再跟下面的内容混 ⇒ 主人观感就是「**这不还是透明度调整吗**」。

## 3. 本版改法（🅰️ 透明法）

**核心动作：在 `ChatPage` 作用域内，把页面底色那次 `Modifier.background` 的颜色替换成全透明。**

| # | 位置 | 改动 |
|---|---|---|
| 1 | **新类 `GmPageHook`** | 挂宿主 **`zc.s`**（= `ChatPage`）。`before`：`sPageDepth++` + `sPageDone = false` + `logOnce` 诊断；`after`：`sPageDepth--`（带 `if-gtz` 下限保护）。两个回调都 `try/catch` 包裹 |
| 2 | `GmBubble` | +字段 `sPageDepth:I`（public）/ `sPageDone:Z`（public） |
| 3 | `GmBg` | +方法 **`real(Context):Boolean`** = `isOn(ctx) && pos(ctx) == 1`（**只有「底图」档才实化**） |
| 4 | `GmBubblePaintHook` | 在 `beforeHookedMethod` **最前面**插「页面分支」（早于原有的计数/替换逻辑） |
| 5 | `DisableFlagSecure` | +注册 `hookM(cl, "zc", "s", GmPageHook)`；注册日志补 `zc.s`；版本串 2 处 → 2.22.30 |
| 6 | `GmBubbleCellHook` | 自检串 → `模块 NL 2.22.30 生效` |
| 7 | manifest | `360/2.22.29` → **`361/2.22.30`** |

### 页面分支的判据链（全部通过才替换）

```
sPageDepth > 0            # ① 正在组合 ChatPage
&& !sPageDone             # ② 本页还没处理过（只吃「第一个」）
&& args.length >= 2       # ③ 有 args[1]
&& method.name == "v"     # ④ 只认 Modifier.background(color, shape)
⇒ sPageDone = true        # ⑤ 打标记（无论后面成不成，本页不再重复判断）
&& GmBg.real(ctx)         # ⑥ 背景开着 && 是「底图」档
⇒ args[1] = Long(0)       # ⑦ Compose Color(0) = 全透明  → 底图露出
```

### 为什么「不加新开关」

「底图（在内容后面）」这个档位的**语义本身就是**「图要在内容下面」——
它过去做不到，本版把它修好，就是「实化」。
⇒ 主人**只要切到「底图」档**（`fuckds_bg_pos = 1`），实化自动生效；切回别的档立即恢复原状。

### 与既有逻辑的共存

`GmBubblePaintHook` 原有的「项内小卡透明化」跑在 `sDepth > 0`（助手**消息项**作用域）下，本版新增的页面分支跑在 `sPageDepth > 0`（**页面**作用域）下，
两者**层级不同**（页面 ⊃ 消息项）、且页面分支在最前面**先执行**，`sPageDone` 保证每页只吃一次 ⇒ **互不干扰** ✓

## 5. ⚠️ 已知风险 / 本版最大未验证点

| # | 风险 | 说明 |
|---|---|---|
| **A** | ⭐ **「本页第一个 `v` 调用 = 页面底色」是假设** | `Lzc;->s`（812 指令）里 `uia.v` **只在 instructionIndex 700 出现一次** —— 位置**偏后**，这一点**可疑**：真正的页面底色通常在最外层（靠前）。若那个 700 的调用其实是某个子组件，本版会**把它透明化**（误伤）而不是页面底色 |
| **B** | 页面底色可能压根不在 ChatPage 内 | 若底色由 `AppEntry` / NavHost 包裹层绘制（例如 `Lzya;->d(Lc76;Ley3;I)V`，它含 `uia.v` 且只有 3 个参数、形如「页面容器 + 背景」），则本版作用域**罩不到** ⇒ 无效 |
| **C** | 也可能是 **Activity 窗口背景**（`android:windowBackground`）而非 Compose 绘制 | 若如此，正解是让 `Window.setBackgroundDrawable` 透明（`GmBg.setBlend` 里已有 `Activity` 句柄，加一行即可），**比 Compose 层简单得多** |
| **D** | `sPageDepth` 泄漏 | 若 `zc.s` 的 `afterHookedMethod` 极端情况下未执行，`sPageDepth` 会只增不减。已加 `if-gtz` 防负，但泄漏本身未消除（风险低，Compose 正常路径必成对） |

**下一版的分支预判**：
- 若 A 成立（误伤）⇒ 给判据加 **「`args[2] == zc.o`（RectangleShape，需反射取）」** 或改成「前 N 次」白名单
- 若 B 成立 ⇒ 锚点从 `zc.s` 上移到 `Lzya;->b` / `Lzya;->d`（代价：要额外判「当前是不是聊天页」，可用 `ChatRoute` 反查当前 destination）
- 若 C 成立 ⇒ 在 `GmBg.setBlend`（已有 `Activity`）里加 window 透明化

## 7. 教训（783~787）

| # | 内容 |
|---|---|
| **783** | ⭐⭐⭐ **「谁挡住了它」比「它在哪」更值得先问**：`GmBg` 的「底图」模式**位置一直是对的**，问题从来是**上层不透明**。定位一个「看不见」的功能时，先画一遍**从底到顶的完整层级**（本例：DecorView → content → `GmBgView`(index 0) → `ComposeView` → Compose 画的底色），**挡住它的那一层就是答案** —— 而不是继续在「它该放哪」上折腾。 |
| **784** | ⭐⭐⭐ **路由清单的价值是「锚点」，不一定是「跳转」**：主人给的是「界面导航管理器」的资料，直觉上会去研究「怎么 navigate」；但真正被用上的是 **`ChatRoute` → 承载类 → `ChatPage` Composable** 这条**定位链**。**拿到一份「角色↔混淆名」索引时，先想它能给我们哪些「作用域锚点」**。 |
| **785** | ⭐⭐ **序列化名（serialName）是比类名更耐升的指纹**：R8 把类名全改了，但 `serialName` 是宿主自己写的字符串常量（还顺手把原 FQ 名写进了 `toString()`/`ObjectSerializer` 构造点）。⇒ **找 Kotlin 类的真身，「字符串里的原始 FQ 名」优先级高于「按字段形状猜」**（本版 `Qj1` / `Lzc` 两次命中都靠它）。 |
| **786** | ⭐⭐ **Composable 的 `trace()` 串是「人话身份证」**：`"com.deepseek.chat.ui.pages.chat.ChatPage (ChatPage.kt:137)"` 直接给出了**类名 + 文件 + 行号**，比反推混淆名可靠得多。⇒ 想确认「这个单字母类是什么」时，**搜它的 `xxx.kt:NNN` 串**。 |
| **787** | ⭐ **实验性改动要把「失败分支」写进日志**：本版对「hook 没上 / 没替换 / 替换了但没用」三种失败各埋一条不同的日志 ⇒ **主人一条回执就能定位**，不用再来回加日志出包。**改动不确定时，把不确定性变成可观测的日志，是最便宜的保险。** |
