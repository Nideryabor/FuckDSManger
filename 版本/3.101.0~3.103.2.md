# 3.101.0 ~ 3.103.2 —— 「宿主の终极美化策略」（替换宿主所有资源文字/图片）

> 2026-11-07 · 尼得亚伯 🐲 ｜ 产物 `FDM-3.103.2-single-signed.apk`（vc946）
> 一句话：宿主里凡是走资源表的东西（**747 条文字 / 204 张图**），都能在模块里改掉，
> **宿主升级不用改代码**；图片能显示**原色**（剥离了 Compose Icon 的 tint）。

## 一、需求与三个拍板

主人原话：「在模块的美化页上面加一个子菜单，能在里面设置/替换**所有宿主**的图片和文字串」

| 项 | 决定 |
|---|---|
| 范围 | 文字 + 图片**全套**（一次到位） |
| 列表来源 | 一开始定「抓取式」，**真机否掉了**（见 §3.1） |
| 生效方式 | 提示「重进页面/重启宿主」生效，不碰宿主生命周期 |

后续追加的需求（都是主人真机用出来的）：
- 图片列表点一下**先预览**，预览里再给「替换」
- 预览必须显示**宿主那张图本身**（不是一句占位文字）
- 把「文件夹授权」提到**首页**（好几条功能的共同前提）
- 图片 tab 加**使用说明**（长图/尺寸问题）
- 「已改」tab 要能列出**改过的图片**

## 二、⭐ 核心结论（这是这一轮最值钱的东西）

### 2.1 文字的漏斗只有一个

```
Compose stringResource  →  k47 (StringResources.android.kt:33)
                        →  Resources.getString(I)          ← 唯一入口
```
真机探针 60 秒命中 **1406 次**，宿主 string 种类 44 个。

⇒ hook `getString(I)` / `getString(I,Object[])` / `getText(I)` 三个就够。

### 2.2 图片的漏斗很绕（这是十几轮的战场）

`painterResource` 的本体是 **`s27.E(IILv15;)Lq88;`**（不是 `j30`！我一开始认错了）。

```
s27.E:
  :2553  Resources.getValue(id, tv, true)
  :2604  v4 = tv.string
  :2615  if-eqz v4, :cond_799          ← string 空 → 位图分支
  :2619  pja.O(v4, ".xml")             ← ★ 判据：tv.string 里有没有 ".xml"
  :2631  if-ne v11, v6, :cond_799      ← 不含 → 位图分支
  :2708  getXml(id) → loadVectorResource   ← 含 .xml → 矢量

:cond_799（位图分支，6512）:
  :6632  Resources.getDrawable(id, theme)
  :6640  check-cast v0, BitmapDrawable     ← ★ 强制转！给不出图会 ClassCastException
  :6644  v0.getBitmap()
  :6680  new vo0(imageBitmap)              ← vo0 = BitmapPainter
```

⇒ **必须两件事同时成立**：
1. `tv.string` 改成**不含 `.xml`** 的值
2. `getDrawable` hook 返回 `BitmapDrawable`

缺第 2 件 → `check-cast` 撞原 VectorDrawable → **豆腐块**；
缺第 1 件 → 永远走 `getXml` → **原图，等于没换**。

### 2.3 ⭐⭐ Compose Icon 的 tint 会吃掉颜色

```
BlendModeColorFilter  color=ff8b8b8b  mode=SRC_IN
Paint.setColorFilter ← hg.l ← do1.q ← zpb.i(图标绘制)
```

`SRC_IN` 的数学定义：**输出 = tint色 × 源图alpha**

| 源图 | tint 后 |
|---|---|
| 透明背景 + 线条（宿主原矢量图） | 线条被染色，正常 |
| **整块不透明**（用户选的照片） | **整块变成纯色方块** |

**这是"蓝色方块 / 灰色豆腐块 / 白色方块 / 半透明蓝方块"所有现象的总根源。**
图其实早就换成功了，只是被颜色覆盖了。

### 2.4 剥离 tint 的正确落点

```
q88.g(Lv24 drawScope, J size, F alpha, gp0 colorFilter)V     ← Icon 走这个
  :106  v0 = p0.c            （上次缓存的 filter）
  :138  if-nez p5, :cond_49  （p5 空就不染色）
  :149  hg.l(v0)
  :180  hg.l(p5)
  :191  iput p5 -> p0.c      （缓存）
```

把第 4 个参数 `gp0` 换成 `null` 即可。frida 实测：**换图=6 / 命中我们的=6 / 剥离=6**（精准，不误伤）。

## 三、实现

### 3.1 清单为什么走**静态提取**（抓取式被真机否掉）

一开始按主人要求做「抓取式」（hook 记下宿主用过什么）。

真机一测就否了：
```
probe2/probe3 60 秒只摸到 44 条 string
—— 因为**用户得把每个界面都点一遍**
```

改成静态扫 smali 硬编码的资源 id：

| 类型 | 资源表总量 | smali 硬编码引用 | 覆盖率 |
|---|---|---|---|
| string | 762 | **747** | 98% |
| drawable | 266 | **204** | 77% |

一次拿全，不用点界面。产物 `fdm-app/res/raw/host_res.json`（48.6 KB）。

> ⚠️ 写工具时踩过一次：资源 id 正则写成 `0x7f0[0-9a-f]{4}`（7 位）⇒ 一条都没匹配，
> 而脚本"成功"输出 0 条，看起来像"宿主没用资源"。**8 位十六进制**才对。

### 3.2 只存资源名，不存 id

宿主资源名**没被混淆**（`session_init_title` / `assistant_message_avatar`…），
而 id（`0x7f0f0312`）会随宿主升级变。

⇒ 配置里只存**名字**，宿主侧 `getIdentifier(name, type, pkg)` 现查。
**宿主升级不用改一行代码。**

配置格式（`fuckds_res_map`，一条 JSON 整体推）：
```json
{"v":1,
 "t":{"session_init_title":"🐲新文字"},
 "i":{"assistant_message_avatar":"fuckds_res__assistant_message_avatar.png"}}
```

> 为什么不一个键一条：`FdmPush` 里「空字符串 = 没设过，不推」⇒ 逐项还原在宿主那边不传播。

### 3.3 宿主侧 `GmResHook.java`（新增，1273 行，7 个 hook）

| # | 落点 | 作用 |
|---|---|---|
| ① | `Resources.getString(int)` | 文字替换（热路径，表空时第一行 return） |
| ② | `Resources.getString(int, Object[])` | 带 `%1$s` 的 |
| ③ | `Resources.getText(int)` | ★ 必须返回 `SpannedString`，不能返回 String |
| ④⑤ | `Resources.getDrawable(int[, Theme])` | 位图分支的出口 |
| ⑥ | `Resources.getValue(int, TypedValue, boolean)` | ★ 改 `tv.string` 去掉 `.xml` |
| ⑦ | `dec.U(int, Context)` | 换 Drawable（**实测这条没被调用，留着无害**） |
| ⑧ | `Resources.openRawResource` | 字节层兜底 |
| ⑨ | **`q88.g`** | ★★ 剥离 tint，显示原色 |

关键实现细节：
- **图片按 id 缓存**（`ConcurrentHashMap`），滚动时不重复 decode
- **两趟解码**：先量尺寸再按 ≤512 采样（原来不采样，1.1 MB 的图直接 OOM）
- **fit 缩放**：整图按比例缩进目标框 + 居中（不是 center-crop！见 §4.2）
- **按宿主原图尺寸适配**：`getDrawable(id).getIntrinsicWidth()` 问出真实尺寸（实测 70×70 / 80×80）
- **防重入**：`ThreadLocal<Boolean> sProbing`，否则 `getDrawable` 探测会无限递归

### 3.4 桥（`FdmBridge`）新增 7 个动作

| cmd | 作用 |
|---|---|
| `res_state` | 回读配置（**UI 唯一真相源**） |
| `res_set_text` | 改一条文字（空 = 还原） |
| `res_set_img` | 改一条图片（只给名字 = 还原） |
| `res_preview` | 把宿主那张图画成 PNG 回传（base64） |
| `res_clear_all` | 全还原（顺带删图） |
| `res_selftest` | 自检一行（含诊断计数） |
| `res_restart_host` | 重启宿主（自杀 + 800ms 后 alarm 拉回） |

顺手把尾部内联的结果广播抽成 `sendResult()` —— 新分支是**提前 return** 的，
不抽就会出现两套发送逻辑。

### 3.5 UI `ResBeauty.kt` + `SafDir.kt`（新增）

- 清单打进 `res/raw/host_res.json`，`LazyColumn` 渲染（951 条，用 Column 会卡死）
- 三个 tab：文字 / 图片 / 已改 + 搜索（按名字**或当前文字**）
- 框架资源（`abc_` `androidx_` `mtrl_`…）**保留但排后面**
- 图片点一下 → **预览弹窗** → 里面才有「替换这张图」/「还原」
- 「已改」列表显示 `→ 换成了什么`（蓝色）

**图片预览的三层兜底**（UI 读不到宿主资源，两个 APK 资源表各自独立）：
1. 已替换的图 → 直接读 `/sdcard/Pictures/FDM/res_<名字>.png`
2. **从 UI 自己的 SAF 授权**读宿主写好的 PNG
3. 宿主把 PNG 转 **base64** 通过广播回传（33756 字符），UI 内存解码

> 为什么 UI 也要单独授权一次：**SAF 的持久授权记在 uid 上**，
> 宿主（`com.deepseek.chat.a`）和我们模块是两个 uid，宿主拿到 ≠ 我们拿到。

## 四、⭐ 这一轮踩的坑（按代价排序）

### 4.1 `$handle` 在 QuickJS 下是 `undefined` —— 十几轮误判的元凶

frida 里想判断"这个 painter 是不是我们造的"，我用了：

```javascript
ourHandles.push(painter.$handle);          // ← undefined！
if (ourHandles.indexOf(this.$handle) >= 0) // ← undefined === undefined 恒真
```

结果：
```
$handle = undefined         ⇒ 手柄: ,,,,, （全空）
命中我们的 = 189            ⇒ 所有图标都被剥了 tint（误伤 181 次）
```

**症状**：宿主所有图标的主题色全没了（复制/喜欢/朗读都变成黑色描边）。

**正确做法**：用 **Java 层的 equals**（引用比较）
```javascript
var ourList = Java.use('java.util.ArrayList').$new();
ourList.add(painter);
if (ourList.contains(this)) { ... }        // ← 走 Java equals，可靠
```
修正后：**命中=6 / 剥离=6**，精准。

### 4.2 长图为什么变成"蓝条" —— fit vs crop

原来用 center-crop（取短边居中裁正方形）：
```
1440×3168 的手机截图 → 只保留正中间 1440×1440
→ 截图中间往往是空白/纯色 → 裁出一块纯色 → 被 tint 染色 → 蓝条
```
改成 **fit**（整图按比例缩进目标框 + 居中 + 四周透明）：
```
整张图都能被看到，任何比例都不会"只裁到一块空白"
```

### 4.3 绘制热路径里做反射 → 宿主直接崩

`do1.q` 一次界面刷新被调 1 万多遍，我在回调里每次都：
```javascript
ib.getClass().getDeclaredField('a')   // 反射上万次
```
⇒ `Process terminated`（OOM/超时）。

**规矩：绘制热路径只能做纯 int 比较，绝不能反射、不能分配对象。**

Xposed 里的实现：`System.identityHashCode(Bitmap)` 建表 + `containsKey`。

### 4.4 改 `tv.string` 的顺序错了两次

| 顺序 | 结果 |
|---|---|
| 只改 `tv.string`，不给图 | `check-cast BitmapDrawable` 撞 VectorDrawable → **豆腐块** |
| 只给图，不改 `tv.string` | 永远走 `getXml` → **原图** |
| **先确认能给出图，再改 `tv.string`** | ✅ |

```java
Drawable d = drawableFor(...);
if (!(d instanceof BitmapDrawable)) return;   // 给不出就什么都不改
tv.string = "fdm_replaced";                   // 确认有图了才改
```

### 4.5 `getText` 不能返回 Java String

```
Implementation for getText expected return value compatible with java.lang.CharSequence
```
必须 `new SpannedString(rep)` 包一层。

### 4.6 UI 读错回执键 → "改了又回弹"

点「确定」发的是 `res_set_text`（回执落 `cmd.res_set_text`），
而界面读的是 `cmd.res_state` ⇒ 永远读到旧值。

⇒ 定 `res_state` 为**唯一真相源**，所有写操作之后回来重新要它。

### 4.7 转圈圈不停

```kotlin
remember(item.name, tick) { mutableStateOf(null) }   // ✗ tick 一变就清空
```
`tick` 每 350ms 刷一次 ⇒ 路径被反复清空 ⇒ 无限循环。

改成 `remember(item.name)`，并给失败态（显示原因 + 重试按钮）。

### 4.8 我认错了类

| 我以为 | 其实 |
|---|---|
| `j30.a` 是 painterResource | `j30` 是另一个类；**`s27.E`** 才是（第 2459 行有 `PainterResources.android.kt:56`） |

⇒ 在错误的类上改了好几轮 `dec.U`。

## 七、给下次的提醒

1. **先静态确认"是不是这个类"，再动手改。** 我认错 `j30`/`s27.E` 白费好几轮。
2. **frida 优先。** 改代码+打包+装包+重启一轮 5 分钟，frida 是秒级。
   你提醒我用 frida 之后，7 轮就定位到根因；之前 10 轮全是猜。
3. **在写 hook 前，先确认"身份比对"这个基础能力可用。**

4. **热路径的代码和普通代码不是一个物种。** 反射、分配对象、字符串拼接都可能要命。
