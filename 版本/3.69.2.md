## 一、主人这份证据有多关键

它把问题从"桥全崩"一刀切成了"**这一段没注入**"：

* ⟦FDM⟧ 包裹在、`【音乐变量】/【追问建议】/【回答排版】` 都在，最后还能接上用户消息

## 二、真凶：尼尼**猜**了存储契约（两条 bug 叠在一起）

### 契约真身（`GmStore.read2`，smali）

```
invoke-interface {v0, p1}, SharedPreferences;->contains(String)Z
if-nez v1, :cond_12
    const-string v0, ""
    return-object v0          ← ★ 键"没写过" ⇒ 返回**空串 ""**（不是 "false"！）
```

于是 `GmRichText.boolOf` 的类型探测（`"true"/"1"/"false"/"0"`）**一个都不匹配**
⇒ 一路落到**它自己的 `def` 参数**上。

> 尼尼在 3.69.0 的注释里写着「read2 对没写过的键直接给 "false"，压根走不到 def」——
> **这句是错的**，而且是这次事故的根源：键名（`_off`）选对了，**def 选反了**。

### Bug ①：约定永远不补

```java
// GmSysPrompt.djSection（旧）
boolean off = GmRichText.boolOf(ctx, "fuckds_dj_off", true);   // ← def=true
if (off) return body;
```
没写过 ⇒ 落到 def=true ⇒ 读成「已关」⇒ **约定一句都不发** ✗

### Bug ②：就算发出去，也不会放

```java
// GmMusicDj.on()（旧）
return GmRichText.boolOf(ctx, K_ON /* "fuckds_dj_on" */, false);
```
而 **UI 从头到尾只写 `fuckds_dj_off`** —— `_on` 这个键**从来没被写过**
⇒ 永远 false ⇒ **开关永远"关"** ⇒ 就算模型写了 `⟦DJ:…⟧`，`handle()` 也只会吞掉不放 ✗

> 两个 bug 是**独立的**：只修一个，功能照样不动。

## 三、修法

1. **只留一个判据**：`GmMusicDj.on()` —— 约定注入**也调它**（不再各读各的键）：

```java
public static final String K_OFF = "fuckds_dj_off";
public static boolean on() {
    ...
    return !GmRichText.boolOf(ctx, K_OFF, false);   // ★ 读「关」键 + def=false
}                                                   //   没写过 ⇒ false ⇒ 没关 ⇒ 开 ✓
```

2. `GmSysPrompt.djSection` 改成：

```java
if (!GmMusicDj.on()) return body;                   // 只问它
String dj = GmMusicDj.promptSection();
GmUtil.logOnce("dj.section", "点歌约定已补入系统提示词（+" + dj.length() + " 字）");
return body + dj;
```

3. 顺手修掉类注释里那句**过时的键名**（还写着 `fuckds_dj_on`）——
　　★ 注释写错比不写更坏：下一个接手的人（包括未来的尼尼）会照着它再错一次。

**逻辑落点总结**（"默认开"的正确组合）：

| | 键 | def | 没写过时 |
|---|---|---|---|
| ✅ 现在 | `fuckds_dj_off` | `false` | `false` ⇒ 没关 ⇒ **开** |
| ✗ 3.69.0 | `fuckds_dj_off` | `true` | `true` ⇒ 已关 ⇒ 关 |
| ✗ 3.69.0 | `fuckds_dj_on` | `false` | `false` ⇒ 关（且 UI 从不写它） |

## 五、教训

**1079 · ⭐⭐⭐ 「存储契约」必须读真身 —— 猜一次就够功能死一次。**
　　尼尼在注释里**断言**「read2 对没写过的键返回 "false"」，而真身返回 `""`
　　（`if (!sp.contains(key)) return "";`），于是 `boolOf` 落到它自己的 `def` 上。
　　⇒ 键名选对、def 选错 ⇒ **静默不生效**（不报错、不崩、就是没反应）。
　　★ 判据：**凡是要"依赖某个键的默认值"，就去把那个读取函数读完**（六行 smali 而已）。

**1080 · ⭐⭐⭐ 同一个开关被两处各读一次 ⇒ 必然漂移。**
　　`GmSysPrompt` 读 `_off`（def 写反）、`GmMusicDj.on()` 读 `_on`（UI 从来不写）
　　⇒ 两个 bug 独立叠加，且**互相掩盖**（都会表现为"功能没反应"，看不出是两件事）。
　　★ 做法：**开关只能有一个读取入口**（`on()`），别的地方**调它**。

**1081 · ⭐⭐ 「默认值」藏在两处：键名的正反 + 读取时的 `def` 参数。**
　　改任一处都要**两边一起想**。正确组合（本次）= `_off` + `def=false`。
　　★ 建议：以后凡"默认开"的开关，在代码里写成一行注释表（像本文第三节那样），
　　把三种组合和结果列出来 —— 比"注释解释为什么"更难错。

**1082 · ⭐⭐ 负向核验和正向核验一样重要。**
　　这次特意查了 `fuckds_dj_on` **在 dex 里不存在** —— 它证明"旧的错键真没了"，
　　而不是"新键加上了、旧的还留着"（那种情况会继续按错的跑）。

**1083 · ⭐⭐ 让主人**抄一份实际输入**，是定位这类问题的核武器。**
　　「桥坏了」是一个含糊的结论；而**把送给模型的提示词整段抄出来**
　　立刻划出了边界（注入通着、唯独这一段没补），把范围从"整个桥"缩到"一个方法"。
　　★ 以后遇到"模型不按约定做"，第一步就该是：**把实际输入抄出来看**。
