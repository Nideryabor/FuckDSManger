## 三、三处「不是宿主升级导致」的真 bug

### ① `clsAll` 的逗号键永不匹配 ★★★ 最严重
拆类行写成 `"x98,qu7,z2c,g83,j37,zi9"`，代码用 `eq(col, old)` **整串比较**
⇒ `cls("x98")` 永不匹配 ⇒ **原样返回 `"x98"`**（2.7.5 里那是只剩 1 个方法的诈尸接口）
⇒ 画底原语 / 气泡背景**整族静默失效**。
**修**：`hitKey()` 遇含逗号的列就逐段比。

> 这条最隐蔽：它让后面 6 条修法**全部白做**（`cls()` 返回的还是旧名）。

### ② `GmEntryHook` 的 case 号三代全错
| 写的 | 实际 | 判定依据 |
|---|---|---|
| `0x1d` | 2.7.5 的 switch 表**只到 `0x1c`** ⇒ 永不成立 | 静态：`:pswitch_data` 表 |
| `0x14` | 我静态推断（唯一 `return Boolean.TRUE` 的特例）—— **错** | frida 实测推翻 |
| **`0x5`** | ✅ 正确 | frida：点「检查更新」时 `[z5.w] this.a=5` |

### ③ `.registers` 加错把参数槽覆盖 ⇒ 崩
`beforeHookedMethod` 只有 1 个参数，`.registers 8` ⇒ 可用 `v0~v6`，`p0 = v7`。
我为了加诊断改成 `.registers 12` 并用 `v10`
⇒ **`v10` 被汇编器映射成 `p0`，覆盖参数引用** ⇒ 整个 hook 崩
⇒ **连带宿主聊天背景也坏**（主人：「背景变黑/白/没了」）。

**铁律**：往 smali 方法里加寄存器前，先算 `p` 的起始位置 = `registers − 参数个数(含 this)`。

## 四、Android 11+ 包可见性（新 Compose UI 打不开的定案）

```
宿主 startActivity(显式 MainActivity)        → ActivityNotFoundException
宿主 startActivity(fdm://open)              → ActivityNotFoundException
宿主 PackageManager.getApplicationInfo(我们) → NameNotFoundException
宿主 ContentResolver 访问 ConfigProvider     → Unknown authority
而模块自己启动自己                           → ✅ 正常（mCallingUid = 模块 uid）
```

宿主 `targetSdk=36` 且清单里没有 `<queries>` 声明我们的包
⇒ **从宿主进程出发的一切跨包操作都被系统过滤**。

**试过但失败的方案**：静态 receiver + 宿主广播换乘
```
am broadcast -a com.little_femaleboy.fdm.OPEN_UI -p <包名>
  → Broadcast completed: result=0     ← 0 个接收者
dumpsys package <包名> | grep receiver
  → 空                                ← 系统没登记（manifest 里明明有）
```
⇒ 已撤回（3.75.23）。**新 UI 的打开方式仍待解**（见待办）。

## 六、Compose 注入路线（已证伪，别再试）

宿主 APK 里 `androidx/compose/runtime/Composer` **一个类都没有**
⇐ 全被 R8 混淆内联：`Composer→v15`、`Modifier→fk7`、`Brush→ks0`、`Shape→yy9`
⇒ 用 Compose 编译器编出的 `$composer: Composer` 类型对不上宿主要求的 `Lv15;` ⇒ 崩。

**能走的替代**：劫 `DrawScope` / 自己画 Canvas（`GmBubbleBg` 就是这套）。
