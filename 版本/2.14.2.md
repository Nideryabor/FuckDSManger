## 一、日志一次给出四个结论

### ① 通道 A 必失败（已预判 ✔）
```
BadTokenException: Unable to add window -- token null is not valid; is your activity running?
  at PopupWindow.showAtLocation
  at GmCallBtn.pop
```
`onResume` 时窗口还没 attach ⇒ token 为 null。**这是"必然发生一次"的，不是意外**。

### ② 通道 B 也跟着失败（新发现 ⭐）
```
IllegalStateException: The specified child already has a parent.
You must call removeView() on the child's parent first.
  at ViewGroup.addView
  at GmCallBtn.show
```
原因：**`PopupWindow.invokePopup()` 在 `WindowManager.addView` 抛异常之前，已经把我们的 contentView 挂到了它内部的 `PopupDecorView` 上**
⇒ 回退通道再 `decorView.addView(同一个 view)` 就"已经有爹"。
**修法**：回退前先 `parent.removeView(view)`（有爹就先摘）。

### ③ 「我点击却被判成拖动」（阈值方向反了）
```
[通话] 悬浮钮按下
[通话] 悬浮钮拖动结束（不触发点击）   ← 明明是点
```
```smali
# ❌ if-gt v3, 0x14, :mv   → 位移 >20 才跳（跳过置位）；位移 ≤20 反而置 sMoved=true
# ✅ if-le v3, 0x14, :mv   → 位移 ≤20 才算"没拖"
```

### ④ 守护线程**从来没启动**（这就是"要切后台一次才出按钮"的真相）
日志里**没有任何** `[通话] 悬浮钮守护已启动（1s 一次）`；而按钮是在**第二次 onResume**（切后台再回来）时才出现的 —— 那时窗口 token 已有效，通道 A 直接成功（日志 `悬浮钮已挂上（PopupWindow）` 在第二次 onResume 后 6ms）。

```smali
# ❌ GmCallTick.start(): if-eqz v0, :ret  → sOn==0（第一次）就 return，永远不 post
# ✅ if-nez v0, :ret                     → 已启动才 return
```
⇒ **第三次**踩同一个 `if-eqz/if-nez` 家族。

## 五、教训（本轮有点多，但都是同一根）

| # | 教训 |
|---|---|
| **513** | ⭐⭐⭐ **`PopupWindow` 失败会"半途留下痕迹"**：`invokePopup()` 先建内部 decor 并 `addView(contentView)`，再 `WindowManager.addView`（这里才抛 BadToken）⇒ **回退到别处挂同一个 view 之前必须先 detach**。**"失败的操作"未必不留副作用。** |
| **514** | ⭐⭐⭐ **同一个反写家族，本轮第三次**（`if-eqz/if-nez` × 2、`if-gt/if-le` × 1）。**本轮起规定：每个分支写完，立刻在旁边用中文写出"走这条路的条件"，并回读一遍**（这是本项目教训第 44/100/494 条的原话，我又犯了三次）。 |
| **515** | ⭐⭐ **"要切后台一次才生效"= 第一次 onResume 里那段代码根本没跑**（不是"时机不对"，而是"压根没执行"）⇒ 例如守护线程守卫写反。**这类现象优先怀疑"启动代码被自己的守卫拦住"。** |
| **516** | ⭐⭐ **兜底逻辑要有"次数上限"**：`ensure()` 重挂不能无限重试（每次重挂都会 remove+add，会打断触摸）；用 `sFail` 计数，超过 3 次就停在"可见"状态。**兜底也要有止损线。** |
