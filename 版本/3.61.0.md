## 〇、一句话

**两件事：把 6 项设置搬进「更多」弹窗；把「灌入/清空」从按钮改成拖卡片的动作。**

   拖进容器 ⇒ 把这一段的约定灌进系统提示词
   拖回抽屉 ⇒ 只摘掉这一段
   落空     ⇒ 什么都不做（原地不动）

## 一、桥侧：新增「只摘一段」的能力

原来的清空只有一个粒度 —— `specs_clear` **两段一起摘**（回答排版 + 追问建议），
而新的语义是**按卡片各摘各的**：

| 卡片 | 灌入（拖进） | 清空（拖回） |
|---|---|---|
| 富文本 | `rich_spec` → `GmRichText.mergeIntoSystemPrompt()` | `spec_remove("rich")` → 摘【回答排版】 |
| 回复建议 | `suggest_spec` → `GmRichText.mergeSuggestIntoSystemPrompt()` | `spec_remove("suggest")` → 摘【追问建议】 |
| 音乐 | `pvar_spec` → `GmPromptVars.mergeIntoSystemPrompt()` | `spec_remove("music")` → 摘【音乐变量】 |

新增（都是**复用既有的** `cutParagraph` + `tidy`，主人自己写的正文一个字不动）：

* `GmRichText.removeSpec(String which)` —— 按特征串定位段落，只剪那一段
* `GmPromptVars.removeSpec()` —— 对称于它自己的 `mergeIntoSystemPrompt()`
* `FdmBridge` 新增命令 **`spec_remove`**（`arg` = `rich` / `suggest` / `music`）

> `specs_clear` **保留**（只是界面不再有按钮了）—— 留一个"两段一起摘"的后门，
> 以后要做「一键全清」时不用再动桥。

## 二、UI 侧：拖动即动作

`PCard` 枚举带上两件事：`pasteCmd`（拖进时发什么）与 `kind`（`spec_remove` 的参数）。

```kotlin
if (boxRect.contains(r.center)) {                    // 拖进容器
    …搬列表…
    card?.let { FdmPush.sendCmd(ctx, it.pasteCmd, null) }        // = 灌入
} else if (drawerRect.contains(r.center)) {          // 拖回抽屉
    …搬列表…
    card?.let { FdmPush.sendCmd(ctx, "spec_remove", it.kind) }   // = 清空这一段
}                                                     // 落空 ⇒ 什么都不做
```

**★ 只在松手那一刻执行一次**（主人选的）：进页面**不**做任何"自动对齐"。
理由很硬 —— 布局是我们存的，提示词是**主人的**；凭"卡片在容器里"就替他改提示词，
是拿我们记的账去覆盖他的正文。（要真做对齐，也得先问。）

**★ 也没有任何提示**（主人说晚点再定）：拖动本身就把两件事做完了 ——
卡片在哪边，就是这一段现在的状态。

## 三、顺手清掉的一处"同值两源"隐患

「更多」弹窗要放那 6 项，而它们的**真值读取 / 推送 / 回显**全在 `ItemRow` 里
（Private，住在 `Pages.kt`）。与其抄一遍，不如把取数逻辑抽出来公用：

```kotlin
private fun stateMap(ctx): Map<String, String>          // 宿主回执（cmd.cfg_state）
private fun itemHostText(ctx, it): String?              // 老格式三处兜底
private fun itemValue(ctx, it, st): Any                 // 模块真值优先 → 本地兜底
@Composable fun ItemsBlock(items: List<It>, onNav: …)    // 公开：弹窗直接用同一套 ItemRow
```

`TreePage` 的循环也跟着改成调这三个函数（**逐字等价**，只抽函数没改行为）
⇒ 同一个开关在**弹窗里**和**页面上**显示的永远是**同一个值**
（"同一份数据两处两个答案"比显示错更难看 —— 老账 978 同源）。

## 七、教训

**1005 · ⭐⭐ 把代码从 A 搬到 B，别"手抄"—— 能切就切。**
　　那 6 项我是**用脚本按行切下来**搬的（还带断言：必须含首项与末项），
　　所以一个字符都没抄错。
　　⚠️ 但同一轮里，**新写的指路卡**我是在脚本里手打的 —— 结果**漏了 `+`**：
　　Kotlin 的相邻字符串**不会自动拼接**（不是 Java 的 `+` 省略，也不是 Python 的隐式拼接），
　　编译直接报 `Expecting ','`。
　　⇒ 规则：**搬代码用切、写代码用改（增量编辑）**；手打整块 = 手抄，一样会错。

**1006 · ⭐⭐⭐ 「同一份数据两处显示」比"显示错"更难看 —— 所以取数逻辑必须同源。**
　　弹窗和页面要显示同一个开关，就不能各写一份读法。
　　⇒ 把 `stateMap` / `itemHostText` / `itemValue` 抽成函数，`TreePage` 与新弹窗**共用**。
　　（这是 978 那条老账的又一次应用：**两处算出的答案不一致，用户就不敢信任何一处**。）

**1007 · ⭐⭐⭐ 「把动作绑到状态上」时，必须明确是**动作**还是**对账**。**
　　"卡片在容器里 = 这一段该在提示词里"听着很自然，但那是**对账** —— 一进页面就替用户改数据。
　　主人选了**动作**语义：**只在松手那一刻执行一次**。
　　⇒ 我们的布局是我们存的账，**提示词是主人的正文**；拿前者去覆盖后者，得先问。

**1008 · ⭐⭐ 装机 ≠ 生效（跨进程那一半要单独记住）。**
　　UI 在我们自己的进程（装完即用），**桥在宿主进程**（要重启宿主**且** LSPosed 路径是新的）。
　　这版两半都动了 ⇒ 交付时必须把"重启宿主 / 必要时关开模块"说清楚，否则会被当成"功能没做出来"。

**1009 · ⭐⭐⭐ 「改文件」和「跑构建」不许并排发 —— 这次又踩了（第三次）。**
　　第一次编出来的包与修完之后的包**哈希不同**（说明第一次编的是中间态），
　　只能重编一遍确认。**同一个错犯三次，说明不是疏忽，是习惯** ⇒
　　从这一版起：**有前后依赖的命令，一次只发一条，看结果再发下一条**。
