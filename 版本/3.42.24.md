## 一、主人给的关键观察（本版的起点）

> 「这个崩溃似乎有不同情况：
> **如果消息列表里面有需要渲染的东西**（比如现成渲染 mermaid 图）→ 点上传图片会**弹吐司然后宿主全局界面卡死**
> （按钮上面的能点但界面不刷新，列表仍然可滑动）
> **如果没有需要渲染的会直接崩溃**」

**两种表现 = 同一个根因**：

```
吐司弹了 ⇒ GmUAvatarHook 命中了 tag==0xf
           （而新宿主 0xf 那条分支本该返回 fs/es，不是我们该碰的东西）

列表里有渲染物 → 那个 State 正被 Compose 读 → 我们塞的 String 让快照失效
              → 无限重组 → 【界面卡死】（能点能滑不刷新）
列表里没有     → 那个 State 冷着 → 雷留到别处引爆 → 【直接崩】
```

**跟崩栈完全咬合**：`l10.A: State.getValue() check-cast dz9` —— `dz9` 就是宿主里那个**「渲染列表」**类型。
⇒ "要渲染的东西"越多，这个 State 越活跃 ⇒ 卡死；没有就崩。

## 二、本版改动：**1 个字节**

```diff
 底座 classes.dex @ 0x2dff2
- 13 02 0f 00     const/16 v2, 0xf    ← 咬在无关分支上，投毒
+ 13 02 12 00     const/16 v2, 0x12   ← 位移后的真正分支
```

**怎么做的**（这次**没有重建 dex**，教训 #341/#342）：

```sh
python3 tools/dex_const_patch.py \
    --apk mod-src/out/FuckDSManger_NL_2.22.133_for_ds2.6.1.apk \
    --out /tmp/base_3424.apk \
    --hex 0A0113020F003321 --offset-in-pattern 4 --value 0x12 --expect 0x0f
```

- 模式 `0A 01 13 02 0F 00 33 21` = `move-result v1` / `const/16 v2,0xf` / `if-ne v1,v2`
  —— 在 199028 字节里**恰好命中 1 处**（脚本强制要求唯一，否则拒绝动手）
- 改完自动重算 dex 头部的 SHA-1 signature + Adler-32 checksum

**为什么新 tag 是 `0x12`**（完整推导见 `版本/3.42.22.md` §〇 与 §二）：

| | 旧宿主 | 新宿主 |
|---|---|---|
| 账号名桶 `s5/a6` | tag `0x8` | tag **`0x8`**（**没位移**）⇒ 所以账号名一直能用 ✓ |
| 账号头像桶 `p5/x5` | tag `0x0f` → `check-cast it9; iget it9;->e` | tag **`0x12`** → `check-cast d9b; iget d9b;->e`（**逐指令同构**）|

> `it9` 与 `d9b` 逐字段同构（`Companion`/`f:[]`/`a`/`b~e:String`），同批改名。
> 两条"能/不能"互为对照 ⇒ 这就是那个 **1 个字节能解释全部现象** 的原因。
