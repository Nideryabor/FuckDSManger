## 三、③ 检查结果：**确认是「追加」，不是覆盖** ✅

`GmRichText.mergeIntoSystemPrompt()` 原文：
```java
String cur = GmSysPrompt.text();                        // 读现有的
if (cur != null && cur.indexOf(SPEC_TAG) >= 0) {
    return "系统提示词里已经有新版格式约定了，没重复加";    // ★ 幂等判据 = 内容特征串
}
String add = spec();
String nv = (cur == null || cur.isEmpty())
        ? add
        : (cur + "\n\n" + add);                          // ★★ 追加！
GmSysPrompt.setText(nv);
```

**⇒ 三点保证**：
1. **只加不改** —— 你自己写的提示词一个字都不动，新约定贴在后面
2. **幂等** —— 重复点不会叠加（判据是内容特征串 `【回答排版】`，不是定界符）
3. **两段约定互相独立** —— `rich_spec`（排版）和 `suggest_spec`（追问建议）各灌各的，互不覆盖

**顺手做的重构**：把两处灌入逻辑抽成公共的 `mergeSpec(add, tag)`（同一套"追加 + 幂等"）。

**返回值也更清楚了**：
```
已写进系统提示词（原文 120 字 → 现在 480 字，追加 360 字）
```

## 六、教训（939~941）

- **939 ⭐⭐⭐ 「前提条件」要写在功能旁边，不能只写在文档里** ——
  这功能上线时"看着没效果"的根因十有八九是"系统提示词没开"。
  **把依赖写在开关上方，比事后排查省十倍事**。
- **940 ⭐⭐ 幂等判据要用「内容特征」而不是「定界符」** ——
  定界符在旧版约定里也可能出现 ⇒ 换了新版约定就点不动了（会白折腾一轮）。
  这条是 3.45.0 踩出来的，这次直接沿用了。
- **941 ⭐⭐ 「追加 vs 覆盖」必须显式确认** ——
  主人专门让查这个，说明这是**信任问题**：用户手写的提示词被覆盖一次就再也不敢用了。
  ⇒ 写这类"帮用户改数据"的功能，**返回值要能看出"原文多少字 → 现在多少字"**。
