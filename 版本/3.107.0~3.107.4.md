## 三、整页的三块硬骨头（每块都是真机崩出来的）

### ① 模块 Resources 在宿主进程里拿不到

我们和宿主是**两个 APK**，资源表各自独立，`createPackageContext` 被包可见性挡死。

**最终解法（主人一句「动态加载 dex」点出来的）**：路径的问题让**模块自己回答**。
```
模块进程 FdmApp.onCreate → FdmPush.push()
    ⇒ payload["apk"] = ctx.getPackageCodePath()      ← 它当然知道自己是谁
宿主进程 FdmBridge.applyPushed()
    ⇒ GmStore.write(ctx, "fuckdsmanger_apk_path", 路径)
整页 HostPage
    ⇒ 读这个键 → AssetManager.addAssetPath(路径) → new Resources(am, dm, cfg)
```
- 全程**只用公开 API**（`addAssetPath` 是标准做法）
- 不查 `PackageManager`（包可见性/隐藏应用列表都管不着）
- 不扫 `/proc/self/maps`、不反射别人的 ClassLoader
  （⚠️ 这两条我一度想走，主人否了：**等于把入侵手法写给宿主看**）

真机证据：`【FdmBridge】已记下模块 APK 路径（整页用）：/data/app/…/base.apk`

### ② 资源 id 都是 `0x7f` ⇒ 一份 Resources 只能认一张表

> ⚠️⚠️ **本节结论已在 3.108.2 被推翻**（保留原文是为了记住那条教训）。
> 真正 `final` 的只有 `Context.getString` —— **`Resources.getText/getString/getDrawable/getColor` 全都可以覆写**。
> 现在的实际做法见 `版本/3.108.0~3.108.3.md` 的 `BridgeRes`：**模块表优先、抛 `NotFoundException` 才回落宿主表**。
> 教训 342：「A 不行」不等于「这一类都不行」—— 先 `javap` 看清到底是哪个 A。

三条取值路径分属两个表（`javap` 逐条查过，不是猜）：

| 路径 | 取哪个 local | 该查哪张表 |
|---|---|---|
| `stringResource(R.string.x)` | `LocalResources` | **模块** |
| Material3 内部 `getString(id)` | `LocalContext.getResources()` | **宿主** |
| `ctx.getString(R.string.x)` | `LocalContext.getResources()` | **模块**（但我们没法只给它换表） |

**两次崩溃把方案一个个否掉：**
| 尝试 | 结果 |
|---|---|
| 覆盖 `getResources()` 返回模块表 | 崩：`Resources$NotFoundException #0x7f0a0179` @ Material3 的 `DefaultBasicAlertDialogOverride` |
| 只给 `LocalResources` 注入模块表 | 崩：`#0x7f0a0066` @ `Lang$S.tagline(Lang.kt:132)` ← 走 `ctx.getString` |
| 覆盖 `Context.getString` | **编译不过**：`'getString' in 'Context' is final` |
| 同一 AssetManager 挂两张表 | 不可能：id 都是 `0x7f`，必然冲突 |

**最终解法**：加扩展函数 `Context.fdmStr(id)`（`HostRes.kt`）——
**先查模块表、查不到回落宿主表**，然后把 UI 里 697 处 `ctx.getString(` 机械替换掉。

- Material3 完全不经过这个扩展函数 ⇒ 它继续查宿主表 ⇒ 不崩
- 模块自己进程里 `HostRes.uiRes == null` ⇒ 直接走原 `getString`，**行为与改之前相同**
- 真机验证：「关于」页、彩蛋 AlertDialog 两条原来崩的路径**都不崩了**

### ③ 配置从哪来

整页在宿主进程里，`getSharedPreferences("fdm_ui")` 会拿到**宿主的**空文件。
⇒ `HostPage.ResCtx` 只接管这两个名字，返回 `HostStore`（直连 `GmStore.read2/write`）。
宿主自己的 SP 一个都不碰。

**类型判定**：宿主存储是强类型的，而 `getString("cfg.fuckds_bg_on")` 不知道该键是 `b` 还是 `i`
⇒ `HostStore` 依次试 `b/i/l/f/s`，**哪次不抛就是真类型**，并缓存（同一键只探一次）。

⚠️ 写布尔必须用 `"true"/"false"`：底座 `GmStore.write` 走 `Boolean.parseBoolean`，
传 `"1"` 会变成 `false`。

## 四、★ 顺手修掉的三个老 bug（跟整页无关，独立存在）

### 4.1 保底卡片的按钮点了没反应

```java
// FdmFallbackDialog.showForce(ctx, reason)
show(ctx, reason, null, null);   // ← onTryLaunch 传 null
```
而 Compose 版卡片里「拉起模块 UI」按钮的回调正是它 ⇒ **任何**走 `showForce` 的保底都是死按钮。
⇒ 改成不传就自己兜一个（复用 `FdmUiHook.launchWithFallback`）。

### 4.2 拉起成功却弹「拉起失败」卡片

真机血证：
```
10:12:40.263 【FdmUiHook】已拉起 Compose UI ✓（显式）
10:12:40.282 【FdmComposeDlg】✅ Compose 版保底弹窗已显示    ← 20ms 后
```
`FdmUpdateIntercept` 在"打开模块"之后**无条件**弹保底，而跨进程其实马上成功了。
⇒ 改成：拉起已发起就交给看门狗判成败，这里不抢跑。

### 4.3 ★ 用户气泡图片泄漏到宿主的设置页

主人报：「字体大小」页底部糊了一整块用户气泡图。日志：
```
11:15:55.165 ③ 认到【用户气泡】元素 #1 @835fe0e
11:15:55.182 ★用户 气泡绘制#1 开关=true 模式=1 尺寸=1440x757
```
`1440` = 屏幕物理宽度 ⇒ 那块东西**铺满整屏**，而消息气泡左右一定有边距，**永远不可能整屏宽**。

**误标根因**：判据只有一条 —— `clip(Modifier, Shape)` 的 Shape 引用等于气泡 Shape，
之后创建的第一个背景 Element 就记成用户气泡。而宿主设置页的卡片也走 `clip` + 同一共享 Shape ⇒ 被误认。

**修法**：`GmBubbleBg.plausibleBubble(w,h)` 尺寸闸门（**物理事实，对真气泡零误伤**）：
```java
if (w > sw * 0.92f) return false;   // 气泡不可能贴满整屏宽
if (h > sw * 3.0f)  return false;
```
**真机验证**：
```
11:22:58 ⛔ 尺寸不像气泡 ⇒ 跳过（1440x1799 · 屏宽 1440 · 已被误标元素 #1）
11:23:34 ⛔ 尺寸不像气泡 ⇒ 跳过（1440x757  · 屏宽 1440 · 已被误标元素 #2）
```
字体大小页恢复成深色背景图，**消息页的用户气泡图照旧正常**。

## 五、⚠️ 纪律（这一轮最该记住的）

> **新功能挂独立入口，绝不去改老路径。**

我这一轮犯的具体错误：为了让「打开模块」走整页，
把整页插进了 `FdmUpdateIntercept` 的选择页回调和 `FdmUiHook.launchWithFallback` 里。
后果：① 老路径的正确性无法单独验证 ② 弄坏了失败路径（4.2 那个假弹窗）

**正确形态**：
```
老路径（跨进程）：一个字不动
整页：独立入口 `--es cmd page_full`，只回答"能不能画"
     · 能 ⇒ 再讨论要不要替换主入口
     · 不能 ⇒ 整块删掉，老路径因为没被碰过，一定还是好的
```

回滚记录：`FdmUpdateIntercept` / `launchWithFallback` 已复原；整页只剩 `page_full` 一个入口。

## 六、整页还不能替代模块入口（下一步）

在整页里点导航，会跳到**模块进程**。原因：整页的 `LocalContext` 仍是宿主的，
而某些动作最终解析到了模块的 Activity。

还有一批功能天然需要真 Activity：
| 功能 | 整页里 | 说明 |
|---|---|---|
| 选图片 / 选文件夹 | ⚠️ 降级提示 | `HostResultOwner` 只 Toast「请在模块本体里操作」 |
| SAF 授权 | ⚠️ 同上 | 需要 `startActivityForResult` 的真回执 |
| 其余（开关/滑杆/文本框/列表） | ✅ 可用 | 纯 Compose 状态 + 直连存储 |

要真接手还得逐项处理，是个无底洞 —— **等主人拍板再动**。

## 八、教训（接 334）

| # | 教训 |
|---|---|
| **335** | ⭐⭐⭐ **新东西挂独立入口，别去改老路径** —— 一插进老路径就同时失去两样东西：老路径的正确性、和新东西的可回滚性。这一轮为此多花了大半程。 |
| **336** | ⭐⭐⭐ **"两条路共用同一个对象"时，方法级的 final 就是硬边界** —— `Context.getString` 是 final，所以"只给我们的调用换表"在 Context 层根本做不到，只能在**调用点**（扩展函数）解决。先 javap 看清楚谁 final，能省一轮崩溃。 |
| **337** | ⭐⭐⭐ **两个 APK 的资源 id 都是 `0x7f` ⇒ 一份 Resources 永远只能认一张表** —— 别指望"挂两张表让它自己挑"，id 冲突在资源系统里是无解的。想共存只能给其中一个换 package id（`aapt2 link --package-id 0x80`，实验过能编过，但 ART 是否接受未验）。 |
| **338** | ⭐⭐ **判据用"物理事实"比用"引用身份"稳** —— 气泡靠 `Shape` 引用相等去认，撞上共享实例就误标；而"气泡不可能铺满整屏宽"是物理事实，对真气泡零误伤。**能用量纲卡住的，就别靠身份。** |
| **339** | ⭐⭐ **一个"检查脚本报 0"不等于功能挂了** —— `install_fdm.sh` 的第③⑤步走 `su`，而 adb shell 没有 root ⇒ 报"模块没加载"是假阴性。要用 devlog 网关（设备侧 uid=0）。 |
| **340** | ⭐⭐ **诊断日志的触发条件必须真能证明它想证明的事** —— 气泡那条「已调用 20 次但都不在助手作用域内」用了个**从不重置的累计值**当条件，从上线起就是噪音（3.106.6 已删）。 |
