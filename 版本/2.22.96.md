## 二、为什么这不是"再写一遍"（架构选择）

### 2.1 挂点本来就是共用的

`pn9.c(ILpe5;Ljb1;Lwr;Lvq;Lc76;Ley3;I)V` 是 **「用户 + 助手」共用的项级 Composable**（这条事实在 **2.21.8** 已经用一次回归 bug 换来：见 `版本/2.21.8.md`）。
那之后我们给它加的是**硬闸门**：

```
扫 args → 找第一个 vq 实例 → 反射 vq.D() → 若 == "USER" ⇒ 直接 return
```

⇒ **"用户气泡"这条路，是我们自己主动堵死的**。所以本版的核心动作不是"新写一条链路"，而是
**把这道硬闸门改成"分流"**：

```
if (role == "USER")  →  sUCntCell++ / sUDepth++  →  if (uOn()) → wrap()   ← 用户支线
else                 →  sCntCell++  / sDepth++   →  if (on())  → wrap()   ← 助手支线
                                                      ↓ 两条支线汇合
                                          扫 args 里第一个 c76 → GmBubble.wrap() → 替换实参
```

⇒ **注入逻辑（`wrap / wrapImg / shape / imgBrush`）一行都没复制**，两条支线共用。

### 2.2 单类双档：`GmBubble` 一个类管两套配置

新增静态档位字段 **`sUDepth`（用户项作用域深度）**，并让三个"取值方法"**在用户作用域内自动切档**：

| 方法 | 作用域外（UI / 助手） | `sUDepth > 0`（用户项渲染中） |
|---|---|---|
| `colorLong()` | `sColor` | **`sUColor`** |
| `radius()` | `sRadius` | **`sURadius`** |
| `imgOn()` | `sImg` | **`sUImg`** |

**为什么这样最省**：`wrap()` 本来就走 `shape()`（内部读 `radius()`）+ `colorLong()` / `imgOn()` / `imgBrush()`；
只要这四个取值在"用户项渲染期间"返回用户档，**`wrap` 自身零改动就自动服务用户气泡**。

⚠️ **`sUDepth` 的语义边界**（很重要的安全设计）：

- 它**只在 `pn9.c` 的 before→after 之间非零** ⇒ 渲染期作用域，UI 对话框读到的永远是助手档；
- **UI 侧也绝不动它** ⇒ "正在编辑用户档"与"正在渲染用户项"是两件事，互不干扰。

### 2.3 用户档的编辑状态用另一条通道

对话框里的点击处理器（色盘 / 圆角 / 开关 / 选图）需要知道"现在编辑的是哪一档"，
但它**不能**用 `sUDepth`（渲染期才有值）⇒ 新增 **`GmBubbleDialog.sUser:Z`**（对话框模式位）。

### 2.4 图片文件名做成动态（而不是复制一份解码链）

`GmBubble.imgBrush` / `saveImage` 里原本硬编码 `"fuckds_bubble.png"`。
复制一份 86 指令的解码链风险太高 ⇒ **改成读一个静态字段**：

```
.field public static sImgName:Ljava/lang/String;      ← <clinit> 初始化 "fuckds_bubble.png"
const-string v2, "fuckds_bubble.png"   ⇒   sget-object v2, GmBubble->sImgName:Ljava/lang/String;
```

**1 指令换 1 指令、寄存器零变化**。谁负责写 `sImgName`：

| 场景 | 写入者 | 取值依据 |
|---|---|---|
| 渲染注入 | `GmBubble.wrap()` 开头 | `sUDepth > 0 ? "fuckds_ububble.png" : "fuckds_bubble.png"` |
| 选图落盘 | `GmBubble.useImgName()`（由 `GmPickHook` 调） | `sUPick ? ububble : bubble` |

### 2.5 选图通道：复用同一个请求码，不新增协议

**没有**新开请求码 `0x435c`。做法是：

- `GmBubble.pickU()` = `pick()` + **`sUPick = true`**（`pick()` 本身顺手把 `sUPick` 清成 false，两条路互斥）
- `GmPickHook` 的 `0x435b` 分支里，在 `saveImage` 前插一句 `useImgName()`（定文件名）
- 成功/失败收尾统一走 **`GmBubble.finishPick(Context, boolean ok)`**：
  它读一次 `sUPick`（**读完即清**）⇒ 决定 `setUImg/setImg` 与 Toast 文案
- `takePicking()` **保持原样**（只清 `sPicking`）—— `sUPick` 必须活到 `finishPick` 才被消费

⇒ **请求码、Intent、读图四路链一个字都没动**（那是 `2.22.22` 用 6 版血换来的）。

## 四、顺手修掉的一个潜伏坑：图片缩放"张冠李戴"

`GmBubbleFitHook`（挂宿主 `tn0.b(J)`）原本从 **`GmBubble.sBmp`（全局单个位图）** 取原图来算 cover 矩阵。
**一张图时看不出来**；一旦 AI 气泡与用户气泡用**两张不同的图** ⇒ 谁最后被 `imgBrush` 解码，谁就统治所有气泡的缩放矩阵。

**修法**：把"这是谁的图"收进**对象自己身上** —— `GmBmpShader` 加实例字段 `bmp`，三处构造点都写回
（`imgBrush` / `FitHook` 内部新建），`FitHook` 改成读 `iget-object v1, v0, GmBmpShader->bmp`。
⇒ **与前缀无关、与全局状态无关**，两个气泡各用各的图、各算各的矩阵。

## 五、回读抓到的 2 处 `if-*z` 反向（本项目 1 号 bug 家族）

**构建全绿 ≠ 逻辑正确**。构建通过后逐条念 smali，抓到两处**方向写反**：

| 位置 | 写成了 | 后果 | 改成 |
|---|---|---|---|
| `GmBubbleCellHook` | `if-eqz v3, :role_user` | `v3 = "USER".equals(role)` ⇒ **等于 USER 时反而不跳** ⇒ **助手/用户两条支线整体对调** | **`if-nez v3, :role_user`** |
| `GmBubbleDialog`（跳 `:skipAZ`） | `if-eqz v3, :skipAZ` | 变成「**AI 模式才隐藏**透明度/放大行」，正好反 | **`if-nez v3, :skipAZ`** |

**产物级验证**（不是看编辑会话）：打出的包里读到

```
const-string  v4, "USER" → equals → move-result v3 → if-nez v3, :cond_6d
:cond_6d  sget v0, GmBubble->sUCntCell:I     ← 用户块在下方（分支目标）
（落下即 sCntCell 助手块）
```

⇒ **分支目标指向用户块、落下是助手块** ⇒ 方向正确 ✅

### ⚠️ 已知未验（首次真机才知道，请重点看这一条）

`pn9.c` 的 `Modifier`（注入目标）是**项级**的：

- 助手项要"整块深色底"（头像+标题+内容），这是**约定俗成的正确**；
- **用户项**这个 Modifier 到底是"**整行**"还是"**右边那个气泡本身**"，**静态分析断不出来**（没有宿主 APK）。

**两种可能**：

| 现象 | 说明 | 我的下一步 |
|---|---|---|
| 自己那条 = **右边一个圆角气泡**被染色（宽度只包住文字） | ✅ 完美，项级 Modifier 就是气泡自己的 | 收工 |
| 自己那条 = **整行一条深色横带**（含左侧留白） | 项级 Modifier 是行容器 | 改成"**在用户项里只重染内层气泡**"（`pg` 已有 `sUDepth` 探针，改动很小） |
