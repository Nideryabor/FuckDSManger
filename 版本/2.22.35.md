## 1. 实化线的两个反常（用现有日志无法定案）

主人提供两份日志（模块 DIAG + 文件 dsm.log），内容一致，关键三行：

```
23:56:52.429 [实化] 页内bg #1 v = -67818912288342016     ← 值为 #FF0F0F0F（页面底色）
23:56:52.441 背景实化作用域开启（NL 2.22.33 起）
（此后整个会话再无 #2~#5，也无 [实化] 聊天页底色已透明）
```

| # | 反常 | 说明 |
|---|---|---|
| **①** | **`#1` 竟然「早于」作用域开启 12ms** | 但 `sPageDepth++` 与那条 `logOnce` 是**同一次 `before` 里紧邻的两句**（++ 在前）⇒ 按代码顺序 `#1` 必须**晚于**它。⇒ 要么 `logOnce` 首次调用被异常吞掉、要么日志顺序不代表执行顺序 ⇒ **现有探针无法分辨** |
| **②** | **`#2`~`#5` 与 `[实化] 聊天页底色已透明` 全程缺失** | 对照 2.22.31：那时 `#1`~`#5` 在 **6ms 内**连续打出 ⇒ 同一次组合内 `uia.v` 至少被调 5 次。⇒ 2.22.34 只剩 1 次，**说明作用域在第一次之后就没再「开着」**，或者 `uia.v` 之后没再被调用 |

## 2. 本版改动（只有 1 个方法）

把 `GmBubblePaintHook.dg` 从「**只在 `sPageDepth > 0` 时记录**」改成「**无条件记录前 8 条，且每条带 `depth` / `cnt` 的真实值**」：

```
旧： [实化] 页内bg #N <方法名> = <args[1]>
新： [实化] bg#N depth=D cnt=C <方法名> = <args[1]>
```

**这一改能一次分开三种可能**：

| 观察到的 | 结论 |
|---|---|
| 后续条目 **`depth=0`** | 作用域被提前归零（`GmPageHook.after` / 组合分段 / `sPageDepth` 计数错） |
| 后续条目 **`depth>0`** 但**没有** `[实化] 聊天页底色已透明` | `pg` 的判据链卡住（哨兵命中 / `real()` false / `cnt>=4`） |
| **完全没有后续条目** | `uia.v` 之后压根没再被调用（页面结构问题 / hook 被卸） |

## 4. 教训（802~803）

| # | 内容 |
|---|---|
| **802** | ⭐⭐⭐ **探针的「门槛」会吃掉它本该提供的信息**：`dg` 原来把 `sPageDepth > 0` 当记录前提 —— 于是「作用域什么时候关的」这件事**恰恰被门槛挡在日志之外**，只剩一个孤零零的 `#1`。⇒ **诊断探针应当记录「为什么没走到这里」，而不仅是「走到之后是什么」**（本次改法：去掉门槛、把判据本身的数值打出来）。 |
| **803** | ⭐⭐ **两条相邻语句的日志时间戳不一致时，先怀疑「跨通道/缓存的排序」，再怀疑逻辑**：`#1` 与「作用域开启」是同一次 `before` 里紧邻的两句，却差了 12ms —— 这说明**日志的呈现顺序不等于执行顺序**。⇒ 排查时序问题时要**用「同一条日志里带出多个变量」**（如本版 `depth=` `cnt=`）来锚定状态，而不是靠多行日志的相对位置。 |
