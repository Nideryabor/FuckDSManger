3.71.4 收工前留下的待办，按风险从低到高，**先做第①条**：

```

   → 重启一次即可判定：打印 null/"" ⇒ 读不到（时序）；打印 "false" ⇒ 存的是 false（写入）
   ★ 只加日志，不动任何逻辑
```

外加尼尼自己补的一条（**同一类嫌疑，顺手一起装**）：

```
② GmStore.read2() 的 catchall 加日志
```

### 为什么加 ② —— 这条可能是真凶

`GmStore.read2()` 的结构是：

```java
if (!sp.contains(key)) return "";
if ("b".equals(type)) return String.valueOf(sp.getBoolean(key, false));   // ← 直接按类型取
...
catchall: return "";                                                       // ← 异常被静默吞掉
```

**`contains()` 只说明"有这个键"，不说明"它是这个类型"。**
宿主那边（MMKV 的 SharedPreferences 包装）如果把这个键存成了 **String `"1"`**，
`getBoolean()` 就抛 `ClassCastException` ⇒ 被 `catchall` 吞掉 ⇒ 返回 `""`
⇒ `Boolean.parseBoolean("")` = **false** ⇒ **开关看起来关了，其实库里是开的**。

现场数据正好长这样：

```
cfg.fuckds_bg_on     = "0"          ← 我们这边读到 0
host.fuckds_bg_on    = "1"          ← 宿主那边是 1
cmd.cfg_put          = {"key":"fuckds_bg_on","ok":true,"value":""}   ← value 是空串！
```

**「写成功了、回读是空串」** = 类型错配的经典指纹。
（`read2` 全程没有一处校验 `getBoolean` 会不会抛 —— 这是本版最想验的一条假设。）

## 二、改动（两处，都是"只加日志"）

### ① `GmBg.isOn()`

```smali
.method public static isOn(Landroid/content/Context;)Z
    .registers 5                     # 原 4，加了 v2/v3 两个临时寄存器

    ... read2(...) → v0 ...

    new-instance v2, Ljava/lang/StringBuilder;   # "【GmBg】isOn raw=[" + v0 + "]"
    ...
    const-string v3, "bgisOn"
    invoke-static {v3, v2}, Lcom/nidyaber/fuckdsmanger/gm/GmUtil;->logOnce(Ljava/lang/String;Ljava/lang/String;)V

    invoke-static {v0}, Ljava/lang/Boolean;->parseBoolean(Ljava/lang/String;)Z
    move-result v0
    return v0
.end method
```

### ② `GmStore.read2()` 的 catchall

```smali
    :catchall_63
    move-exception v1

    # 【GmStore】类型错配 key=<键> 期望类型=<b/i/f/l> 异常=<异常类名>
    ...
    invoke-static {v2, v3}, Lcom/nidyaber/fuckdsmanger/gm/GmUtil;->logOnce(Ljava/lang/String;Ljava/lang/String;)V

    const-string v0, ""
    return-object v0
```

`logOnce(tag, msg)` 是**两参数**（2.10.97 踩过的坑），两处都按两参调。
`.registers` 相应 +2（`GmBg` 4→5 / `GmStore.read2` 6→8），临时寄存器不碰 `p0/p1/p2` 与结果寄存器。

## 四、装机后怎么看日志（请主人照这个来）

日志落盘：`/data/data/com.deepseek.chat/files/DSMlogs/dsm.log`（`GmLog`）

**第一步：强停宿主 → 重启 → 进聊天页 → 看背景有没有**

| 日志里出现 | 结论 | 下一步 |
|---|---|---|
| `【GmStore】类型错配 key=fuckds_bg_on 期望类型=b 异常=java.lang.ClassCastException` | 🎯 **真凶抓到**：宿主存的是 String，我们按 boolean 读 | `read2` 加**宽容取值**（先按目标类型试，CCE 就按 `String` 取再自己 parse）—— 这是改 `read2`，动的是全局读取路径，**要单独一版 + 先回读 smali 再装机** |
| `【GmBg】isOn raw=[]`（空）+ 没有类型错配 | **时序**：启动时 MMKV 还没就绪 / 键还没同步过来 | 在**调用方**延迟重试（绝不改 `GmStore.get`，见 3.71.4 规则 Q） |
| `【GmBg】isOn raw=[false]` | **写入侧**：库里真就是 false，是「开关打开了但没写进去」 | 查 UI→宿主 `cfg_put` 那条链路（现场显示 `ok:true` 但 `value:""` ⇒ 写入真的落盘了吗） |
| `【GmBg】isOn raw=[true]` 但背景还是不显示 | 读没问题 ⇒ 问题在**绘制侧**（`GmBg.real()` / 位图加载 / 绘制钩子） | 往 `GmGlass`/`GmBgView` 那条线走，另开一版 |
| 一条 `【GmBg】` 都没有 | `isOn()` **根本没被调用** ⇒ 挂载点没进来 | 回 3.71.0 的锚点清单查调用点（教训 O：`count=1` ≠ 会跑） |

> `logOnce` 同一个 tag 只打一次 ⇒ 日志里每个 tag 至多一行，**不会刷屏**。
