## 一、主人的验证把推论钉死了

| 条件 | 结果 |
|---|---|
| 有网络（有服务器下发） | 启动闪一下 → **下发覆盖内存** → 卡消失 |
| **断网（无下发）** | 🎯 **卡一直在** |

**⇒ 机制彻底确认**：
- **无下发** ⇒ 宿主用 **MMKV**（我们已改成 `true`）⇒ 卡在
- **有下发** ⇒ 宿主**直接用网络数据更新内存**，不重读 MMKV ⇒ 卡没了

**⇒ 结论：必须阻止"下发数据"覆盖模型列表。**

---

## 二、本版思路：与其改 JSON 内部，不如**整项摘掉**

宿主 `p66.h` 的代码本来就长这样：

```java
Lev4 mc = map.get("model_configs");
if (mc == null) → 整段跳过                       ← ★ 天然支持"没有这一项"
bx4 b = fv4.e(mc);
Lev4 value = (Lev4) b.get("value");
MMKV.q("kv_remote_settings_model_configs_v1", value.toString());
```

**⇒ 只要在下发进入 `p66.h` 之前，把 `Map` 里的 `model_configs` 移除**：
- 宿主**不会用下发的模型列表覆盖**（既不写盘也不更新内存）
- 于是它继续用**启动时从 MMKV 读到的那份**（= 我们改过的 `true`）
- **⇒ 切换卡常驻，且不需要改任何 JSON 内部结构** ✅

**本版改动**（`GmDsHook.beforeHookedMethod`，已持有下发 `Map`）：

```java
map.remove("model_configs");     // 整项摘掉
GmUtil.log("[ds] 已从下发数据中移除 model_configs（防覆盖模型切换）");
```

- 整段包在 try/catch 里：若 `Map` 不可变，会打 `移除 model_configs 失败（Map 不可变？）` 并放行（**不会崩**）

> 副作用（已知）：服务器若**新增/调整模型列表**，我们这边就不跟随了 —— 需要时可关掉「模型切换」开关恢复原状。

## 四、教训

| # | 教训 |
|---|---|
| **327** | ⭐⭐⭐ **"去掉干扰项"往往比"改造干扰项"简单一个数量级**：与其构造宿主内部的 JSON 对象，不如让宿主**根本收不到**这一项（而且宿主代码本来就有 `null` 分支） |
| **328** | ⭐⭐⭐ **判定实验的价值**：主人做的"断网启动"是**单变量实验**，一发就把"覆盖源"锁定为服务器下发 |
| **329** | ⭐⭐ **改别人的 Map 要防不可变**：`Map.remove` 可能抛 `UnsupportedOperationException` ⇒ 必须 try/catch 并留一条可读日志 |
| **330** | ⭐⭐ **缓存型配置（读一次就存内存）** ⇒ 任何"事后写盘"都是徒劳，必须作用于**它正要用的那份数据** |
