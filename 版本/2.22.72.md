## 0. 真凶：我把一个装着活对象的寄存器当临时变量用了

主人日志里那行就是答案：

```
VerifyError: Verifier rejected class com.…GmBubblePaintHook:
  void …pg(…) failed to verify: [0x70] check-cast on non-reference in v3

hookM FAIL uia.v
hookM FAIL uia.u
```

**根因**：

```smali
aget-object v3, v0, v1          # ★ v3 = args[1]（那个 Long 对象）—— 它是活的！
…
instance-of v1, v3, Ljava/lang/Long;
…
# 我在 2.22.70 插的白名单：
invoke-virtual {v1, v2}, Ljava/lang/String;->equals(Ljava/lang/Object;)Z
move-result v3                  # ✗✗ 拿 v3 当布尔临时用 ⇒ 把那个 Long 踩没了
…
check-cast v3, Ljava/lang/Long; # ⇒ 「对非引用类型做 check-cast」⇒ VerifyError
```

**⇒ `GmBubblePaintHook` 整类验证失败 ⇒ 它挂的所有钩子一个都没装上**（`hookM FAIL uia.v` / `uia.u`）。

**⇒ 所以"开了跟没开一样"根本不是判据的问题** —— 是**判据所在的钩子压根没被安装**。

### ⚠️ 我上一版的诊断方向也错了

## 3. 教训（162~165）

| # | 内容 |
|---|---|
| **162** | ⭐⭐⭐ **用寄存器当临时变量之前，先问"它现在装着什么"** —— `v3` 从 `aget-object` 起就装着 `args[1]`（那个 `Long`），我用它接 `equals()` 的布尔返回值 ⇒ 直接把活对象踩没了。⇒ **手写 smali 的铁律：动手前把该方法的"寄存器分配表"写出来**（哪个寄存器在哪个区间装什么、能不能复用）。**方法已经很挤（`.registers 10` 里 v0~v6 都在用）时，只碰"明确空着"的槽位（v7/v8）。** |
| **163** | ⭐⭐⭐ **一个类 VerifyError ⇒ 它挂的钩子全灭** —— 现象是"**完全没效果**"，而不是"部分失效"；而且**报错时机在类加载**（`handleLoadPackage`），日志里明明白白写着 `hookM FAIL`。⇒ **凡是"整块功能突然完全无效"，第一件事是查类加载/验证错误，不是查业务判据。** |
| **164** | ⭐⭐⭐ **"钩子没装上"和"判据不匹配"在界面上长得一模一样** —— 上一版我直接跳到"查判据"，甚至为它写了判断表；**答案却在主人第一条日志里**。⇒ **排查顺序必须是：① 类验证/加载是否成功 ② 钩子是否注册成功 ③ 判据是否命中 ④ 值是否符合预期**。**跳级排查 = 白烧一轮。** |
| **165** | ⭐⭐⭐ **破了自己的规矩，就要付账**：项目文档 **铁律 6** 早写明「**MT 的 `edit_check` 不做字节码校验**」，而我改 `pg` 时**没把它落到 `tmp/` 跑 `vercheck.pl`**（新类我都跑了，改老方法反而没跑）⇒ VerifyError 直接上了真机。⇒ **今后：任何 smali 改动（包括老方法里插一段），先落 `tmp/`、跑 `vercheck.pl`，再进会话。** vercheck 的第 2 类检查（**类型冲突**）**正好能抓这次的 `int → check-cast` 冲突**。 |
