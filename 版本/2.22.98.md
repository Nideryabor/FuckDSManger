## 1. 现场（主人日志 · 15:00:05 ~ 15:00:34）

```
15:00:05.678 [气泡] 已发起选图（pick 已武装）
15:00:06.461 [气泡] 本次请求码 = 0x435b（气泡选图）⇒ 直判处理      ← 第1次（带 uri）

15:00:12.019 ...                                                  ← 第4次
（15:00:24 再选一次 ⇒ 15:00:25 / 27 / 29 / 31 / 33 / 34 六次）
```

**判据**：`本次请求码 = 0x435b` 与 `选中 uri = …1000021428` **每次都带完整数据**（不是取消），间隔约 1.8s，且**每次都跑完整 `saveImage`**。

### 1.1 `saveImage` 一次的代价（`GmBubble.saveImage`）

```
openInputStream → BufferedInputStream → BitmapFactory.decodeStream（整张原图 ≈ 12MP ⇒ ≈48MB 位图）
→ FileOutputStream + compress(PNG, 100)（重编码，最贵的一步）
→ flush / close / recycle
```
**全在主线程**（`onActivityResult` 的 before hook 里）⇒ 单次约 0.3~1.8s；连做 5~6 次 ⇒ **"巨卡 → 内存尖峰 → 崩"** ✓✓ **完全对上主人的描述**。

## 2. ⭐ 这一条同时解释了 2.22.96 那条"串图"反馈

`finishPick()` 的语义是 **"读完即清" `sUPick`**（项目老教训 693/696：**「取走即清」的一次性标志天生怕"别人先伸手"**）。而回调来了 5~6 次：

| 回调 | `sUPick` | 走的档 | 结果 |
|---|---|---|---|
| 第 1 次 | `true` | **用户** | ✅ 写 `fuckds_ububble.png` + `setUImg(true)` |
| 第 2~6 次 | **已被第 1 次清成 `false`** | **助手** | ❌ `useImgName()` 取名 `fuckds_bubble.png` ⇒ **把同一张图写进 AI 气泡的图片文件** + `setImg(true)` + Toast「气泡图已保存」 |

⇒ **"用户修改气泡图片会应用到 AI" 的真凶 = 一次性标志被吃掉之后又跑了 5 次**（不是档位读错，也不是 `sImgName` 逻辑错）。
⇒ 反方向「AI 改图应用到用户」同理可解释（AI 选图同样被投递多次，只是档位恰好都是助手，用户侧由 `applyColor/setUImg` 的时序造成）。

**⇒ 一个"重复投递"的宿主行为，同时造成了 ① 卡崩 ② 串图 两个看起来无关的现象。**

## 3. 修法（**一条指令**）

`GmPickHook` 的 `0x435b` 直判分支里**本来就有** `takePicking()`，只是**返回值没人用**（原代码 `move-result v2` 后直接 `saveImage`）。现在让它当闸门：

```
invoke-static {}, Lcom/varuns2002/disable_flag_secure/gm/GmBubble;->takePicking()Z
move-result v2
if-eqz v2, :cond_72          ; ★ v2==false（标志已被消费）⇒ 重复投递 ⇒ 直接跳过
invoke-static {v1, v0}, Lcom/varuns2002/disable_flag_secure/gm/GmBubble;->saveImage(Landroid/content/Context;Landroid/net/Uri;)Z
```

⇒ **只有第 1 次回调真干活**：不再重复解码、不再重复重编码、不再重复写盘、不再重复 toast、不再误走助手档 ⇒ **卡崩 + 串图一起消失**。

- 直判分支：`if-eqz v2, :cond_72`（跳到"解除武装后 return"）
- 老兜底分支（`:cond_137` 段，理论上已被直判覆盖）：同样加 `if-eqz v2, :cond_137`

**产物回读**：`line 110 move-result v2 / if-eqz v2, :cond_71 / saveImage` ✓ · `line 304 move-result v2 / if-eqz v2, :cond_135 / saveImage` ✓

### 3.1 为什么这条闸门"语义正确"而不是"凑合"

| 场景 | 行为 |
|---|---|
| 正常选图（第 1 次回调） | `sPicking==true` ⇒ 通过 ⇒ 保存 ✓ |
| 宿主重复投递（第 2~6 次） | `sPicking==false` ⇒ 跳过 ✓ |
| 用户取消（intent/uri 为 null） | 走 `:cond_72` ⇒ 消费标志且不保存 ✓（老逻辑，未改） |
| 用户重新选图 | `armPick()/pick()/pickU()` 重新武装 `sPicking` ⇒ 下次通过 ✓ |

## 6. 教训 257 ~ 262

| # | 要点 |
|---|---|
| **257** | ⭐⭐⭐ **"两个看似无关的现象，往往同一个根因"**：本轮"卡崩"与"串图"共用一条 = **宿主对同一次 pick 重复投递 `onActivityResult`**。**先找共同根因，再分别修** |
| **258** | ⭐⭐⭐ **忽略返回值 = 关掉了一道闸门**：`takePicking()` 的返回值**原代码就一直丢弃**（不是我引入的）⇒ "一次性标志"变成了"被消费但不生效" ⇒ **每个"取走即清"的 API，其返回值都必须被用**（教训 693/696 的**实现级**版本） |
| **259** | ⭐⭐⭐ **主线程上的重活 × 重复投递 = 必崩**：`onActivityResult` 在主线程；"解码整张原图 + PNG 100% 重编码"是秒级重活；**只要有重复投递，就是 5~6 次秒级重活** ⇒ 崩。⇒ **判断"会不会崩"时，先算「单次代价 × 投递次数」** |
| **260** | ⭐⭐ **"一直保存"这种描述要直接翻译成"循环/重复"**：用户说"一直保存"，正确动作是**去日志里数同一条事件出现了几次**（本轮一眼看到 4 次、6 次）⇒ 不要去查"保存函数是不是有 bug" |
| **261** | ⭐⭐ **宿主日志里"重复出现的完整数据"是投递重复的铁证**：每次回调都带**完整 uri**（不是取消）⇒ 排除"用户手滑/取消导致的重试"，锁定**投递机制** |
| **262** | ⭐⭐⭐ **修在"入口"比修在"重活"里好**：本轮没有去优化 `saveImage`（解码/编码），而是在**回调入口加一道一次性闸门** ⇒ 改动 1 条指令、风险最低、且**顺带修掉串图**。⇒ **先问"这次调用该不该发生"，再问"它跑得快不快"** |
