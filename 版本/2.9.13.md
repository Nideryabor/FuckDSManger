# FuckDSManger 2.9.13

> 综述：**新增「设备身份伪装」** —— 伪造 `android_id`，让服务端把本机当成一台新设备。
> 产物：`FuckDSManger_2.9.13_for_ds2.5.2.apk`（100 / 2.9.13，**77 类**，V1+V2+V3）
> 宿主：`com.deepseek.chat` **2.5.2**（versionCode 273）

---

## 一、为什么要做这个

2.9.12 适配完 2.5.2 后，真机仍然复现：

```
POST /api/v0/users/create_sms_verification_code
→ {"code":0,"msg":"","data":{"biz_code":11,"biz_msg":"RISK_DEVICE_DETECTED","biz_data":null}}
```

而环境伪装（数美 Java 侧信号全清、libsmsdk.so 未变、`sr9.w` 已接管）**本身是好的**。
⇒ 结论：**服务端已经"记住"了这台设备**，光清信号不够，得让它认不出这是同一台。

## 二、抓包分析（本轮的关键突破）

主人抓到的请求头里，服务端认设备的依据是这三条：

| 头 | 来源 | 性质 |
|---|---|---|
| `x-device-id: h+d1kCW+mvCsnc1sQ05u7BNc969T8kOewq0U6vxZ83A=` | `Lex2;->b()` | **宿主自己的设备主键** |
| `x-rangers-id: 7683678479451168525` | `Lnqa;->g()`（字节 AppLog） | 埋点 SDK 设备 ID |
| （无头，SDK 上报） | 数美 smid | 服务端查数美风控库 |

### 2.1 ⭐ `x-device-id` 算法（已完全解出并反验）

```java
// Lex2.b()
if (!同意服务协议) return "";
androidId = Settings.Secure.getString(cr, "android_id");
plain     = androidId + "_" + Build.BRAND;
return a(plain, getPackageName());

// Lex2.a(plain, key)
SecretKeySpec spec = new SecretKeySpec(MD5(key.getBytes()), "AES");   // key = 包名
Cipher c = Cipher.getInstance("AES/CBC/PKCS5Padding");
c.init(ENCRYPT, spec, new IvParameterSpec(new byte[16]));             // IV = 全 0
return Base64.encodeToString(c.doFinal(plain.getBytes()), 0);
```

**反验**：主人抓的值 → 32 字节密文 ⇒ 明文 24 字节 = `android_id(16) + "_" + "OnePlus"(7)`，
与设备 `PJZ110`（一加 13）完全吻合 ✅

⇒ **只要 `android_id` 变了，`x-device-id` 就跟着变** —— 而且**不需要我们手写 AES**
（让宿主自己去加密，我们只改输入）。

## 三、实现

### 3.1 新增 2 个类

| 类 | 职责 |
|---|---|
| `GmDevice` | 状态与逻辑：开关（`fuckds_device_on`）、伪 ID（`fuckds_device_id`）、随机 16 位 hex 生成、`install/reset` |
| `GmDeviceHook` | `beforeHookedMethod`：`args[1] == "android_id"` 时把返回值换成伪 ID |

**Hook 目标**：`android.provider.Settings$Secure;->getString`（`hookAllMethods`，覆盖全部重载）
**过滤条件**：`args[1]` 是 `String` 且等于 `"android_id"`，其余设置项**原样放行**
**持久化**：伪 ID 存 MMKV（`fuckds_device_id`，类型 `s`），**生成一次就固定**，重启不变

### 3.2 改动 4 个类

| 位置 | 改动 |
|---|---|
| `GmEnv.install` | `hookRoot()` 之后追加 `GmDevice->install(cl)`（仍在 `handleLoadPackage` 最早期） |
| `GmEnv.refresh` | 追加 `GmDevice->refresh(c)`（跟随现有刷新时机，改开关即时生效） |
| `GmEnvSwitch` | 新增 `m == 2` 分支 → `GmDevice.setOn()` |
| `GmEnvClick` | 新增 `m == 2` 分支 → `GmDevice.reset()`（换新 ID） |
| `GmEnvDialog` | 「环境伪装」页新增一行：**设备身份伪装**（开关）+ 按钮**换一个新设备身份** |
| `AndroidManifest.xml` | `99/2.9.12` → `100/2.9.13` |

### 3.3 关键设计：懒加载，保证抢在第一次读取之前

`handleLoadPackage` 阶段可能还没有 Context，所以：

```
GmDeviceHook.beforeHookedMethod
  → GmDevice.ensure()        // 首次进入时用 AndroidAppHelper.currentApplication() 拿 Context
  → 读出开关 + 伪 ID（读不到就现场生成）
  → 之后每次只判静态缓存，开销可忽略
```

⇒ 无论宿主在什么时候第一次读 `android_id`，我们都已经就绪。

### 3.4 默认值

| 键 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `fuckds_device_on` | `b` | **关** | 设备身份伪装总开关（行为可预期，用户主动开） |
| `fuckds_device_id` | `s` | 自动生成 | 伪 android_id（16 位 hex，与真实格式一致） |

- 打开开关：若还没有伪 ID 就生成一个
- 关闭开关：清掉内存里的伪值，**重启宿主后恢复真实 `android_id`**
- 「换一个新设备身份」按钮：重新随机 + 顺带打开开关

## 四、风险与注意事项（重要，别踩）

1. **一次性换、换完固定**：同账号短时间内 `device_id` 反复变化是**典型盗号特征**，
   可能触发比现在更严格的风控。换一次、登录上去，就别再点。
2. **服务端会校验设备**：`/api/v0/users/auth_token/check_device` 存在于启动/会话流程里，
   换了身份后可能被要求二次验证。
3. **属于"账号级"操作的功能不受影响**：
   `/api/v0/users/logout_all_sessions`（登出所有设备）由服务端按账号失效全部 token，
   与 `device_id` 无关；宿主也没有"设备列表"页面。**改了身份照样能一键登出所有设备。**
4. **影响面**：只 hook 宿主进程内读 `android_id` 的调用，其它设置项不碰；
   宿主内其它 SDK（数美 / AppLog）看到的也会是伪值 —— 这正是"换一台设备"的意图。
5. **必须重启宿主生效**：`Lex2.b()` 有内存缓存，改完要强停重启。

## 六、本轮教训（补充第十一节）

| # | 教训 |
|---|---|
| 71 | **「清信号」和「换身份」是两件事**，风控被拦时要先问自己：服务端认的是**行为特征**还是**设备标识**？本轮的 `RISK_DEVICE_DETECTED` 属于后者 |
| 72 | **抓包头的价值极高**：一个 `x-device-id` 直接指明了破解方向。逆向顺序应该是「**先看客户端发什么，再回代码里找生成点**」，比盲扫 SDK 快得多 |
| 73 | **能借力就不要自己实现**：需要「AES(android_id+Branch)」时，不用手写 AES —— **改输入（hook `android_id`）让宿主自己算**，一行 hook 顶 150 行加密代码 |
| 74 | **手写 smali 的反向判断又犯了 8 次**（`if-eqz`↔`if-nez`），全部靠**逐行回读**抓回。结论不变且要加固：**每个条件跳转写完立刻念一遍中文语义**（"等于 0 跳" / "不等于 0 跳"） |
| 75 | **改 `.registers` 时先确认方法体有没有用到被"挤下去"的 vN**：参数个数不变时，`pX` 的符号引用不受影响，但**原来当作局部的 vN 含义会变** |
