# FuckDSManger 2.9.16

> 综述：**修 2.9.15 的三处问题**（诊断日志看不见 / 标记会把入口锁死 / 宿主 androidx hook 一直失败）。
> 产物：`FuckDSManger_2.9.16_for_ds2.5.2.apk`（103 / 2.9.16，80 类，V1+V2+V3）

---

## 一、起因：主人贴的 LSPosed 日志

```
FuckDSManger: hookM FAIL androidx.activity.ComponentActivity.onActivityResult |
  ClassNotFoundException: androidx$activity$ComponentActivity
FuckDSManger: hookM FAIL androidx.fragment.app.FragmentActivity.onActivityResult
  ClassNotFoundException: androidx$fragment$app$FragmentActivity
    at DisableFlagSecure.handleLoadPackage(Unknown Source:178 / 187)
```

### 1.1 这条日志**不是**对话框不弹的原因

- 它影响的是 **选图回调（`GmPickHook`）**，跟「设备身份」入口无关；
- 而且它证明了一件好事：**模块注入成功，且 `handleLoadPackage` 执行到了第 178/187 行**，
  说明**它前面的所有 hook（含 `GmTouchHook`，约在 120 行）都注册了**。

### 1.2 但它暴露了 `GmPickHook` 早就失效（真 bug）

实测宿主 dex：

| 检查 | 结果 |
|---|---|
| `Landroidx/activity/ComponentActivity;` | **不存在**（搜索 0 命中） |
| `com.deepseek.chat.MainActivity` 的父类 | **`Lgs;`**（= `androidx.appcompat.app.AppCompatActivity` 被 R8 改名） |
| `Lgs;` 内部引用 | `Landroidx/appcompat/app/b;` 等 —— **R8 只混淆了类名，保留了包路径** |

⇒ 宿主对 androidx 做了**类名混淆**，模块按原类名 `findClass` 必然失败。

## 二、我自己的两个坑（复查时发现的）

### 2.1 ⭐ `GmDiag.log` 写不进 LSPosed 日志

| 方法 | 去向 |
|---|---|
| `GmUtil->log` / `logFail` | **XposedBridge → LSPosed 日志**（能看见） |
| `GmDiag->log` | **仅内存缓冲**（在模块 UI 的「下发查看」里看） |

2.9.15 我把诊断日志全写成了 `GmDiag.log` ⇒ **主人根本看不到** ⇒ "让你贴日志"这条建议等于白说。

**已全部改成 `GmUtil->log` / `logFail`。**

### 2.2 ⚠️ 标记会在"弹窗失败"时被写掉 ⇒ 入口永久锁死

2.9.15 的 `promptIfNeeded` 是「先写 `fuckds_device_asked=true`，再弹窗」，而弹窗内部是
try/catch 静默的 ⇒ **万一弹窗构建失败，标记已经写掉了，之后再也不会弹**。

**改成：标记由对话框按钮写入**（用户真正"处理过"才记）；弹窗失败则下次仍会尝试。

## 三、改动清单

| # | 位置 | 改动 |
|---|---|---|
| 1 | `GmDevice.promptIfNeeded` | 去掉标记写入；日志改 `GmUtil->log`；catch 改 `logFail`（异常可见） |
| 2 | `GmDeviceClick.onClick` | 新增：在按钮回调里写 `fuckds_device_asked=true`（真正的"已处理") |
| 3 | `GmDeviceDialog` | catch 块加 `FuckDSManger: device dialog build FAIL` 日志 |
| 4 | `GmTouchHook` | 手势日志改 `GmUtil->log`（`FuckDSManger: touch gesture -> open device dialog`） |
| 5 | `DisableFlagSecure` | ⭐ 新增 `hookPickAll(cl)`：**从 `MainActivity` 沿 `getSuperclass()` 逐层 hookAllMethods("onActivityResult")**，替代原来 3 条硬编码 `hookM` ⇒ 免疫 R8 改名，且日志不再刷 FAIL |
| 6 | `AndroidManifest.xml` | `102/2.9.15` → `103/2.9.16` |

### 3.1 `hookPickAll` 的意义

```
MainActivity → gs(AppCompatActivity) → br3 → … → null
                 └─ 每层只要声明了 onActivityResult 就 hookAllMethods
```

- 不再依赖任何硬编码的 androidx 类名 ⇒ **宿主再升级、再混淆也不会失效**
- 日志会打印 `FuckDSManger: pick hooks dynamic total=N`，一眼看出挂了几层

## 五、本轮教训（补充第十一节）

| # | 教训 |
|---|---|
| 84 | ⭐⭐ **诊断日志必须写到"用户能拿到的地方"**：本项目有两套日志（`GmUtil` → LSPosed / `GmDiag` → 内存），我埋诊断时用错了那套 ⇒ 白埋。**加日志前先确认它输出到哪** |
| 85 | ⭐ **"已处理"标记要由用户动作写入，不能由"尝试动作"写入**：前者失败可重试，后者一失败就永久锁死（本次的 `fuckds_device_asked`） |
| 86 | **宿主会对第三方库（androidx 等）做类名混淆**：`MainActivity` 的父类都成了 `Lgs;`。凡是硬编码 `androidx.*` 的 hook 都可能失效 ⇒ 改为**沿继承链动态找** |
| 87 | **一条 FAIL 日志要看它在注册表的哪个位置**：`handleLoadPackage:178` 往前推，就能确认"它之前的 hook 都成功了"——**日志行号是免费的进度条** |
