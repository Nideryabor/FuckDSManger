## 二、借这轮把「空结果吃掉标志」**从协议上根治**

原来的协议是 **「取走即清」**：链上任何一家一旦被调到就把自己的标志消费掉。
⇒ **如果某个回调（不带数据/不是我们那次）先命中，我的标志就被白白吃掉**，真正带数据的那次反而没标志（上一轮日志里「同一毫秒 ×6 次 entered」正说明「一次操作 → 多个回调」是常态）。

**改成「先看数据、再消费」**：

```
GmBubble.isPicking()      ← 新增：只看不清
   ↓ 先检查 Intent / uri / sAct 是否齐全
   ↓ 不齐全 ⇒ 直接 :cond_76（★ 标志还留着，下次回调还有机会）
GmBubble.takePicking()    ← ★ 确认有数据了才真正消费
   ↓ saveImage → setImg(true) → Toast
```

**改动**
| # | 位置 | 改动 |
|---|---|---|
| 1 | `GmBubble` | 新增 **`isPicking()Z`**（只看不清） |
| 2 | `GmPickHook` | 第四家入口改 `isPicking()`；三条 bail 目标 `:bubble_rearm` → **`:cond_76`**（**不消费标志**）；`saveImage` 之前插入 `takePicking()`（**此时才消费**） |
| 3 | `GmBubbleCellHook` / manifest | 自检行 → `2.22.6`；`336/2.22.5` → **`337/2.22.6`** |

## 四、教训

| # | 要点 |
|---|---|
| **696** | ⭐⭐⭐ **协议要从「取走即清」升级为「先看数据、再消费」**：只有"确认这次回调确实是我要的"，才允许销毁一次性状态。**凡是"一次性标志 + 可能被多个回调命中"的组合，都必须这样写。** |
| **697** | ⭐⭐ **要日志就给「判读的窗口」**：这次日志在点击后 2.3 秒就断了 ⇒ 关键那一段（选图返回）根本没截到。**下次直接说"点完图之后的那几行"。** |
| **698** | ⭐ **「已发起选图」出现本身就是有价值的中间态**：它把问题从「按钮没生效」缩小到「结果没回来/没被消费」——**给链路的两端各放一个日志，缺失的那一段就是现场。** |
