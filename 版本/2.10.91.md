## 二、🔍 请求链路勘探结论（本轮把材料摸清了）

| 项 | 结论 |
|---|---|
| 网络栈 | **Ktor client + OkHttp engine**（`OkHttpEngineContainer` 类名保留；`en0` = OkHttp 的 `RetryAndFollowUpInterceptor`） |
| 域名 | `https://chat.deepseek.com`（`z90` 里的 oauth 串暴露） |
| 鉴权 | **Ktor `BearerAuthProvider`**（`ka0`，含 `"Bearer Auth Provider is not applicable for "`）⇒ **token 在内存回调里，不在 MMKV/SP**（`h02` = 远程配置管理器，只有 `kv_*` 设置） |
| PoW | `/api/v0/chat/create_pow_challenge`（`hz0`）+ `X-DS-PoW-Response`（`hx2`）+ native `com.deepseek.crypto.PowCalculator.calculateDeepSeekHashV1Pow` |
| completion 请求参数 | **`e41`**（implements `u01`，11 字段 data class：`a/c/g/i/j/k:String`、`b:Integer`、`d:List`、`e/f/h:Z`） |
| completion 构造 | `hx2.g(u01, Long) → z40` |
| ⚠️ 关键否决 | **`z40` 不是"可执行请求"，而是协程挂起状态包装**（`z40.b(li3,hf2)` 有几十个调用点，全是 `xxx.A(Object)` 续体恢复点）⇒ **"调 g 再执 b"这条路走不通** |
| 端点清单 | `chat/completion`·`regenerate`·`history_messages`·`stop_stream`·`message_feedback`·`tts/*`·`chat_session/update_title`·`create_pow_challenge`·`file/upload_file`·`users/*`·`client/settings`·`index/query`·`asr/ws` ⇒ **没有任何"标题生成/摘要"之类的单发辅助接口** |

**⇒ 结论：要"单发请求生成预回复"，只能自己发 `/api/v0/chat/completion`（或等价地复用宿主链路）。**

## 四、教训

| # | 教训 |
|---|---|
| **424** | ⭐⭐⭐ **先看清"返回值"是什么，再决定要不要走这条路**：`hx2.g → z40` 一度让我以为找到了"构造请求的钥匙"，直到发现 `z40` 是**协程状态包装**（几十个续体恢复点）—— **一个 `xref` 就省掉几版弯路** |
| **425** | ⭐⭐ **"没有现成接口"也是重要结论**：把端点全列一遍，确认宿主**没有**"标题生成"这类单发接口 ⇒ 后面所有设计都建立在"必须自己发请求"这个确定前提上 |
| **426** | ⭐⭐ **token 不在磁盘上**：`h02`（远程配置管理器）里只有 `kv_*` 设置 ⇒ 鉴权态**只活在内存**（Ktor auth provider）⇒ 想拿只能 hook 请求头 |
