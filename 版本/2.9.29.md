## 一、推理链（怎么锁到这一个键的）

| 事实 | 出处 |
|---|---|
| `AssistantIcon` composable 是**线性**的，`painterResource(0x7f070059)` 无前置分支 | 2.9.28 逐行读完 `Lcka;` 4984→5290 |
| `Ljt5;->B(composer)`（coil3）只用来算 **group key**，不产 painter | 同上 |
| 真机：`kf5.K` 从未以 `0x7f070059` 调用；四个 Toast 一个不弹 | 2.9.28 回执 |
| ⇒ **头像 composable 根本没被合成** | 上述三条的必然结论 |

「谁让 App 不画头像」——宿主里现成一个开关：

```
宿主 Lc30;   ：kv_settings_hide_assistant_avatar → kv_remote_settings_id_hide_assistant_avatar（App 自己的设置项）
宿主 Lh02;   ：:cond_f61  const-string "hide_assistant_avatar"  →  Lbx4;->get(...)   ← 特性表读取
模块灰度表    ：hide_assistant_avatar | b | 「隐藏助手头像」      ← 模块纳管的键之一（GmDialog 表里）
模块 GmStore ：= 宿主进程 MMKV(SharedPreferences) 的读写口 ⟹ 模块可以直接读写宿主的 kv_* 设置
```

**时间线也吻合**：2.9.8~2.9.11（宿主 2.5.1）头像可见 ⇒ 那时候是「蓝方块」（tint 问题）；
之后一路做**灰度键纳管 / 下发覆盖自动重应用**（2.9.1、2.9.7、2.9.12+），
服务端下发的 `hide_assistant_avatar=true` 被写进宿主设置 ⇒ 头像从「蓝方块」变成「整个没有」。

## 二、本版改动

| 项 | 内容 |
|---|---|
| **新类 `GmAvatarFix`** | `run(Context)`：① 读 `GmAvatar.isOn` + `kv_settings_hide_assistant_avatar`(b) + `kv_remote_settings_hide_assistant_avatar`(b)，拼成一行日志并 Toast：`AVFIX: avatar_on=… hide_settings=… hide_remote=…` ② 若「修改助手图片」为开，则**把这两个键写回 `false`**（`GmStore.write(ctx, key, "false", "b")`），再打一行 `AVFIX: hide_assistant_avatar forced false (restart host)` |
| `GmResumeHook` | 在 `MainActivity.onResume` 里调用 `GmAvatarFix.run(this)`（`GmEntry.sAct` 已就位之后），**每进程一次**（`sDone` 守卫） |
| 版本号 | 入口日志 → `v2.9.29`（含转发类）；`AndroidManifest.xml` `115/2.9.28` → **`116/2.9.29`** |

> **写入何时生效**：宿主在**启动时**读自己的设置，所以 `onResume` 写进去的值要**下一次启动**才被读到。
> ⇒ 安装后「打开一次 App（写入）→ 再重启 App（生效）」= 重启两次；之后就一直是对的。

## 五、教训（补充）

**第 120 条：⭐⭐「功能不生效」的第零步 —— 先确认「你要改的那段代码到底有没有跑」。**
本轮花了 3 个版本，根源是一直在「渲染层」找问题，而实际是**上游把整块 UI 藏了**。
判据形态是「**完全没有日志**」——这种"静默"极其像"hook 没挂上"，但真因可能是
**宿主自己的开关**。⇒ 以后凡是「hook 挂上了、目标代码却毫无动静」，先把宿主**自带的设置/灰度键**过一遍。

**第 121 条：模块纳管的灰度键里，可能有「与本模块功能互斥」的键。**
`hide_assistant_avatar` 就是典型：它是宿主「隐藏助手头像」的开关，与「修改助手图片」**目的相反**。
⇒ **功能增强型模块必须检查自家管理表里有没有会掐死自家功能的键**，并在功能开启时把它钉住
（本版做法：`GmAvatar.isOn` ⇒ 强制该键 false）。

**第 122 条：⭐「诊断也要有兜底通道」——尤其是屏幕上没人可看的时候。**
Toast 打不出、日志翻不到，都是可能的；本版改成**同时**做三件事：
读值 → 写进 LSPosed 日志 → 顺手自愈。就算用户什么都没看到，**自愈本身也会留下痕迹**
（`AVFIX:` 行 + 下一次启动头像恢复）。

**第 123 条：⭐⭐⭐「服务端下发」是本地功能失效的隐形元凶（本轮真凶）。**
宿主的显示行为由**远端灰度**决定，而模块为了「灰度全量纳管」会把这些键也一起管起来、
并在下发时**自动重应用** ⇒ 远端一旦把某个 UI 开关灰成「关掉」，就会**直接掐死模块自己的功能**，
而且症状是「代码根本没跑」，与 hook 失效极像、极难二分。
⇒ 两条纪律：
1. **凡是被自动重应用的下发键，先做一遍「它会不会关掉我家功能」的审查**，会的话就钉住（白名单/强制值）；
2. 排查「目标代码没跑」时，**先看相关宿主键的下发原值**（本次一行 `AVFIX:` 日志就定案）。
