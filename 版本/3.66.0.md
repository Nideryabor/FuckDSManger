### 编译期撞的那一下（值得记）
```
error: no value passed for parameter 'onOpen'.
error: argument type mismatch: actual type is '() -> Unit', but 'String' was expected.
```
真因：**Kotlin 的尾随 lambda 只能对应"最后一个参数"**，而我写的签名是
`HelpEntry(onOpen, label = "…")`。调用处 `HelpEntry { … }` 于是把 lambda 喂给了 `label`。
⇒ 改成 `HelpEntry(label = "…", onOpen)`：**把回调放最后**（这也是 Compose 的惯例）。

## 五、教训

**1042 · ⭐⭐⭐ 说明文字会**腐坏**，而腐坏的说明比没有说明更坏。**
　　那几张卡写着"点下面的「① 把格式约定写进系统提示词」"—— 而那个按钮**两版之前就删了**。
　　⇒ 把说明收进一处（`Help.kt`），并且**在做法改变时，把说明当成代码的一部分一起改**。
　　（老账 3.57.1 教训 984「位置本身就是功能的一部分」的姊妹条：
　　**"说明里的路径"也是功能的一部分**。）

**1043 · ⭐⭐ 尾随 lambda 只能给最后一个参数 —— 回调就放最后。**
　　`fun f(a, cb)` 里 `f { }` 会把 lambda 喂给 `a`（如果 `a` 恰好是函数类型就更隐蔽）。
　　⇒ 签名顺序按惯例：**数据在前、回调在后**。

**1044 · ⭐⭐ 纯文本渲染的地方，别写 Markdown 标记。**
　　我们的弹窗/说明卡都是 `Text(纯字符串)` ⇒ `**加粗**` 会原样露出来。
　　⇒ 想强调就用「」或符号；这条也写进了 `Help.kt` 的注释。
