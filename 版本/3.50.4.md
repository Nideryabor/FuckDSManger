# 3.50.4（vc652）—— 「发错会话」修复：判据从「消息最多」改成「最近活跃」

> 🐲 尼得亚伯 · 2026-10-05
> 前置：`版本/3.50.0.md`（建议按钮全链路闭环）

---

## 〇、真机 bug（主人报的）

> **「我点了以后发送到了另一个对话，是不是 id 搞错了」**

**是的，就是判据搞错了。**

---

## 一、真因

`GmSender.pickCurrent()` 原来只用了**一个判据**：

```java
// ❌ 旧：挑「sid 非空 + 消息表最大」的那个 gh2
if (sz > bestSize) { bestSize = sz; best = x; }
```

**问题**：宿主进程里同时活着**多个** `gh2`（每个打开过的会话一个）。
主人**当前**在看的会话消息不多，但**另一个会话消息更多** ⇒ **选错了**。

> ⚠️ 讽刺的是：这个判据当初是"实测出来的"（那次恰好当前会话消息最多），
> 就被当成了通解 —— **"样本里成立"被误当成"规律"**。

---

## 二、修法：**「最近活跃优先」**

### 核心洞察

**正在显示的那个会话，它的 `gh2` 会被 UI 持续调用**（渲染要读消息）；
后台会话不会频繁调。

⇒ **谁刚被调过，谁就是当前会话。**

### 实现

```java
/**
 * ★★★ 「最近活跃」的 gh2 —— 选会话最可信的依据
 */
private static volatile Object sRecent = null;
private static volatile long sRecentAt = 0L;
private static final long RECENT_TTL = 15000L;   // 15 秒没用过就不信它
```

**装钩子**（`GmSender.install`）里新增一条：
```java
XposedBridge.hookMethod(mNs /* gh2.W() */, new XC_MethodHook() {
    @Override protected void afterHookedMethod(MethodHookParam p) {
        Object x = p.thisObject;
        if (x != null) { sRecent = x; sRecentAt = System.currentTimeMillis(); }
    }
});
```
**开销 = 一次赋值**（零日志、零分配）⇒ 挂在 `W()` 这种高频方法上也没问题。

**发送时的选择顺序**：
```
① 最近活跃（15 秒内被调过 且 sid 非空）  ← 首选
② 兜底：实例表里「sid 非空 + 消息数最多」  ← 会打一行警告日志
```

**兜底时的警告日志**（方便主人一眼看出是不是又退化了）：
```
[发送] ⚠ 最近活跃不可用，回退到「消息数最多」的会话 —— 可能不准，请留意
```

## 四、备选加强方案（如果还错）

**用 `x42` 反查**：
- `gh2.a0()` 返回它的 `x42`
- `x42.o()` 是"取输入框状态"（**纯 UI 行为**，只有正在显示的会话才会调）
- ⇒ hook `a0()` 建立 `x42 → gh2` 映射；hook `o()` 拿到 `x42` 后反查 `gh2`
- **能 100% 锁定当前会话**，代价是多一层映射维护

（本轮先上了简单的那个，够用就不折腾。）

## 五、教训（944~945）

- **944 ⭐⭐⭐ 「样本里成立」不等于「规律」** ——
  旧判据（消息数最多）是"实测出来的"：那次恰好当前会话消息最多 ⇒ 被当成通解 ⇒ 换个场景就翻车。
  ⇒ **从观测里提炼规则时，要问一句"它凭什么是普适的"**；
  只有**能解释清楚因果**的判据（"正在显示的会话会被频繁调用"）才敢当通解。
- **945 ⭐⭐ 高频方法上挂钩子，只要"只赋值"就可以很便宜** ——
  `W()` 每秒可能被调几十次，但 `sRecent = x; sRecentAt = now;` 的开销可以忽略。
  ⇒ **不要因为"这是热路径"就放弃最准的那个观测点**，先看看能不能把钩子做成 O(1) 无分配。
