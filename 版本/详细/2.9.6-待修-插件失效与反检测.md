## 一、「插件失效」的头号嫌疑（我自己的锅）

`GmEnv.install()` 被插在 `DisableFlagSecure.handleLoadPackage` 的**最开头**：

```
:cond_24
iget-object v0, ...->classLoader
invoke-static {v0}, GmEnv;->install(Ljava/lang/ClassLoader;)V   ← 这里
const-string v1, "kf5"        ← 后面一大串模块核心 hook 注册
...
```

LSPosed 对 `handleLoadPackage` 的调用是**整体 try/catch**：
只要 `install()` 中途抛出，异常被框架吃掉，但**同一次调用里后面的代码全部不执行**
⇒ 偷换入口（`GmResTextHook`/`GmClickHook`）、`GmTouchHook`、`GmPainterHook`、`GmVectorHook`、
`GmResumeHook`、防撤回、头像…**全部不注册** → 表现就是「插件整个失效」。

### 可能在 install() 里抛的位置（按嫌疑排序）

| # | 位置 | 说明 |
|---|---|---|
| 1 | `hookShumei()` / `hookRoot()` 里的 `new-instance GmEnvHook(...)` | `h()` 里**new 实例在 try/catch 之外**；若该类 VerifyError / NoClassDefFound，异常直接窜出 |
| 2 | `toastOnce()` → `GmUtil->toast` | `Toast.makeText(...).show()` **没有 try/catch**，早期无 Looper / Context 异常会窜出 |
| 3 | `GmDiag.log(...)` | 待确认是否有文件 IO 依赖 |
| 4 | `AndroidAppHelper.currentApplication()` + `refresh()` | refresh 内部有 try/catch，嫌疑低 |

## 二、反检测无效的原因（已可判定）

- 服务端判风险，且数美 **native 侧（libsmsdk.so，字符串加密）**采集的 root 信号
  在 Java 层改不了 → 清 Java 侧信号不够
- 本轮 Java 侧清单（Xposed 探测 / `/proc/self/maps` 模块扫描 / API 监控表）**是打掉了的**，
  但那只覆盖了「模块检测」，「root」那部分大概率在 native

## 三、2.9.6 要做的修改

1. **`GmEnv.install` 整体包 try/catch**（`sInit` 标记之后全部内容），
   保证**无论任何异常都不影响 `handleLoadPackage` 后续 hook 注册**
2. `h()` 改法：`new GmEnvHook(mode)` 放进 try/catch；失败只记日志
3. `toastOnce()` / `refresh()` 各自再包一层 try/catch（双保险）
4. `GmEnv.bad()` 去掉 **`"/su"`** 这个误伤极大的子串（它会把 `/xxx/subject`、`/xxx/support` 之类
   的**正常路径**判成 root，`File.exists` 会返回 false）→ 只保留精确 su 路径 + 明确的关键字
5. 稳妥起见：`key_env_api`（系统 API 伪装）**默认改关**，总开关保持开
   —— 先确认「Java 层伪装」到底有没有用，避免它带来的副作用干扰判断
6. 新增：把 `install()` 的每一步结果写进 `GmDiag`，真机上能一眼看出卡在哪

## 四、下一步调查（需要 MCP 恢复）

1. `create_pass_code` 请求的**字段构成**（搜 `pass_code` / `create_pass_code` / 请求体字段名）
   —— 如果客户端显式上报了风险字段，就有客户端侧的抓手
2. `GmDiag` 全文（确认 log() 是否可能在早期抛）
3. 若 Java 层确认无解：走 **LSPosed 隐藏/DenyList + Shamiko**（挡 native），模块层只保留 Java 侧清理
