# 2.4.8 —— 在 MMKV 写入那一刻拦截服务端覆盖（2026-09-12）

> 解决「自定义内容/模型切换重启后被服务端下发覆盖」。

---

## 一、为什么 2.4.5 的「事后重应用」不够

2.4.5 的做法是：hook 下发应用点 `uv1.u` / `az5.h` 的 `afterHookedMethod`，
推送落地**之后**再把 MMKV 改回来。

问题：**改晚了**。App 在下发过程中已经把服务端的值写进 MMKV，
并且可能已经派生出内存状态（`Luv1.i` 的 `ConcurrentHashMap` 等）。
重启后用户看到的仍是服务端行为。

---

## 二、本体实证：找到 MMKV 的真实写入方法 ✅

用 `DeepSeek2_2.4.5.apk` 搜 `Lcom/tencent/mmkv/MMKV;->` 的调用点，得到方法名映射：

| 混淆名 | 含义 |
|---|---|
| `k()Lcom/tencent/mmkv/MMKV;` | **defaultMMKV()**（静态取默认实例 —— 与模块用的 `"k"` 一致 ✅） |
| **`p(Ljava/lang/String;Ljava/lang/String;)Z`** | **写 String** ← 关键 |
| `c(Ljava/lang/String;Z)Z` | 写 boolean |
| `m(ILjava/lang/String;)V` | 写 int |
| `n(JLjava/lang/String;)V` | 写 long |
| `u(Ljava/lang/String;)V` | remove |
| `i(Ljava/lang/String;)Ljava/lang/String;` | 读 String（无默认） |
| `j(Ljava/lang/String;Ljava/lang/String;)Ljava/lang/String;` | 读 String（带默认） |
| `contains(Ljava/lang/String;)Z` | 是否存在 |

且在 `Laz5` 里能看到正是它写下发值：

```smali
invoke-virtual {v3, v7, v6}, Lcom/tencent/mmkv/MMKV;->p(Ljava/lang/String;Ljava/lang/String;)Z
```

---

## 三、方案：写入拦截

**hook `com.tencent.mmkv.MMKV.p(String,String)Z` 的 `beforeHookedMethod`**，
在服务端值真正落盘之前把它换掉：

```
服务端推送 → Luv1.u → mmkv.p(key, serverValue)
                            ↑ 在这里替换
                        GmMmkvHook
                          ├── key == kv_remote_settings_model_configs_v1
                          │     ├── 模型切换开 → "\"switchable\":false" → true
                          │     └── 有 prompt_feature 覆盖 → patch 进去
                          └── key == kv_remote_settings_welcome_msg
                                └── 有覆盖 → 整个值替换为用户的 JSON
```

**为什么这样更彻底**：服务端的值**从未落盘**，
所以 MMKV、以及任何从 MMKV 读出来的派生状态，拿到的都是我们的值。
（`Laz5` 里大量使用 `i()/j()` 读 MMKV，说明取值路径确实走 MMKV。）

**自我写入不会打架**：模块自己写这两个键时也会经过这个 hook，
但补丁是**幂等**的（`false→true` 再替换一次不变；`patch` 同一份 user JSON 结果相同），所以无副作用。

## 四、新增 / 改动

| 类 | 说明 |
|---|---|
| **新增 `GmMmkvHook`** | `beforeHookedMethod`：只处理 `(String,String)` 两参调用，命中两个键就替换 `args[1]` |
| `GmSync` | `ensure()` 里加挂 MMKV 的 `p` 方法；新增 `ctx()`（`GmEntry.sAct` → `AndroidAppHelper.currentApplication()` 双保险） |
| `GmSync.reapplyAll` | 改用 `ctx()`，Context 来源更稳 |

> 2.4.5 的「事后重应用」**保留**，两者构成双保险。

```
changedClassCount : 14（含 1 个新增类）
classes           : 47 → 48
changedZipEntries : AndroidManifest.xml（versionCode 64, versionName 2.4.8）
```

## 七、风险 / 注意

1. **MMKV 的方法名是 R8 混淆过的单字母**（`p` = putString）。
   App 升级后如果变了，需要重新用同样的办法（搜 `Lcom/tencent/mmkv/MMKV;->` 的调用点）定位。
   → 所以日志里保留 `sync hooks ensured` 便于确认。
2. 只处理 `(String,String)` 两参调用，非 String 的写入不受影响。
3. 若 `ctx()` 拿不到 Context（极早期），本次拦截跳过，靠 `reapplyAll` 事后兜底。
4. `prompt_feature` 的补丁需要 `kv_remote_settings_model_configs_v1` 已被读到；若服务端首次推送前
   该键尚无内容，`GmPrompt.patch` 也不会出错（只是没有可替换的段落）。
