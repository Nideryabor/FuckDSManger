## 二、为什么前 8 项用「裸键」、后 3 项用「全键」

宿主的取值优先级是 **`kv_settings_<key>`（本地） → 内存缓存 → `kv_remote_settings_<key>`（下发）**。
`GmDialog.addRow` 的规则：键以 `kv_` 开头 → 原样当存储键；否则存 `kv_settings_<key>`。

| 键 | 宿主有没有 `kv_settings_*` | 模块策略 | 是否要给 hook |
|---|---|---|---|
| 7× `tts_*` | ✅ 有（`Lh02;->c..i` 先 `contains("kv_settings_tts_*")`） | **裸键** → 模块写 `kv_settings_tts_*`，天然压过下发 | ❌ 不需要 |
| `thinking_auto_fold_enabled` | ✅ 有（`Lv77;<init>` 先 `contains("kv_settings_thinking_auto_fold_enabled")`） | **裸键** | ❌ 不需要 |
| `report_http_failure_paths` | ❌ 无（`Lsg8` 直接读 `kv_remote_settings_report_http_failure_paths`） | **全键** 直写宿主键 | ✅ 必须 |
| `alert` / `banner` | ❌ 无（`Lp66;->d/e` 直接 `MMKV.k("kv_remote_settings_alert"/"_banner")`） | **全键** 直写宿主键 | ✅ 必须 |

> `tts_*` 的类型实证：`Lh02;->c..i` 里走 `MMKV.f(默认值, 键)I` / 写侧 `MMKV.n(I, 键)V` ⇒ **int**

## 三、⭐ 关键设计：为什么要影子键 `fuckds_pin_*`

**踩到的坑**：第一版 hook 直接 `read2(ctx, 同一个键, "s")` 当覆盖值 ——
用户**从没设过值**时，键里已有上一次下发写入的旧值 ⇒ **后续公告永远不再更新**（回归）。

**解法**（沿用模块自有 `fuckds_*` 约定，如 `fuckds_welcome_msg` / `fuckds_bak_`）：
- 用户 pin 存 **`fuckds_pin_<appKey>`**（由 `GmStore.write/remove` 自动镜像）
- hook 只读影子键：**没 pin ⇒ 空 ⇒ `GmPrompt.ok()` false ⇒ 下发照常落地** ✅
- 有 pin ⇒ 把下发的值替换掉 ✅
- 清空输入框 ⇒ `save()` → `GmStore.remove(appKey)` → 同时删影子键 ⇒ 恢复下发 ✅

**另一条“能不能自锁”的实证**（重要，写下来省得下次再查）：
```
q(String key, String value)Z  →  private native encodeString(handle, key, value)   ← 下发/服务端路径，args[0]=键
putString(String, String)     →  private native encodeString                       ← Editor 路径，模块写值走这条
putInt(String, I)             →  private native encodeInt                          ← 同上
apply() / commit()            →  sync()（纯 native）
```
⇒ **模块自己写值走 `putString/putInt`，根本不经过被 hook 的 `q`** ⇒ 不会出现「hook 把刚写的值替换回旧值」的自锁。

## 七、2.9.2 —— 修 VerifyError（真机一装就崩，2026-09-12）

### 现象（LSPosed 日志）

```
java.lang.VerifyError: Verifier rejected class com.varuns2002.disable_flag_secure.gm.GmStore:
  void GmStore.remove(android.content.Context, java.lang.String) failed to verify:
  [0x2B] register v2 has type Precise Reference: java.lang.String
         but expected Reference: android.content.Context
  at GmPrompt.get → GmPrompt.reapply → GmSync.reapplyAll → GmResumeHook.afterHookedMethod
```

⇒ 只要 App 一 `onResume`（`GmResumeHook` → `reapplyAll`）就 **FATAL**。
**整个类校验失败**，所以看起来是 `GmPrompt` 崩，实际坏的是 `GmStore`。

### 根因：寄存器压参（经典坑）

- `GmStore.remove` 声明是 **`.registers 4` + 2 个参数** ⇒ 局部寄存器只有 **v0、v1**，
  **`p0 = v2`（Context）**、`p1 = v3`
- 我插的影子键代码写了 `const-string v2, "fuckds_pin_"` ⇒ **把 `p0`（Context）覆盖成了 String**
- 紧接着 `invoke-static {p0, v1}, GmStore->remove(Context,String)V` 传进去的 v2 已是 String
  ⇒ 字节码校验器直接拒绝整个类

### 修法

该块的临时寄存器改用 **v0 / v1**（v0 在 `apply()` 之后已死，安全复用），`p0`（v2）保持不动。
版本号 `88/2.9.1` → **`89/2.9.2`**，产物 `FuckDSManger_2.9.2_for_ds2.5.1.apk`。

### 同一轮把 4 个改动方法的寄存器预算全算了一遍

| 方法 | `.registers` | 参数个数 | `p0` 落在 | 本次用到的寄存器 | 结论 |
|---|---|---|---|---|---|
| `GmDialog.<clinit>` | 6 | 0 | — | v4, v5 | ✅ |
| `GmMmkvHook.beforeHookedMethod` | 12 | 1 | v11 | v0, v2, v5, v6, v7 | ✅ |
| `GmStore.write` | 7 | 4 | v3 | v1, v2（局部上限 v2） | ✅ |
| `GmStore.remove` | 4 | 2 | **v2** | 原 v1,v2 → 改 **v0,v1** | 🔴 → ✅ |

### ⚠️ 教训（写进肌肉记忆）

1. **`edit_check(runBuildChecks=true)` 只保证「能合并成 dex」，不做字节码校验** ——
   它会放过 VerifyError。**产物必须回读 smali 人工复核**（本次就是这么抓到的）。
2. 插 smali 前先算：**局部寄存器上限 = `.registers − 参数个数`**，
   临时变量**只能用 `< 上限`** 的寄存器；参数寄存器一律不碰。
   （`.registers 4` + 2 参这种小方法最危险 —— 只剩 2 个局部寄存器可用。）
3. 崩溃日志里「类 X 的方法 Y 校验失败」要按 **Y 所在类** 去修，别被上层调用栈（`GmPrompt`）带偏。
