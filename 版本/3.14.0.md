## 一、为什么非改不可

现役宿主 2.5.2 的**清单包名是 `com.deepseek.chat.a`**，而它**自己的类名**是 `com.deepseek.chat.*`。
我们到处写的 `startsWith("com.deepseek.chat")` **只是恰巧为真**。

真出事那天长这样：

```
底座 GmEntry 的总闸 packageName.startsWith("com.deepseek.chat") 不通过
  ⇒ return-void
  ⇒ 51 条钩子一条都不注册
  ⇒ 而且总闸在日志之前 ⇒ 【静默全灭】，logcat 一片空白
```

⇒ 判据必须从 **「它叫什么」** 改成 **「它在不在 / 它调没调我」**。

## 二、底座重建（2.22.120 → 2.22.121）

底座是 128 类二进制成品，这次必须动。走了**可 diff、可复核**的本地流水线：

```
baksmali classes.dex → tmp/base120/sm
  ├─ ① hookPickAll 起点   "com.deepseek.chat.MainActivity" → "android.app.Activity"
  ├─ ② 总闸 .line 36      startsWith(包名) → 锚点探针 findClass("kf5"/"uia")
  ├─ ③ onResume 落点      "com.deepseek.chat.MainActivity" → "android.app.Activity"
  └─ ④ 日志文案           "hooked MainActivity.onResume OK" → "hooked Activity.onResume OK"
smali assemble --api 26 → classes121.dex（197 184 B，+36 B）
```

### 2.1 为什么敢换框架类（先验证据，不是拍的）

| 问题 | 实测答案 |
|---|---|
| 宿主 `MainActivity` 自己声明了 `onResume` 吗？ | ✅ 声明了（10 个方法：`<init>/onConfigurationChanged/onCreate/onNewIntent/onResume/r/s/t`） |
| 它声明了 `onActivityResult` 吗？ | ❌ **没有** ⇒ 今天真正生效的就是"从 MainActivity 往上爬到框架 `Activity`"那条路 ⇒ **换成直接挂框架类是零损失** |
| `GmResumeHook` 认不认 MainActivity？ | ❌ 不认。它只做 `thisObject as Activity` → `setAct` + 环境/设备/头像/同步维护，**天生与名字无关** |
| `GmPickHook` 会不会误伤别的 Activity？ | ❌ 不会。它**只认 `requestCode == 0x435b`**，自带过滤 |
| 底座自己用没用过框架类落点？ | ✅ `GmResumeHook.ensurePick` 早就在挂 `android.app.Activity.onActivityResult` ⇒ 这是**回归它本来的写法** |

### 2.2 新总闸（名字无关）

```smali
.line 36
:try_start_g1
const-string v1, "kf5"          ← 宿主自己的混淆类（本来就是底座第一梯队挂的锚）
... findClass(kf5) 成功 ⇒ 是宿主，goto 继续
.catchall ⇒ 试下一个锚点

```

**顺带修好了"静默"**：万一两个锚点都不在，现在会**留下一行日志**（以前是无声无息全灭）。

## 三、桥侧（真编译，4 个文件）

| 文件 | 改动 |
|---|---|
| `FdmEntry.java` | 删掉 `HOST` 常量与 `startsWith` 门；改用 **锚点探针** `isHost(cl)`（`kf5`/`uia`/`fh6`）；探桥落点从 `com.deepseek.chat.MainActivity.onCreate` 换成 **`android.app.Application.onCreate`**（名字永不变，且**只跑一次**拿 Context 更早更省），失败退 `android.app.Activity.onCreate` |
| `ConfigProvider.java` | 删掉 `HOST_PREFIX` 白名单；改 **token + uid 握手**：UI 生成随机 token → 随广播给 hook 层 → hook 层回带；**认下第一个用对 token 的 uid 后只认它** |
| `FdmPush.java` | 推送时带上 `bridge_token`（`ensureToken()` 没有就现造） |
| `FdmBridge.java` | 接下令牌（`sToken`），调 provider（`heartbeat` / `getConfig`）时带回去 |

## 四、新增出包自检 ⑫（让铁律不靠记性）

`pipeline/build_single.py`：

```
⑫.1 自身包名     : MODULE_PKG 必须 == 脚本里的 PKG
⑫  宿主包名依赖  : 底座 dex + 桥 dex 里出现 com.deepseek.chat / com/deepseek/chat ⇒ 拒绝出包
```

**为什么扫 dex 不扫源码**：源码注释里还留着"旧写法是 `startsWith("com.deepseek.chat")`"
这种**历史说明**（该留），扫源码必然误报；**dex 里有这个串才是真的写进了字节码**。

## 五、⚠️ 行为变化（真机要盯的三点）

| # | 变化 | 为什么是安全的 | 要观察什么 |
|---|---|---|---|
| 1 | `onResume` 从"只有 MainActivity"变成**每个 Activity** | `GmResumeHook` 的活（`setAct` + 维护）本来就是幂等的；而且**只有框架 `Activity.onResume` 被调**才触发（宿主 override 时通常都会 `super`） | 有没有**重复弹窗 / 卡顿**（维护多跑了几次） |
| 2 | `onActivityResult` 变成框架类 | `GmPickHook` 只认 `requestCode == 0x435b` | 选图/拍照回执照旧能用 |
| 3 | provider 在**令牌到手之前**会被拒 | 广播才是主通道；令牌在 UI 推第一次配置时就到了 | 日志里会看到 `（还没拿到令牌 ⇒ provider 会拒；等 UI 推一次配置就会补上）`，属**正常** |

## 七、这一版记住的事

- **判据要判"东西在不在"，不要判"它叫什么"。** 名字会变，存在性不会。
- **"静默失败"比"报错失败"贵一百倍。** 总闸原先是**没有日志**的 return-void；这次顺手给它装了一行。
- **二进制成品的改动，必须走"可 diff 的流水线"。** baksmali → 文本改 → smali → **反编译回来跟原始 diff**，
  只允许出现意料之中的那几行；再核对 types/methods/classes 三个计数不变。
- **自检要扫产物，不要扫源码** —— 源码里有正当的历史注释，产物里才是真相。
