> ```
> call l / call t / call k / call G / call D / call A / call d    ← 第 1 条
> call l / call t / call k / call G / call D / call A / call d    ← 第 2 条

---

## 一、结论一：**方法名没问题**

七次调用全部成立 ⇒ `pick()` 每次都成功 `getMethod` + `invoke` ⇒ **这些方法在 `vq` 上都存在、都能调**。

**⇒ 病不在"找方法"，而在"这些方法本身不产出正文"**（都返回 null/空 ⇒ `pick` 静默返回 null ⇒ 无异常、无日志 —— 完全符合现象）。

## 二、结论二：`vq.l()` **不是渲染路径**

查了 `Lvq;->l()` 的全部调用点 —— **整个宿主只有 3 处**：

| 调用者 |
|---|
| `Lu30;->v()` |
| `Lxg1;->e(Lrg1; Lif2;)`（×2 处指令） |

**⇒ 渲染消息列表时**根本不走它** ⇒ 我选的这一串方法（`l/t/k/G/D/A/d`）是"**业务侧**"的方法，`C()`/`r()` 这类 final 方法则是它们的内部辅助。**

**⇒ 真正的"UI 取文本"入口，一定是**渲染层（`h91.a` / `e91` / layout 那一片）**调用的某个方法 —— 我还没找到它。**

## 三、本版：日志带类名

`pick()` 的日志格式改为：

```
call l @<元素类名>
```

**⇒ 一次同时拿到"方法名 + 元素真实类"** ⇒ 我就能：
1. 定位这是哪个 `vq` 子类（用户消息 / AI 回复 / 文件 / 思考块 …）
2. 去反编译那个子类 + 它的渲染路径，**找到真正产出正文的方法**

## 五、教训

| # | 教训 |
|---|---|
| **451** | ⭐⭐⭐ **"方法存在且被调用、但返回空" ⇒ 立刻去查它的调用者**：`xref` 一出就知道 `l()` 只有 3 个调用点 ⇒ **立刻排除它是主路径**，省掉继续试方法名的弯路 |
| **452** | ⭐⭐⭐ **类名是最值钱的一个词**：有了元素真实类名，就能顺着它去找 UI 渲染路径；没有它，只能在"可能的几十个方法"里穷举 |
| **453** | ⭐⭐ **"全部方法都返回空"往往是**对象不对**的强信号**：一个正常的消息对象不至于七个取文本方法全空 ⇒ 要么对象类型特殊，要么文本根本不从这些方法出 |
