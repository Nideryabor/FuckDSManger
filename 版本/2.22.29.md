## 0. 主人回执与一句话结论

> 「一打开我们的模块就发现了三个问题：① AI 生成的文字区域标题阴影没去 ② 文字底部图片会随着 AI 生成内容增加无限放大 ③ 底部图片不能自定义透明度」

三条**全部成立**，而且三条**根因完全不在同一个地方** —— 分别是「宿主阴影层没碰过」「我们自己的 cover 公式」「宿主把 alpha 焊死了」。

| # | 现象 | 真根因 | 修法 |
|---|---|---|---|
| ① | 标题阴影还在 | 2.21.10 只把「已思考」小卡的**底色**刷透明，**阴影从来没动过**；「深色底是阴影消音器」一旦换成彩色图片底就失效 | 新 `GmShadowHook` 挂宿主 **`jd8`**（`ShadowGraphicsLayerElement`）的构造器，作用域内 `elevation = 0f` |
| ② | 图片随内容无限放大 | 2.22.23 用的是 **cover**（`s = max(w/bw, h/bh)`），而**气泡高度 h 会随 AI 内容一路长高** ⇒ `s` 无限增大 | `max` 之后再套一层 **`min(…, 最大放大倍数)`** 闸门 ⇒ 到顶后不再放大，超额部分由 `CLAMP` 自动用**图片边缘色**填 |
| ③ | 透明度调不了 | 宿主 `se0`（`BackgroundElement`）的构造器把 **`c:F`（alpha）硬编码成 `1.0f`**，`uia.u(...)` 的第 4 参是**默认参数掩码**不是 alpha ⇒ **宿主根本没留入口** | 新 `GmAlphaHook` 挂 `se0.<init>` 之后 + `se0.c(Lb76;)V` 之前，把 `c` 字段改成配置值 |

## 1. 三条根因的完整链路（证据）

### ① 阴影：`jd8` = `ShadowGraphicsLayerElement`

2.21.10 的处置是「**把项内小卡的底色刷透明 + 借深色底藏阴影**」—— 文档里那句
> 「阴影落在深色卡上几乎不可见」

说得非常准确：**它是被藏起来的，不是被去掉的**。主人一换图片底，消音器没了，阴影立刻现形。

**怎么找到 `jd8` 的**（本版最值钱的一招）：
Compose 的 `Modifier.shadow` 形态是 `fun Modifier.shadow(elevation, shape, clip, ambientColor, spotColor)`（**非 inline**）⇒ R8 会保留它的**调用者函数体和 `new ShadowGraphicsLayerElement`**；
而 Kotlin 给这种 `ModifierNodeElement` 自动生成的 `toString()` 里**带原始类名字符串**：

```
const-string v1, "ShadowGraphicsLayerElement(elevation="      ← 在 Ljd8; 里
```

⇒ 一次 `search smali "shadow"` 就命中了。
```smali
.class public final Ljd8;          # ShadowGraphicsLayerElement
.field a:F      # elevation
.field b:Lmd8;  # shape
.field c:Z      # clip
.field d:J      # ambientColor
.field e:J      # spotColor
.method public constructor <init>(FLmd8;ZJJ)V
```
**`xref` 反查构造器 ⇒ 恰好 2 个调用点**（`Lwe5;->E(...)` = `Modifier.shadow` 的公开重载 · `Lgh6;->c(...)`），**没有第 3 个** ⇒ hook 构造器 = 覆盖全 App 所有 `Modifier.shadow`，再用作用域一收就只剩助手气泡。

### ② 放大：cover 的基准是「内容尺寸」

```smali
div-float v10, v6, v8      # w / bw
div-float v11, v7, v9      # h / bh
invoke-static {v10, v11}, Ljava/lang/Math;->max(FF)F
```
`max` 的语义是「**哪一维更缺就放大哪一维**」。短消息时气泡矮、`w/bw` 主导；**内容一长，`h/bh` 迅速反超并持续增大** ⇒ 图被越放越大、裁得越来越狠。

**修法（主人拍板 C 案）**：保留 cover 的观感，但**加一个可调的放大上限**：
```smali
invoke-static {}, GmBubble;->zoomF()F          # 新增：最大放大倍数（默认 2.0x）
move-result v14
invoke-static {v10, v14}, Ljava/lang/Math;->min(FF)F
move-result v10                                 # s = min(cover, 上限)
```
到顶之后 `bw*s < w`（或 `bh*s < h`），`postTranslate` 的居中补偿仍然正确，**剩下的区域由 `TileMode.CLAMP` 自动拿图片最外一行/列像素填充** —— 这就是主人要的「**到顶后使用图片边缘色**」，**一行都不用额外写**。

### ③ 透明度：宿主自己把 alpha 焊死了

```smali
# Lse0;-><init>(JLsn0;Lmd8;I)V
and-int/lit8 v0, p5, 0x1
if-eqz v0, :cond_6
sget-wide p1, Lq32;->h:J          # flags&1 ⇒ color = Color.Unspecified
:cond_6
and-int/lit8 p5, p5, 0x2
if-eqz p5, :cond_b
const/4 p3, 0x0                   # flags&2 ⇒ brush = null
:cond_b
iput-wide p1, p0, Lse0;->a:J
iput-object p3, p0, Lse0;->b:Lsn0;
const/high16 p1, 0x3f800000       # ★ 1.0f —— 写死的
iput p1, p0, Lse0;->c:F           # ★ alpha 永远 1.0f
iput-object p4, p0, Lse0;->d:Lmd8;
```
再看调用方：
```smali
# Luia;->u(Lc76;Lsn0;Lmd8;I)Lc76;
and-int/lit8 p3, p3, 0x2
if-eqz p3, :cond_6
sget-object p2, Lzc;->o:Lc84     # flags&2 ⇒ shape = RectangleShape
:cond_6
const/4 v5, 0x1                   # ← 我们一直传的是这个位置：flags
invoke-direct/range {v0 .. v5}, Lse0;-><init>(JLsn0;Lmd8;I)V
```
⇒ **第 4 参是「默认参数掩码」，`se0.c` 是真 alpha 且被常量写死**。宿主没留门，我们只能**自己开一扇**：
hook `se0.<init>` 的 `afterHookedMethod`（element 刚构造完、`b` 已赋值）+ `se0.c(Lb76;)V` 的 `beforeHookedMethod`（每次 element 更新），判据是**只有我们有的类型**：

```
getObjectField(thisObject, "b") instanceof GmBmpShader   ⇒  setFloatField(thisObject, "c", alphaF())
```
`GmBmpShader`（2.22.23 建的 `BitmapShader` 子类）在这里**第二次派上用场**：它同时是「我们的图刷」的**唯一身份牌**，零宿主混淆名依赖。

## 4. 教训（776~782）

| # | 内容 |
|---|---|
| **776** | ⭐⭐⭐ **`toString()` 里的类名字符串是 R8 打死也留着的路标**：Kotlin 给 `ModifierNodeElement` 自动生成的 `toString()` 会带上**原始类名**（`"ShadowGraphicsLayerElement(elevation="`）。**找混淆后的 framework 元素类时，先 `search smali` 类的"人话名"** —— 比按字段形状一个个猜快一个数量级（`jd8` 一次命中）。 |
| **777** | ⭐⭐⭐ **「藏起来」≠「去掉了」**：2.21.10 让阴影「落在深色卡上几乎不可见」，这是**借宿主的颜色规则消音**；一旦我们自己改变了底色（图片底），消音条件就消失。**任何依赖"对比度低所以看不见"的处置都必须在文档里标成"未解决"**，否则它迟早以「明明修过怎么又来了」的形式回来。 |
| **778** | ⭐⭐⭐ **cover 的缩放基准如果取"内容尺寸"，就会随内容无限增长**：`max(w/bw, h/bh)` 在「高度 = 内容高度」的场景下天然发散。**凡是把"尺寸相关量"喂给"视觉参数"的算子，都要先问一句「这个尺寸会不会被用户内容一直撑大」** ⇒ 要么换基准（`min`/按宽），要么加**可调上限**。 |
| **779** | ⭐⭐⭐ **给"参数被写死"的宿主类型开门的通用姿势 = hook 构造器 + hook 更新方法**：`se0` 的 alpha 只在 `<init>` 里被写成 `1.0f`，那就在 `<init>` 的 `afterHookedMethod` 覆写它；同时挂 `c(Lb76;)V` 的 `beforeHookedMethod` 覆盖「element 被复用时的 update 路径」。**两处都挂 = 创建/更新两条路都堵死**，不用赌 Compose 走哪条。 |
| **780** | ⭐⭐ **同一个自建类型可以反复当"身份牌"**：`GmBmpShader` 在 2.22.23 用来标记「我们的图刷」，本版又用它当 `se0.b` 的判据 —— **子类化框架类（`BitmapShader`）得到的是零宿主依赖、不可能撞车的标记**。新建诊断/过滤点时优先复用它，别再造新标记。 |
| **781** | ⭐⭐ **"到顶之后怎么办"往往不需要写**：`BitmapShader` + `TileMode.CLAMP` 天然就是「超出部分拿最后一行/列像素拉伸」。把缩放**封顶**之后，"图片边缘色填充"是**免费送**的 —— **先看平台原语能不能白捡这个行为，再考虑手写**。 |
| **782** | ⭐ **改宿主元素类的**`final`**字段在运行时可写**：`se0.c` 是 `public final float`，但 DEX 的 final 只约束编译期；`XposedHelpers.setFloatField`（内部 `setAccessible(true)`）能改**实例** final 字段（`static final` 才会被内联/拒绝）。**"它是 final 所以我改不了"是个假障碍。** |

## 5. 遗留 / 后续可选

1. **透明度的「立即生效」**：本版靠宿主下次重组（划列表 / 来新消息）刷新。若主人希望点一下当场变，需要额外触发一次重组（hook 里 `invalidate` 拿不到 Compose 的 recomposer，成本较高）—— 先看真机手感再定。
2. **阴影是否要"可选"**：本版是**作用域内一律归零**。若将来想保留头像那一层的立体感，可再拆细（按 `jd8.b`（shape）或 elevation 阈值区分）。
3. **图片「铺法」升级**：`GmBubbleFitHook` 现在同时有 `min` 闸门与 `max` cover；若想要 contain/按宽，只需把 `Math.max` 换 `Math.min`（但会与上限闸门语义重叠，需要重新设计 UI）。
