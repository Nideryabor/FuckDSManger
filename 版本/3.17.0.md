## 二、改了什么（桥，两处）

**① `syncPins` 变成"可重试"**

```java
private static volatile boolean sPinsSynced = false;   // 幂等标记

private static boolean syncPins(Context ctx) {
    if (sPinsSynced) return true;
    SharedPreferences sp = GmStore.get(ctx);
    if (sp == null) {                                  // ★ 新增：宿主存储还没就绪
        log("pin 表同步：宿主存储还没就绪（MMKV 未初始化）⇒ 稍后重试");
        return false;                                  // ★ 不再对着 null 调 getAll()（那是 NPE 的来源）
    }
    …灌表…
    sPinsSynced = true; return true;
}
```

**② 周期任务改成"两件事一起推"**

原来那个"每 4 秒索要配置、最多 30 次"的定时器，现在**每次都顺手推进一次 pin 表同步**，
并且**两件事都完成才收摊**：

```
run():
    pinsOk = syncPins(ctx)              ← 宿主 MMKV 迟早会初始化好
    if (pinsOk && sGotConfig) 收摊
    if (已试 30 次) 收摊（日志会打出"配置=? · pin 表=?"，方便定位是谁没成）
    sendBroadcast(ACTION_REQ)           ← 继续索要配置
    再排 4 秒
```

⇒ 两个"宿主启动早期的时序问题"共用**同一个重试窗口**（4 秒 × 30 = 2 分钟），够了。

| `pin 表同步：宿主存储还没就绪 ⇒ 稍后重试` | 第一次必然出现（宿主 MMKV 还没初始化）—— **正常** |

| `配置已到手 · pin 表已同步 ⇒ 停止周期任务` | 周期任务圆满收摊 |
| **`[mmkv] pin 命中（读时替换）`** | ✅✅ **第三次该有了** |

## 五、这一连串失败里，值得留下的东西

| # | 教训 |
|---|---|
| 1 | **"宿主调哪个方法"必须从字节码抄，不能从签名猜**（3.15.0：猜了 2 参 `k`，实际是 1 参 `j`） |
| 2 | **写进去了 ≠ 有人读**（3.15.0 之前：影子键写满存储，全底座没人读） |
| 3 | **"表注册成功" ≠ "表里有货"**（3.16.0：`setPins` 成功，但同步那步 NPE ⇒ 空表） |
| 4 | **宿主启动是有时序的**：`Application.onCreate` 之后 **不等于** 存储已就绪（`MMKV.initialize()` 更晚）⇒ 凡是要读宿主存储的初始化动作，都该**放在重试窗口里**，并**能容忍 null** |
| 5 | 每一步都用**日志证据**定位，而不是"再猜一版"——这三轮每轮都缩小了范围，没有一步是白走的 |
