## 一、★ 手势分工：**点**是个状态，**拖**是个状态，**跳页**是第三个 —— 别让它们互相抢

一张卡上压着三种意图，最容易写成一团。这版的分工：

```
Row ─┬─ Column(weight=1f)  ← 标题 + 说明（点它 ⇒ 展开）
     └─ IconButton(▸)      ← 子节点自己吃掉点击 ⇒ 不会连带展开（也不会连带拖动）
```

而拖动**不是**加在某个把手上的，是加在整张卡上：

```kotlin
.clickable { onToggle() }                       // ① 点击
.pointerInput(id) { detectDragGestures(...) }   // ② 拖动（写在 clickable **后面**）
```

**★ 顺序是有讲究的**：修饰符链里**越靠后 = 越内层**，而内层**先拿到事件** ——

* 手指**超过 touch slop** ⇒ 拖动检测 consume ⇒ 点击**自动作废**（不会"拖完还展开一下"）
* 手指**几乎没动**就抬起 ⇒ 拖动检测**不 consume** ⇒ 点击照常生效

⇒ 两个手势不打架，**不需要**给卡片单独做一个"拖动把手"。
（对照 3.51.0 的悬浮便签：那次**必须**做把手，因为拖的地方是**整条顶栏**、按钮又压在顶栏里；
这次的卡片只有一个小图标钮，靠"内层先拿事件"就分得开。）

## 二、★ 跨容器拖拽：根坐标系 + 幽灵层 + 矩形撞击

「从抽屉拖到容器」难在**两个容器不在同一层**（抽屉是叠在内容上的 `Box`，还会自己上下滑）。
如果去算"抽屉里的坐标 → 容器里的坐标"，会陷进一堆相对换算（还要跟抽屉的偏移联动）。

⇒ 换一个坐标系：**全部用根坐标（`boundsInRoot()` / `positionInRoot()`）**。

| 环节 | 做法 |
|---|---|
| 记投放区 | 容器 / 抽屉内容各自 `onGloballyPositioned { rect = it.boundsInRoot() }` |
| 记卡片 | 每张卡同样记 `bounds`（用于排序）+ `origins`（左上角，用于把手指位置换成根坐标） |
| 拖动中 | 页面根节点上画一张**幽灵卡**跟着手指（`zIndex(10f)`）—— 被拖的那张**原地不动** |
| 手指位置 | `手指根坐标 = 卡片原点(根坐标) + change.position(卡内坐标)` |
| 松手 | 拿手指的**根坐标**去撞两个矩形：容器？抽屉？都不是？⇒ **不动** |
| 排序 | `插入下标 = 同列表里"中心在我上面"的卡片数` ⇒ 拖拽排序顺手就有了 |

**为什么"被拖的那张不动"**：卡片一移动，它的 `origins` / `bounds` 就会变，
而这两个值正是换算手指位置的基准 ⇒ **基准一动，坐标就漂**。
让本体原地不动、只让幽灵走，基准就是稳的。

> ⚠️ 一个必须知道的边界：**幽灵卡是用"被拖卡片当时的原点"换算的**。
> 也就是说拖动期间**不能让这个列表滚动**（滚了原点就过时）。
> 这版卡片最多三张、抽屉半屏放得下 ⇒ 抽屉内容**故意不做滚动**（要做的话，
> 得改成记 `LayoutCoordinates` 并在滚动时重算，另说）。

## 三、落盘：**手动**保存（这是个设计选择，不是偷懒）

* 键：`cfg.sysprompt_v2_layout`，存在**我们自己的** SharedPreferences（`FdmPush.sp`）⇒ **不推给宿主**
* 值：`{"drawer":[…],"box":[…],"expanded":[…]}`（`org.json`，Android 自带，零依赖）
* **写盘只在点 💾 时发生**；拖动过程中不写
* 进页面读一次；坏数据（JSON 坏了 / 认不出的卡片 id）**一律当没存过**，不把页面卡死
* **谁都没提到的卡片补回抽屉** —— 以后加新卡片（比如 `sysprompt` 本体）不会凭空消失

> **为什么坚持手动**：拖拽这类操作"手一抖就落盘"的体验很糟 ——
> 主人看到的东西**被自动记住了**，而他要的是"我摆好了，你记住"。
> **保存是一个动作，不该是一个副作用。**

## 四、搭出来的顺带效果：内容区跟着抽屉让位

抽屉拉开时，内容区（容器）会**跟着变矮**：

```kotlin
Column(Modifier.padding(bottom = (handlePx + live).toDp()))   // live = 抽屉拉起来多少
```

* 收着的时候：容器占满，只是底部给把手留了 28dp
* 拉开的时候：容器**刚好在抽屉上沿收住** ⇒ ① 不会被抽屉盖住半截
  ② **投放区（`boxRect`）真实变小** ⇒ "拖到容器里"的判定跟**看得见**的区域一致

## 八、教训

**995 · ⭐⭐⭐ 同一块区域上的多个手势，靠「层级顺序」分工，不靠「抢」。**
　　`clickable` 在前、`pointerInput` 在后 ⇒ 拖动在**内层**、先拿事件、超过 slop 就 consume
　　⇒ 点击**自动作废**；而点击不动时拖动不 consume ⇒ 点击照常。
　　（3.51.0 必须做"拖动把手"是因为按钮压在整条可拖区里；**这次不用** —— 
　　　先看清"谁在谁里面"，再决定要不要额外做把手。）

**996 · ⭐⭐⭐ 跨容器拖拽，先统一坐标系，再谈判定。**
　　把"抽屉里的坐标换算到容器"这条路**整条掐掉**，改成"所有东西都记根坐标 + 幽灵层跟手指"
　　⇒ 没有一处相对换算，也没有"抽屉滑动了导致偏移对不上"的连带 bug。
　　★ 附带一条：**被拖的那张必须原地不动** —— 它就是换算基准，动了坐标就漂。

**997 · ⭐⭐⭐ 一个 unresolved，会伪装成一串「这个库里没这个方法」。**
　　这轮的报错长这样：`optJSONArray` 不认识 · `类型推断失败` · `boundsInRoot 不在 LayoutCoordinates 上`……
　　真凶只有两个：**① 漏了 `import …bridge.FdmPush`**（它一倒，后面 `JSONObject(s)` 全成 error，
　　　于是"库方法不存在"其实是"接收者类型是错的"）
　　**② `boundsInRoot` / `positionInRoot` 是扩展函数**（`androidx.compose.ui.layout` 下的），
　　　**必须显式 import** —— 它们不是 `LayoutCoordinates` 的成员，光有类名不够。
　　⇒ **读编译错误要挑"最根上的那一条"下手**，别看数量。（`javap` 一验就知道库里到底有没有那个方法。）

**998 · ⭐⭐ 「保存」是动作，不是副作用。**
　　拖拽布局这种东西如果**自动落盘**，手一抖就被记住 —— 用户想要的是"我摆好了，你记住"。
　　⇒ 工具栏上放个 💾，**点了才写**；拖动过程零写入。
　　（并留一条：坏数据/陌生 id **一律当没存过**，别让一个坏 JSON 把页面卡死。）

**999 · ⭐⭐ 投放判定要能"什么都不做"。**
　　「落在容器」和「落在抽屉」之外，还必须有**第三种结果：什么都不发生（原地不动）**。
　　⇒ 判据穷举要写全（A / B / 其它），否则"拖到屏幕中间松手"就成了不可预期的行为。
