## 0. 一句话

```

    java.lang.String GmSuggestAi.dbSid() failed to verify:
```

只是以前这条堆栈**只在 logcat 里一闪而过**（`logE` 不落盘、`logFail` 又把它压成一行）。

## 1. 根因：两层，都是 `dbSid()` 的「汇合点」问题

```smali
    if-eqz v2, :cond_7a        # listFiles() 为 null ⇒ 直接跳到汇合点
    array-length v3, v2        # ┐ v3 只在「非 null」这条路径上才诞生
    const/4 v4, 0x0            # ┘ v4 同上
    :goto_44 …
    :cond_7a
    :goto_7a
    … "END v4=" + v4 + " v3=" + v3 …     # ← 汇合点之后却要用它们
```

| 层 | 寄存器 | 问题 |
|---|---|---|
| **1** | `v4` | 「null 路径」上**从未写过** ⇒ `append(I)` 读它 ⇒ **Undefined**（真机报的就是这条） |
| **2** | `v3` | null 路径上是 `const-string v3, "/databases"`（**String**），非 null 路径上是 `array-length`（**Integer**）⇒ 汇合点 **类型冲突** |

> ⚠️ **关键细节（容易搞反）**：`const/4 vX, 0x0` 在 Android verifier 里是特殊的 **Zero 类型** ——
> 它**既能 merge 成 int、也能 merge 成 null 引用**。所以「给返回值 `v0` 预置 `const/4 v0, 0x0`」是**合法**的；
> 而 `String` ↔ `int` 才是**真冲突**。这决定了修法不能简单地在入口补一个 `const/4 v3, 0x0`。

---

## 2. 修法（3 处，全在 `dbSid`）

| # | 位置 | 改动 | 治的是 |
|---|---|---|---|
| 1 | 方法入口（`:try_start_1` 之前） | 加 `const/4 v4, 0x0`、`const/4 v11, 0x0` | 层 1（v4）+ 给「数量」一支**专用**寄存器 |
| 2 | `array-length v3, v2` 之后 | 加 `move v11, v3` | 让 v11 承接「数组长度」（int 语境） |
| 3 | `END …` 日志 | `append(v3)` → **`append(v11)`** | 层 2：**让 `v3` 不再被跨分支使用**，冲突随之消失 |

⇒ `v4` / `v11` 在**所有路径**上都是 int ✓；`v3` 虽然仍是 Conflict 类型，但**无人使用** ⇒ verifier 不再报错。
（日志文案保持 `END v4=… v3=…` 不变，值也仍然正确，只是取值的寄存器换了。）

**`.registers 12` 未改动**（v11 本来就在可用范围内）。

## 5. 新增工具：`tools/vercheck.pl`（迷你 verifier）

MT 的 `edit_check` **不做字节码校验**（铁律 6），手写 smali 的 VerifyError 只有真机才炸。
本版顺手写了个小工具补这一刀：输入 `mt_apk_read_text` 抓下来的 class JSON，输出「未初始化 / 类型冲突」的使用点。

**它在本版双命中**（注意过程：第一版只抓到 `v4`，升级「类型跟踪」后才抓到 `v3`）：

```
❌ 发现 2 处隐患：
  [.method static dbSid()Ljava/lang/String;] #66  invoke-virtual {v9, v4}, …append(I)
        ↳ 寄存器 v4：未初始化（Undefined）
  [.method static dbSid()Ljava/lang/String;] #69  invoke-virtual {v9, v3}, …append(I)
        ↳ 寄存器 v3：分支合并后类型冲突（两条路径写成了不同类型）
```

修完后：

```
✅ 未发现未初始化 / 类型冲突隐患
```

- **用法**：`perl tools/vercheck.pl /tool_outputs/<抓下来的类>.txt`
- **原理**：CFG + 前向数据流；类型只分「int 家族 / 对象家族 / Zero / long」两档；合并用 **交集**（verifier 语义）
- **局限（有意保守）**：不进入 catch handler；参数寄存器恒视为已定义；不做精确类层次

## 7. 教训（762~767）

| # | 教训 |
|---|---|
| 762 | ⭐⭐⭐ **「整类被否决」= 一次连坐好几个 hook**：verifier 是**类级**的 —— 一个方法有问题，`Class.forName` 就失败，所有以它为 hook 类的注册点全灭（本项目第一次把这条看全） |
| 763 | ⭐⭐⭐ **`const/4 vX, 0x0` 是 Zero 类型，不是 int**：它既能 merge 成 int 也能 merge 成 null 引用 ⇒ 「给返回值预置 0」合法；但 `String` ↔ `int` 是真冲突 ⇒ **别用「补一个 0」的套路去治类型冲突** |
| 764 | ⭐⭐⭐ **寄存器复用是类型冲突的温床**：`v3` 先当 `const-string` 再当 `array-length`，只要有一条路径把两者汇合后继续用就炸 ⇒ **跨分支传递的值要用专用寄存器**（本次 v11） |
| 765 | ⭐⭐ **诊断日志最容易引入 verifier 错误**：`END v4=/v3=` 这段日志**本身就是炸弹**（想打印循环变量，却没考虑「循环根本没进」的路径） |
| 766 | ⭐⭐ **「等不到读数」要先怀疑「方法根本没装载」**：2.12.9 那条待办绕了很久，根子是类被否决 |
| 767 | ⭐⭐ **MT 的 build 检查不含字节码校验** ⇒ **必须自备 verifier**（本次产物：`tools/vercheck.pl`） |
