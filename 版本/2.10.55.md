## 一、从主人给的日志里读出的关键事实

```
1789792933810 [mmkv] 命中 model_configs 键，评估 switchable
1789792934284 [mmkv] 命中 model_configs 键，评估 switchable
1789792934285 [mmkv] 命中 model_configs 键，评估 switchable
1789792934285 [mmkv] 命中 model_configs 键，评估 switchable
（全文没有一条 "[mmkv] switchable false→true 已替换"）
```

| 观察 | 结论 |
|---|---|
| 「命中」出现 **4 次** | ✅ 宿主的 MMKV 读写**确实经过我们的 hook**（注入点是对的） |
| 「已替换」**0 次** | ❌ **替换从来没发生** |

⇒ **所以"被服务器下发顶掉"这个描述要修正**：不是"写进去了又被覆盖"，而是 **我们根本没写进去过**（闪一下的那次很可能是别的路径/别的版本留下的残影）。

⇒ 卡点只可能是 `handle` 里那三道闸之一：
1. `GmUtil.app()` 拿不到 Context
2. **`GmModel.isOn(ctx)` 为 false**（模型切换开关没开）
3. **值里没有 `"switchable":false`**（字段名/取值与我们假设的不一样）

**⇒ 上一版我恰好把这三条都憋着没打出来 —— 这就是"信息太少"的根因。**

## 二、本版改动：让 `handle` 把决策链说清楚

新增 `GmMmkvHook.dump(String)`，在每次命中目标键时打一条**样本行**（`logOnce`，避免刷屏）：

```
[mmkv] 样本 len=<长度> 开关=<true/false> 含false=<true/false> 含true=<true/false> 前160=<宿主 JSON 前 160 字>
```

并把三道闸各自的失败原因**分别**打出来：

| 出口 | 日志 |
|---|---|
| 拿不到 Context | `[mmkv] 跳过：拿不到 Context` |
| 开关没开 | `[mmkv] 跳过：模型切换开关未开` |
| 值不匹配 | `[mmkv] 跳过：值里没有 switchable:false` |
| 成功 | `[mmkv] switchable false→true 已替换` |

**⇒ 主人下次只要给我 `[mmkv]` 开头的那几行，我就能一次性定位**：
- `开关=false` ⇒ 开关本身没打开（去设置里开）
- `含false=false` ⇒ **字段名不对**（我们会看到"前160"里宿主的真实字段，据此改写目标串）
- `含false=true 且 已替换` ⇒ 替换成功，问题在**后面又被谁覆盖**

## 五、教训

| # | 教训 |
|---|---|
| **296** | ⭐⭐⭐ **埋点要覆盖"每个出口"**：只在入口和成功点打日志 ⇒ 失败时只能看到"进了门但没出来"。**每一条 `return` 前都该有原因** |
| **297** | ⭐⭐⭐ **"被覆盖"与"从没写进去"是两种病**：前者要找后写入者，后者要查自己的判断条件。**日志必须能区分**（本次靠"命中 N 次 vs 成功 0 次"才分开） |
| **298** | ⭐⭐ **把"输入样本"打出来**：判断条件不满足时，`样本 len/前 160 字` 比任何猜测都直接（能立刻看出字段名对不对） |
| **299** | ⭐⭐ 日志用 `logOnce` 做去抖，避免高频路径（每次渲染都读 MMKV）把文件刷爆 |
