## 一、真凶：UI 里那个**手写 JSON 解析器不还原转义**

```kotlin
private fun jsonToMap(s: String): Map<String, String> {
    val re = Regex("\"([^\"]+)\"\\s*:\\s*\"((?:[^\"\\\\]|\\\\.)*)\"")
    re.findAll(s).forEach { m[it.groupValues[1]] = it.groupValues[2] }   // ✗ 原样存
}
```
这个正则**会**把 `\n` 当成"合法转义"匹配进去（所以不会截断 ✓），但**不还原** ⇒ `"a\nb"` 变成字符串
`a\nb`（**反斜杠 + n 两个字符**）⇒ 显示是"一坨"，用户一保存还把**转义版写回存储** ✗

真机取证（MMKV 原始字节，换行是**字面 `\n`** 而不是 0x0A）：
```
fuckds_suggest_text  →  \n举个具体的例子\n点我启动原神\n
```
⇒ 底座 `GmSuggest.templates()` 是按**真换行** `"\n"` split 的 ⇒ 拆不开 ⇒ 宿主那边就是一条 ✗

## 二、修法（读 + 写两侧）

| # | 位置 | 改法 |
|---|---|---|
| 1 | `Pages.kt` `jsonToMap` | 改用 **`org.json.JSONObject`**（它负责还原 `\n` `\"` `\uXXXX`）；解析失败再退回老正则兜底 |
| 2 | `FdmBridge` 新增 `splitLines()` | **真换行**和**字面 `\n`** 都当行分隔（`"\\r?\\n|\\\\n"`）⇒ 历史脏数据也能自愈 |
| 3 | `FdmBridge` 新增 `joinLines()` | 归一化回"真换行"再交给模块的 `setText` |
| 4 | `dispatchText` 三处 | 招呼语/提示词/回复建议全部走 `splitLines`（回复建议额外 `joinLines` 归一化） |

## 五、教训

| # | 要点 |
|---|---|
| 1 | ⭐⭐⭐ **"能匹配"≠"能还原"** —— 手写正则解析 JSON 时，把转义匹配进来却不 unescape，是本轮"一坨"的唯一根因。**JSON 一律交给 JSON 解析器**，别自己写（这次栽的正是这一条）。 |
| 2 | ⭐⭐⭐ **转义只该活在"序列化层"** —— 一旦转义文本被**用户编辑后写回存储**，它就"落地成脏数据"，之后所有读方都要兼容。**写入侧做一次归一化（两种换行都认）是便宜的止损**。 |
| 3 | ⭐⭐ **"显示难看"往往是"数据真的变了"** —— 界面上看到 `\n`，第一反应不是"显示问题"，而是**去存储里看原始字节**（这次一看就定案）。 |
| 4 | ✅ **`xposedscope` 真机确认生效**（主人回执：作用域自动勾好了）—— "重装必重勾"这条老毛病正式退役。 |
