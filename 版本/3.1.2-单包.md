## 四、3.1.0 → 3.1.1：两个雷（都是真机炸出来的）

### 雷 1 ⭐ 底座选错：`gm` 包还挂着**模板作者**的包名

3.1.0 装上去立刻：

```
java.lang.NoClassDefFoundError: Failed resolution of:
    Lcom/nidyaber/fuckdsmanger/gm/GmCrashHook;
	at com.nidyaber.fuckdsmanger.GmEntry.handleLoadPackage(GmEntry.java:32)
```

我用的底座是 **2.22.110**。而 git log 里躺着一条：

```
b730faa  NL 2.22.112：退掉模板包名（整个 gm 包搬家到 com.nidyaber.fuckdsmanger.gm）
```

实测对照（`dexinfo.py`，按 class_defs 表数，不是 grep）：

| 包 | `com.varuns2002…gm.*` | `com.nidyaber…gm.*` |
|---|---|---|
| 2.22.110 | **123 个** | **0 个** ← 我用了这个 |
| 2.22.112 | 0 | 126 个 |
| **2.22.120** | 0 | **135 个** ← 改用这个 |

⇒ `GmEntry` 是按新包名编的，底座里根本没有那些类。
（**顺带白捡一条好消息**：这条报错的堆栈说明 **`GmEntry` 本身跑起来了**，
而它在 `classes2.dex` 里 ⇒ **LSPosed 的内存多 dex 加载是好的**；单包方向没问题。）

### 雷 2 ⭐⭐ 两个 dex 出现**同名类**

换了 2.22.120 之后，它那份 dex 里**已经包含** `GmEntry` / `GmUi` / `GmHomeUi` / `GmAboutUi`
（`mod-src/src` 里我们也在编这几个——它们是"在宿主里自绘 UI"时代的产物）。
两个 dex 定义同一个类 ⇒ **谁被加载取决于 dex 顺序** ⇒ 看起来能跑、行为随机。

**解法：入口分两层。**

```
xposed_init → bridge.FdmEntry        （我们的，全新建的类名）
                  │ ① 装探桥钩子（MainActivity.onCreate）
                  └ ② 反射转发给 com.nidyaber.fuckdsmanger.GmEntry（底座里的真入口）
```

`GmEntry` / `GmUi` / `GmHomeUi` / `GmAboutUi` 全部移进 **`mod-src/src-archive/`**
（它们是给"UI 长在宿主进程里"服务的，新架构用不着了 —— UI 已经搬进 Compose）。
⇒ 我们的 dex 缩到 **4 个类 / 8.6 KB**，与底座**零同名**。

## 六、3.1.1 → 3.1.2：雷 3 ⭐⭐⭐ **丢文件**（自作自受的经典款）

现象（UI 一画第一帧就崩）：

```
ExceptionInInitializerError
	at kotlinx.coroutines.Dispatchers.getMain
	at androidx.compose.ui.text.platform.DispatcherKt.<clinit>
	...
	at androidx.compose.ui.platform.AbstractComposeView.attachedToWindow
Caused by: IllegalStateException: Module with the Main dispatcher is missing.
```

**真正扎心的**：这条报错**在我们自己的文档里躺着**（`UI-方案B-可运行版.md` 踩坑表）：

> `Main dispatcher is missing` ｜ 协程实现类**只被 META-INF/services 文本引用** ⇒ 被裁 + **服务文件没进 APK** ｜ 手动把 services 文件塞进 APK

**真因**：组装脚本里我为了丢旧签名，写了一句：

```python
if n.startswith("META-INF/"):
    continue          # ← 一刀切，把 META-INF/services/ 也砍了
```

而 `META-INF/services/` 里住着两个**只被文件名引用**的服务声明：

```
META-INF/services/kotlinx.coroutines.CoroutineExceptionHandler
META-INF/services/kotlinx.coroutines.internal.MainDispatcherFactory
      → kotlinx.coroutines.android.AndroidDispatcherFactory
```

**ServiceLoader 找实现类，靠的是这个「文本文件」，不是代码引用** ⇒ 丢了它，
`Dispatchers.Main` 就找不到实现，Compose 第一帧必崩。

**修法**：只丢真签名 —— `^META-INF/(MANIFEST\.MF|.*\.(SF|RSA|DSA|EC))$`。
apksigner 重签时会自己重建 MANIFEST.MF / .SF / .RSA。

**并且加了一道「不许丢东西」的检查**（`check_carryover`）：

```
⑤ 条目搬运      : 源 77 项 → 保留 77 项；services 文件 2 个 ✓
```

规则一句话：**源包里除【签名 / 清单 / dex】以外的条目，一件都不许少** —— 少了就拒绝出包。

> 教训（值得刻进骨头）：
> **"我要丢掉这一类"和"我要丢掉这一件"是两件事。**
> 写 `startswith("META-INF/")` 的时候，脑子里想的是"3 个签名文件"，
> 实际砍掉的是"5 个文件里的 2 个活口"。
> **凡是用"前缀/通配"做删除，都要在出包前把它跟源清单对一遍。**

## 五、出包前自检（`pipeline/build_single.py::preflight` + `check_carryover`）

这个 bug 不该由主人装一次来发现。所以写成了脚本，每次出包先过五关：

```
类定义          : 底座 137 个 / 我们 4 个
① 同名类        : 0 个 ✓                    ← 雷 2
② 底座入口      : com.nidyaber.fuckdsmanger.GmEntry 在 ✓   ← 雷 1
③ 我们的入口    : com.nidyaber.fuckdsmanger.bridge.FdmEntry 在 ✓
④ 底座资源引用  : 0 个 ✓（可以安全复用 UI 的 resources.arsc）
自检全部通过 ✓
```

配套新工具 **`mod-src/pack/dexinfo.py`**：按 dex 头部 → `class_defs` → `type_ids` → `string_ids`
解出**真正被定义**的类。

> 为什么不能用 `grep`：`b"...GmCrashHook" in dex` 为 True 只说明**名字被提到过**
> （别的类引用它也算），根本分不清「定义」和「引用」。
> 这个坑今天差点又踩一次（我第一版对照表就是用 grep 写的）。
