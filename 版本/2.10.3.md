## 一、🎯 主人这句话推翻了「chip 不出现」的旧结论

| 旧认知（2.10.0 ~ 2.10.33 一直这么以为） | 真机实际 |
|---|---|
| 「输入框上方**没有** chip」⇒ 以为注入的列表没被渲染 | **chip 出现了**，只是**里面没有文字**、**点不动**、**滑不动** |

⇒ 34 版探针之所以一直「看不到成果」，很可能是**把「空壳 chip」误读成「没有 chip」**。

### 1.1 为什么是空壳（本版的核心推理）

宿主渲染 chip 文案走 **`pd5.I(g56, ctx)`**：

```
d != null  ⇒  context.getString(d)      ← 资源ID 优先
d == null  ⇒  直接返回 c（content）      ← 只有这时才用我们的文字
```

我 2.10.1 用自己反射造出来的 `g56`，`d` 落成了 **0（非 null）** ⇒ 走 `getString(0)` ⇒ **空字符串**。
文字为空 ⇒ 宿主点击链（去抖 / 发送）直接把自己挡掉 ⇒ **点不动**。

（这同时说明 2.10.1 的替换**其实生效了** —— 否则显示的是宿主那 4 条有字的默认模板。）

## 二、本版改法：**不再造对象，改为「就地改造宿主给的真对象」**

```
宿主列表（4 个真 g56，随 args 一起送进来）
   ↓ 取前 N 个（N = 我们模板池条数，默认 3）
   ↓ setObjectField(o,"c", 我们的文案)      ← 填进 chip 显示字段
   ↓ setObjectField(o,"d", null)           ← ★ 关键：清掉资源ID，逼 pd5.I 回落到 c
   ↓ setIntField(o,"a", 0x2329+i)          ← 换 id，避开宿主的点击去抖 key 冲突
   ↓ 装进新 ArrayList 塞回去
```

好处（为什么这招比自造对象强得多）：

| 诉求 | 自造对象（2.10.0~2.10.2） | **改造真对象（2.10.3）** |
|---|---|---|
| 字段类型对不对 | 要猜构造器（猜错就 `NoClassDefFoundError` / 空字段） | ✅ 宿主给的实例，天然正确 |
| `d`（资源ID） | 猜不到，落成 0 ⇒ **空文字** | ✅ 显式清成 null ⇒ 必走 `c` |
| 点击可用性 | 空文字 ⇒ 点不动 | ✅ 仍是宿主的对象，点击链完好 |
| 需要几个 | 要几个造几个 | 取 `min(模板数, 宿主数)`，不够就少显示 |

新增方法：`buildMut(List)`（改造主逻辑）+ `put` / `putInt`（带 try/catch 的字段写入）+ `str`（安全 toString）。
`GmSuggestHook`(yb5.e) 与 `GmSuggestHook2`(yb5.f) **都改走 `buildMut(宿主列表)`**。
自造对象那条路（`build`/`make`/`tryCtor`/`dumpCtors`）**保留作后备**，暂不删除。
