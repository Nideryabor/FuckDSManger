# FuckDSManger 2.10.38（回复建议 · 对照实验：chip 标签到底读什么）

> 产物：`FuckDSManger_2.10.38_for_ds2.5.2.apk`（**189 / 2.10.38**，91 类，V1+V2+V3，sha256(partial) `c38b56c7…`）
> 触发：主人「还是无字」+ 日志（无 `按资源 id 接管` 行）

## 一、已经排除的三条通道（都排除了）

| 通道 | 证据 | 结论 |
|---|---|---|
| `c`（content 文本） | **宿主自己的对象 `content=这是什么`，chip 照样空** | ❌ 不是它 |
| `d`（contentRes 资源 id → `getString`） | 我们的 `GmResIdHook` 挂上了，日志**没有**「按资源 id 接管」 | ❌ chip 不请求资源 |
| `pd5.H/I` 的返回值 | 日志有「文案已接管(H) 能再展开讲讲吗？」，chip 仍空 | ❌ 返回值没被用于标签 |

⇒ **列表接管成功（`f 列表=1`）+ 文字确实产出（`文案已接管`）**，但可见标签**三条通道都不吃**。

## 二、本版对照实验：把 `a` 改成宿主自己的 id

```smali
    putInt(inst, "a", 9 + i)      ← 原来是我们自己的 0x2329+i
```

思路：如果标签是"**按 id 在宿主内部表里查**"（例如 `c56` 伴生对象里的映射），
那么用宿主的 id（9）就会显示出**宿主自己的文案「这是什么」**。

| 实验结果 | 结论 | 下一步 |
|---|---|---|
| chip 显示「这是什么」 | **标签 = 宿主内部表按 id 查**（我们的文字永远进不去这条通道） | ⇒ 换路线（自绘，见下） |
| chip 仍然空 | 这些 chip 在本版本**不显示文字**（可能是纯图标按钮） | ⇒ 换路线（自绘） |

## 三、路线选择（请主人拍板）

| 路线 | 说明 | 依据 |
|---|---|---|
| **A. 自绘 chip 条** | 我们自己在输入框上方画一排按钮（档案里 2.10.15~19 的 `GmSuggestView` 路线，**当年真机验证过"显示 + 点击→发送"**，只是定位/切页要打磨） | 显示与点击完全由我们控制，**不依赖宿主任何字段语义** |
| B. 继续挖宿主标签 | 需要在宿主 UI 代码（`yb5.f`/`pd5` 之外）继续找 | 已连查 3 条通道全灭，**收益递减明显** |

> 我的建议：**A**。理由是：我们已经证明了「宿主那排的列表可以接管、但它的文案通道对我们不可用」——
> 再往下就是在逆向宿主的渲染细节，成本极高；而自绘路线的**显示与点击当年就被证实可用**。
