## 二、✅ 已确认的硬结论（下次直接用，不用重查）

### 数据库（**明文 SQLite，未加密**）

```
路径  /data/user/0/com.deepseek.chat.a/databases/
主库  deepseek_chat.db                （只有 app_user_info）
会话库 deepseek_chat_<id>.db          （332KB 级；★ 消息在这里）
      同名 -wal / -shm 是伴生文件，不能当库打开（否则 SQLITE_NOTADB）
```

### 表结构

```sql
-- 消息表（一个库里有 6 张，每会话一张）
CREATE TABLE 'chat_session_messages_<会话UUID>'(
  message_id INTEGER PRIMARY KEY,   -- 排序用
  parent_id INTEGER,
  role TEXT,                        -- USER / ASSISTANT / SYSTEM
  status TEXT,                      -- FINISHED / …
  inserted_at REAL,
  tips TEXT,                        -- 空数组
  fragments TEXT,                   -- ★★ 正文（JSON 数组）
  … );

-- 会话索引
CREATE TABLE chat_session_list(id, title, updated_at, current_message_id, …);
```

### 正文格式（`fragments`）

```json
[{"type":"REQUEST",  "id":1, "content":"<用户输入>"}]
[{"type":"THINK", …}, {"type":"RESPONSE", "id":2, "content":"<AI 正文>"}]
```

**⇒ 取数公式（已在本机用 Perl 验证过）：**

```sql
① SELECT id FROM chat_session_list ORDER BY updated_at DESC LIMIT 1
② SELECT role, fragments FROM chat_session_messages_<id>
   WHERE status='FINISHED' ORDER BY message_id DESC LIMIT 8
③ 解析 JSON：只取 REQUEST / RESPONSE 的 content（跳过 THINK），倒序拼上下文
```

### 走过的死路（别再走）

| 路 | 结论 |
|---|---|
| 内存对象 `nx` / `hp8` | **空骨架**（30 字段全空），正文不在里面 |
| `vq` 的 `l/t/k/G/D/A/d` | 全部存在、全被调用、**全返回空**（不是正文通道） |
| `hx2.g → z40` | `z40` 是**协程挂起包装**，不是可执行请求 |
| 自己发 HTTP | 需要 token（只在内存）+ PoW ⇒ 成本高 |
| 宿主单发辅助接口 | **不存在**（端点全表已列） |

## 四、其它坑位备忘

| 现象 | 说明 |
|---|---|
| `GmUtil.logOnce` | **是两个参数**（`String,String`）⇒ 单参会 `NoSuchMethodError` |
| `logE` | 有堆栈但**不落盘** ⇒ 诊断要用 `log` |
| 日志"丢行" | 落盘有**限流** ⇒ 关键信息**拼成一行**再打（`DIR` 那行就是范例） |
| `.registers N` | 必须与参数个数对齐（`p0` 落在 `v(N-1-参数数)`）；**一个寄存器只装一种类型**（两次 `VerifyError` 都是这个） |
| `insert_before_match` | 不消费锚点 ⇒ 别在 writeText 里重复锚点行 |
