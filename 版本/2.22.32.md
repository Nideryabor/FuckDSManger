## 1. 两处修法

| # | 改动 | 为什么 |
|---|---|---|
| **1** | `GmBg.real()`：`pos == 1` → **`pos != 0`** | 主人的档位是 **`pos=2`「混合（真背景）」** —— 这才是他嘴里「真背景那个选项」。旧闸门只认 `pos=1`（底图），**把最该生效的那一档排除了** ⇒ 改成「只要不是「蒙层」档就实化」（`isOn && pos > 0`） |
| **2** | `sPageDone:Z`（一次性）→ **`sPageCnt:I`（前 4 次）** | 页面底色是**三层 `#FF0F0F0F`**，只透明化第一层 ⇒ 上面两层照样挡图 ⇒ 必须**把同层的几层一起透明化**。取 **4** 是因为日志显示「前 4 次 `v` 调用全部是宿主底色层」（`#0F0F0F`×3 + `#292929`×1），第 5 次才轮到 `u`（渐变）与后续内容 |

**判据链（新）**：

```
sPageDepth > 0            # 在 ChatPage 里
&& sPageCnt < 4           # 本页还没处理满 4 次
&& args.length >= 2
&& method.name == "v"
&& args[1] != colorLong() # ★ 哨兵：不是我们自己注入的气泡色
⇒ sPageCnt++              # 计数（本页最多 4 次）
&& GmBg.real(ctx)         # 背景开着 && 非「蒙层」档
⇒ args[1] = Long(0)       # 该层全透明
```

`sPageCnt` 在 `GmPageHook.before`（每次 `ChatPage` 组合）重置为 0 ⇒ **每次重组都会重新透明化那几层** ✓

## 2.5 ⚠️ 出包后真机报 **VerifyError**（同一版内修复，现已重出）

主人装第一版 2.22.32 后回执：

```
23:41:17.110 hookM FAIL uia.u
23:41:17.110 E java.lang.VerifyError: Verifier rejected class
      com.varuns2002.disable_flag_secure.gm.GmBubblePaintHook: ...
      [0x7F] not array type Integer with aget
```

**根因（我自己的错）**：2.22.32 版我把「诊断段」直接**内联**进了 `beforeHookedMethod`，而那段里两条失败路径
（`if-ge sPageCnt` / `if-lt args.length`）**与后续逻辑汇合到同一个 `:pg_skip` 标签**，
汇合点上 `v0` 在一条路径是 `int`、另一条是 `Object[]` ⇒ **类型冲突** ⇒ ART verifier 拒绝**整个类**
⇒ 该类的**所有** hook 连坐失效（`uia.v` / `uia.u` 两条都没装上）。

**修法（不是打补丁，是重写结构）**：把「诊断」与「页面分支」**各自抽成独立的 `private static` 方法**
（`dg(...)` / `pg(...)`），在 `beforeHookedMethod` 的 `:try_start_0` 之后**只留两行 `invoke-static`**：

```smali
    :try_start_0
    invoke-static {p1}, Lcom/.../GmBubblePaintHook;->dg(Lde/.../MethodHookParam;)V

    invoke-static {p1}, Lcom/.../GmBubblePaintHook;->pg(Lde/.../MethodHookParam;)V

    <原计数逻辑原样不动>
```

并在两个新方法里统一采用「**失败即跳方法出口 `:end`**」的写法（`:end` 紧接 `return-void`，其后无任何指令使用寄存器）
⇒ **汇合点不存在「后续使用」，类型冲突自然无害**。原 `beforeHookedMethod` 的寄存器状态**完全不受影响**。

**验证**：`tools/vercheck.pl tmp/GmBubblePaintHook.smali` → **`✅ 未发现未初始化 / 类型冲突隐患`**（本版已重出，sha `5e8855e5…`）

> 教训见 §4 的 795~797。

## 4. 教训（791~794）

| # | 内容 |
|---|---|
| **791** | ⭐⭐⭐ **「闸门」比「算法」更容易成为最终瓶颈**：2.22.30/2.22.31 两版的透明化逻辑其实一直是可用的，但它前面挂着一个 `pos == 1` 的条件，而**真机上的档位是 `pos = 2`** ⇒ **整个功能空转两版**。⇒ **给新功能加前置条件时，必须逐条核对「真机当前状态下这个条件成立吗」**，否则「逻辑正确」会伪装成「功能正常」。 |
| **792** | ⭐⭐⭐ **「一层」是幻觉，页面底色通常是「套娃」**：`#0F0F0F` 被连续画了**三次**（`#1`/`#2`/`#3`），`#4` 才换色。⇒ 只处理「第一个」等于只撕掉最外面一层纸。**「找页面底色」的正确问法不是「哪一次调用」，而是「哪几次调用」**。 |
| **793** | ⭐⭐ **探针要打「序列」而不是「结果」**：这一版能一次定位，全靠 `[页内bg] #1~#5` 把**调用序列**原样端出来（序号 + 方法名 + 原始值）。若只打「最终替换成了什么」，就永远看不到「有三层同色」这件事。**诊断输出要保留「顺序」信息。** |
| **794** | ⭐⭐ **把原始 long 换算成 ARGB 是「一眼定性」的最短路径**：`-67818912288342016` → `#FF0F0F0F` 只用一次进制换算，立刻认出是「深色模式 background」。**混淆日志里的数值先翻译成人话，再开始推理。** |

| **795** | ⭐⭐⭐ **手写 smali 的「汇合点类型冲突」是头号杀手，而且它会连坐整个类**：`GmBubblePaintHook` 只是 `v0` 在两条路径上分别是 `int` / `Object[]`，ART 就**拒绝整个类** ⇒ 该类挂的 `uia.v` + `uia.u` **两条 hook 一起失效**。⇒ **症状是「好几种功能同时哑掉」，别逐个查，先翻日志有没有 `hookM FAIL` / `VerifyError`。** |
| **796** | ⭐⭐⭐ **避免汇合点冲突最省事的写法：新逻辑一律抽独立方法 + 单出口**：把「诊断」「页面分支」各自写成 `private static dg(..)` / `pg(..)`，方法内**所有失败路径都跳方法末尾的 `:end`**（其后只剩 `return-void`）⇒ 汇合点之后**没有任何指令再读寄存器** ⇒ 类型冲突天然无害，且**原方法的寄存器状态完全不受影响**。**比在长方法里逐条抠路径类型便宜十倍。** |
| **797** | ⭐⭐⭐ **`tools/vercheck.pl` 要在出包前跑，而不是等真机报错**：本次改完 `GmBubblePaintHook` 直接 build，`edit_check` / `dex_merge` **全绿**（它们**不做字节码校验**，铁律 6），真机一装就 VerifyError。补跑 `perl tools/vercheck.pl tmp/xxx.smali` → ✅ 干净才敢重出。**「MT 全绿」≠「ART 能过」。** |
