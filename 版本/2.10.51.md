## 一、好消息先记下来

**50 版之后：不崩 ✓、chip 上出现文字 ✓**（而且是**我们模板池的文字**）
⇒ 说明三件事同时成立：
1. 越界 `d` 已彻底断掉（`GmSuggestHook2` + `d=null`）
2. **`pd5.H` 的文案接管真正生效了**（`idxOf` 修好）
3. **chip 文字确实可以靠 `pd5.H` setResult 来决定**（与 2.10.16 时代"接管了但屏上没字"的结论相反 —— 那时 `idxOf` 恒 -1，其实从没接管成功）

## 二、剩下两个现象，其实是**同一个原因的两面**

| 现象 | 原因 |
|---|---|
| 两个 chip 的**文字完全一样**（都是模板池第 1 条） | 列表接管停着 ⇒ 屏幕上那两条是**宿主自己的对象**，它们的 `id` 不是 9/10/…，被 `idxOf` 归一后**都落在下标 0** ⇒ 都取模板池第 1 条 |
| chip **只有两条**（不是模板池条数） | 同上：数量由**宿主**决定（我们没接管列表） |

⇒ 一句话：**50 版只修好了"文字通道"，但"条数与身份"还归宿主管。**

## 三、本版改动（3 处）

| # | 改动 | 说明 |
|---|---|---|
| 1 | **恢复两处列表接管**：`GmSuggestHook`（`yb5.f` 的 args[1]）与 `GmSuggestHook2`（args[0]）重新调用 `buildMut` | 让"那排 chip"由**我们的模板池**决定（放心：`d=null` 已经不会再越界） |
| 2 | `buildMut2` 条数算法：`min(模板数, 宿主列表条数)` → **`min(模板数, 8)`** | chip 条数跟着**模板池**走，不再被宿主的 4 条/2 条卡住 |
| 3 | `GmPromptTextHook.idxOf` 严谨化：**只认 9~16**（`id-9 ∈ [0,8)` 才接管），其余返回 -1 放行 | 避免误伤宿主的其它文案 |

### 3.1 一条重要取舍

`buildMut2` 里造对象的 `a`（id）**保持 `9 + i`**（与宿主/服务器同一段），而不是换成我们的专属段 `0x2329+i`：

- `9+i` 与宿主数据形状一致 ⇒ 宿主任何"按 id 索引"的逻辑都能对上（**已验证过的形状**）
- `idxOf` 对 9~16 映射到 0~7 ⇒ 每条 chip 拿到**不同的**模板 ✓

### 3.2 由此形成的完整链路

```
templates() 模板池（你的条目）
   └─ 造 N 条 g56：a = 9+i · b = 复制宿主场景 · c = 我们的文字 · d = null
        └─ 替换宿主列表（GmSuggestHook / GmSuggestHook2）
宿主渲染那排 chip：yb5.c → pd5.H(g56)
   └─★我们的 hook(after idxOf 修复)：setResult(模板池[i % size])
       ⇒ chip 显示我们的文字，且从不触及 Resources.getString(d) ⇒ 不可能再 NotFound
```
