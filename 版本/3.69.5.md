## 一、日志铁证

```
【DJ】点歌 红色高跟鞋 - 蔡健雅 ⇒ 放了 红色高跟鞋 - 蔡健雅（精确命中）      × 18 次
【DJ】点歌失败（零结果）：迷宫 - 王若琳                                    × 154 次
```

**根因**：`GmMusicDj.handle()` 挂在 `GmRichTextHook.rebuild()` 里 ——
而**每次重绘都会 rebuild**（流式输出一段一段长、滚动、重组…）
⇒ 同一条 `⟦DJ:…⟧` 被处理 N 次 ⇒ 搜 N 次、播 N 次、吐司 N 次。

而 `GmMusicPlayer.play()` 每次都会 `startCurrent()`
⇒ **歌一遍遍从 0 重开**（主人感受到的"多次播放"就是这个）。

★ 这是"**把有副作用的动作放在渲染路径里**"的经典坑：
渲染是**幂等**的（同输入同输出），而这个动作**不幂等**（每调一次真的去搜、去播、去弹）。

---

## 二、修法

### ① 去重（15 秒窗）

```java
private static final long DEDUP_MS = 15000L;
private static final HashMap<String, Long> DEDUP = new HashMap<>();

// handle() 里，解析出 歌名/歌手/hidden 之后：
final String dedupKey = (hidden ? "H|" : "") + song + "|" + artist;
if (recentlyHandled(dedupKey)) {
    GmUtil.logOnce("dj.dup." + Math.abs(dedupKey.hashCode()),
            "同一条点歌被重复渲染 ⇒ 跳过（不重复搜/放/吐司）：" + dedupKey);
    return show;                 // ★ 仍然显示「♪ 正在给你放…」（显示是幂等的），但不搜不播不吐司
}
```

**为什么带时间窗而不是永久去重**：用户过一会儿**再点同一首**是合理需求，得放行。
15 秒 = 够覆盖一条消息的整个流式渲染，又不会拦掉"再点一次"。

### ② 顺手加：组合关键词零结果 ⇒ 退回**纯歌名**再搜

真机看到的 `迷宫 - 王若琳` 组合词常常搜不到（154 次零结果）。
⇒ `song + " " + artist` 没结果时，**用纯 `song` 再搜一次**，然后再挑。

（为此把"挑一首 + 起播"抽成 `doPick(list, song, artist)`，好给两级搜索复用。）

## 四、教训

**1092 · ⭐⭐⭐ 有副作用的动作**绝不要**直接放在渲染路径里 —— 渲染会跑很多次。**
　　`rebuild()` 是渲染钩子，流式/滚动/重组都会调它（实测同一条消息 18 次）。
　　而搜索/起播/吐司都是**非幂等**动作 ⇒ 一次一条消息变成 18 次。
　　★ 判据：**"同输入同输出"的代码可以放渲染路径；"会发包/会出声/会弹窗"的必须去重**。

**1093 · ⭐⭐ 去重键要选"用户意图的粒度"，再加时间窗。**
　　键取 `歌名|歌手|hidden`（= 用户想要什么），而不是"消息 id / 文本长度"
　　（流式过程中长度一直在变，当键会失效）。
　　★ 时间窗（15s）负责"同一次渲染过程"，键负责"是不是同一首歌" —— 两者配合才既不多播、也不误拦重播。

**1094 · ⭐⭐ 「显示」和「动作」分开：显示可以重复，动作只能一次。**
　　去重时**仍然返回 `show`**（那一行「♪ 正在给你放…」照常渲染），
　　只是不再搜/播/吐司 ⇒ 界面看起来完全正常，副作用只发生一次。

**1095 · ⭐⭐ 修 bug 时别用 sed 做"方法级搬家"。**
　　这次把"搜索→挑歌"抽成 `doPick` 时，用脚本按行号切，
　　结果**旧方法的尾巴（`}); return show; } catch…`）残留在了新方法里** ——
　　虽然 javac 恰好编过了，但那是运气。
　　★ 正确姿势：**整段读出、整段重写**（尼尼读了 150~300 行之后才发现残留）。

**1096 · ⭐ logcat 调大的收益是复利的。**
　　3.69.4 把缓冲从 256 KiB 调到 16 MiB 之后，这次**直接看到 18 次重复的完整证据**；
　　要是还是 256 KiB，大概只能看到最后两三条，又会去猜。
