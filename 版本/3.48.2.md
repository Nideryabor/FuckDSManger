## 〇、一句话

**`<c#FF0000>红字</c>` 一直显示成宿主的正文色（浅色黑 / 深色白），而 `<bg#FFFF00>` 正常。**

根因不在颜色编码、不在宿主覆盖，而在**我自己拼串的顺序**：

> 我用 `append(AnnotatedString, start, end)` 搬原文，**它会把原串覆盖该区间的 span 一起搬进来**；
> 而搬进来的时机在 `pushStyle(我们的颜色)` **之后** ⇒ 宿主的 `color=浅灰白` 排在**我们后面**
> ⇒ Compose「**后加的赢**」⇒ 我们的颜色被盖掉。
>
> 而 `background` 宿主**从不设**（255 个 SpanStyle 实例全是 `background=Color(0,0,0,0)`）
> ⇒ 没人跟我们抢 ⇒ 黄底活下来了。

**这个"一死一活"的对比，才是这次能定位的关键。**

---

## 一、现象与误导

| 写什么 | 结果 |
|---|---|
| `<c#FF0000>红</c>` `<c#00FF00>绿</c>` `<c#8A2BE2>紫</c>` | **全是宿主正文色**（浅色主题黑、深色主题白） |
| `<c1>…<c9>` 色板 | 同上（不生效） |
| `<bg#FFFF00>` `<bg#FF0000>` | **正确显示** |
| `<b>` `<i>` `<u>` | 正常 |

**"背景活、文字死"这个反差，指向的绝不是编码问题** —— 因为两者共用同一个 `spanOf()`，
只有 mask 位不同。**是我一开始就该抓住这个线索的。**

## 二、排查路径（含两次走错路，都记下来）

### 第 1 步：自检"值有没有写进去"

3.48.0 加了自检 —— 构造完 `SpanStyle` 后把 `color` 字段读回来对账：

```
自检 color want=0xff8a2be200000000 got=0xff8a2be200000000 ✓ 一致
```

**⇒ 构造是对的。但这条自检有个致命局限：它只证明「我算的值确实写进去了」，
完全没证明「我算的值是对的」。**（教训 922）

### 第 2 步：查「宿主有没有硬设颜色」—— 排除了一个假设

翻了 smali，宿主渲染 Markdown 用的是：

```smali
36224:  sget-wide v8, Lgx2;->h:J     ← Color.Unspecified
```

**⇒ 看起来"宿主没硬设颜色"，所以"被覆盖"这个假设当时被我排除了。**
**（这个判断后来证明是错的 —— 因为我没有查全。`w2b.n` 的实参里有一份现成的
`rla.a`（基础 SpanStyle），而那是运行时才可见的东西。）**

### 第 3 步：★ 误判 —— 从位移"推"getter 语义

我看到四个 getter 的位移各不相同：

```smali
d(J)F → >>> 56     e(J)F → >>> 32     g(J)F → >>> 40     h(J)F → >>> 48
```

**然后我"推"出 `d=red, h=alpha`，进而断定我的 `argb << 32` 编码全错**，
还把这个结论当事实讲给了主人。

**后来找到 ground truth**：`k53.smali` 里有个 `S0(J[FI)V`，把颜色解构进 float 数组，
顺序是 **`h, g, e, d`** —— 而 Compose 的 `toComponents` 顺序是**红绿蓝透明度**：

```
h = red(>>>48)   g = green(>>>40)   e = blue(>>>32)   d = alpha(>>>56)
```

**⇒ 布局就是 `alpha(56) red(48) green(40) blue(32)`，我原来的 `argb << 32` 是对的。**

**我推出来的语义正好全反了。**（教训 923）

### 第 4 步：★★ frida 扫全场 —— 拿到决定性数据

frida 网关投一个 job，`Java.choose('f0a')` 把内存里所有 SpanStyle 打出来：**255 个**。

```
#1  SpanStyle(color=Color(0.972549, 0.972549, 0.972549, 1.0, sRGB), fontSize=17.0.sp, ...)
#8  SpanStyle(color=Color(0.40392157, 0.6, 0.99607843, 1.0, sRGB), ...)      ← 链接色
...
（255 个里）background=Color(0.0, 0.0, 0.0, 0.0, sRGB)     ← ★ 一个设背景的都没有
```

**两条铁证：**
1. **宿主确实会给正文 span 设 `color`**（`#F8F8F8` = 深色主题的正文色）
2. **宿主从不设 `background`**（255/255 全是透明）

**⇒ `color` 有主（会被抢），`background` 无主（谁写谁的）** —— 现象完全对上。

### 第 5 步：★★★ 查 `in.c` 的 span 提取器 —— 找到 mechanics

`append(AnnotatedString, start, end)` 内部走 `pn.a(Lkn;IILq3;)`：

```smali
.method public static final a(Lkn;IILq3;)Ljava/util/List;
    if-nez p1, :cond_45              # start == 0 ?
    iget-object p0, p0, Lkn;->b:Ljava/lang/String;
    invoke-virtual {p0}, Ljava/lang/String;->length()I
    if-lt p2, p0, :cond_45           # 且 end >= 全长 ?
        return-object v0             # 直接原样返回 spans（整条搬，不裁剪）
    :cond_45
        ... 裁剪路径：把落在 [start,end) 的 span 裁到区间内，一并返回
```

**⇒ 不管走哪条路，它都会把「原串在该区间的 span」一起带出来。**

**而我的重建顺序是：**

```java
pushStyle(我们的颜色)                    // 我们的 span 先进列表
append(orig, plain, i)                  // ★ 宿主的 color=浅灰白 也进来了，排在**我们后面**
                                        //   ⇒ 后加的赢 ⇒ 我们的颜色被盖
```

**⭐⭐ 到这里机制闭环，"一死一活"精确解释，无需再猜。**

## 三、修法

**当我们自己压着样式时，不要用会夹带原串样式的 `append(AnnotatedString,…)`，
改用 `append(String)` 纯文本：**

```java
private static void appendText(Object nb, Object orig, String text,
                              int from, int to, boolean styled) throws Exception {
    if (to <= from) return;
    if (styled) {
        mAppendStr.invoke(nb, text.substring(from, to));      // 纯文本：不带原串任何样式
    } else {
        mAppendKn.invoke(nb, orig, Integer.valueOf(from), Integer.valueOf(to));   // 原样搬（含样式）
    }
}
```

两处调用点（`emitPlain` 的循环内 + 循环外）都改成 `!stack.isEmpty()` 作为判据。

**代价**：被我们压着样式的那段文字会**丢掉原文的 markdown 样式**（粗体/链接等）。
标记段本来就是我们接管的部分，要粗体自己写 `<b>` —— 可接受。

**而 `emit` / `emitAnon`（模板段 / 匿名包裹段）本来就用 `append(String)`，所以它们一直是对的。**
**这也解释了为什么"裸标签模式"出问题、"模板模式"没出问题。**

## 四、★ 教训（922~926）

| # | 教训 |
|---|---|
| **922** | ⭐⭐⭐ **自检要验「值对不对」，不能只验「写进去没有」** —— 我那句 `want == got` 只证明了赋值成功，对"编码是否正确"零信息量，却让我以为自己排除了一条路 |
| **923** | ⭐⭐⭐ **不要从位移/字节码结构去"推"语义** —— 我推的 `d=red, h=alpha` 正好全反，而 ground truth（`toComponents` 的调用顺序）就在隔壁文件里。**找参照物，别推** |
| **924** | ⭐⭐⭐ **Compose 合并重叠 span 的规则是「后加的赢」** —— 所以"我以为我加了颜色"和"颜色生效"之间，还差一个**顺序** |
| **925** | ⭐⭐⭐ **`append(AnnotatedString, start, end)` 会夹带原串的 span** —— 想要"只有我这段样式"就必须用 `append(String)`。这个坑很隐蔽，因为搬文本本身看起来完全正常 |
| **926** | ⭐⭐ **"一死一活"的现象是金线索** —— `bg` 活 / `color` 死，一开始就该直指"有人在抢 color 这条道"，而我先去怀疑编码，绕了两圈 |

## 六、顺带：这轮的两个"工具收获"

**① 「失败画成图」比任何日志都快**

3.48.1 让渲染失败时把原因画成一张红框图，直接回给宿主显示在气泡里。
**不用回读 DIAG、不用 frida、不用抢时序** —— 主人一眼就看到是哪一步炸的。

**② frida 扫全场（`Java.choose`）是"取证"的杀器，但有边界**

`Java.choose('f0a')` 一次把 255 个 SpanStyle 全打出来，两条铁证都是它给的
（宿主设 color / 不设 background）。**但它扫不到"已经被回收的对象"** ——
那几条带颜色的 `AnnotatedString` 就怎么都扫不到（Compose 释放太快）。
所以：**能扫"常驻对象"，扫不到"瞬时对象"。**
