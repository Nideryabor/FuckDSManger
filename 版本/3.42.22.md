## 〇、★ 主人更正（2026-10-01 21:5x）—— 这条让整条诊断链**闭合**了 ★

> 主人原话：**「助手头像替换正常，账号替换不行，但账号名称能替换」**

之前的档案含糊写成「头像+账号名 ✅」，是错的。正确的三分是：

| 功能 | 锚点 | 状态 |
|---|---|---|
| **助手头像** | `GmAvatarHook` → `getDrawable` | ✅ 正常（**自包含型**，不碰宿主成员名） |
| **账号名** | `GmNameHook` → `s5.v()` + `a==0x8` → `it9.c` | ✅ **能** |
| **账号头像** | `GmUAvatarHook` → `p5.v()` + `a==0xf` → `it9.e` | ❌ **不能**（而且还崩） |

**这两个"能/不能"不是巧合 —— 它们是同一个现象的两面：**

```
            旧宿主 tag        新宿主 tag        结果
账号名桶 s5/a6:  0x8     →     0x8   （没位移）  ✅ 活着
账号头像桶 p5/x5: 0xf    →    0x12  （位移了）  ❌ 死 + 投毒
```

- `s5` 的 **0x8 位移后恰好还在 0x8** ⇒ `getIntField(obj,"a")==8` 依然命中账号名分支 ⇒ **能用** ✓
- `p5` 的 **0xf 位移到了 0x12** ⇒ `==0xf` 命中的是 `fs`/`es` 那条无关业务 ⇒
  ① 账号数据类分支**从来没人碰** ⇒ **头像永远不变** ② 每次还 `setResult(String)` 投毒 ⇒ **崩**

> ⇒ **"账号头像不行"和"点上传图片崩"是同一个根因。**
> ⇒ **3.42.22 这一处改动，理论上一次修两个。**

### 交叉验证（三条独立证据）

1. **类型同构**：`it9` 与 `d9b` 逐字段同构（`Companion` / `f:[]` / `a:Object` / `b~e:String`），
   且 `ht9→c9b`、`ta5→ac6`、`wt9→s9b` 都是同批改名 ⇒ 同一个类。
2. **分支代码逐指令同构**：
   `旧 0x0f: getValue → check-cast Lit9; → iget Lit9;->e:String → return` ↔
   `新 0x12: getValue → check-cast Ld9b; → iget Ld9b;->e:String → return`
   而新 0xf 分支的形状完全不同（`fs` → `instance-of Les` → 分支树）。
3. **读字段的调用方也配对**：旧 `{p5, dm0, gt9}` 读 `Lit9->e` ↔ 新 `{x5, b9b, g99}` 读 `Ld9b->e`（一一对应）。
   且 `专题/宿主2.6.1-适配-体检报告.md` 早先就记着「账号头像 `p5.v()`+`a==0xf` → `it9.e`」+「账号名 `s5.v()`+`a==8` → `it9.c`」。

## 二、证据链（纯静态、可复查、不需要真机）

### 2.1 `p5.v()` / `x5.w()` 不是普通方法，是**分派桶**

```
iget v0, p0, Lx5;->a:I          # this.a = tag
iget-object p0, p0, Lx5;->b:Lk2a;  # 捕获的 State
packed-switch v0, :pswitch_data_186   # 29 个 case（0x0 ~ 0x1c）
```

每个 case：`getValue() → check-cast 成自己那一族的类型 → return-object`。

⇒ **同一个 tag 号，两版指向完全不同的业务。** R8 把 case 顺序重排了。

### 2.2 逐 case 对齐（`tmp/h252/p5.smali` ↔ `tmp/h261/x5.smali`，全 29 个）

| tag | 2.5.2 分支 cast | 2.6.1 分支 cast | |
|---|---|---|---|
| 0x0 / 0x1 / 0x2 / 0x6 / 0x8 / 0xc / 0x1a | String / Number / List / Boolean / Number / Boolean / String | 同型 | ✓ 没动（7 个） |
| **0xf** | `:pswitch_92` → **`it9`**（账号数据类） | `:pswitch_c3` → `fs` / `es` | ❌ **错位** |
| 0x12 | `:pswitch_6d` → `yp1` | `:pswitch_95` → **`d9b`** | ❌ 错位 |

**剩下 20 个也都错位了** —— 只是只有 0xf 这一条会 `setResult` 覆盖返回值，所以只有它咬人。

### 2.3 为什么 `0x12` 才是新宿主里的账号头像锚点

```
2.5.2  tag 0xf   : :pswitch_92 → getValue() → check-cast Lit9;  → iget-object v1, Lit9;->e:Ljava/lang/String;  → return-object v1
2.6.1  tag 0x12  : :pswitch_95 → getValue() → check-cast Ld9b;  → iget-object v1, Ld9b;->e:Ljava/lang/String;  → return-object v1
```

- **逐指令同构**（`if-eqz → getValue → check-cast → if-eqz → iget e → :cond → return v1`）
- `it9 → d9b` 正是重定位表里那条「账号数据类」映射；字段 `e` 两版都没改名
- `:pswitch_95`（0x12）段落以 `return-object v1` 结束，不会 fallthrough 到下一个 case ✓

### 2.4 崩的机理（和 frida 活体抓到的完全吻合）

旧包判据写 `0xf` ⇒ 在新宿主上命中的是 `:pswitch_c3`（本该返回 `fs`/`es`）⇒
`setResult(String)` 把它污染掉 ⇒ 调用方 `l10.A: State.getValue() check-cast dz9` 崩。

> frida 抓到的顺序是：`GmUAvatarHook 触发 → 吐司 → setResult = String → ClassCastException: String cannot be cast to dz9` ——
> **吐司弹出的那一刻就是投毒的那一次**。✅ 与本静态结论一致。
