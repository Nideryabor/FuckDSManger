## 一、2.9.21 的日志说明了什么

```
FuckDSManger: prompt SKIP already-prompted
```

- **没有 `prompt ENTER`** ⇒ `logOnce` 已去重 ⇒ 这**不是第一次**调用
- 有 `SKIP already-prompted` ⇒ 现在 `if-nez` 判断是**对的**（`sPrompted == true` 才跳这里）

⇒ 结论：**曾有一次调用通过了守卫并置位了 `sPrompted`**（也就是说 2.9.21 的修复生效了），
而那一次必然留下了 `prompt OPEN dialog` / `SKIP done-flag` / `prompt FAIL` 三者之一。

**问题已转移到最后一环**：`GmDeviceDialog.open()` 有没有真的把窗口显示出来。

## 二、本版改动（只加观测，不动逻辑）

### 2.1 `GmDeviceDialog.open` 三段留痕

| 位置 | 日志 |
|---|---|
| 进入 try | `dialog build start` |
| `show()` 之前 | `dialog showing` |
| `show()` 之后 | `dialog shown OK` |
| 异常 | `device dialog build FAIL` + 堆栈（原有） |

### 2.2 `promptIfNeeded` 的 OPEN 分支加回 Toast

```
设备身份窗口已打开：如需更换身份请点窗口里的按钮
```

⇒ **即使对话框没显示出来，用户也能凭 Toast 判断"逻辑到底有没走到"**。

### 2.3 版本

`AndroidManifest.xml`：`108/2.9.21` → `109/2.9.22`

## 三、判读表（下次日志照这个看）

| 日志组合 | 结论 |
|---|---|
| `prompt ENTER` + `prompt OPEN dialog` + `dialog build start` + `dialog showing` + `dialog shown OK` | 逻辑全通，**问题在窗口不可见**（UI 层） |
| …`dialog build start` 后**没有** `dialog showing` | 构建 UI 中途抛异常（应有 FAIL 日志） |
| 有 `dialog shown OK` 但屏幕无窗口 | `Dialog.show()` 成功但被宿主/系统遮挡 ⇒ 换显示方案 |
| 完全没有 `prompt OPEN dialog` | 又被"已弹过/done-flag"挡了 |
| Toast 出现但无对话框 | 同上：逻辑通、UI 不通 |

## 四、教训（补充第十一节）

| # | 教训 |
|---|---|
| 104 | ⭐ **"调用链末端"最容易被漏掉监控**：前面每一环都加了日志，唯独最关键的"窗口是否真的显示"没有 —— 排查时应当**从末端往前补齐观测点**，而不是只盯入口 |
| 105 | **`logOnce` 在排查中会"吃掉"现场**：它适合长期降噪，但排查期会掩盖"第几次调用"这一关键信息。**排查版本应临时换成普通 `log`**（或换 key） |
