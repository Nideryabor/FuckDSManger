⇒ 「按签名找宿主原语」这条路**成立**，`x98.s` 被正确调用并返回了一个真 Modifier。
同时也确认：老代码按名字调 `"z"` / `"B"` / `"y"` 在 2.7.2 **全部失效**（`x98.z` 已被 R8 挪给 `z(View)View`）。

### 1.2 ★★ 主人那句"是不是应用了但被宿主打回来了" ——**有机制支撑**

`cfb.g`（2.7.2 气泡单元 Composable，`(ILel6;Lt62;Lys;Lxr;Lyj7;Lr15;I)V`）里，
第 6 参 `p5` 就是宿主传进来的 Modifier（= 我们替换掉的那个）。它在方法体里被用了 4 次：

```smali
1645  move-object/from16 v15, p5
1653  invoke-interface {v15, v3}, Lyj7;->F(Lyj7;)Lyj7;   # 我们的 .then(宿主 v24)
      move-result-object v11                            # v11 才是最终拿去画的

1744  move-object/from16 v10, p5
1805  invoke-interface {v10, v3}, Lyj7;->F(Lyj7;)Lyj7;   # 另一分支同样 .then(v24)
```

`Lyj7;->F(Lyj7;)Lyj7` = **`Modifier.then(it)`**。
Compose 的 `background` **按链顺序绘制、后画的盖前面的** ⇒
我们塞在链头的背景在**最底层**，宿主 `then` 上去的 `v24` 若含不透明背景，就会被**完整盖住**。

⇒ **「贴上了但看不见」在结构上完全成立**，不是玄学。

### 1.3 顺带确认：宿主自己在气泡里**不直接画背景**

扫 `cfb.g` 全方法，颜色/刷子背景原语的调用**只有一处**（`Lcc3;->J(Lyj7;JLhy4;)Lyj7;` = `Modifier.background(color, shape)`），
且它用的寄存器是 `v14`（不是 `p5`）—— 说明那是**宿主自己另起的一条链**，跟我们的 `p5` 平行。

## 二、两次失败的完整尸检

### 2.1 3.73.1 / 3.73.3 —— 失败原因（现在才看清）

这两版我让 `GmPrims` **先跑**，把返回值直接塞进 `args`。当时不知真假地认为它返回 null，
**实际（3.73.4 诊断证明）它返回了真 Modifier** —— 所以那两版真正的失败原因**不是"没注入"**，
而可能是**注入了但被 `v24` 盖住**（1.2 那条）+ 用户气泡那条路上有别的判定问题。
⚠️ **这两版的具体死因我没有完全证实**，只证实了"原语调用本身是成功的"。

### 2.2 3.73.5 —— 致命：`VerifyError`

真机日志（13:34）：

```
[气泡] hook 内部异常（已吞，不影响宿主）
E java.lang.VerifyError: Verifier rejected class com.nidyaber.fuckdsmanger.gm.GmBubble:
  java.lang.Object GmBubble.wrap(ClassLoader, Object) failed to verify:
  [0x8B] register v2 has type Undefined but expected Reference: java.lang.Object[]
```

**整个 `GmBubble` 类被 ART 拒绝加载** ⇒ 所有气泡逻辑（含完全没改过的老代码）一起死
⇒ 表现就是主人看到的两条：**气泡背景全没、用户气泡不显示**。

**真因（我的错）**：我在 `catch` 处理器里重建 `{modifier, color, shape}` 数组，
用了 `v2`（args 数组）和 `v4`（shape）。这两个寄存器**只在 `try` 区内被赋值** ——
而 `catch` 处理器的入口是"任意一条指令抛了"，**包括还没执行到赋值那一行的时候**，
所以校验器认为它们在入口处是 `Undefined` ⇒ 直接判类非法。

> ⚠️ 这条限制很硬：**`catch` 处理器里只能碰形参（p*）和处理器内部自己赋过值的寄存器。**

## 三、3.73.6 的修法：把"重建"搬进 Java

smali 侧退化成**只有两个参数**的形状 —— `p0`(ClassLoader) 和 `p1`(Modifier)，
这两个**在任何路径上都一定已定义**，不可能触发 `Undefined`：

```smali
invoke-static {p0, p1}, Lcom/nidyaber/fuckdsmanger/bridge/GmPrims;->backgroundAutoColor(Ljava/lang/ClassLoader;Ljava/lang/Object;)Ljava/lang/Object;
```

`GmPrims` 新增两个"全自动"入口，内部用反射去 `GmBubble` 取 `shape()` / `colorLong()` / `imgBrush()`：

| 入口 | 干什么 |
|---|---|
| `backgroundAutoColor(cl, mod)` | 取 `shape` + `colorLong` → 调颜色版原语 |
| `backgroundAutoBrush(cl, mod)` | 取 `shape` + `imgBrush` → 调刷子版原语 |

反射调 `GmBubble` 时**两个 ClassLoader 都试**（宿主那份 + 自己那份），任一份能看见就用。

四个接入点（顺序都是"新路优先，老路兜底"）：

| 位置 | 逻辑 |
|---|---|
| `wrap()` 的 `catchall` | 老 `"z"` 抛异常 → `backgroundAutoColor` → 还不行返回 **原对象 p1** |
| `wrapImg()` 的 `catch_bub_y` | 老 `"B"`/`"y"` 都失败 → `backgroundAutoBrush` → 还不行返回 null |
| `ubMod()` 开头 | `backgroundAutoBrush` 成功即返回 → 否则 `backgroundAutoColor` → 否则**原样落到老 `B`/`C`** |

**最坏结果严格等于改动之前**。

## 四、这次学到的（教训 1124~1127）

| # | 教训 |
|---|---|
| **1124** | **`catch` 处理器里只能碰形参和处理器内赋过值的寄存器**。用 try 区内的局部变量 ⇒ `Undefined` ⇒ **整个类不加载**（比"功能失效"严重一个量级：连没改的老代码一起死） |
| **1125** | **"能让宿主少做事的改动"要先做影子跑** —— 3.73.4 只打日志不改行为，才在不造成损伤的前提下拿到 1.1 的真相。**先观察，再接管。** |
| **1126** | **改完必须自己反向校验**：我写了一个扫全部 `catch` 处理器的脚本（块内读的 v 寄存器若没在块内赋过值就报警）。它当场抓到 `wrapImg` 一处（误报，但流程是对的）。**这类校验不能靠"看起来没问题"。** |
| **1127** | **宿主传进来的 Modifier 只是"链的起点"** —— 它后面还会被 `.then()` 追加。往链头塞背景 = 垫在最底层。要换"宿主自己画的那层"，只能 hook 它画的那个原语，不能靠修改链头。 |
