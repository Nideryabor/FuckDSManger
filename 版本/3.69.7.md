# 3.69.7（vc715）—— 🐛 「大窝没应声」的真因：**等错了信号**（结构性错误）

> 🐲 尼得亚伯 · 2026-10-11
> 前置：`版本/3.69.6.md`
> 主人：「**等等，你看看图左上角**」——
> 指系统提示词页那个浮窗：写着「拼合后的系统提示词（**145 字**）」
> 但正文是「（大窝没应声嗷）…」，而**下面的聊天明明在正常跑**（AI 回复、迷你条、我们模块的吐司都活着）。

## 一、抓证据（不是猜）

### ① UI 发出的命令，宿主收到了吗？

```
UI  : 13:22:42.395 → 动作 cfg_state
宿主: 13:22:42.402 【FdmBridge】动作 cfg_state      ← 6 毫秒后收到 ✓
…（13 次，时间戳一一对应）
UI  : 13:22:49.028 → 动作 cfg_state
宿主: 13:22:49.034 【FdmBridge】动作 cfg_state      ✓
```

⇒ **UI→宿主 完全正常**（0.6 s 一发，正是 3.69.4 改的"先发再等"节奏）。

### ② 那 `host.at` 为什么不动？

```
host.at = 1791696138388  →  13:22:18（UI 上次记下"宿主回话"的时刻）
```

而宿主在 13:22:41~13:22:49 明明**回答了 13 次**。⇒ **宿主回了、UI 没记上。**

### ③ 追到根：`host.at` 是谁写的

* `host.at` 由 `FdmPush.saveHostState()` 写 —— 它挂在 **ACTION_STATE** 广播的接收器上；
* 而宿主**只在"自己定期回读配置"**时才发 ACTION_STATE（`FdmBridge` 里那个 readback 方法）；
* **回答 `cfg_state` 走的是另一条路**：`ACTION_RESULT` → UI 存成 `cmd.cfg_state`。

⇒ **两条路，互不相干。**
`showComposed()` 等的 `host.at`，**跟它自己发的那条命令毫无关系** ——
只有"宿主碰巧在那 14 秒里做了一次定期同步"，它才可能等到。
⇒ 这就是"明明在跑却说没应声"的**结构性原因**（不是窗口长短问题，
3.69.4 把 7.2s 拉长到 14s 只是让误判**概率低一点**，没治本）。

## 二、修法：等 UI **真正要读的那样东西**

```kotlin
val sp = FdmPush.sp(ctx)
sp.edit().putString("cmd.cfg_state", "").apply()      // ★ 先清空当"信箱"
repeat(24) {
    FdmPush.sendCmd(ctx, "cfg_state", null)           // 先问
    kotlinx.coroutines.delay(600)                     // 再等
    val raw = sp.getString("cmd.cfg_state", null)
    if (!raw.isNullOrEmpty()) {                       // ★ 回执到货（非空 = 新回执）
        val t = jsonToMap(raw)["sysprompt_text"]
        promptPreview = t ?: <"宿主回了、但没带提示词正文">
        return@launch
    }
}
promptPreview = <"大窝一直没回话">
```

**三个好处**：

1. **等的是自己发的那条命令的回执** ⇒ 一有回执就返回（实测往返只需几百毫秒，
   不再傻等 14 秒）；
2. 清空当"信箱" ⇒ 读到的一定是**新的**回执 ⇒ 顺带根治 3.64.4 那个
   「拼合结果是旧的」（旧值已被清掉，不可能再读到）；
3. 宿主**回了但没带正文**时，给的是另一句更准确的话（不再一律说"没应声"）。

★ **纯 UI 改动 ⇒ 不用重启宿主**（这次问心无愧地省了主人一次重启）。

## 四、教训

**1101 · ⭐⭐⭐ 「等错了信号」比"等待时间不够"难查得多。**
　　3.69.4 以为是窗口短（7.2s→14s），其实等的是一个**跟本次对话无关**的信号
　　（`host.at` 只在宿主定期同步时更新）⇒ 拉长窗口只是降低误判率，永远治不了本。
　　★ 判据：**要等就等"自己那条请求的回执"**，别等一个"全局的、别人触发的"状态位。
　　（回执可以是同一个 SP 键 —— 先清空、再看到非空，就是"这一问得到了这一答"）

**1102 · ⭐⭐⭐ 排查"两端谁没说话"，最省事的是**对时间戳**。**
　　UI 的 `→ 动作 cfg_state` 与宿主的 `【FdmBridge】动作 cfg_state` 并排一看：
　　6 毫秒的间隔、13 条一一对应 ⇒ **5 秒内排除了整个 UI→宿主 方向**。
　　★ 比读代码快得多，也比"猜哪一步断了"可靠。

**1103 · ⭐⭐ 同一件事有两条通道时，先确认"我要的那条"是哪条。**
　　宿主→UI 有两条：`ACTION_STATE`（host.* 真值）与 `ACTION_RESULT`（cmd.* 回执）。
　　这次就是把 A 通道的状态位，当成 B 通道的到货信号用了。
　　★ 做法：**给每个"等待"标注它在等哪条通道的回执**（写进注释）。

**1104 · ⭐⭐ 「先清空信箱再等回信」是一个很好用的请求/响应模式。**
　　它把"内容有没有变"这种脆弱的判断，换成"**信箱有没有东西**"这种确定的判断；
　　而且天然免疫"返回同样的内容"（内容一样也照样能识别为新回执）。
