## 二、🎯 但我 47 明明停了它 —— 真凶是**第二个接管点**

我 47 搜的是 `buildMut2`，只找到它被 `buildMut` 调用一处，就以为断干净了。

```
dex_class:…gm/GmSuggestHook2;
    invoke-static {v2}, …GmSuggestHook;->buildMut(Ljava/util/List;)Ljava/util/List;   ← ★★★
```


| 类 | 挂哪 | 动作 |

⇒ 所以 `d = 0x7f0f021f + i` 从来没断过，47/48/49 三版的"停用"都只停了一半。

## 三、🔧 顺手挖出的第二个废码

`GmPromptTextHook.idxOf(I)I`：

```smali
const/16 p0, 0x9
if-ne p0, p0, :cond_1a     ← p0 != p0 恒假 ⇒ 永不跳转
const/16 p0, 0xa
if-ne p0, p0, :cond_1c     ← 同上
…（一路到底）
return v0                  ← v0 = -1
```

⇒ **`idxOf()` 永远返回 -1** ⇒ `if-ltz v6, :cond_88` 直接放行 ⇒ **`pd5.H/I` 的"文案接管"从来没执行过 setResult**（这就是"钩子在、逻辑通、屏上没字"的另一半原因）。

## 四、本版改动（4 处）

| # | 改动 | 目的 |
|---|---|---|
| 1 | **`GmSuggestHook2` 停掉 `buildMut` 调用**（改打 `suggest.off2` 日志） | ★根治：第二个末端接管点，越界 id 的来源 |
| 2 | **`buildMut2` 里 `d = 0x7f0f021f + i` → `d = null`** | 双保险：即使将来有人复活它，也不会再越界 |
| 3 | **`GmPromptTextHook.idxOf` 改成 `id - 9`** | 让 `pd5.H/I` 的文案接管**真正生效** ⇒ chip 显示我们的模板池 |
| 4 | **`GmResTextHook` 加"死 id 保险丝"**：`0x7f0f0221` / `0x7f0f0222`（宿主资源表缺失）直接返回空串 | 万一还有别处拿到这些 id，也永不 `NotFoundException` |

### 4.1 为什么第 3 条是"正向"关键

chip 文字 = `getString(g56.d)`；而 `pd5.H` 是这条链的**必经之路**。
在 `pd5.H` 的 `beforeHookedMethod` 里 `setResult(模板池[id-9])` ⇒ **宿主拿不到 g56.d，也就不会去 getString** ⇒ 既不崩、又显示我们的文字。

⇒ 一次改动同时解决"崩溃"和"不显示"。

## 七、教训

| # | 教训 |
|---|---|
| **274** | ⭐⭐⭐ **同一个宿主方法可能被多个 hook 类同时挂**：`yb5.f` 被 `GmSuggestHook`(args[1]) 与 `GmSuggestHook2`(args[0]) 各挂一个 ⇒ 停一处不等于停干净。**停机前先搜"该功能函数的所有调用者"** |
| **275** | ⭐⭐⭐ **搜调用要搜"被调函数名"而不是"实现名"**：我搜 `buildMut2` 漏掉了搜 `buildMut(` |
| **276** | ⭐⭐⭐ **资源 id 只能来自宿主资源表，不能"往后推一个"**：`0x7f0f021f+i` 这种"已知 id + 偏移"的写法，偏移到 3 就踩到不存在的 id ⇒ `NotFoundException`。**要造 id 就用自己专属段（0x7f7f0000+）** |
| **277** | ⭐⭐ **真堆栈 > 一切推理**：拿到 `pd5.H → vc5.d0 → getString(0x7f0f0221)` 后，10 分钟就闭环了；此前 10 个版本都在猜 |
| **278** | ⭐⭐ **"退化废码"要顺手清理**：`if-ne p0,p0` 这种恒假跳转让 `idxOf` 永远返回 -1，静默毁掉了文案接管 |
| **279** | ⭐⭐ **崩溃捕手必须是"自己先被验证"的功能**（48 因反判断没装上，浪费一轮；49 修好后立刻拿到堆栈） |
