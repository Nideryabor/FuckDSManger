## 1. 本轮改动：让日志"装得下整屏"

**问题**：`StackTraceElement.toString()` 会带上 `r8-map-id-<64位哈希>` 作文件名 ⇒ **每一帧约 90 字符**，其中 90% 是哈希。⇒ 10KB 窗口只装得下 ~20 条，**看不完整屏**。

**修法**：**自己拼帧**，只用「类名.方法名:行号」：

```smali
# 旧：invoke-virtual {v5}, StackTraceElement->toString()Ljava/lang/String;   ≈ 90 字符/帧
# 新：
invoke-virtual {v5}, StackTraceElement->getClassName()Ljava/lang/String;
append  +  "."  +  getMethodName()  +  ":"  +  getLineNumber()             ≈ 20~30 字符/帧
```

⇒ **每条记录从 ~900 字符缩到 ~300 字符**，10KB 窗口能装 **~30 条**（原来 ~11 条）。
同时**层数 6 → 10**（`const/16 v4, 0x8` → `0xa`）：因为前 4 帧是噪音，剩下 6 帧才是宿主上下文。

**新格式示例**（预期）：

```
[实化] bg#129 … v = -67818912288342016  cls=v42  from=com…GmBubblePaintHook.beforeHookedMethod:3 < de.robv…XC_MethodHook.callBeforeHookedMethod:1 < s.intercept:36 < l.proceed:35 < android.content.ZurkCheardGielt.v:-1 < ju.q:2104 < ju.q:2103 < …
```

**改动清单（2 处 + 版本）**：

| # | 位置 | 改动 |
|---|---|---|
| 1 | `GmUtil.stack()` | 帧格式 → `getClassName() + "." + getMethodName() + ":" + getLineNumber()`；层数 `0x8` → **`0xa`**（10 帧） |
| 2 | 版本串 ×3 + manifest | `2.22.64/395` → **`2.22.65/396`** |

**产物回读验证**：`2.22.65` · `396` · **`128 类`** · V1+V2+V3 · sha256(partial) `fdacd1b9…` ✓

## 3. 教训（135~138）

| # | 内容 |
|---|---|
| **135** | ⭐⭐⭐ **`StackTraceElement.toString()` 在 R8 后的 App 里是"90% 噪音"**：文件名被替换成 `r8-map-id-<64位哈希>` ⇒ 每帧 90+ 字符、其中哈希占 70+。**自己拼 `类名.方法:行号` 能省 70% 的长度**，直接决定"一个窗口里能装下几条记录"。⇒ **凡"要往定长缓冲里塞很多条"的场景，先看每条有没有可压掉的固定噪音。** |
| **136** | ⭐⭐ **`cls=`（元素类名）证明"类名不能当身份证"**：两条不同来源的记录 `cls=v42` 完全相同（同一个 Compose element 类型）。**判据要选"会变的那个维度"** —— 这里会变的是**调用点**。（又一次印证：**身份在"谁调用的"里，不在"它是什么类"里**） |
| **137** | ⭐⭐ **读栈要"掐头去尾看中段"**：`GmUtil.stack()` 的头 4 帧永远是 Xposed 自己的调用链（`beforeHookedMethod → callBeforeHookedMethod → s.intercept → l.proceed`），**有用的信息在"宿主那个函数"之后**。⇒ **日志格式设计时，要把"恒定的噪音"和"变化的信息"分开摆**，否则读的人要先学会"跳着看"。 |
| **138** | ⭐ **`matchText` 命中失败的第三个原因：自己上一次编辑吃掉了空白行**。上一刀我把 `:next`（它后面**没有**空行）连同标签一起换掉，结果新文本里 `aget-object` 直接贴到了 `if-ge` 的下一行 ⇒ 这一次按"有空行"去匹配必然失败。⇒ **改完一个方法后，如果要再改它，先读一次现场**（`mt_apk_read_text`），别拿"自己以为的样子"去匹配。 |
