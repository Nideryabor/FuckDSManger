⇒ 既拿到了二级菜单，又**没有让 200 行手写 smali 变成死代码**，改动只有 **8 处小改 + 2 处加分支 + 1 个新类**。

## 2. 改动清单（11 处，全部小改）

### 2.1 新类 `GmBubbleDialog`（+1 类 → **120 类**）

| 成员 | 说明 |
|---|---|
| `sAct` / `sDlg` | 与其它自绘 Dialog 同款 |
| **`sBox:Landroid/widget/LinearLayout;`** | **承载那三块气泡 UI 的容器**（美化页填、本页取） |

| `close()` | `sDlg.dismiss()` |

`.registers 10`（无参数），用到 v0..v7 ✓

### 2.2 `GmClick`：+2 个 id（原最大 `0x3c`）

| id | 动作 |
|---|---|
| `0x3d` | `GmBubbleDialog.open()` |
| `0x3e` | `GmBubbleDialog.close()` |

（替换尾部 `:cond_1e6 / return-void / .end method` 那三行，前面的 `if-ne … :cond_1e6` 链不变）

### 2.3 `GmBeautyDialog.open()`：8 处

## 3. 为什么这么设计（取舍）

| 方案 | 代价 | 结果 |
|---|---|---|
| A. 把三块 UI **剪切**到新类 | 要精确匹配并删除 ~200 行手写 smali（易失败） | 代码干净，但风险高 |
| B. 三块 UI **留在美化页**，改挂载目标 + 新页搬容器 | **4 处单行替换 + 1 处插入** | ✅ **本版采用**：改动最小、旧代码不浪费、新页内容与旧版逐像素一致 |
| C. 新页**重写**三块 UI | 手写 ~150 行新 smali | 清晰但重复，且可能与旧版细节漂移 |

**B 的注意点（都已覆盖）**：
- `sBox` **只在美化页 `open()` 时被赋值** ⇒ 气泡页的入口既然在美化页里，**必然先有 `sBox`** ✓
- 容器**只能有一个父**：`sBox` 只被 addView 到气泡页 ✓（重复 addView 会先自动 detach）
- 美化页**每次打开都重建** `v10` 并覆盖 `sBox` ⇒ 旧容器被丢弃，无害 ✓
- 气泡页沿用 `GmUtil.sc` ⇒ 内容高时**可滚动**（2.22.24 的修复自动生效）✓

## 5. 教训 / 备注（768~772）

| # | 内容 |
|---|---|
| 768 | ⭐⭐ **「搬容器」比「搬代码」省一个数量级**：想给一组 UI 换地方时，先问「能不能只换它的**父**」—— 本次 4 处单行替换搞定 200 行的搬迁 |
| 769 | ⭐⭐ **MT 的 `replace_match` 里，标签与紧随其后的指令之间常常没有空行**（`":cond_1e6\n    return-void"`）⇒ 抄 matchText 时**必须照抄空行分布**（本版在此处失败过一次） |
| 770 | ⭐ **`.registers` 想加临时寄存器就整方法 `+1`**：只要方法**无参数**，加一个不会影响既有 `v0..vN` 的含义 ✓ |
| 771 | ⭐ **入口在 A 页、内容在 B 页 ⇒ B 页可以放心依赖「A 页已构建的资源」**（本次 `sBox`），但要接受「B 页不能单独打开」这个前提 |
| 772 | ⭐ **改动越少越好**（本项目铁律精神）：本次 11 处小改 + 1 新类，`vercheck.pl` 一把过 ✅ |
