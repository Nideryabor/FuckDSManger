## 一、症状

宿主升到 2.8.0 后，**首页的助手头像变成蓝色小方块**（豆腐块）。

---

## 二、根因：铁律被绕过 —— 「只改了一半」

`GmResHook` 的图片替换是**两步必须同时成立**（3.104.9 就写进文档的铁律）：

| 步骤 | 落点 | 2.7.5 | 2.8.0 实际 |
|---|---|---|---|
| ① 把 `tv.string` 改成非 `.xml` | `Resources` 层（系统类）| 挂得上 | **照样挂得上** |
| ② 让 `getDrawable` 返回 BitmapDrawable | **`dec.U`**（宿主类）| `dec.U` | **`pac.y`** |

而 `GmResHook` 里**写死**了：

```java
Class<?> dec = XposedHelpers.findClass("dec", hl);                      // ← 2.7.5 的名字
XposedHelpers.findAndHookMethod("dec", hl, "U", int.class, Context.class, …);
```

⇒ 2.8.0 里 `findClass("dec")` 失败 ⇒ ② 没挂上，但 ① 照样执行
⇒ 宿主拿到 `tv.string = "fdm_replaced"`，判定「不是矢量」，去当位图解析
⇒ 解析失败 ⇒ **蓝色小方块**

> ⚠️ 这正是 3.104.9 文档里那条铁律：
> 「改 `tv.string` + `getDrawable` 返回 BitmapDrawable **必须同时成立且顺序不能反**」

---

## 三、★ 又是「拆类」

`dec` 在 2.7.5 是 **54 个方法**的巨型合并类。2.8.0 里被拆开：

| 2.7.5 | 2.8.0 | 用途 |
|---|---|---|
| `dec.w` | **`ee.s`** | `clip(Modifier, Shape)` ← 另一条线（`clipmod.clip`）|
| `dec.U` | **`pac.y`** | `U(int,Context)Drawable` ← 本轮的坑 |

**同一个类的两个方法跑到两个不同的新类里。**
⇒ 光把 `dec → ee` 写进表，`dec.U` 仍然会挂错/挂不上。

判据：全树 `(I,Context)Drawable` 的**静态方法只有一处** = `pac.y`。

## 四、修法（3.105.3）

### 4.1 新增语义键

```
CLS7: {"painter.res"×6, "pac"}
MTH : {"painter.res.U"×7, "pac", "y"}
```

### 4.2 GmResHook 全部改走 GmRemap

| 原来（写死） | 现在 | 2.8.0 值 |
|---|---|---|
| `findClass("dec")` + `"U"` | `GmRemap.clsFor("painter.res","U")` | **`pac.y`** |
| `findClass("vo0")` | `GmRemap.cls("ok0")` | **`xo0`** |
| `findClass("q88")` | `GmRemap.cls("ku6")` | **`ra8`** |
| `findClass("rf")` | `GmRemap.cls("le")` | `rf`（不变）|
| `findClass("gp0")` | `GmRemap.cls("vk0")` | **`hp0`** |

### 4.3 加一道「宁可不动手」的闸

```java
if (!GmRemap.hit(PR_KEY, PR_MTH)) {
    log("✗ MTH 表里没有键 ⇒ 不挂 painterResource 钩子（宁可图片不换，也不能只换一半）");
    throw new IllegalStateException("painter.res 未登记");
}
```

## 五、修法（3.105.4）—— 顺手修 tint 剥离

`q88.g` 原来也写死了首参类型 `"v24"`：

```
2.7.5: q88.g(Lv24;JFLgp0;)V
2.8.0: ra8.g(Ld34;JFLhp0;)V
```

⇒ 不再写死 `"d34"`，改成**从方法签名派生**：

```java
// 找 g(X, long, float, <Paint>) 重载，X 就是要的类型
for (Method m : q88Cls.getDeclaredMethods()) {
    if (!"g".equals(m.getName())) continue;
    Class<?>[] pt = m.getParameterTypes();
    if (pt.length == 4 && pt[1] == long.class && pt[2] == float.class
            && pt[3].getName().equals(gp0Cls.getName())) { firstArg = pt[0]; break; }
}
```

> 这是这一轮学到的**最高价值手法**：名字会被 R8 改，但**方法形状不会**。
> 与其写死下一个名字，不如从形状反推。

## 七、教训

| # | 教训 |
|---|---|
| **D** | ⭐⭐⭐ **「必须同时成立」的两步，只要一步换了名字，就会变成毒药** —— 不是「少个功能」，是**主动破坏宿主渲染**。凡是「A 改状态 + B 兜底」的成对 hook，**A 挂上了而 B 挂了**，必须立刻把 A 也关掉 |
| **E** | ⭐⭐⭐ **拆类会让同一个旧类的两个方法跑到两个新类** —— `dec.w→ee.s` 而 `dec.U→pac.y`。表里一行只能记一个类，遇到这种情况必须**拆成两个语义键** |
| **F** | ⭐⭐⭐ **能派生就别写死** —— `g` 的首参类型从 `(X,long,float,Paint)` 形状反推，比再写死一个 `d34` 强得多 |
| **G** | ⭐⭐ **`findClass` 失败是静默的** —— 必须像 `painter.res` 那样加「表里没键就抛」的硬闸，否则又是「看起来跑了其实没挂」 |

## 八、当时为什么会漏（复盘）

我静态分析时 `dec → ee` 只验了 **`dec.w`（clip）** 那一个方法就对位成功了，
就以为整个 `dec` 对应 `ee`。**没有逐个方法验**。

⇒ 以后做类映射，**只要有 ≥2 个锚点落在同一个旧类**，必须**分别用各自的方法签名**去定位，
不能拿一个方法的结论代替整类。
