## 二、根因：`hookM` 的实现

读 `DisableFlagSecure.hookM`：

```java
Class<?> c = XposedHelpers.findClass(className, cl);
Class<?> h = Class.forName(hookClassName);        // ← 异常出在这一段
XC_MethodHook inst = (XC_MethodHook) h.newInstance();
XposedBridge.hookAllMethods(c, methodName, inst);
```

实测：**第一次**（`yb5.e` → `GmSuggestHook`）成功；**第二次**（`yb5.e` → `GmPromptHook`）失败。
新类确实在 dex 里（已用 `mt_apk_list` 验证），所以失败点在 `Class.forName` / `newInstance`。

> 📌 **未解之谜**：为何第二次的 `Class.forName(新类)` 会失败 —— 待查（可能与 LSPosed 在
> legacy hook 场景下 module classloader 的行为有关）。
> **本版直接用「合二为一」绕开了它，不依赖这个答案。**

## 三、修法：合并（不再二次注册）

| 动作 | 说明 |
|---|---|
| `GmSuggestHook` 新增 `prompt(MethodHookParam)` | 原 `GmPromptHook.beforeHookedMethod` 的逻辑（改 `args[1]` 列表 / `args[4]` 可见性 / `args[7]` changed bits / holder 的 `c1`,`i1`） |
| `beforeHookedMethod` 加路由 | `if (key.equals("yb5.e")) prompt(p1);` |
| 删掉 `hookM("yb5","e","…GmPromptHook")` | 注册点移除 |
| `GmPromptHook` 类保留 | 不再被引用（无害），留作参考 |

⇒ 因为 `yb5.e` **本来就已经挂在 `GmSuggestHook` 上**（日志 `count=1`），合并后**必然生效** ✔

## 六、教训

| # | 教训 |

| 126 | ⭐ **同一个「类.方法」不要用两个不同的 hook 类去注册** —— 项目自带的 `hookM` 在这种情形下会失败（`hookM FAIL`）。要么把逻辑合并进已注册的那个类，要么换注册方式 |
