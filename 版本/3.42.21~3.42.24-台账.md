### ⭐ 本轮加的最重要一道保险

```
mod-src/work/GmEntry.261.smali     ← GmEntry.smali 的【模板】
```

`GmEntry.smali` 在 `patch_261.py` 的 `SKIP_FILES` 里（类名替换不碰它），
它那两处 `GmRemap.cls()/method()` 是**手工加进 smali 树里的** —— 3.42.22 就是被这个坑掉的。

⇒ 现在 `patch_261.py` 每次生成完树，**自动从模板覆盖回去**，并打自检：

```
✓ GmEntry.smali 已从模板恢复：GmRemap 调用 3 处（应为 3）
```

（找不到模板会打 `✗✗ ... 锚点会全灭，别继续！`）

## 五、本轮教训（编号接上）

| # | 教训 |
|---|---|
| **341** | ⭐⭐⭐ **"重跑生成脚本"本身就是一个改动。** `patch_261.py` 是 `rmtree + copytree`，任何**只活在产物树里、没写回脚本/模板**的手工改动都会被静默抹掉。⇒ 重跑前先 diff 产物。 |
| **342** | ⭐⭐⭐ **手写的 smali 必须模板化。** 手工改动住在"产物目录"里就是定时炸弹。 |
| **343** | ⭐⭐ **"疑似致崩所以关掉"的开关，不能只信注释。** 注释写着"晚重开"，但 3.42.21 出包时是关的 —— **用产物反推开关状态**（这次就是靠 diff 反推出来的）。 |
| **344** | ⭐⭐ **改动前先"拍照"。** 重建脚本留的 `.bak-<时间戳>` 让这次 5 分钟就定位到了。 |
| **345** | ⭐⭐⭐ **改一个常量就直接改那个字节，别重建。** 重建会引入 smali 往返噪声，"到底改了什么"说不清；字节级改动能给出硬证明。 |
| **346** | ⭐⭐ **用户的现象描述能顶半天逆向。**「有渲染内容就卡死、没有就崩」直接点亮了"投毒 → State 失效 → 无限重组"这条链。 |
