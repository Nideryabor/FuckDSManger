## 一、`nx` 是什么：**消息本体**

```
.class public final Lnx;
.super Lvq;                    ← 就是 vq 的子类
构造器字符串： "ASSISTANT" / "DEFAULT"
字段：C/i/m/n/x/y:String · s/v:List · D/E/V/W:rs8(状态) · 另外 20+ 个
```

**⇒ `nx` 是聊天消息对象（role = USER / ASSISTANT）** ⇒ 我们一直拿的元素是**对的**。

## 二、读源码：那七个取文本方法为什么不吐正文

| 方法 | 实现 | 结论 |
|---|---|---|
| **`nx.D()`** | `iget-object p0, p0, Lnx;->i:Ljava/lang/String;` | **它返回的是 role（"USER"/"ASSISTANT"）** |
| **`nx.A()`** | `E(状态).getValue() → w91.a` | 从**状态**取字符串（状态空 ⇒ 返回空） |
| **`nx.G()`** | `D(状态).getValue() → w91.a` | 同上 |

**⇒ 而 `vq.l()` 的逻辑是：`D()` 的结果 == "USER" ? `r()` : `C()` —— 两者都从 `s()`（blocks 列表）取 ⇒ 空。**

**⇒ 所以：`nx` 的正文**不在 blocks 里**，而在它自己那二十几个字段 / 状态里。**

## 三、本版：`dump()` 把所有非空字段打出来

新增 `dump(Object)`：反射遍历 `getDeclaredFields()`，对每个**非空**字段输出

```
F <字段名>=<值前 80 字>
```

并在 `grab()` 里对**第一个元素**调一次。

**⇒ 日志里会直接出现类似：**
```
F C=你好，帮我写一段…
F m=…
F x=…
```

**⇒ 哪个字段装着正文，一眼可见。**

## 五、关于主人的另一个思路（用助手头像定位文本框）

**思路本身成立**（从 UI 层反推文本），但它要 hook Compose 的布局/语义树，成本高且随版本易碎。

**优先顺序**：先看 `dump` 结果 —— 如果正文就在 `nx` 的某个字段里，我们**直接读字段**就行（稳定、零 UI 依赖）；只有 dump 显示"字段里也没有正文"（比如正文只存在于渲染后的文本节点），才值得走 UI 那条路。

## 六、教训

| # | 教训 |
|---|---|
| **454** | ⭐⭐⭐ **拿到元素类名后"读它的实现"胜过"猜方法名"**：一读 `nx.D()` 就知道那 7 个方法取的是 role/blocks，**根本不是正文通道** |
| **455** | ⭐⭐⭐ **"枚举字段"是最终的兜底手段**：当方法层反复无果，**把对象的非空字段全打出来** —— 数据藏在哪一眼可见，比继续试方法省得多 |
| **456** | ⭐⭐ **`insert_before_match` 不会消费锚点**：要手动补回锚点行会**重复声明**（本次踩了两回：先插进方法体、后重复 `.method`），**正确姿势：锚点行只在原处，插入内容里不重复它** |
